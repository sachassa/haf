## §0. 이 문서의 위치와 정본 경계

- **정본은 specs/03-loop.md §3.2다.** 이 문서는 그 Core Contract의 **인스턴스**이며, 계약을 재정의·확장하지 않는다. 계약 요소는 § 포인터로만 참조한다(structure.md §7 C-1과 같은 인스턴스 원칙).
- 이 문서는 `framework/loop/` 아래 **루프 상태 기록 포맷**을 확정한다. 03 §3.2-A(전이 이벤트)·§3.2-B(단계 상태)·§3.2-C(Learn 트리거)의 계약을 이 경계 위에 배치·대조한다.
- **이 문서는 Module 구현 디렉터리 문서다.** `framework/loop/`는 structure.md §2가 지정한 Module 구현 디렉터리 경계이며, 이 문서가 그 경계의 **첫 실사용 인스턴스**다(structure.md §8 트리에서 loop는 종전 미실현·경계만 확보된 빈 디렉터리였다 — `framework/memory/`가 v0.4에, `framework/verifier/`가 v0.5에 자기 경계의 첫 실사용 인스턴스가 된 것과 동형). 이 문서 본문은 특정 AI 이름·모델명·제품 기능명·언어명·툴체인명·직렬화 형식명·물리 경로·확장자를 두지 않는다(structure.md §5 C-3 확장, 03 §3.3 INV-9).
- **물리 실현 비서술(경계).** 루프 상태 기록의 **물리 형식·직렬화·저장 위치·물리 경로**는 이 문서가 서술하지 않는다. 이는 **Adapter Binding 문서 소관**이다(03 §4.1 루프 상태 기록 직렬화 행·§4.2 이식 교체 지점 SP-3; 물리 격리 경계는 `framework/adapters/<adapter>/`, structure.md §2·§6). 필요한 자리에는 일반형 표기 `<adapter>`와 소관 포인터만 둔다(§7).
- **인스턴스화 대상 경계.** 본 문서의 인스턴스화 대상은 위임 input이 지정한 03 §3.2-A/B/C 세 계약과 그 append-only 불변(03 §3.2-A·INV-3)이다. 단계 전이 규칙(03 §3.1-A)·재작업 루프(03 §3.1-B)·종료 규칙(03 §3.1-C)·사람 개입 지점(03 §3.1-D)의 상세는 인스턴스화 대상이 아니며 03 정본 § 포인터로만 참조한다(재정의·확장 0). 이들 규칙이 생성하는 **전이**만 이 문서의 기록 스키마(§2)로 남는다.
- **단계 전이 시점·판정 비정의.** 이 문서는 루프 상태 기록 포맷만 인스턴스화한다. 단계 전이의 시점·판정·시퀀싱은 정의하지 않는다(03 §3.1 소관). Verify 판정 내용은 06 소관, Memory 내부 포맷·후보 승격은 04/05 소관, 회수 이력의 **소비**(재발 판정)는 05 소관이다 — 본 문서는 회수 이력의 **기록 소관**만 다룬다(§6).
- **03 내부 § 포인터 표기 관례.** 03 정본 셀을 보존할 때, 03의 내부 § 포인터는 `03 §…` 접두로 명시하여 본 문서 자신의 절 번호와 구분한다. 이는 셀의 대상 지시를 명료화하는 표기이며 셀 내용(필드명·의미·필수 표기)을 변경하지 않는다(verification-report §0의 "06 내부 § 포인터 표기 관례"와 동형).
- 용어는 specs/00-glossary.md 정본(§3.2-J J-03)만 사용한다. 새 용어를 신설하지 않는다. "전이 이벤트·단계 상태·Learn 트리거·검증 게이트" 등은 J-03 표제어(루프 상태 기록·단계 전이·재작업 루프)와 03 §3.2 정본이 정의한 스키마·서술 명칭이며 본 문서가 신설한 용어가 아니다.

## §1. 목적

`framework/loop/`의 이 규격은 네 가지를 확정한다.

- **전이 이벤트 스키마** — 각 단계 전이의 기록 단위(전이 이벤트)의 10필드와 각 필드의 필수 표기(§2).
- **단계 상태·Learn 트리거** — 각 단계가 취하는 5종 상태(§3)와 실패·성공에서 후보를 도출하는 Learn 트리거(§4).
- **append-only 불변·재구성 요건** — 루프 상태 기록이 append-only이며 그 기록만으로 사이클 전체를 재구성·검증할 수 있게 하는 포맷 규칙(§5).
- **회수 이력 기록 방식** — Consult 전이 이벤트의 `ref`에 그 사이클 회수 집합 참조를 기록하는 방식과 그 결정 근거(§6, Advisor 결정 DP-L5).

이 규격은 03 §3.2-A·§3.2-B·§3.2-C Core Contract의 **인스턴스**다. 계약 요소(필드·상태·트리거·불변 규칙)를 재정의·확장하지 않는다. 형태 A(문서)에서 형태 B(실행 코드)로 전환되어도 03 §3 Core Contract 변경은 0이며, 위반(형태 B가 03 §3 계약을 바꾸어야만 성립하는 경우)이 발견되면 구현하지 않고 Advisor에게 보고한다(structure.md §7 C-1과 같은 불변 원칙).

## §2. 전이 이벤트 스키마 인스턴스 (정본: 03 §3.2-A)

루프 상태 기록은 전이 이벤트(Transition Event)의 순서 있는 append-only 로그다(03 §3.2-A). 전이 이벤트는 단계 전이 하나의 기록 단위다. 아래 필드·의미·필수 표기는 03 §3.2-A 정본을 **그대로 보존**한다(재정의 0, 새 필드 0). 필드명뿐 아니라 필수 속성 표기(예/아니오)까지 정본과 일치시킨다.

| 필드 | 의미 | 필수 |
|---|---|---|
| `cycle_id` | 이 Lifecycle 사이클의 식별자. 하나의 위임 = 하나의 사이클. | 예 |
| `seq` | 사이클 내 전이 순번. 단조 증가한다. | 예 |
| `from_stage` | 전이 이전 단계. 사이클 시작 시 없음. | 아니오 |
| `to_stage` | 전이 이후 단계. | 예 |
| `trigger` | 전이 사유 — 완료 조건 충족 / Verify 실패 / 재작업 되돌림 / 에스컬레이션. | 예 |
| `outcome` | 단계 결과 — pass / fail / escalated. | 예 |
| `retry_count` | 현재까지 재작업 되돌림 횟수 (03 §3.1-B). | 예 |
| `actor` | 전이를 유발한 역할 (Advisor/Planner/Worker/Verifier) 또는 human(사람 개입 시). | 예 |
| `ref` | 관련 산출물·보고 참조 (위임/완료/실패 보고, Verifier 판정 참조). | 아니오 |
| `at` | 전이 시점. 순서 보장용 추상 시각. | 예 |

- **필수 표기(정본 보존).** 10필드 중 8필드(`cycle_id`·`seq`·`to_stage`·`trigger`·`outcome`·`retry_count`·`actor`·`at`)는 **예**, 2필드(`from_stage`·`ref`)는 **아니오**다. `from_stage`는 사이클 시작 전이(첫 전이)에 없다 — 그 전이는 `to_stage`만 가진다. `ref`는 관련 산출물이 없는 전이에서 생략될 수 있다(회수 집합 참조를 기록하는 Consult 전이의 경우는 §6).
- **순서 보장 필드.** `seq`는 사이클 내에서 단조 증가하며 `at`은 순서 보장용 **추상 시각**이다. 두 필드가 전이의 순서를 확정한다. `at`의 물리 시각 표현은 이 문서가 규정하지 않는다 — Adapter Binding 소관이다(§7, 03 §4.1).
- **열거 값(정본 보존).** `outcome` 값 3종(pass / fail / escalated), `trigger` 사유 4종(완료 조건 충족 / Verify 실패 / 재작업 되돌림 / 에스컬레이션), `actor` 값(Advisor/Planner/Worker/Verifier/human)은 03 §3.2-A 정본이며 재정의·추가하지 않는다.
- 필드의 상세 정본은 03 §3.2-A가 유지한다. 본 표는 그 스키마를 인스턴스화할 뿐 계약을 재정의하지 않는다.

## §3. 단계 상태 인스턴스 (정본: 03 §3.2-B)

각 단계는 다음 5종 상태 중 하나를 가진다. 아래 상태·의미는 03 §3.2-B 정본을 **그대로 보존**한다(재정의 0, 새 상태 0).

- `Pending` — 진입 전.
- `Active` — 진입 후 진행 중.
- `Passed` — 완료 조건 충족. 다음 단계로 전이 가능.
- `Failed` — 완료 조건 불충족. 재작업 루프 대상.
- `Escalated` — 사람 개입 또는 상위 에스컬레이션 대상.

- **읽기 보조 관찰(비계약).** 종료 상태(`Passed`/`Failed`/`Escalated`)의 명칭은 전이 이벤트 `outcome` 값(pass/fail/escalated, §2)과 어휘를 공유한다 — 한 단계의 결과가 그 단계에서 나가는 전이의 `outcome`에 기록된다. `Pending`/`Active`는 전이가 아직 기록되지 않은(전이 전) 단계 상태다. 이 대응은 두 정본 요소(03 §3.2-A `outcome` 열거, §3.2-B 상태 열거)를 읽는 보조이며 새 계약이 아니다 — 각 열거의 정본은 03 §3.2-A/B가 유지한다.
- 상태의 상세 정본은 03 §3.2-B가 유지한다. 본 절은 그 상태 집합을 인스턴스화할 뿐 계약을 재정의하지 않는다.

## §4. Learn 트리거 인스턴스 (정본: 03 §3.2-C)

Learn 단계는 실패와 성공에서 후보를 도출한다(03 §3.2-C). 아래 산출 후보·트리거 규칙은 03 §3.2-C 정본을 그대로 보존한다(재정의 0).

**산출 후보 2종:**

- **Lesson 후보** — 실패 경로에서 도출. 입력은 재작업 루프의 각 Verify 실패와 차단 실패의 실패 보고(02 §3.2-D)이며, 그 `lesson_candidate` 표시를 근거로 한다. 모든 실패는 Lesson 후보다.
- **Best Practice 후보** — 성공 경로에서 도출. 사이클이 Verify 통과로 Complete를 향할 때. 모든 성공은 Best Practice 후보다.

**트리거 규칙(03 §3.2-C):**

- 재작업 루프 진입(Verify 실패)마다 그 실패의 실패 보고가 이 사이클의 **누적 실패 집합**에 추가된다. 각 되돌림은 루프 상태 기준으로 하나의 전이 이벤트(`outcome` = fail, `retry_count` 증가)로 §2 스키마에 남는다(03 §3.1-B, §5).
- Learn 진입 시, 누적 실패 집합 전체가 Lesson 후보로, 성공 시 그 사이클이 Best Practice 후보로 도출된다.
- 성공이든 에스컬레이션이든 사이클 종료 전 Learn은 항상 실행된다(**INV-5**). 실패가 학습 없이 버려지지 않는다. Learn 단계의 진입·완료 역시 전이 이벤트(`to_stage` = Learn, 이어 `to_stage` = Memory Update)로 루프 상태 기록에 남는다.

**경계.** Learn은 후보를 **도출만** 한다. 후보의 포맷·생성 규칙·승격은 04/05 소관이다(§ 포인터). 실제 기록은 Memory Update 단계에서 Memory Service Interface(단일 Port) 경유로 이뤄진다(03 §5, INV-7). 본 문서는 이 트리거가 루프 상태 기록에 남기는 전이만 다루며, 후보의 내부 포맷을 인용·추측하지 않는다.

- 트리거·산출의 상세 정본은 03 §3.2-C가 유지한다. 본 절은 그 트리거를 인스턴스화할 뿐 계약을 재정의하지 않는다.

## §5. append-only 불변·사이클 재구성 포맷 규칙 (정본: 03 §3.2-A 불변 규칙·INV-3·§7)

루프 상태 기록의 불변 규칙을 포맷 규칙으로 명문화한다. 아래는 03 §3.2-A 불변 규칙·03 INV-3·03 §7 완료 기준의 인스턴스이며 재정의하지 않는다.

**불변 규칙:**

- **append-only(INV-3).** 루프 상태 기록은 append-only다. 전이는 **기록된 뒤에 유효하다**. 기록되지 않은 전이는 없다. 기존 전이 이벤트는 정정·삭제하지 않는다 — 갱신·정정이 필요하면 기존 이벤트를 바꾸지 않고 **새 전이 이벤트를 추가**한다(memory-store §4.1 append-only 원칙과 동형이나, 본 로그의 불변 정본은 03 §3.2-A·INV-3이다).
- **전이 누락 금지(INV-3).** 모든 단계 전이는 정확히 하나의 전이 이벤트로 append된다. 성공 경로 7단계 선형 전이(03 INV-1)뿐 아니라 재작업 되돌림(03 §3.1-B, 각 되돌림 = 하나의 전이 이벤트)과 에스컬레이션(`outcome` = escalated)도 모두 append 대상이다. 기록되지 않은 전이는 없다.
- **순서 확정.** `seq` 단조 증가(§2)와 `at` 추상 시각(§2)이 전이의 순서를 확정한다. 이 순서로 사이클의 단계 경로가 재현된다.

**재구성 가능 요건(03 §7):**

- 이 로그만으로 **사이클 전체를 재구성·검증할 수 있어야 한다**(03 §3.2-A, §7 전이 기록 시연). 각 전이 이벤트의 `from_stage`·`to_stage`·`trigger`·`outcome`·`retry_count`·`actor`·`ref`가, 그 사이클의 단계 경로·재작업 되돌림·에스컬레이션·회수 참조까지 복원하기에 충분해야 한다.
- 재구성 검증은 Verifier가 이 로그를 파싱해 전이 순서·완료 조건 충족·append-only 여부를 확인하는 방식으로 수행된다(03 §7 검증 방법). 이 문서는 그 검증이 대상으로 삼는 기록 포맷의 불변만 명문화한다.

**경계.** append-only·순서 확정을 **물리 저장·직렬화가 어떻게 실현하는가**는 이 문서가 서술하지 않는다 — Adapter Binding 소관이다(§7). 본 절은 계약 수준 불변만 확정한다.

## §6. 회수 이력 기록 방식 — 결정 기록 (Advisor DP-L5)

**결정 (Advisor DP-L5).** Consult 단계의 전이 이벤트는 `ref` 필드에 **그 사이클의 회수 집합 참조**(Consult에서 수행된 Recall의 결과 집합 참조)를 기록한다.

**근거:**

- **(a) 03 §3.2-A `ref` 계약의 인스턴스(계약 확장 0).** 03 §3.2-A `ref`의 계약 본문은 "관련 산출물·보고 참조"이며, DP-L5은 괄호 열거(위임/완료/실패 보고, Verifier 판정 참조)를 **예시(비한정)**로 해석한다. 회수 집합은 Consult 단계에서 수행된 회수(03 §5 Recall)의 결과 집합이므로 그 단계의 "관련 산출물"에 자연 포함된다. 따라서 이 기록은 03 §3.2-A `ref` 계약의 **인스턴스**이며 계약 확장이 아니다(새 필드 0, `ref` 의미 재정의 0, 필수 표기 아니오 유지).
- **(b) 소관 배정의 해소 지점.** 회수 이력(작업별 회수 집합)의 **저장 소관**은 04 §9·05 §9 결정 기록에서 "03의 루프 상태 기록 소관으로 확정. 05는 입력으로 받는다"로 기배정되었다. 본 기록 방식이 그 소관의 **해소 지점**이다 — 회수 이력이 루프 상태 기록의 어느 전이 이벤트·어느 필드에 남는가를 확정한다.

**효과 (05 재발 판정 입력의 도출 전환):**

- 재발 판정(05 §3.1-C Judge Recurrence)의 `was_recalled`(05 §3.2-E) 입력 — "그 Lesson이 해당 작업의 회수 집합에 포함되었는가" — 은 종전 수동 제공을 전제했다. 본 기록 방식은 이 입력을 **루프 상태 기록 기반 도출**로 전환한다: Consult 전이 이벤트의 `ref` 회수 집합 참조가 `was_recalled` 판정의 근거가 된다.
- 05·04의 내부 포맷·판정 규칙·회수 집합의 **소비** 방식(재발 판정 3분류 등)은 05·04 소관이며, 본 문서는 재서술하지 않고 § 포인터로만 참조한다(05 §3.1-C·§3.2-E, 04 §9·05 §9 결정 기록). 본 문서는 회수 이력의 **기록 소관**(어느 전이 이벤트의 어느 필드에 남기는가)만 확정한다.

**경계:**

- 회수 집합의 **내용**(무엇이 회수되었는가)과 회수 정책(필요할 때만·목적 명시·최소 범위)은 03 §5·04·05 소관이다. 본 절은 그 결과 집합의 **참조가 Consult 전이 이벤트 `ref`에 남는다**는 기록 위치만 정한다.
- 회수 집합 참조의 **물리 표현**(참조가 어떤 형식으로 직렬화되는가)은 Adapter Binding 소관이다(§7).

## §7. 경계와 비의존 (직렬화·저장 위치 · 재정의 0 · 07 R2 · 금지 토큰 · Glossary)

본 문서가 준수하는 경계를 한자리에 모은다. 검증 대조 지점이다.

**직렬화·저장 위치 경계 (Adapter Binding 소관 포인터):**

- 루프 상태 기록의 **직렬화 형식·저장 위치·물리 경로**는 이 문서가 **일절 확정하지 않는다.** Core Contract(03 §3.2)는 추상 스키마이며, 직렬화 형식(파일 형태·문법)은 Adapter Binding이 정한다(03 §3.2 도입, §4.1 루프 상태 기록 직렬화 행).
- `at` 필드의 물리 시각 표현, `seq`의 물리 인코딩, 회수 집합 참조의 물리 표현, append-only의 물리 실현은 전부 **Adapter Binding 문서 소관**이며 `framework/adapters/<adapter>/` 뒤로 격리된다(03 §4.1·§4.2 이식 교체 지점 SP-3; structure.md §2·§6 Adapter 경계). 이식 시 §2~§6의 필드·불변·회수 이력 기록 방식은 유지되고 물리 실현만 교체된다(03 §4.2, SP-3). 필요한 자리에는 일반형 표기 `<adapter>`와 "Adapter Binding 문서 소관" 포인터만 둔다.

**재정의 0 · 인스턴스화 대상 경계:**

- **03 계약 재정의·확장 0.** §2~§6의 모든 필드·상태·트리거·불변은 03 §3.2의 인스턴스이며 § 포인터로만 참조한다. 스키마 표는 정본을 그대로 보존한다(재정의 0, 새 필드·새 상태 0). 위반이 발견되면 구현하지 않고 Advisor에게 보고한다.
- **인스턴스화 대상 경계.** 위임 input(03 §3.2-A/B/C) 밖의 03 절(§3.1-A 단계 전이 규칙·§3.1-B 재작업 루프·§3.1-C 종료 규칙·§3.1-D 사람 개입 지점)은 재서술하지 않고 § 포인터로만 참조한다(§0). 이들이 생성하는 전이만 §2 기록 스키마로 남는다.
- **단계 전이 시점·판정 비정의.** 단계 전이의 시점·판정·시퀀싱은 정의하지 않는다(03 §3.1 소관). Verify 판정 내용은 06 소관, Memory 내부 포맷·후보 승격은 04/05 소관, 회수 이력의 소비(재발 판정)는 05 소관이다.

**동시 작성 경계·금지 토큰·Glossary:**

- **07 R2 경계.** 같은 Wave에서 동시 작성 중인 형제 산출물의 미완성 내용은 인용·추측하지 않는다. 확정된 정본(03·01·02·04·05·structure.md·Glossary)과 기존 Baseline 문서만 참조한다.
- **금지 토큰 비의존(structure.md §5 C-3 확장, 03 INV-9).** 본 문서 본문에는 특정 AI 이름·모델명·제품 기능명·언어명·툴체인명·직렬화 형식명·물리 경로·확장자 토큰을 두지 않는다. 금지 토큰의 예시조차 본문에 나열하지 않는다 — 구체 인스턴스가 필요한 자리에는 일반형 표기(`<adapter>`)와 "Adapter Binding 문서 소관" 포인터만 둔다(mention/use 경계). 다음은 금지 토큰이 아니다: (i) 전이 이벤트 필드 값의 열거 명칭(pass/fail/escalated) 및 단계 상태 명칭(Pending/Active/Passed/Failed/Escalated) — 03 §3.2 정본의 평이한 열거 값; (ii) Lifecycle 단계 명칭(Consult/Plan/Execute/Verify/Learn/Memory Update/Complete)과 역할 명칭(Advisor/Planner/Worker/Verifier/human) — Glossary·AGENT.md 정본 어휘; (iii) 저장소 문서 식별자(`specs/…`·`framework/…`·`docs/…` 상호 참조 및 본 문서 자신의 식별자 `framework/loop/loop-state-record.md`) — 문서 식별자이며 직렬화 형식·물리 경로 토큰이 아니다(verification-report §7 분류 선례 동형).
- **자가 전수 스캔.** 위 후보 집합 전체(AI 이름·모델명·제품 기능명·언어명·툴체인명·직렬화 형식명·물리 경로·확장자·특정 Adapter Binding 문서명)로 본문을 전수 스캔하여 0건임을 확인했다(단일 토큰 검색 하나로 넓은 결론을 내지 않고, 후보 부류별 전수 대조). 직렬화 형식·물리 저장 위치가 필요한 자리는 전부 일반형 `<adapter>`와 "Adapter Binding 문서 소관(03 §4.1)" 포인터로 대체했다.
- **Glossary 정본.** 사용 용어는 전부 specs/00-glossary.md §3.2-J(J-03: 루프 상태 기록·단계 전이·재작업 루프) 정본이다. 새 용어를 신설하지 않는다. "전이 이벤트·단계 상태·Learn 트리거"는 03 §3.2 정본이 정의한 스키마·서술 명칭이며 본 문서 신설 용어가 아니다.

## §8. 요약 (규격 한눈에 보기)

- **전이 이벤트(§2)** — 10필드(`cycle_id`/`seq`/`from_stage`/`to_stage`/`trigger`/`outcome`/`retry_count`/`actor`/`ref`/`at`). 03 §3.2-A 스키마 인스턴스, 필수 표기(8 예·2 아니오 — `from_stage`·`ref`가 아니오) 정본 보존.
- **단계 상태(§3)** — 5종(`Pending`/`Active`/`Passed`/`Failed`/`Escalated`). 03 §3.2-B 인스턴스. 종료 상태와 `outcome` 어휘 공유는 읽기 보조 관찰(비계약).
- **Learn 트리거(§4)** — 실패 경로 → Lesson 후보(누적 실패 집합), 성공 경로 → Best Practice 후보. 종료 전 Learn 불가피(INV-5). 도출만 — 포맷·승격은 04/05 소관.
- **append-only·재구성(§5)** — 기록은 append-only(INV-3), 기록되지 않은 전이는 없다, 갱신은 새 이벤트 추가, 로그만으로 사이클 재구성·검증 가능(03 §7).
- **회수 이력 기록(§6, DP-L5)** — Consult 전이 이벤트 `ref`에 회수 집합 참조 기록. 03 `ref` 계약 인스턴스(괄호 열거 = 예시, 계약 확장 0). 05 `was_recalled` 입력을 루프 상태 기록 기반 도출로 전환(§ 포인터).
- **직렬화·경계(§7)** — 직렬화 형식·저장 위치·물리 경로 비서술(Adapter Binding 소관). 03 재정의 0, 07 R2 경계, 금지 토큰 0(자가 전수 스캔), Glossary 정본만 사용.
- 모든 스키마는 03 §3.2의 인스턴스이며, 물리 실현은 Adapter Binding 소관이다. 형태 A → 형태 B 전환에도 Core Contract 변경은 0이다.
