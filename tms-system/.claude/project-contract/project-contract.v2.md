## 1. 정체성·의도 (Meta · Intent)

- 인스턴스 식별자: `pc-tms-001`
- schemaVersion: `1.0` / instanceVersion: `2` / supersedes: `1`(v1 인스턴스를 대체·이력 append-only)

국내 화물자동차(트럭) **운송주선업(3인 사업장)**을 위한 **운송관리시스템(TMS)**이다.
화주의 화물을 받아 차주/운송사에 배차하고 운송을 관리하며 운임을 정산하는 종합 전산 시스템이다.

도입 동기는 네 가지 모두다.

1. 수작업(엑셀·전화·수기) 비효율 해소
2. 물량·거래처 확장 대비
3. 정산 정확도·비용 절감
4. 화주/기사 대상 가시성·서비스 차별화

전 과정(수주 → 배차 → 운송 → 정산)을 전산화하되 **최우선은 정산**이다. (Intent는 v1과 동일 — 유지.)

## 2. 기능 요구 (Requirements · Functional)

v1 F1~F9를 유지하되, 성숙으로 확정된 설계 방향(§6)을 각 요구에 반영했다.

1. **수주·오더 관리** — 화주 화물 접수(상·하차지, 품목·중량, 희망일시, 운임).
2. **배차 관리** — 세 채널 병행: (a) 고정·전속 차주 직배차, (b) 화물정보망(24시콜·화물맨 등)
   수시 섭외, (c) 용차(협력 운송사) 재위탁. **세 채널을 단일 배차 진입점으로 흡수하는
   채널 불가지 어댑터로 설계**(SD-D13). 배차 확정·기사 통보 포함.
3. **운송 진행·추적** — 상차 → 운송 → 하차 상태 관리, 인수증(인수확인).
4. **정산 (최우선)** — (a) 화주 청구운임 ↔ 차주/용차 지급운임 **건별 자동 대조(2자·3자 정산 혼재)**,
   **오더에 청구(AR)/지급(AP) 라인 분리 모델로 2자·3자를 단일 흡수, 마진=파생**(SD-D4),
   (b) 화주·노선·건별 **단가표(청구용/지급용 분리) 기반 자동 계산**(SD-D6),
   (c) **전자세금계산서** 발행/역발행 수취(대행 API — SD-D8),
   (d) **월마감·미수/미지급 자동 집계·대사**(정산 원장=건별, 월마감=파생 — SD-D7).
5. **거래처·차량·단가 마스터** — 화주·차주·운송사·차량 정보, 노선/구간 단가표(청구용/지급용 분리).
6. **실적·매출 리포트·조회** — 매출·건수·미정산 현황 통계.
7. **대외 채널** — 화주용 조회 포털, 기사용 모바일 PWA(배차 수락·상태 입력·인수증 사진 전송).
8. **외부 연동** — 전자세금계산서(대행 API), 문자·카카오 알림, 회계·ERP. (화물정보망 연동은 리스크로 별도 — §5.)
9. **예외 처리** — 재배차(기사 펑크/취소), 화물 사고·클레임, 정산 이의·수정·재발행,
   미수·연체 관리(추적·독촉 근거).

## 3. 품질 요구 (Requirements · Quality)

- **권한·접근 통제** — 화주는 자기 건만, 기사는 자기 배차만, 정산 등 민감정보는 내부만 접근.
  (내부 얇은 RBAC + 외부 행 단위 소유권 스코핑 서버 강제·정산 은닉 — SD-D10.)
- **기존 엑셀 데이터 이관** — 거래처·단가표·미정산 내역 초기 이관.
- **감사이력 (확정 포함)** — append-only 변경로그(정산·배차·오더 대상·이전값→이후값)를 확정 포함한다.
  (v1 A4 가정 → 사용자 결정으로 **확정 요구화** — SD-D11.)
- **백업 (확정 포함)** — 매니지드 DB 자동 스냅샷 + PITR(시점복구)을 확정 포함한다.
  (v1 A3 가정 → 사용자 결정으로 **확정 요구화** — SD-D12.)

## 4. 제약 (Constraints)

- **3인 사업장**(관리자 + 배차·정산 겸직자 + 1) — 권한 설계 단순(겸용 화면·내부 얇은 RBAC).
- **도입 방식** — 정산부터 단계적 확장(SD-D17 단계화).
- **전달 접점 3개** — 사무실 웹(PC) + 기사용 모바일(PWA) + 화주용 조회 포털.
- **배포 = 클라우드(SaaS) 확정**, 국내 리전 권장(매니지드). (v1 A2 가정 해소.)
- **대상 화주 = 기업 화주 위주 확정.** (v1 A1 가정 해소.)
- **우리 전용(단일 테넌트) 확정**, 멀티테넌트-ready(tenant_id 준비 — SD-D15).
- **기술스택 = TS 풀스택 권장안 채택 확정**(Node/NestJS + React/Next.js + 기사 PWA + PostgreSQL — SD-D16).

## 5. 리스크 (Risks)

- **R1 화물정보망 연동 (high · 관리됨)** — 자동연동 미확정(공개 공식 API 근거 없음).
  **반자동(엑셀 업로드) 폴백 확보(관리됨)**, 운영사 공식 문의 병행, 확보 시 자동 승격.
  **크롤링 배제**(대법 2021도1533·정보통신망법). 실현 방식은 채널 어댑터로 격리(SD-D13).
- **R2 정산 복잡도 (medium · 설계 대응 완료)** — 청구(AR)/지급(AP) 라인 분리(SD-D4)로 설계 대응.
  잔여는 구현 난이도(정산 원장=건별·월마감=파생 SD-D7).
- **R3 운영 예외 (medium)** — 정산 상태머신(SD-D9)+감사로그(SD-D11)로 대응.
- **R4 외부 연동 벤더 종속·심사 리드타임 (medium · 신규)** — 세금계산서 대행·카카오 알림톡
  채널/템플릿 사전심사 등 벤더 종속·심사 리드타임. 폴백(SMS)·단계화(Phase 4 조건부)로 관리.
- **R5 회계 연동 방식 확정 지연 (medium · 신규)** — 더존 대상 세부 제품 미확정으로 방식 확정 지연.
  기본 반자동(전표 내보내기), 제품 확정 시 API 재평가(SD-D14·SA2).

## 7. 가정 원장 (Assumption Ledger)

종단이 **ReadyWithAssumptions**이므로 원장은 비어 있지 않다. 성숙으로 v1의 A1·A2·A3·A4·A6은
사용자 결정으로 **해소**되어 decisions/constraints로 이동했고(원장에서 제거), 잔여 3건이 남는다.

| ID | 대상 필드 | 내용 | 위험 | 상태 |
|---|---|---|---|---|
| SA1 | Requirements | 사용 시점·장소(WHEN/WHERE)=사무실 업무시간+기사 현장 실시간(모바일) — 3접점 설계로 사실상 정합이나 명시 미확인 | 저위험 | 미해결 |
| SA2 | Architecture Direction | 더존 대상 세부 제품 미확정 → 반자동(전표 내보내기) 기본 가정, 제품 확정 시 API 재평가 | 구현 전 확인 | 미해결 |
| SA3 | Requirements / Risks | 화물운송 부가세 처리(면세/과세)를 표준 과세로 가정 | 세무 확인 필요 | 미해결 |

> **해소된 v1 가정(원장에서 제거).** A1(기업 화주)→C5 확정, A2(클라우드 SaaS)→C4 확정,
> A3(백업)→Q4 확정 요구, A4(감사이력)→Q3 확정 요구, A6(회계/정보망 대상)→SD-D14·R5·SA2로
> 분해. A5(WHEN/WHERE)는 SA1로 승계(잔존). 성숙은 4건을 해소했다.
