## §0. 이 문서의 위치와 정본 경계

- **이 문서는 시연 절차서다.** 시연 3종을 **어떻게 수행하고 무엇으로 판정하는가**의 절차·입력·기대 전이 이벤트 명세·기대 관측·판정 문장·기록 포맷을 정의한다. 시연의 실제 **수행 기록**은 별도 산출물(docs/v0.6-demo.md — 후속 Task L10)이, **독립 판정**은 검증 단계(Verifier = CP2, 검증 리포트)가, **최종 승인**은 Advisor(CP3)가 담당한다. 이 절차서는 그 세 작업의 입력이다. 자기 점검은 최종 승인이 아니다 (02 §3.2-A).
- **정본은 specs/03-loop.md(§3 Core Contract·§7 완료 기준·§8 예1~3)와 확정 framework/loop/ 3문서(W1·W2)·framework/adapters/claude/loop-binding.md(W3)·memory-binding.md(v0.4)·config-schema.md §7(v0.3)이다.** 이 절차서는 그 계약·완료 기준·물리 구조를 **재정의·확장하지 않는다**. 계약 요소·판정 문장·필드·물리 구조는 § 포인터로만 참조하고, 필수/선택 표기·열거 값은 정본 그대로 보존한다.
- **판정 문장은 인용이다.** 각 시연의 판정 문장은 03 §7 시연 가능 문장 또는 ROADMAP v0.6 완료 조건의 **원문 인용 또는 그 검증 가능 환원(예/아니오)**이며, 새 판정 기준을 창설하지 않는다. 전이 이벤트 필드 값(cycle_id·seq·from_stage·to_stage·trigger·outcome·retry_count·actor·ref·at)·열거 값(outcome pass/fail/escalated·trigger 4종·actor 5종)·단계 상태(Pending/Active/Passed/Failed/Escalated)는 전부 03 §3.2-A/B·loop-state-record §2/§3·loop-binding §3 정본에서 인용한다.
- **전이 이벤트 명세는 정본 스키마의 인스턴스다 (재정의 0).** 각 시연의 (C) 기대 전이 이벤트 표는 loop-state-record §2(정본 03 §3.2-A)의 10필드 스키마를 그 시연 경로에 적용한 **기대 값 명세**이며, 필드·의미·필수 표기·열거 값을 재정의하지 않는다. `actor`·`trigger` 값은 03 §3.2-A 열거와 02 §3.1 역할 책임에서 **도출**한다 — 각 전이의 `actor`는 그 전이를 유발한(= from_stage 완료를 이끈) 역할이고, 첫 전이(from_stage 부재)의 actor는 사이클을 개시하는 Loop 호스트(Advisor 주 세션, §6)다. 역할 내부 계약·판정 내용은 02·06 소관이며 본 절차서는 재정의하지 않는다.
- **물리 구조는 loop-binding §3 정본을 그대로 따른다 (OQ-LB-1 해소 반영).** 루프 상태 기록의 물리 위치·파일 구조·직렬화·`at`/`ref` 물리 표현은 loop-binding §3(DP-L4 + OQ-LB-1 채택 확정)이 정본이다. 본 절차서는 그 구조를 **재확정하지 않고** 시연이 밟을 실행 명세로만 참조·인용한다. Memory Update 실기록의 물리 절차는 memory-binding §3(정본)을 따른다.
- **후속 시연 산출물 실재 불주장 (R2·L-07).** 시연이 생성할 산출물 — docs/v0.6-demo.md(수행 기록)·docs/v0.6-demo-fixtures/(픽스처)·`framework/adapters/claude/loop-data/`(루프 상태 기록 데이터)·Memory Update가 추가할 memory-data 항목 — 은 **전부 후속 Task L10이 생성할 예정**이며, 본 절차서는 그 실재를 주장하지 않는다. 현 시점 `loop-data/`는 **미생성**이다(loop-binding §7 실측 대조와 정합). 본 절차서는 명세만 하고 데이터·픽스처·수행 기록을 생성하지 않는다.
- **동시·후속 작성 산출물 불인용 (07 R2).** 같은/후속 Wave에서 작성될 시연 수행 기록(L10)·픽스처의 미완성 내용을 인용·추측하지 않는다. 확정 입력(03·framework/loop/ 3문서·loop-binding·memory-binding·config-schema·ROADMAP·docs/v0.5-demo-procedure·02·Glossary·L-07·L-09)만 참조한다.
- **소유 경계 준수 (07 R4).** 본 작업의 소유 경계는 이 1파일(docs/v0.6-demo-procedure.md)이다. 픽스처 파일·디렉터리·loop-data 데이터·memory-data 항목·demo.md를 생성하지 않으며, framework/·specs/·기존 Baseline 산출물·기존 memory-data 30건을 수정하지 않는다.
- **토큰 사용 허용 (docs/ 경계).** 이 문서는 `docs/` 소속 운용 문서이므로 Core/Module 경계 금지 토큰 규칙(structure.md §5 C-3 확장)의 직접 대상이 아니며, 물리 경로(`framework/adapters/claude/loop-data/…`·`.jsonl`·`.claude/agents/…`)·구체 토큰(JSON·mi-id·`model: opus`)의 사용이 허용된다 — 시연이 밟을 물리 실행 명세이기 때문이다(loop-binding §0 격리 지점이 소유한 토큰을 인용). 단, 03 §3 본문의 AI 비의존(03 §7-⑦·INV-9)은 **실계약 산출물(specs/03-loop.md §3)** 에 대한 별개 요건이며, 본 절차서의 물리 토큰 사용과 무관하다(§2 배정).
- **라벨 주의 (새 용어 신설 없음).** "시연 ⓐ/ⓑ/ⓒ", "판정 문장", "예/아니오 환원", "기대 전이 이벤트 명세", "기록 포맷", "픽스처"는 조직 편의를 위한 **서술 라벨**이며 Glossary 표제어가 아니다. 계약 용어(루프 상태 기록·전이 이벤트·단계 전이·재작업 루프·검증 게이트·재시도 한도·Lesson 후보·Best Practice 후보·회수 집합)와 필드명·열거 값은 전부 Glossary §3.2-J·03 §3·framework/loop/ 정본에서 인용한다.

## §1. 목적과 범위

이 절차서의 책임은 세 가지다.

- v0.6 시연 3종 각각에 대해 **[절차 단계 / 입력 / 기대 전이 이벤트 명세 / 기대 관측 / 판정 문장(예/아니오 환원) / 기록 포맷]** 요소를 정의한다 (§8·§10·§11). v0.5-demo-procedure 관례와 동형이며, **기대 전이 이벤트 명세(필드 값 수준)**가 v0.6에서 중심 요소다 — 시연은 이 명세대로 loop-data/`<cycle_id>.jsonl`을 생성하고, CP2가 그 파일을 재현·재계산의 대조 기준으로 쓴다.
- 각 시연의 판정 문장을 **03 §7 시연 가능 문장 7건 + 검증 방법 5항목 + ROADMAP v0.6 완료 조건 4건**의 해당 문장에 1:1 대응(배정)시키고, 재현이 아닌 정적·스캔형 판정(03 §7-⑦ AI 비의존)을 CP2 소관으로 명시 배정한다 (§2).
- 시연 수행 기록(후속 Task L10)이 그대로 채우는 **공통 기록 포맷·기록 요건**(§3), **픽스처 명세**(§4), **물리 기록 명세**(§5), **수행 주체·역할 배치**(§6), **실패 처리 규칙**(§7)을 정의한다.

시연 3종 (done 대상 — 각 시연에 입력·절차 단계·기대 전이 이벤트 명세·기대 관측·판정 문장(예/아니오 환원)이 존재):

- **시연 ⓐ 정상 사이클 (03 §8 예1 동형).** 실 위임 1건이 Consult→Plan→Execute→Verify→Learn→Memory Update→Complete 7단계를 **사람 개입 0**(actor=human 0건)으로 통과한다. 각 전이의 기대 전이 이벤트(필드 값 수준)를 명세한다 — Consult 전이의 `ref`에 회수 집합 참조(mi-id 배열) 실기록, `retry_count`=0 종료, CP3 통과 후 완료 보고 산출. (§8)
- **시연 ⓑ 재작업 루프 (03 §8 예2 동형).** 의도적 결함 픽스처로 CP2 Fail → 재작업 지시(4필드) 발행 → Execute 되돌림(`retry_count`=1, `outcome`=fail 이벤트) → 재작업 이행 → CP2 재판정 Pass → Complete. 기대 전이 이벤트를 명세한다. (§10)
- **시연 ⓒ 한도 초과 에스컬레이션 (03 §8 예3 동형).** 해소 불가 결함 픽스처로 CP2 반복 Fail → `retry_count`가 `retry.limit`(2, config-schema §7)을 초과 → **종료 전 Learn→Memory Update 실행(INV-5 — 누적 Lesson 후보 실기록)** → 에스컬레이션 종료(`outcome`=escalated). **완료 보고 미생성** 확인 절차. **사용자 개입 1회**(Advisor가 세션에서 사용자에게 에스컬레이션 제시 → 사용자 확인 응답)로 `actor`=human 전이 실기록 — 03 §3.1-D 조건 1의 **정당 개입**(개입 최소 INV-6 위반 아님). (§11)

이 절차서는 위 세 시연의 **절차와 판정 기준**만 정의한다. 시연의 실제 수행·판정·승인은 시연 수행 Task L10(수행 기록 docs/v0.6-demo.md)·검증 단계(Verifier = CP2)·Advisor(최종 승인 = CP3)의 소관이다 (§7).

| 필드 | 내용 |
|---|---|
| 판정 문장 | (시연별 (D)에서 확정 — 수행 Task가 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (loop-data line 원문·필드 값·memory-data 항목·완료 보고 여부 — 실값 인용, 요건 2·3) |
| 수행 단계 로그 | (단계별 관측 로그 + append된 전이 이벤트) |
| 수행 물리 지점 | (loop-data/ 경로·서브에이전트·memory-data/ — loop-binding §3·§5 참조) |

판정 값(충족/위반/판정 불가)의 최종 판정은 검증 단계(Verifier = CP2)가 06·verification-report 정본으로 수행한다. 수행 기록은 그 판정의 입력이며, 스스로 최종 승인을 내지 않는다(게이트 경계 — 자기 점검은 최종 승인이 아니다, 02 §3.2-A).

### §3.2 기록 요건 (done 7 — 재발 방지·재구성 확인·Consult)

1. **실경로·실값 인용 ("수행했다" 서술 금지, L-07).** "근거 (관측한 것)"에는 추상 주장이 아니라 **실재 파일 경로와 실값**을 남긴다 — loop-data/`<cycle_id>.jsonl`의 실경로, 각 전이 이벤트 **line 원문**(또는 필드 값 전건), Memory Update가 append한 memory-data 항목의 실 id·`source`·`kind`·`labels`. "사이클을 수행했다"·"전이가 기록됐다" 류의 서술만으로는 근거가 불충분하다(L-07 — 상태 서술은 실측 후 기록). 파일이 실제로 존재하고 그 내용이 명세와 일치함을 실측으로 확인한 뒤 기입한다.
2. **`at`·시각 주장은 순서 값 / 실측 구분 (L-09).** 전이 이벤트 `at` 필드는 **순서 값**이다(loop-binding §3.3 — 사이클 내 단조 증가하는 순서 값, 물리 벽시계 시각 아님). 수행 기록은 `at`을 "실제 수행 시각"으로 서술하지 않는다 — 순서 값과 물리 생성 시각(예: 파일·line의 mtime 실측)의 성격을 구분해 서술한다. 물리 시각이 필요하면 실측 후에만 별도로 공개한다(L-09). 시각 주장을 넣지 않으면 넣지 않았음을 근거에 명시한다.
3. **기록만으로 3사이클 재구성 확인 절차 (03 §7 검증 방법 5항목 대응).** 수행 기록은 loop-data/ 3파일(ⓐ·ⓑ·ⓒ)만으로 각 사이클을 재구성·검증할 수 있음을 아래 절차로 확인한다(loop-state-record §5 재구성 요건, 03 §7):
   - **(가) 전이 순서·완료 조건·append-only 확인** — 각 파일의 line 순서와 `seq` 단조 증가 일치, 첫 line의 `from_stage` 부재, `from_stage`→`to_stage` 연쇄로 단계 경로 복원, 기존 line 무변경(append-only). (검증 방법 1번째)
   - **(나) 되돌림 대상·종료 유형 확인** — ⓑ의 `outcome`=fail·`retry_count` 증가 line이 Execute 되돌림을, ⓒ의 반복 fail·`outcome`=escalated·`actor`=human line이 한도 초과 에스컬레이션을 복원함. ⓐ·ⓑ는 Complete 종료, ⓒ는 에스컬레이션 종료로 구분. (검증 방법 2번째)
   - **(다) Learn 트리거 시점 대조** — ⓐ의 성공 경로 Learn이 Best Practice 후보를, ⓒ의 종료 전 Learn이 누적 Lesson 후보를 도출한 시점을 03 §3.2-C와 대조하고, Memory Update가 memory-data에 append한 실 항목과 대조. (검증 방법 3번째)
   - **(라) Complete 차단 확인** — ⓒ 파일에 `to_stage`=Complete 전이가 **부재**하고 완료 보고가 **미생성**임을 확인(INV-2). (검증 방법 4번째)
4. **시연 착수 시 Memory Consult 수행·회수 집합 기록.** 시연 수행 Task는 각 사이클 착수(Consult 단계)에서 Memory Service Interface로 회수(Recall)를 실제 수행한다 — `purpose`(예: "v0.6 Loop 시연 사이클에 관련된 Active Lesson·BP 회수")와 `scope`(narrowing: `kind`=`lesson`/`best-practice`, `labels`: status=Active + 상황 투영), 기본 `detail`=index를 명시한다. 회수된 집합(회수 건수·매칭 라벨·회수된 `id` 목록)을 수행 기록에 남기고, **그 회수 집합 참조(mi-id 배열)를 해당 사이클 Consult 전이 이벤트의 `ref`에 기록**한다(loop-state-record §6 DP-L5, loop-binding §3.3). 물리 Consult 절차는 memory-binding §3.2(index-first) 소관이며, 회수·기록이 단일 Port(Recall) 경유·우회 0건임을 확인한다(03 INV-7).

## §4. 픽스처 명세 (done 4, v0.5-demo-fixtures 관례 동형)

시연 3종은 격리된 픽스처를 대상으로 사이클을 구동한다. 이 절은 그 픽스처의 **명세**를 확정한다 — **픽스처의 실물 생성은 이 절차서 소관이 아니라 시연 수행 Task L10 소관이다** (constraint, §0). 픽스처는 저장소 실계약 문서를 건드리지 않는 **자기완결** 대상물이다.

### §4.1 위치·격리 경계

- **위치.** 픽스처는 신규 디렉터리 **`docs/v0.6-demo-fixtures/`** 아래에 둔다. 이 디렉터리와 그 안의 파일은 **시연 수행 Task L10이 생성한다** — 이 절차서는 생성하지 않는다(현 시점 미존재).
- **자기완결(저장소 실계약 문서 무침범).** 시연 대상 위임의 대상물은 전부 이 디렉터리 안에 자기완결로 둔다 — 시연 사이클의 Execute 산출물도 이 경계 안에만 생성한다. `specs/`·`framework/`(loop/adapters/memory 등 실계약 문서)·기존 memory-data 30건을 **읽거나 참조는 하되 수정하지 않는다**. 시연이 실계약 산출물을 변경하지 않게 하기 위함이다.
- **CP2 전수 스캔 제외 경계 (verifier_scope 관례).** 픽스처의 의도적 결함(§4.3)은 `docs/v0.6-demo-fixtures/` 내부에만 존재한다. 03 §7-⑦ AI 비의존 전수 스캔(§2.2, CP2 소관)이나 실계약 산출물 대상 검증이 수행될 때, 픽스처 디렉터리는 **대상 경계에서 제외**하고 제외 사실을 `verifier_scope`에 명시한다(v0.5-demo-fixtures §4.2 격리 조건·criteria-catalog "정당 보유 지점 제외·제외 명시"와 동형). 픽스처의 의도적 결함이 실계약 경계의 위반으로 계상되지 않게 한다.

### §4.2 머리 명시 요건 (필수)

각 픽스처 파일의 **머리에 다음 두 문구를 명시**한다.

- **"시연 픽스처 — 실계약 문서 아님."** 픽스처가 검증 대상 계약 문서가 아니라 시연을 위해 구성된 대상물임을 표시한다.
- **"의도적 결함 정당 보유."** 시연 ⓑ·ⓒ용 결함을 담은 픽스처는 그 결함이 시연을 위해 **의도적으로 심긴 정당한 보유물**임을 명시한다 — 실계약 문서의 결함으로 오인되지 않게 한다. (v0.5-demo-fixtures "Core류 문서 역할·실계약 파일 아님" 명시와 동형.)

### §4.3 시연별 픽스처 구성 (성격 수준 명세 — 실물·구체 결함은 L10 생성)

세 픽스처는 시연 대상 위임의 대상물(자기완결)이며, ⓑ·ⓒ는 CP2 판정이 특정 결과를 내도록 설계된 **의도적 결함**을 성격 수준으로만 규정한다(구체 결함 내용은 L10이 픽스처 디렉터리 내부에 생성).

| 시연 | 픽스처 대상물 | 의도적 결함 (성격 — L10이 실물 구성) |
|---|---|---|
| **ⓐ 정상 사이클** | 자기완결 대상 명세 + 위임 완료 조건(done)이 **첫 산출로 전 항목 충족 가능**하게 설계된 대상물. | 결함 없음 — CP2 첫 판정 Pass가 기대되는 통과 케이스. |
| **ⓑ 재작업 루프** | 자기완결 대상 명세 + done 항목. | **1종 결함** — done 항목 중 1건을 **첫 Execute 산출이 충족 못 하도록** 픽스처(또는 위임 done)가 설계된다. CP2가 산출물 결함으로 이 항목을 Fail 판정 → 재작업 지시(4필드) → Worker 재구현으로 **충족 가능**(재판정 Pass 도달). 근본 원인 = 산출물 결함 → 되돌림 대상 = Execute(03 §3.1-B 기본). |
| **ⓒ 한도 초과 에스컬레이션** | 자기완결 대상 명세 + done 항목. | **해소 불가 결함** — done 항목에 **상호 모순되거나 픽스처 경계 내에서 원리적으로 동시 충족 불가**한 조건이 있어, 어떤 재구현으로도 CP2 전 항목 충족(Pass)에 도달할 수 없게 설계된다. 각 재작업 시도는 서로 다른 산출을 내지만 CP2가 그 미충족 조건을 반복 검출 → 반복 Fail → `retry.limit`=2 초과 → 에스컬레이션. 이는 실제(비모의) 해소 불가이며, Worker 재구현이 진정으로 충족에 도달하지 못한다(L-07 실측 요건, §6). |

- **결함의 지위.** ⓑ의 "1종 결함"과 ⓒ의 "해소 불가 결함"은 **Loop 메커니즘(재작업 루프·한도 초과)** 을 실증하기 위한 구성물이며, 06의 판정 기준·검증 유형(VT-1~VT-5)·거짓 완료 검출과 무관하다 — CP2가 done 미충족을 판정하는 것만으로 시연이 성립한다. 구체 결함 내용은 픽스처 디렉터리 내부에만 존재하고, 본 절차서 본문에는 성격만 서술한다(§0 소유 경계).
- **claim(완료 보고)의 지위.** 각 사이클의 Execute는 Worker 완료 보고(02 §3.2-C, self_check 포함)를 산출하나, 그 self_check "충족" 주장은 CP2 판정의 **참고 입력**일 뿐 판정 근거가 아니다(06 독립성). ⓑ·ⓒ에서 CP2는 산출물 근거로 독립 판정하여 Fail을 낸다.

## §5. 물리 기록 명세 (done 5 — loop-binding §3 정본 구조 그대로)

시연이 생성할 물리 기록 두 종의 명세다. **둘 다 후속 Task L10이 생성할 예정**이며, 본 절차서는 명세만 한다(R2·L-07 — 실재 불주장, 현 시점 loop-data/ 미생성).

### §5.1 루프 상태 기록 — `framework/adapters/claude/loop-data/<cycle_id>.jsonl` (loop-binding §3 정본)

- **위치·구조 (loop-binding §3.1, DP-L4 + OQ-LB-1 채택 확정).** 루프 상태 기록은 Adapter 경계 이하 `framework/adapters/claude/loop-data/`에 격리되며, **사이클당 파일 1개**로 두고 **1 line = 1 전이 이벤트의 append-log**로 직렬화한다: `loop-data/<cycle_id>.jsonl`. 파일명 `<cycle_id>` = 전이 이벤트 `cycle_id`(하나의 위임 = 하나의 사이클). **시연 3종 = 파일 3개**(cycle_id는 L10이 사이클별로 배정 — 예: 시연 ⓐ·ⓑ·ⓒ 각각 1개). Advisor가 이 구조를 채택 확정했으므로(OQ-LB-1 해소), 시연은 이 정본 구조 **그대로** 생성한다.
- **10필드 직렬화 (loop-binding §3.2 / 정본 loop-state-record §2·03 §3.2-A).** 각 line은 전이 이벤트 10필드를 JSON 객체로 직렬화한다. 필수 표기 보존 — 8필드(`cycle_id`·`seq`·`to_stage`·`trigger`·`outcome`·`retry_count`·`actor`·`at`)는 필수, 2필드(`from_stage`·`ref`)는 아니오. 첫 line(사이클 시작 전이)은 `from_stage` 생략. 열거 값 보존 — `outcome`(pass/fail/escalated)·`trigger`(완료 조건 충족 / Verify 실패 / 재작업 되돌림 / 에스컬레이션)·`actor`(Advisor/Planner/Worker/Verifier/human).
- **`at` = 순서 값 (loop-binding §3.3, L-09).** `at`은 사이클 내에서 **단조 증가하는 순서 값**으로 직렬화한다 — `seq`와 함께 전이 순서를 확정하며 **물리 벽시계 시각이 아니다**. 수행 기록은 `at`을 물리 시각으로 주장하지 않는다(L-09 — §3.2 요건 2). 순서 값의 구체 형식(정수 서수 등)은 Adapter 선택이며 L10이 정본 구조 내에서 배정한다.
- **`ref` = 경량 참조 (loop-binding §3.3, DP-L5).** `ref`은 관련 산출물·보고의 **식별 참조**만 담는다(원문 중복 저장 금지) — 위임/완료/실패 보고·검증 리포트의 식별 참조, **Consult 전이 이벤트는 회수 집합 참조**(그 사이클에서 회수된 memory-data store id 배열, 스킴 `mi-<정렬가능토큰>`; §3.2 요건 4). 원문이 필요하면 그 id로 Memory 백엔드에서 Recall한다(경량 id 참조).
- **append-only·재구성 (loop-binding §3.2 / loop-state-record §5·03 INV-3·§7).** 기존 line은 재작성·삭제하지 않는다 — 갱신·정정은 새 line 추가로 표현한다. 각 사이클 파일의 line 집합만으로 그 사이클의 단계 경로·재작업 되돌림·에스컬레이션·회수 참조가 복원돼야 한다(§3.2 요건 3 재구성 확인 절차).

### §5.2 Memory Update 실기록 — 정식 memory-data append (memory-binding §3 / OQ-9)

- **정식 append (OQ-9, v0.4 시연 M7 선례 동형).** 시연의 Memory Update 단계는 Learn이 도출한 후보(ⓐ 성공 → Best Practice 후보, ⓒ 종료 전 누적 실패 → Lesson 후보)를 **정식 memory-data에 append**한다 — memory-binding §3.1 Record 물리 절차(store/`<id>.json` 쓰기 + index/index.jsonl line append 정합, 04 INV-7)로 단일 Port(memory-service §7) 경유. 우회 접근 0건(03 INV-7).
- **`source` 시연 유래 표기 (OQ-9).** append되는 각 Memory Item·Index Entry의 `source` 필드에 **시연 유래를 표기**한다 — v0.4 시연이 `source`=`"v0.4-demo-M7"`, v0.5가 `"v0.5-V10-ii"`를 쓴 선례 동형으로, v0.6 시연은 `source`=`"v0.6-demo-L10"`(또는 L10이 확정하는 시연 유래 식별자)를 쓴다. 이는 시연으로 등록된 항목을 정식 회수·재발 판정 대상 위에서 유래별로 식별 가능하게 한다.
- **mi 번호 실측 순차 배정·기존 무변경 (OQ-9).** `id`는 memory-binding §2 스킴(`mi-<정렬가능토큰>`)으로, **수행 시점 실측으로 순차 배정**한다. 현 시점 store·index는 **실측 30건**(`mi-0001`~`mi-0030`)이므로, 시연 append는 그 다음 순번(예: `mi-0031`부터)에서 시작하되 정확한 번호는 L10이 수행 시점에 실측해 배정한다(선취 금지 — 구체 번호를 본 절차서가 확정하지 않는다). **기존 30건은 무변경**이며 append-only만 수행한다.
- **라벨 투영 (memory-binding §5.4).** append 항목의 `labels`는 memory-binding §5.4 정본 키(`situation`·`stable_id`·`status`·`verdict`·`matched_lesson_id`)로 투영한다 — Lesson/Best Practice 후보는 status=`Candidate`(승격 승인은 Advisor 전속, 05 INV-4 — 시연 Memory Update는 후보 등록까지). 무엇을 투영하는가는 05 소관, 키 이름·값 형태는 memory-binding §5.4 소관이며 본 절차서는 재정의하지 않는다.
- **loop-data ↔ memory-data 접속.** Memory Update 전이 이벤트(loop-data line)와 append된 memory-data 항목은 별개 백엔드다 — loop-data는 전이 기록, memory-data는 후보 실기록. Consult 전이의 `ref`(회수 집합 mi-id 배열)가 두 백엔드를 잇는 지점이며, memory content를 loop-data에 중복 저장하지 않는다(§5.1 경량 참조).

## §6. 수행 주체·역할 배치 (done 6 — Advisor 결정 OQ-7)

- **Advisor 주관 구동 (Loop 호스팅 = 주 세션).** 시연 사이클은 **Advisor(주 세션)** 가 주관 구동한다 — Loop 호스팅은 Claude Code 세션/턴의 Serve 구간이며(loop-binding §2 #1), Advisor 주 세션이 오케스트레이션(위임 수령 → Consult 회수 → Plan 채택 → Execute 위임 → Verify 트리거 → Learn → Memory Update → Complete/에스컬레이션, loop-protocol §3)을 구동한다. Consult 참조 주도·Plan 채택·CP3 최종 승인은 Advisor가 수행한다(02 §3.1).
- **Execute·CP2 실위임 (모의 시연 금지, L-07 실측 요건).** 시연은 기록물만 작성하는 **모의 시연이 아니다** — **Execute는 Worker 서브에이전트**(`.claude/agents/worker.md`, 실측 `model: opus`)에, **CP2는 Verifier 서브에이전트**(`.claude/agents/verifier.md`)에 **실제 위임**한다(loop-binding §5.1 역할 실행 = 서브에이전트 디스패치). 실 산출물이 생성되고 실 판정이 이뤄진 뒤에만 그 결과를 전이 이벤트·기록으로 남긴다(L-07 — "수행했다" 서술 금지, 실측 후 기록). Plan 초안은 Planner 서브에이전트(`planner.md`)가 담당할 수 있다(초안은 Advisor 채택 대상).
- **역할 ↔ actor 대응.** 전이 이벤트 `actor`는 그 전이를 유발한 역할이다(§0) — CP1(Worker 자체 점검)은 Execute→Verify 전이의 근거, CP2(Verifier 독립 판정)는 Verify 전이의 판정, CP3(Advisor 최종 승인)은 Complete 진입 게이트(stage-transition-rules §2.2). 사람 개입(ⓒ)만 `actor`=human이며, 이는 Advisor가 사용자에게 에스컬레이션을 제시하고 사용자가 확인 응답한 실 개입이다(loop-binding §5.2 사람 개입 물리 채널 — 주 세션 사용자 제시).
- **Worker(본 절차서 작성자)의 후속 담당.** 픽스처(docs/v0.6-demo-fixtures/) 준비·수행 기록(docs/v0.6-demo.md) 정리는 **Worker(Task L10)** 담당이다. 본 절차서(Task L9)는 그 실행 명세만 확정하며, 픽스처·기록물을 생성하지 않는다(§0 소유 경계).

## §7. 실패 처리 규칙 (v0.5-demo-procedure §7 동형)

시연이 기대 관측과 **다르게 관측될 때**의 처리 규칙이다.

1. **은폐 없이 그대로 기록한다.** 관측이 기대와 달라도 실제 관측을 §3 기록 포맷의 "근거 (관측한 것)"에 그대로 남긴다. 실패·불일치를 숨기지 않는다(Worker 금지 사항 — 실패 은폐 금지, 02 O5). loop-data line 원문·실 필드 값을 그대로 인용한다.
2. **판정 값으로 표기한다.** 기대와 다르게 관측되면 해당 시연의 "관측 결과"를 **위반**으로 표기한다. 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기하며, 판정 불가를 충족으로 위장하지 않는다.
3. **재작업 여부 판단은 게이트 소관이다.** 이 절차서와 수행 기록은 관측·기록까지만 한다. 위반·판정 불가의 **재작업 여부 판단**은 검증 단계(Verifier = CP2)와 Advisor(CP3)의 소관이다. 수행 기록·절차서가 스스로 통과 처리하거나 재작업을 결정하지 않는다.
4. **음성/양성 구분.** 시연이 실패·되돌림·에스컬레이션을 **기대**하는 경우(ⓑ CP2 Fail → 되돌림, ⓒ 반복 Fail → 에스컬레이션)와 예기치 못한 실패를 근거에 구분해 기록한다. 기대된 되돌림·에스컬레이션이 정확히 관측되면 그 시연은 **충족**이다.
5. **연산 실패와 정상 fail/escalated 전이의 구분.** 시연 중 Loop 사이클 구동 연산 자체가 수행 불능(서브에이전트 디스패치 불가·loop-data 기록 불가)이면 이는 **연산 실패**이며, 재작업 루프의 정상 `outcome`=fail 전이(ⓑ·ⓒ)나 정상 `outcome`=escalated 전이(ⓒ 한도 초과)와 다르다. 둘을 혼동해 기록하지 않는다 — 연산 실패는 별도로, 정상 fail/escalated는 기대 전이 이벤트로 기록한다.

## §8. 시연 ⓐ — 정상 사이클 (03 §8 예1 동형)

목표: 실 위임 1건이 Consult→Plan→Execute→Verify→Learn→Memory Update→Complete 7단계를 **사람 개입 0**(actor=human 0건)으로 통과해 Complete에 도달하고, 각 전이가 loop-data/`<cycle_id>.jsonl`에 append-only로 남으며(`retry_count`=0 종료), Consult 전이의 `ref`에 회수 집합 참조가 실기록되고, CP3 통과 후 완료 보고가 산출됨을 보인다. 근거: 03 §7 자동 통과·검증 게이트·개입 최소·Learn 생성(성공측)·전이 기록 시연·§8 예1, ROADMAP v0.6, loop-protocol §3, stage-transition-rules §2, loop-binding §3·§5.

### (A) 절차 단계 (loop-protocol §3 오케스트레이션 8단계)

1. **위임 수령.** Advisor(주 세션)가 시연 ⓐ 위임 메시지 1건(02 §3.2-B 8필드 — 대상 = 픽스처 ⓐ 자기완결 대상물)을 수령한다. 위임 완전성(입력·출력·완료 조건·컨텍스트 존재)을 확인한다(02 INV-6). cycle_id를 배정하고 loop-data/`<cycle_id>.jsonl`을 연다.
2. **Consult 구동.** Advisor가 상위 규약·Architecture·관련 spec 참조를 주도하고, Memory 회수(Recall)를 수행한다(§3.2 요건 4 — purpose·scope 명시). 회수 집합(mi-id 배열)을 Consult 전이 이벤트 `ref`에 기록한다(loop-state-record §6 DP-L5). → Plan 전이 append.
3. **Plan 구동.** Planner 초안 → Advisor 채택(02 §3.1). → Execute 전이 append.
4. **Execute 구동 (Worker 실위임).** Worker 서브에이전트(worker.md)에 실위임 → 픽스처 대상물 산출 + 자체 점검(CP1, self_check). 산출물은 픽스처 디렉터리 내부. → Verify 전이 append.
5. **Verify 구동 (Verifier 실위임, CP2).** Advisor가 입력{산출물 + criteria}을 구성해 Verifier 서브에이전트(verifier.md)에 실위임 → CP2 독립 판정. 통과 케이스이므로 **CP2 PASS**. → Learn 전이 append.
6. **Learn 구동.** 성공 경로이므로 이 사이클을 **Best Practice 후보**로 도출한다(03 §3.2-C). → Memory Update 전이 append.
7. **Memory Update 구동.** Best Practice 후보를 memory-data에 정식 append(§5.2 — `source`=시연 유래·status=Candidate, 단일 Port). → Complete 전이 append.
8. **Complete.** Advisor CP3 최종 승인(게이트) → 사이클 정상 종료, 완료 보고(02 §3.2-C) 산출. `retry_count`=0, actor=human 0건.

### (B) 입력

- 시연 ⓐ 위임 메시지 1건(픽스처 ⓐ 자기완결 대상물 — done 전 항목 첫 산출 충족 가능, §4.3). 실물·cycle_id는 L10 배정.
- Runtime Context(effective config — `retry.limit`=2 포함, 소비만).

### (C) 기대 전이 이벤트 명세 (loop-data/`<cycle_id>.jsonl` — 7 line, loop-binding §3 정본)

아래는 시연 ⓐ 사이클이 loop-data 파일에 append할 **기대 전이 이벤트**다(필드 값 수준). 필드·열거 값 정본 = loop-state-record §2·loop-binding §3.2; `actor`·`trigger`는 03 §3.2-A 열거·02 §3.1 역할 책임에서 도출(§0). cycle_id·`at` 순서 값·`ref` 실 참조는 L10이 수행 시점에 실값으로 채운다(여기서는 구조·기대 값 명세).

| seq | from_stage | to_stage | trigger | outcome | retry_count | actor | ref | at |
|---|---|---|---|---|---|---|---|---|
| 1 | (없음) | Consult | 완료 조건 충족 | pass | 0 | Advisor | **회수 집합 참조 = 회수된 mi-id 배열**(DP-L5) | 1 |
| 2 | Consult | Plan | 완료 조건 충족 | pass | 0 | Advisor | (Plan 초안 참조) | 2 |
| 3 | Plan | Execute | 완료 조건 충족 | pass | 0 | Advisor | (채택된 계획 참조) | 3 |
| 4 | Execute | Verify | 완료 조건 충족 | pass | 0 | Worker | 완료 보고(self_check, CP1) 참조 | 4 |
| 5 | Verify | Learn | 완료 조건 충족 | pass | 0 | Verifier | 검증 리포트(CP2 PASS) 참조 | 5 |
| 6 | Learn | Memory Update | 완료 조건 충족 | pass | 0 | Verifier | (Best Practice 후보 참조) | 6 |
| 7 | Memory Update | Complete | 완료 조건 충족 | pass | 0 | Advisor | 완료 보고(02 §3.2-C) 참조 | 7 |

- **필드 값 근거.** `trigger`=완료 조건 충족(성공 경로 선형 전이, 03 §3.2-A 열거). `outcome`=pass(각 단계 완료 조건 충족). `retry_count`=0(재작업 되돌림 0회). `actor` — Consult/Plan 채택/CP3는 Advisor, Execute 완료(CP1)는 Worker, Verify(CP2 PASS)는 Verifier(Verifier가 Learn 입력 제공, 03 §3.1-A Learn 활동). 첫 line `from_stage` 부재(loop-state-record §2). **actor=human 0건**(사람 개입 없음 — 자동 통과·개입 최소).
- **Consult `ref` = 회수 집합 참조 (핵심).** seq 1의 `ref`에 그 사이클 Consult에서 회수된 memory-data store id 배열을 경량 참조로 기록한다(loop-state-record §6 DP-L5, loop-binding §3.3, §3.2 요건 4). content 원문은 담지 않는다(경량 id 참조).

### (D) 판정 문장 (인용 + 예/아니오 환원 — §2 대응)

> (03 §7 자동 통과 시연 인용) 단일 작업이 사람 개입 없이 7단계를 통과해 Complete에 도달함을 보인다(INV-6).

> (03 §7 검증 게이트 시연 인용, 통과측) Complete가 게이트(CP1→CP2→CP3) 통과 후에만 도달됨을 보인다(INV-2).

> (03 §7 개입 최소 시연 인용) 사람 승인이 §3.1-D 열거 조건에서만 요구되고, 그 외 전이가 자동 진행함을 보인다(INV-6).

> (03 §7 Learn 생성 시연 인용, 성공측) 성공이 Best Practice 후보를 Learn에서 생성함을 보인다(§3.2-C).

> (03 §7 전이 기록 시연 인용) 각 단계 전이가 루프 상태 기록에 append-only로 남고, 그 기록만으로 사이클을 재구성할 수 있음을 보인다(INV-3).

> (ROADMAP v0.6 인용) 단일 작업이 사람 개입 최소로 전체 Lifecycle을 통과한다.

**예/아니오 환원:** 시연 ⓐ 사이클이 사람 개입 0(actor=human 0건)으로 Consult→…→Complete 7전이를 `retry_count`=0으로 통과하고, loop-data/`<cycle_id>.jsonl`에 7 전이 이벤트가 append-only로 남으며(Consult 전이 `ref`에 회수 집합 참조 실기록), Best Practice 후보가 memory-data에 append되고, CP3 승인 후 완료 보고가 산출됐는가? (예 → 충족 / 아니오 → 위반)

## §10. 시연 ⓑ — 재작업 루프 (03 §8 예2 동형)

목표: 의도적 결함 픽스처(§4.3 ⓑ)로 CP2가 산출물 결함을 Fail 판정 → 재작업 지시(4필드) 발행 → 재작업 루프가 근본 원인(산출물 결함)에 따라 **Execute로 되돌리고**(`retry_count` 0→1, `outcome`=fail 전이) → Worker 재구현 → CP2 재판정 **Pass** → Complete에 도달함을 보인다. 근거: 03 §7 재작업 루프 시연·§8 예2·§3.1-B, ROADMAP v0.6, loop-protocol §4·§5.1, stage-transition-rules §2, loop-binding §3·§5.

### (A) 절차 단계 (loop-protocol §3·§4)

1. **위임 수령 ~ Execute (1차).** ⓐ와 동일하게 위임 수령 → Consult(회수·`ref` 기록) → Plan 채택 → Execute 실위임(Worker). 픽스처 ⓑ 대상물의 **첫 산출은 done 1건을 충족 못 한다**(§4.3). CP1 self_check 수행. → Verify 전이 append.
2. **Verify 구동 (CP2 Fail).** Verifier 실위임 → CP2가 산출물 근거로 독립 판정 → 미충족 done 항목을 검출 → `final_verdict`=Fail, 재작업 지시(`rework` 4필드 — violated_items·expected_state·revalidation_criteria·evidence_gap, 06 §3.2-D)를 산출한다. self_check "충족" 주장과 무관(독립성).
3. **재작업 루프 구동 (Execute 되돌림).** 근본 원인 = 산출물 결함 → 되돌림 대상 = **Execute**(03 §3.1-B 기본). 재작업 지시를 재위임 입력으로 라우팅(loop-protocol §5.1). `retry_count` 0→1. → **Verify→Execute 전이 append(`outcome`=fail, `retry_count`=1)**. 이 실패 보고는 누적 실패 집합에 추가되어 Learn 입력이 된다(03 §3.2-C).
4. **Execute (2차) ~ Verify 재판정 (CP2 Pass).** Worker 재구현으로 미충족 항목 충족 → CP1 → **Execute→Verify 전이 append(pass, `retry_count`=1)**. Verifier 재판정 → **CP2 PASS** → Verify→Learn 전이 append.
5. **Learn ~ Complete.** Learn에서 이 실패의 **Lesson 후보**(누적 실패)와 성공 **Best Practice 후보**를 함께 도출(03 §8 예2) → Memory Update 정식 append(§5.2) → CP3 승인 → Complete, 완료 보고 산출. `retry_count`=1 종료, actor=human 0건.

### (B) 입력

- 시연 ⓑ 위임 메시지 1건 + 픽스처 ⓑ(1종 의도적 결함 — 첫 산출이 done 1건 미충족, 재구현으로 충족 가능, §4.3). 실물·cycle_id는 L10 배정.

### (C) 기대 전이 이벤트 명세 (loop-data/`<cycle_id>.jsonl` — 9 line)

| seq | from_stage | to_stage | trigger | outcome | retry_count | actor | ref | at |
|---|---|---|---|---|---|---|---|---|
| 1 | (없음) | Consult | 완료 조건 충족 | pass | 0 | Advisor | 회수 집합 참조(mi-id 배열) | 1 |
| 2 | Consult | Plan | 완료 조건 충족 | pass | 0 | Advisor | (Plan 초안 참조) | 2 |
| 3 | Plan | Execute | 완료 조건 충족 | pass | 0 | Advisor | (채택된 계획 참조) | 3 |

- **핵심 전이 = seq 5 (재작업 되돌림).** `from_stage`=Verify → `to_stage`=Execute, `trigger`=재작업 되돌림, `outcome`=fail, `retry_count`=1(0→1 증가), `actor`=Verifier(CP2 Fail 판정이 되돌림을 유발), `ref`=검증 리포트(Fail)+재작업 지시 4필드 참조. 03 §3.1-B "각 재작업 되돌림은 하나의 전이 이벤트로 기록"과 03 §8 예2 "outcome=fail 전이와 retry_count=1"을 실현한다. (`trigger` 열거의 "Verify 실패"와 "재작업 되돌림" 중, 이 전이는 되돌림 전이이므로 "재작업 되돌림"으로 표기한다 — CP2 Fail(Verify 실패)이 그 원인이며, 원인은 `ref`의 검증 리포트로 복원된다.)
- **`retry_count` 누적 보존.** seq 6~9는 `retry_count`=1을 유지한다("현재까지 재작업 되돌림 횟수", 03 §3.2-A — 감소하지 않음).
- **종료.** Complete 도달(정상 종료), actor=human 0건 — 재작업은 Agent 자동 판정으로 진행하며 사람 개입을 요하지 않는다(재시도 한도 미초과, INV-6).

## §11. 시연 ⓒ — 한도 초과 에스컬레이션 (03 §8 예3 동형)

목표: 해소 불가 결함 픽스처(§4.3 ⓒ)로 CP2가 반복 Fail → `retry_count`가 `retry.limit`(2, config-schema §7)을 초과 → **종료 전 Learn→Memory Update 실행(INV-5 — 누적 Lesson 후보 실기록)** → 에스컬레이션 종료(`outcome`=escalated), **완료 보고 미생성**을 보인다. 그 사람 개입 1회(Advisor가 사용자에게 에스컬레이션 제시 → 사용자 확인, `actor`=human)는 **03 §3.1-D 조건 1(재시도 한도 초과)의 정당 개입**이며 개입 최소(INV-6) 위반이 아님을 명시한다. 근거: 03 §7 재작업 루프(한도측)·Learn 생성(실패측)·검증 게이트(미통과측)·개입 최소 시연·§8 예3·§3.1-B·§3.1-C·§3.1-D, ROADMAP v0.6, loop-protocol §4·§5.4, config-schema §7, loop-binding §3·§5.

### (A) 절차 단계 (loop-protocol §3·§4·§5.4)

1. **위임 수령 ~ Execute (1차) ~ Verify (CP2 Fail #1).** ⓑ와 동일 경로로 Execute 실위임 → CP2 Fail #1(픽스처 ⓒ의 해소 불가 조건 검출) → Execute 되돌림(`retry_count` 0→1).
2. **Execute (2차) ~ Verify (CP2 Fail #2).** Worker 재구현(다른 산출) → CP2가 여전히 해소 불가 조건 검출 → Fail #2 → Execute 되돌림(`retry_count` 1→2).
3. **Execute (3차) ~ Verify (CP2 Fail #3 → 한도 초과).** Worker 재구현(또 다른 산출) → CP2 Fail #3. **되돌림 결정으로 `retry_count`가 2→3으로 증가하나**, 초과 판정(3 > `retry.limit` 2, 03 §3.1-B 초과 조건·config-schema §7)에 따라 **되돌림을 수행하지 않고 에스컬레이션 경로로 전이한다**(사람 개입 조건 1, 03 §3.1-D). 초과 조건(3 > 2)이 기록 필드 `retry_count`=3으로 참이 되어 로그만으로 재계산 가능하다(03 §7).
4. **종료 전 Learn→Memory Update (INV-5 불가피).** 에스컬레이션 종료 직전 반드시 Learn을 거쳐 **누적 실패 집합 전체를 Lesson 후보로 도출**하고(03 §3.1-C·§3.2-C, INV-5, 03 §3.1-A Learn 진입 조건 (b)), Memory Update가 그 Lesson 후보를 memory-data에 **정식 append**한다(§5.2 — `source`=시연 유래·status=Candidate). → Verify→Learn(`outcome`=fail·`retry_count`=3), Learn→Memory Update(escalated·`retry_count`=3) 전이 append.
5. **에스컬레이션 종료 (사람 개입 1회).** Advisor(주 세션)가 사용자에게 에스컬레이션을 제시하고(loop-binding §5.2 — 주 세션 사용자 제시), 사용자가 확인 응답한다 → 종료 전이 append {`from_stage`=Memory Update, `to_stage`=**에스컬레이션**(03 §3.1-A Memory Update 실패 경로 전이 목적지), `outcome`=escalated, `actor`=human, `retry_count`=3}. 사이클은 **에스컬레이션 종료**(사람 승인 대기), **완료 보고 미생성**(검증 게이트 미통과, INV-2).
6. **완료 보고 미생성 확인.** loop-data/`<cycle_id>.jsonl`에 `to_stage`=Complete 전이가 **부재**하고, 완료 보고(02 §3.2-C)가 **생성되지 않았음**을 확인한다(§3.2 요건 3-(라), INV-2).

### (B) 입력

- 시연 ⓒ 위임 메시지 1건 + 픽스처 ⓒ(해소 불가 결함 — done에 상호 모순/원리적 충족 불가 조건, 어떤 재구현으로도 CP2 Pass 도달 불가, §4.3). 실물·cycle_id는 L10 배정.
- Runtime Context — `retry.limit`=2(config-schema §7, effective config).

| 2 | Consult | Plan | 완료 조건 충족 | pass | 0 | Advisor | (Plan 초안 참조) | 2 |

- **재작업 되돌림 2회 (seq 5·7).** 1차·2차 CP2 Fail이 각각 Execute 되돌림을 유발하며 `retry_count`가 1·2로 증가한다(03 §3.1-B, ⓑ seq 5와 동형).
- **한도 초과 → 에스컬레이션 (seq 9~11 — OQ-2 판정 반영, Advisor 2026-07-06).** 3번째 CP2 Fail(seq 8 이후)에서 되돌림 결정으로 `retry_count`가 2→**3**으로 증가하나, **초과 판정(3 > `retry.limit` 2, 03 §3.1-B)** 에 따라 되돌림을 수행하지 않고 **에스컬레이션 경로로 전이한다** — {`from_stage`=Verify, `to_stage`=Learn, `trigger`=에스컬레이션, `outcome`=fail, `retry_count`=3}(03 §3.1-A Learn 진입 조건 (b) — 에스컬레이션 종료 직전 Learn). `retry_count`=3은 **되돌림 결정 시점에 귀속**되며, 이로써 03 §3.1-B 초과 조건(3 > 2)이 **기록된 필드 값으로 참**이 되어 로그만으로 재계산·검증이 가능하다(03 §7 재구성 요건). 종료 전 반드시 Learn·Memory Update(seq 10, escalated, `retry_count`=3)를 거쳐 누적 Lesson 후보를 도출·기록한 뒤(INV-5), 사람 개입 종료 전이(seq 11)로 넘긴다. `retry_count`=3은 seq 9~11 전건 유지된다.
- **종료 전이 `to_stage`="에스컬레이션" (seq 11 — OQ-1 판정 반영, Advisor 2026-07-06).** 에스컬레이션 종료 전이는 {`from_stage`=Memory Update, `to_stage`=**에스컬레이션**, `trigger`=에스컬레이션, `outcome`=escalated, `actor`=human, `retry_count`=3}으로 기록한다. `to_stage`="에스컬레이션"은 **03 §3.1-A 6. Memory Update 행 정본 문면 "전이(실패 경로): → 에스컬레이션(§3.1-C)"이 지정한 실패 경로 전이 목적지의 인스턴스**이며 — 새 단계 값 신설이 아니라 03 §3.1-A가 스스로 지정한 목적지의 기록이다(§ 포인터로 근거 명시). **완료 보고 미생성 — `to_stage`=Complete 전이는 이 파일에 부재한다**(INV-2).

- **개입 최소 정당성 (INV-6 위반 아님).** seq 11의 `actor`=human은 03 §3.1-D **조건 1(재시도 한도 초과)** 의 열거된 정당 개입이다 — 개입 최소(INV-6)는 열거 조건에서의 사람 승인을 허용하며, ⓒ의 사람 개입은 그 조건에 정확히 부합한다. ⓐ·ⓑ의 자동 진행(actor=human 0건)과 대비하여, 사람 승인이 오직 §3.1-D 조건에서만 요구됨을 함께 실증한다.

### (D) 판정 문장 (인용 + 예/아니오 환원 — §2 대응)

> (03 §7 재작업 루프 시연 인용, 한도측) 재시도 한도 초과 시 사람 개입으로 에스컬레이션함을 보인다(§3.1-B).

> (03 §7 검증 게이트 시연 인용, 미통과측) 게이트 미통과 시 Complete가 차단됨을 보인다(INV-2).

> (03 §7 Learn 생성 시연 인용, 실패측) Verify 실패가 Lesson 후보를 Learn에서 생성함을 보인다(§3.2-C, 종료 전 Learn 불가피 INV-5).

> (03 §7 개입 최소 시연 인용) 사람 승인이 §3.1-D 열거 조건에서만 요구됨을 보인다(INV-6 — 조건 1 재시도 한도 초과).

### §12.2 결정 기록 (Advisor 판정 — 초안 open_questions 2건 해소, 2026-07-06)

초안(r1)에서 open_questions로 에스컬레이션한 2건을 Advisor가 판정으로 확정했다(재개정 지시 Task L9 r2). 두 판정 모두 **03 재정의가 아니라 03 §3.1-A/§3.1-B의 인스턴스 확정**이며, § 포인터로 근거를 명시한다. 본문(§11 (C)·(A)·(E))은 이 판정으로 갱신했다.

- **DP(OQ-1 해소) — 종료 전이 `to_stage`="에스컬레이션".** 시연 ⓒ의 에스컬레이션 종료 전이(§11 (C) seq 11)의 `to_stage`는 **"에스컬레이션"** 으로 기록한다. 근거: **specs/03-loop.md §3.1-A 6. Memory Update 행 정본 문면이 실패 경로 전이 목적지를 "전이(실패 경로): → 에스컬레이션(§3.1-C)"으로 스스로 지정**한다. 따라서 종료 전이 {`from_stage`=Memory Update, `to_stage`=에스컬레이션, `trigger`=에스컬레이션, `outcome`=escalated, `actor`=human}은 새 단계 값의 신설이 아니라 03 §3.1-A가 지정한 실패 경로 전이 목적지의 **인스턴스**다(§ 포인터로 근거 명시). 완료 보고는 미생성이며 `to_stage`=Complete 전이는 이 파일에 부재한다(INV-2).
- **DP(OQ-2 해소) — 에스컬레이션 분기 이벤트 `retry_count`=3 (모델 b).** 되돌림 카운트 증가는 **되돌림 결정 시점에 귀속**된다 — 1차 CP2 Fail → Execute 되돌림(`retry_count`=1), 2차 Fail → Execute 되돌림(`retry_count`=2), 3차 Fail → 되돌림 결정으로 `retry_count`가 3으로 증가하나 **초과 판정(3 > `retry.limit` 2)** 에 따라 되돌림을 수행하지 않고 에스컬레이션 경로로 전이한다: {`from_stage`=Verify, `to_stage`=Learn, `trigger`=에스컬레이션, `outcome`=fail, `retry_count`=3}(03 §3.1-A Learn 진입 조건 (b)). 이후 Learn→Memory Update→종료 전이도 `retry_count`=3을 유지한다. 근거: 03 §3.1-B 초과 조건("`retry_count`가 재시도 한도를 초과하면 에스컬레이션한다")이 **기록된 필드 값으로 참**(3 > 2)이 되어야 로그만으로 재계산·검증이 가능하다(03 §7 재구성 요건). 초안 제안 (a)(`retry_count`=2 + 서술 보충)는 기록 필드상 초과 조건이 참이 되지 않아 배제되었다. 초과 판정 규칙 자체는 03 §3.1-B 소관 불변이며, 이 표기는 계약 변경이 아니라 인스턴스 확정이다.

이 두 판정은 §11 (C) 전이표(seq 9~11)·(A) 단계 3~5·(E) 근거에 반영되었고, §2.2 배정표·§13 요약 등 파급 지점은 정합 갱신했다(L-06 재발 방지 — 전 지점 확인). 11-line 구성(되돌림 2회 + 에스컬레이션 분기 1)은 유지된다.
