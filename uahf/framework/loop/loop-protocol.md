## §0. 이 문서의 위치와 정본 경계

이 절이 본 문서의 경계 선언 정본이다(§7은 이 절을 가리키는 포인터일 뿐 반복하지 않는다).

- **정본은 specs/03-loop.md §3.1이다.** 이 문서는 그 사이클 구동 연산 계약의 **인스턴스**이며 연산·재작업 루프·종료·개입·기록 계약을 재정의·확장하지 않는다(structure.md §7 C-1). 위반(형태 B가 03 §3 계약을 바꾸어야만 성립하는 경우)이 발견되면 구현하지 않고 Advisor에게 보고한다.
- **운용 절차 전개 관례.** 03 §3.1 연산을 운용 절차로 전개하되(§3), 절차의 각 단계는 대응 정본 03 §를 가리키고 그 §가 진위 판정 기준을 유지한다(verifier-protocol.md §2.1 관례 동형).
- **인스턴스화 대상 경계(사이클 구동 연산 vs 단계 전이 규칙).** 대상은 03 §3.1 사이클 구동 연산(입출력·재작업 루프 구동·종료·사람 개입·Memory 접근 시점·Verify 트리거·재작업 지시 라우팅)이다. **단계 전이 규칙 상세(03 §3.1-A)는 대상이 아니며** 그 인스턴스는 framework/loop/stage-transition-rules.md가 소유한다 — 본 문서는 "03 §3.1-A 소관" 일반 포인터로만 가리키고 단계 전이의 시점·전이 판정 규칙은 정의하지 않는다.
- **형제 소유 경계.** 전이 기록 스키마(전이 이벤트·단계 상태·Learn 트리거)와 회수 이력 기록 방식(DP-L5)의 인스턴스 소유는 framework/loop/loop-state-record.md이며, Loop Provider Module 등록 서술자는 framework/loop/module-manifest.md 소관이다 — 본 문서는 재서술하지 않고 § 포인터로만 참조한다(이중 갱신 방지).
- **Module 구현 디렉터리 문서.** 본문 전체에 금지 토큰(AI 이름·모델명·제품 기능명·언어명·툴체인명·직렬화 형식명·물리 경로·확장자)을 두지 않는다 — 규칙·분류 정본은 structure.md §5 C-3(및 03 §3.3 INV-9)이다. 작성 시점의 동시 작성 형제 불인용(07 R2)·추측 0(07 R4) 준수 서술 = 종전 문면 git 앵커 90ca19c(정본 = uahf/specs/07-workflow.md §3.2-C). 재위임·역할 실행 채널, 루프 상태 기록 직렬화·저장, 사람 개입 물리 채널, Memory 배선 등 물리 실현은 Adapter Binding 문서 소관이며(03 §4.1) 일반형 `<adapter>`와 소관 포인터만 둔다.
- **서술 라벨 경계.** "형태 A / 형태 B"(§6)는 structure.md 확정 조건 C-1·C-2의 서술 라벨이며 Glossary 표제어가 아니다.
- 용어는 specs/00-glossary.md 정본만 사용한다(§3.2-J J-03 · §3.2-H Human Approval — 계약화 03 §3.1-D). 새 용어를 신설하지 않는다.

## §2. 사이클 구동 연산 인터페이스 인스턴스 (정본: 03 §3.1)

| 요소 | 값 (정본: 03 §3.1) |
|---|---|
| **입력** | 위임 메시지 1건(02 §3.2-B) + Runtime이 Serve 구간(01 §3.1-C)에 제공하는 호스팅 컨텍스트(01 §3.2-C Runtime Context — effective config·계약 해소·자원). Loop는 이 컨텍스트를 **소비만** 하고 변경하지 않는다. |
| **출력** | 완료 보고 메시지(02 §3.2-C) — Complete 도달 시. 또는 **에스컬레이션 산출** — 사람 승인 요청 및/또는 실패 보고 메시지(02 §3.2-D). |
| **완료 조건** | 7단계를 순서대로 통과하고 검증 게이트(03 §3.1-A Verify, §3.1-C)를 통과한 뒤 Complete에 도달한다. |
| **실패(에스컬레이션)** | 재시도 한도 초과·차단성 실패·사람 개입 필요 시 에스컬레이션한다(03 §3.1-C, §3.1-D, §6-실패 모드). |

- **역할 책임 비재정의.** 전이 판정을 유발하는 각 역할의 책임은 02 §3.1을 따른다. CP1=Worker 자체 점검(02 §3.2-C), CP2=Verifier 독립 판정(06 §3.1), CP3=Advisor 최종 승인(02 §3.2-A)의 역할 구분은 확정되어 있고, Loop는 순서만 배열한다.
- **호스팅 소비 경계.** Loop는 Runtime의 Bootstrap/Shutdown을 재정의하지 않고 Serve 구간(01 §3.1-C)을 소비한다(03 INV-8) — 요구 표면은 effective config 읽기·계약 해소·Serve 구간 자원 세 가지다(03 §9 정합 확인).

## §3. 오케스트레이션 절차 ↔ 정본 03 § 1:1 대응표

각 절차 단계의 진위 판정 기준은 대응 정본 03 §이다(§0). 각 단계는 오케스트레이션 행위(구동·회수·기록·트리거)이며, 단계 전이 규칙 자체는 03 §3.1-A와 stage-transition-rules.md 소관이다(재서술 0).

| 오케스트레이션 절차 단계 | 하는 일 (요지 — 오케스트레이션 행위) | 대응 정본 03 § |
|---|---|---|
| **1. 위임 수령** | 단일 위임 메시지 1건(02 §3.2-B) + Runtime Context(01 §3.2-C)를 수령한다. 위임 완전성이 Consult 진입의 전제다 — 불완전하면 진입하지 않고 반환·질의한다. | 03 §3.1 **입력** · 03 §3.1-A Consult 진입 조건(포인터) · 02 INV-6 |
| **2. Consult 구동** | 착수 컨텍스트 확보를 오케스트레이션하고, 이 단계에서 Memory 회수(Recall)를 수행한다. | 03 §3.1-A Consult(포인터) · 03 §5 Recall(§5.3) · loop-state-record §6(§5.3) |
| **3. Plan 구동** | 작업 계획·분해를 오케스트레이션한다(역할 책임은 02 §3.1 소관, Loop는 순서만 배열). | 03 §3.1-A Plan(포인터) · 02 §3.1 |
| **4. Execute 구동** | 산출물 생성을 오케스트레이션한다. Worker 산출 + 자체 점검(CP1)이 Verify 입력이 된다. | 03 §3.1-A Execute(포인터) · 02 §3.2-C · 02 §3.2-A |
| **5. Verify 구동** | 게이트 순서(CP1→CP2→CP3) 하에서 CP2 입력{산출물+criteria}을 구성해 판정 연산을 구동한다. Fail/Conditional이면 재작업 루프(§4), PASS면 Learn으로 이어진다. | 03 §3.1-A Verify(포인터) · 06 §3.1(§5.2) · 03 §3.1-B(§4) |
| **6. Learn 구동** | 누적 실패 → Lesson 후보, 성공 → Best Practice 후보 도출을 오케스트레이션한다(도출만). | 03 §3.1-A Learn(포인터) · 03 §3.2-C · INV-5 |
| **7. Memory Update 구동** | 후보 기록(Record)을 오케스트레이션한다 — 모든 접근은 단일 Port 경유다. | 03 §3.1-A Memory Update(포인터) · 03 §5 Record(§5.3) · INV-7 |

## §4. 재작업 루프 구동 (정본: 03 §3.1-B)

검증 게이트의 어느 체크포인트라도 실패하면(단계 5의 Fail 분기) 재작업 루프가 동작한다. 되돌아갈 단계는 결함의 근본 원인에 따라 결정된다(정본 문면 보존).

| 결함 근본 원인 | 되돌아갈 단계 |
|---|---|
| 산출물 결함 (CP1/CP2가 산출물 자체의 완료 조건 미충족을 지목) | Execute |
| 계획 결함 (계획 자체가 잘못되었음이 판정됨) | Plan |
| 전제·컨텍스트 결함 (착수 전제가 틀렸음이 판정됨) | Consult |

- **기본 되돌림 대상은 Execute다.** 상위 근본 원인이 판정된 경우에만 Plan 또는 Consult로 되돌린다(03 §3.1-B).
- **retry_count 증가 규칙.** 각 되돌림마다 retry_count가 1 증가하고, 각 되돌림은 하나의 전이 이벤트(`outcome` = fail)로 기록된다(스키마는 loop-state-record.md §2 소관). 되돌림의 원인이 된 실패 보고(02 §3.2-D)는 누적 실패 집합에 추가되어 Learn 입력이 된다(03 §3.2-C).
- **재시도 한도 초과 판정.** retry_count가 재시도 한도를 초과하면 에스컬레이션한다(03 §3.1-C·§3.1-D 조건 1). Loop는 판정 규칙만 정의하고 **한도 값은 정의하지 않는다** — 값·스코프 정본 소유는 framework/core/config-schema.md §7 추상 키 `retry.limit`이며(effective config로 주어짐, 01 §3.2-B) 본 문서는 재선언하지 않는다.
- **무한 재작업 없음(INV-4).** 재작업은 언제나 재시도 한도 안에서만 반복된다. 한도 초과 시의 종료·에스컬레이션 절차는 §5.4다.
- **재작업 지시의 라우팅**은 §5.1이 규정한다.

## §5. 이연 해소 (정본이 03 소관으로 이연한 4지점)

네 지점 모두 **오케스트레이션 수준(추상)**에서만 규정하며, 물리 채널·직렬화·물리 실행은 Adapter Binding 문서 소관이다(03 §4.1).

### §5.1 ⓐ 재작업 지시 라우팅 채널 (이연 정본: 06 §3.2-D · rework-instruction.md §5)

- **라우팅 규정.** Verify 구동(단계 5)에서 CP2 판정이 Fail 또는 Conditional이면(06 §3.2-C), 검증 리포트의 재작업 지시(`rework`)를 §4 근본 원인별 되돌림 단계의 **재위임 입력**으로 라우팅한다. 재위임은 02 §3.2-B 위임 메시지로 이뤄진다(03 §4.1 "재작업 지시 전달" 행과 정합).
- **포맷 재서술 0.** 재작업 지시 포맷 정본은 06 §3.2-D, 인스턴스는 rework-instruction.md §2(4필드)다 — 본 문서는 문서명+§ 참조로만 가리킨다. 라우팅 규정은 그 지시가 어느 되돌림 단계의 재위임 메시지에 실리는가만 정한다.
- **재위임 입력 구성(추상).** 재작업 지시의 위반·판정 불가 항목과 기대 상태·재검증 기준이 재위임 위임 메시지의 input·done을 형성하는 근거가 된다. Conditional의 재량 판정·최종 승인은 Advisor 소관이며(06 §3.2-C, 02 §3.2-A) Loop는 CP3·사람 개입(§5.4)으로 라우팅만 한다.

### §5.2 ⓑ Verify 트리거 (이연 정본: verifier-protocol.md §4 DP-V3)

- **트리거 규정.** Execute 완료(산출물 + 자체 점검 CP1 존재) 시점에 Loop가 CP2 독립 판정을 위한 입력{산출물 + criteria}을 **구성**하여 판정 연산을 **구동**한다(위임 생성 — 02 §3.2-B). 이것이 DP-V3가 열어 둔 "입력이 언제 자동으로 주어지는가"의 해소다(06 INV-9 — 시점·전이는 03 소관).
- **입력 구성(추상).** 판정 대상은 위임 output이 지정한 Execute 산출이고, 대조 기준(criteria)은 위임 완료 조건·규격·경계 규칙·시연 기준에서 도출된다(06 §3.2-A `criteria_basis` — 포인터). 판정 연산의 절차·기준·리포트는 06·verifier-protocol 소관이다(재서술 0).
- **게이트 순서 안에서의 구동.** CP2 구동은 게이트 순서(CP1→CP2→CP3, 03 §3.1-A) 안에서 이뤄진다. "Verify 통과"는 CP2 PASS이며(03 INV-2), 통과 후에만 완료 보고가 생성될 수 있다(02 INV-4). 매핑 상세 정본은 03 §3.1-A다.
- **물리 실행 경계.** 판정 연산을 구동하는 위임의 물리 실행 채널은 Adapter Binding 소관이다(03 §4.1). 무인 자동 실행 코드는 형태 B다(§6).

### §5.3 ⓒ Memory 접근 시점 (정본: 03 §5 · INV-7)

- **회수(Recall) 시점 — Consult 구동(단계 2).** 착수 전 관련 Lessons·이전 결정·컨텍스트를 회수한다. 회수는 **필요할 때만·목적을 명시하고·최소 범위로** 수행하며 매 전이마다 전량을 로드하지 않는다(03 §5). 회수 연산 정본은 memory-service.md §3.2(정본 04 §3.1-B)이며 재서술하지 않는다.
- **기록(Record) 시점 — Memory Update 구동(단계 7).** Learn이 도출한 후보(03 §3.2-C)를 기록한다. 기록 연산 정본은 memory-service.md §3.1(정본 04 §3.1-A)이며, 후보의 내부 포맷·승격은 04/05 소관이다.
- **회수 집합 기록의 위임.** Consult 회수 집합의 기록 방식은 framework/loop/loop-state-record.md §6(DP-L5 — Consult 전이 이벤트 `ref`에 회수 집합 참조)에 위임한다(재정의 0).
- **단일 Port 경유(INV-7).** 모든 접근은 Memory Service Interface 경유이며 영속성 백엔드에 직접 접근하지 않는다. 물리 배선·저장·직렬화는 Adapter Binding 소관이다(03 §4.1).

### §5.4 ⓓ 종료 2유형·Learn 불가피·사람 개입 (정본: 03 §3.1-C · §3.1-D · INV-5·INV-6)

Loop는 반드시 종료한다(03 INV-4). 종료는 정확히 두 유형 중 하나다(03 §3.1-C).

- **정상 종료(Complete).** CP3(Advisor 최종 승인)을 게이트로 사이클을 닫고 완료 보고 메시지(02 §3.2-C)를 반환한다(단계 8).
- **에스컬레이션 종료.** 종료 직전 반드시 Learn → Memory Update를 거쳐 누적 후보를 기록한 뒤(03 INV-5) 사람 개입 및/또는 실패 보고로 넘긴다. 사유는 재시도 한도 초과(§4)·차단성 실패(blocking = 차단됨, 02 §3.2-D)·사람 개입 필요 조건 발생이다. 이 경우 완료 보고는 생성되지 않는다(검증 게이트 미통과).

**사람 개입 지점(03 §3.1-D — 목록이 계약이다, INV-6).** Loop는 사람 개입 없이 7단계를 자동 통과하는 것을 기본으로 하며, 사람 승인은 아래 열거된 조건에서만 요구된다. 목록에 없는 전이는 Agent 역할의 자동 판정으로 진행한다.

1. **재시도 한도 초과** — 재작업 루프가 Config 재시도 한도를 초과한다(§4, 03 §3.1-B).
2. **차단성 실패** — 실패 보고의 blocking = 차단됨(02 §3.2-D). 자동 재작업으로 해소 불가.
3. **의존 계약 미확정 / 추측 필요** — Consult·Plan에서 의존 인터페이스가 미확정이라 추측 없이 진행 불가하다(02 O4).
4. **상위 규약·Architecture 충돌** — 단계 수행 중 상위 규약 또는 Architecture와의 충돌을 발견한다. 자동 해석하지 않고 사람에게 보고한다.
5. **역할 경계 초과 결정** — Architecture 결정 등 Agent 역할 권한을 넘어 사람 승인이 명시적으로 요구되는 사항.

- **개입 기록.** 각 사람 개입 발생은 루프 상태 기록에 `actor` = human으로 남는다(03 §3.1-D·§3.2-A; 스키마는 loop-state-record.md §2 소관). 사람 승인 요청의 물리 채널은 Adapter Binding 소관이다(03 §4.1).
