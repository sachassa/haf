## §1. 목적·범위 (done 1)

**대상.** v1.0 Dogfooding 대상은 소형 CLI 유틸리티 **`uahf-lessons`**다(DP-V2·DP-V4).

**목적.** `uahf-lessons`는 UAHF Memory Index 파일(`index.jsonl`)을 읽어, 그 안의 각 레코드(Lesson·Best Practice·재발 판정)를 조회·필터·표시하는 **외부 열람 유틸리티**다. Memory에 쓰지 않으며, 프레임워크 런타임 경로(단일 Port)를 경유하지도 않는다 — 직렬화된 파일을 여는 텍스트 열람 도구다(성격 결정 §7).

**범위 안 (이 CLI가 하는 일).**

- `index.jsonl` 경로를 인자로 받아 파일을 **읽기 전용**으로 연다.
- `--status` / `--kind` / `--stable-id` 필터(각 선택·조합 가능)로 레코드를 좁힌다.
- 매칭된 레코드를 표시하고, 건수 요약을 출력한다.

**범위 밖 (이 CLI가 하지 않는 일 — Non-Goals).**

- Memory에 쓰기(Record)·수정. `index.jsonl`·store 파일을 절대 변경하지 않는다(§4 DI-INV-3).
- Lessons status 생애주기 해소(Candidate→Active→Superseded/Retired의 "현재 상태" 계산)·최신 Active 해소. 이는 05/lessons.md 계약 소관이며 이 열람 유틸리티의 책임이 아니다(§3 근거).
- 프레임워크 내부 Memory 소비(Agent·Loop·Workflow·Verifier의 회수 경로). 이 CLI는 단일 Port(04)의 소비자가 아니다(§7).
- 새 Memory 연산·필드·`kind` 값·라벨 키의 창설(memory-binding.md 정본 불가침).

### §1.1 입력 인터페이스

| 요소 | 값 | 필수 | 의미 |
|---|---|---|---|
| 위치 인자 `<index-path>` | `index.jsonl` 파일 경로 | **예** | 읽을 Memory Index 파일. 부재·미접근 시 오류 종료(§4 케이스 d). |
| `--status <값>` | `Candidate` / `Active` / `Superseded` / `Retired` (memory-binding.md §5.4 status 값) | 아니오 | 각 라인의 `labels.status`가 `<값>`과 같은 레코드만 남긴다. |
| `--kind <값>` | `lesson` / `best-practice` / `recurrence-judgment` (memory-binding.md §5.1 `kind` 3종) | 아니오 | 각 라인의 `kind`가 `<값>`과 같은 레코드만 남긴다. |
| `--stable-id <값>` | 안정 식별자 (예: `L-07`, `BP-01`) | 아니오 | 각 라인의 `labels.stable_id`가 `<값>`과 같은 레코드만 남긴다. |

- 세 필터는 각각 선택이며 **조합 가능**하다. 여러 필터를 동시에 지정하면 **논리곱(AND)** 으로 좁힌다(§3 DI-SEM-2).
- 필터를 하나도 지정하지 않으면(무필터) 파일의 모든 레코드를 대상으로 한다(§4 케이스 a).

### §1.2 출력 형식

- **레코드 표시.** 매칭된 각 레코드에 대해 최소 다음 필드를 표시한다 — `id`, `kind`, `labels.status`(없으면 `-`), `labels.stable_id`(없으면 `-`), `digest`. 이 5개 표시 필드는 Index Entry 6필드(memory-binding.md §2 #4: `id`·`kind`·`source`·`timestamp`·`labels`·`digest`)의 부분집합이며, `digest`가 사람이 읽는 한 줄 요약이다. 표시 렌더링의 세부(표/라인/정렬 방식)는 개발 Task 재량이되, 위 5개 필드는 반드시 표시한다.
- **건수 요약.** 출력 말미에 매칭된 레코드 총 건수를 명시하는 요약 라인을 1개 이상 낸다(예: `matched: N`). 무필터면 총 레코드 수를 보고한다(§4 케이스 a → 61).
- **0 매칭.** 매칭이 0건이어도 오류가 아니다 — 빈 결과 + `matched: 0`을 출력하고 정상 종료(exit 0)한다. (memory-binding.md §5.2 "매칭 없으면 빈 집합, 실패 아님"과 동형.)

## §2. CLI 기능 범위 요약 (done 1)

- **이름:** `uahf-lessons`.
- **한 줄 정의:** `index.jsonl`(경로 인자)을 읽어 Lesson/BP/재발 판정 레코드를 필터 조회·표시하는 읽기 전용 CLI 열람 유틸리티.
- **입력:** `<index-path>`(필수) + `--status`/`--kind`/`--stable-id`(각 선택·조합 가능).
- **처리:** 파일을 라인 단위로 읽어 각 라인을 독립 레코드로 파싱하고, 지정된 필터를 AND로 적용한다(§3).
- **출력:** 매칭 레코드 표시(§1.2 필드) + 건수 요약.
- **부작용:** 없음 — 읽기 전용(§4 DI-INV-3).

## §3. 필터 의미론 확정 (done 2)

**확정: `uahf-lessons`의 필터는 "인덱스 라인 필터 기준(index-line filter basis)"을 채택한다.**

### §3.1 확정된 의미론

- **DI-SEM-1 (라인 = 독립 레코드).** `index.jsonl`의 각 라인을 하나의 독립 레코드로 취급한다. 필터는 각 라인의 필드값과 직접 대조하며, 라인들을 stable_id로 묶어 "현재 상태"를 해소하지 **않는다**. 따라서 같은 `stable_id`의 Candidate 라인과 Active 라인은 서로 별개의 레코드로 계수된다.
- **DI-SEM-2 (필터 대조 대상 = 라인의 해당 필드).**
  - `--status <값>` → `labels.status == <값>` 인 라인.
  - `--kind <값>` → `kind == <값>` 인 라인.
  - `--stable-id <값>` → `labels.stable_id == <값>` 인 라인.
  - 여러 필터 동시 지정 시 각 조건의 논리곱(AND)을 만족하는 라인만 남긴다.
- **DI-SEM-3 (라벨 부재 라인의 처리).** `--status`·`--stable-id`가 대조하는 라벨이 없는 라인은 해당 필터에 **매칭되지 않는다**. 예: `kind=recurrence-judgment` 라인은 `labels.status`·`labels.stable_id`가 없으므로(memory-binding.md §5.4 — 재발 판정 라인은 `verdict`·`matched_lesson_id`만 가짐) `--status`나 `--stable-id` 어떤 값에도 매칭되지 않는다.
- **DI-SEM-4 (`--stable-id`는 `labels.stable_id`만 대조).** `--stable-id L-07`은 `labels.stable_id == "L-07"` 인 라인만 매칭한다. `labels.matched_lesson_id == "L-07"`(재발 판정이 L-07을 참조)인 라인은 `stable_id` 필드가 아니므로 매칭하지 않는다. 실측: 본 리포에서 `--stable-id L-07` = 2건(라벨 `stable_id` 기준)이며, `matched_lesson_id`로 L-07을 참조하는 라인은 별도로 3건 존재하지만 `--stable-id` 대상이 아니다.

### §3.2 근거 (라인 필터를 택하고 stable_id 최신 상태 해소를 택하지 않는 이유)

1. **성격 정합(§7).** `uahf-lessons`는 직렬화 파일에 대한 **외부 열람 유틸리티**다 — 텍스트 검색 도구가 파일을 여는 것과 동급이다. 열람 도구의 책임은 파일에 **적힌 그대로의 레코드**를 필터·표시하는 것이지, Lessons 계약의 status 생애주기를 재현하는 것이 아니다.
2. **소유 경계 준수.** status 생애주기(Candidate→Active→Superseded/Retired)와 "최신 `timestamp` = 현재 상태"라는 **최신 Active 해소 규칙은 05/lessons.md 계약이 소유**한다(memory-binding.md §5.3 — "status 생애주기·최신 Active 해소 규칙은 전부 05 계약 소관"). CLI가 stable_id별 최신 상태를 해소하면 Lessons 계약 의미론을 열람 유틸리티 안에 재구현하게 되어 소유 경계를 침범한다. 라인 필터는 계약 의미론을 재현하지 않으므로 이 경계를 지킨다.
3. **검증 가능성·결정성.** 라인 필터의 결과는 원본 파일과 라인 단위로 직접 대조(예: 라벨 값 일치 라인 계수)해 예/아니오로 판정할 수 있다. append-only 상태 전이 모델을 CLI가 해석할 필요가 없어 유틸리티의 범위가 최소로 유지되고, 출력이 파일과 결정적으로 대조된다.
4. **완료 기준 정합.** 위임 완료 기준(§4)의 수치 — 무필터 61 · `--status Active` 19 · `--kind recurrence-judgment` 9 — 는 전부 **라인 필터 계수값**이다. 라인 필터 의미론이 이 수치들과 정합한다. (참고: stable_id 최신 상태 해소를 택했다면 서로 다른 값이 나온다 — 예컨대 본 리포의 서로 다른 `stable_id`는 33종이므로 "현재 Active인 stable_id 수"는 19와 다르다. 위임이 명시한 "19건(라인 필터 기준)"은 라인 필터를 확정한다.)

### §4.2 완료 기준 불변 규칙

- **DI-INV-1 (실측 정합).** 완료 기준 수치는 대상 `index.jsonl`의 실제 라인 내용과 라인 필터 대조로 일치해야 한다. 파일이 갱신되어 수치가 달라지면, 판정은 "그 시점의 실측값"을 기준으로 하며 개발 Task는 실측값을 기입한다.
- **DI-INV-2 (0이 아닌 종료 코드로 실패 신호).** 필수 인자 부재·경로 미접근·읽기 불가 시 CLI는 0이 아닌 종료 코드로 종료하고 오류를 stderr로 낸다(케이스 d).
- **DI-INV-3 (읽기 전용).** CLI는 `index.jsonl` 및 Memory store에 **쓰지 않는다**. 열람만 한다(케이스 e). 이는 §7 성격 결정(외부 열람 유틸리티)의 직접 귀결이다.
- **DI-INV-4 (실제 실행 관측).** 완료는 위 케이스를 **실제로 실행해 관측**함으로써만 성립한다. 실행 없는 "구현 완료" 주장은 무효다(§6, 13 §3.2-A 검증 게이트·02 INV-4).

### §5.1 moduleSelection 근거

- **13 §3.2-A (최소 구성 집합 5요소).** 상위 규약 문서 · Agent 역할 정의 4종 · 위임·완료/실패 보고 프로토콜 · 검증 게이트(구현 주체와 검증 주체 분리) · 작업 추적. 이 5요소가 핵심 루프(위임 → 구현 → 검증 → 승인) 성립의 전제다.
- **모듈 대응.** `runtime`(호스팅·Bootstrap) + `agent`(역할 4종 + 위임·보고 프로토콜) + `verifier`(검증 게이트). 세 모듈이 최소 구성 5요소를 성립시킨다.
- **12 CK-2 / INV-2.** `moduleSelection`은 Runtime Bootstrap 필수 계약을 만족하는 최소 집합을 반드시 포함해야 하며(CK-2), Modular 원칙상 **필요한 모듈만** 설치한다(INV-2). `uahf-lessons`는 단순 열람 CLI이므로 `loop`·`memory`·`workflow`·`plugins` 등 선택 Module 없이 최소 집합으로 충분하다. (핵심 루프 1 사이클 구동은 Bootstrap 상태에서 agent 역할 + 검증 게이트의 관행으로 실현된다 — v0.9 설치가 이 최소 집합으로 루프 동작을 시연한 것과 동형: install-manifest.template.md 최소 필수 집합 `[runtime, agent, verifier]`.)
- **설치 검증.** 설치 직후 Runtime Bootstrap이 `Ready`(또는 `Degraded`)로 성공하고, VerifyInstall CK-1~CK-8을 통과해야 한다(12 §3.1·§3.2-C, docs/v0.9-install-guide.md §2). 구체 설치 세션 출력은 설치 Task 소관 — 이 명세는 계획만 확정한다.

## §7. DP-V4 결정 기록 — `uahf-lessons`의 성격 (done 6)

**결정 주체:** Advisor (결정 DP-V4, 2026-07-06).

**결정:** `uahf-lessons`는 **직렬화 파일에 대한 외부 열람 유틸리티**다. 04 단일 Port 계약의 **적용 대상 밖**이다.

**근거·성격 구분:**

- **무엇인가.** `uahf-lessons`는 UAHF Memory Index 파일(`index.jsonl`)이라는 **직렬화된 산출물 파일**을 인자로 받아 여는 외부 도구다. 텍스트 검색 도구가 로그·데이터 파일을 여는 것과 동급이다.
- **무엇이 아닌가.** 이 CLI는 **프레임워크 내부 Memory 소비자가 아니다**. 04(Memory) §3의 단일 Port(Memory Service Interface)는 소비자 목록 — Agent·Loop·Workflow·Verifier(ARCHITECTURE 5.1, Glossary §3.2-C) — 이 Memory에 접근하는 유일한 경로를 규정한다. `uahf-lessons`는 이 소비자 목록에 속하지 않으며, Record/Recall 연산(04 §3.1)을 호출하지 않는다. 파일을 직접 열어 읽을 뿐이다.
- **왜 단일 Port 적용 대상 밖인가.** 04 INV-1(단일 Port)·INV-8(백엔드 비의존)이 규율하는 것은 **프레임워크 구성요소가 Memory를 소비할 때** 반드시 Port를 경유하고 백엔드를 직접 참조하지 않는다는 것이다. `uahf-lessons`는 프레임워크 구성요소로서 Memory를 소비하는 주체가 아니라, 백엔드가 남긴 파일을 밖에서 여는 별개의 도구다. 파일을 여는 외부 열람 행위는 Port 소비가 아니므로 단일 Port 계약의 적용 대상이 아니다. (비유: 백엔드가 JSONL을 파일로 격리해 둔 그 파일을 사람이 텍스트 에디터로 여는 것이 04 Port 위반이 아닌 것과 동일하다.)
- **귀결 (§3·§4에 반영).** 이 성격 때문에 (1) CLI는 status 생애주기 해소 등 Lessons/Memory 계약 의미론을 재현하지 않고 라인 그대로 필터한다(§3.2 근거 1·2), (2) CLI는 읽기 전용이다(§4 DI-INV-3). 열람 유틸리티는 파일을 해석·재구성하지 않고 열어 보여줄 뿐이다.
- **경계.** 이 결정은 `uahf-lessons`(외부 열람 도구)에 한정된다. 장차 프레임워크 내부에서 Lessons를 회수하는 구성요소를 만든다면, 그것은 04 단일 Port를 경유해야 하며 이 결정의 대상이 아니다.
