## §1. 핵심 목표 (사용자 고정 2026-07-13)

새 독립 Capability의 추가가 아니라, **확정된 전체 흐름의 실행 가능 연결과 검증**이다:

```
Discovery ──▶ Contract v1 (Ready) ──▶ Solution Design ──▶ Contract v2 (supersedes v1) ──▶ UAHF (How-implement)
```

- Solution Design 결과는 v1을 mutable하게 수정하지 않는다 — **v1 문면 byte 불변**, v2 신규 발행(append-only 계보, 03 §3.4·PC-INV 9).
- 성숙된 v2는 이후 UAHF 구현 단계의 **선택 입력**이다(03 §3.5-A).
- 유지 원칙 10건(사용자 §4): 6요소 파이프라인 유지·planning rename 금지·Draft/Final mutable 불도입·append-only 계보·v1 in-place 수정 금지·중복 Capability 금지·사용자 게이트 불우회·정본 아키텍처 무변경·버전 번호 선전제 금지·Ground Truth/Baseline 우선.

- append-only·1 사건 = 1 레코드·순서값 seq 전속(시각은 별도 실측 성격, L-09)·"기록만으로 run 재구성" 성립.

### §4.4 Policy 실값 축 (W1 확정 — Policy as Data)

- **성숙/스킵 판정 기준**: 입력 vN의 미결 신호(architectureDirection.open 비공집합 ∨ readiness.openQuestions 비공집합 ∨ assumptionLedger 비공집합) 또는 다관심사 지표 → 성숙 필요; 전부 부재·단일 관심사 → 스킵(T9 경량 확인). 구체 문면·값은 W1 소관.
- **역할 선택 규칙**: 판정 근거의 관심사에서 파생·관심사당 최소 역할·상한(소수) — 고정 팀 열거 금지(SP-INV 5·8).
- **Projection 선택 정책**: 대상 워크스페이스에 해당 유형 정본이 이미 실재하면 신규 강제 0(동적 선택·전 유형 강제 금지, 04 §3.5).

### §4.5 책임 경계 문안 (Solution Design vs Contract Maturation — 사용자 요구 명시)

> **Solution Design은 활동이고, Contract Maturation은 그 활동이 산출하는 갱신 유형이다.** Solution Design(04)은 Ready vN을 입력으로 복잡도 판정·역할 협업·사용자 게이트를 수행하는 **UAF 레벨 활동**이며, 그 성숙 경로 종단(Matured)의 산출이 **Contract Maturation**(03 §3.4 갱신 유형) — 동일 append-only·supersedes 메커니즘에 의한 v(N+1) 재발행 — 이다. 활동 계약은 04가, 재발행 메커니즘·인스턴스 거버넌스는 03이 소유한다. 어느 쪽도 상대를 재정의하지 않는다.
