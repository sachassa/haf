## §0. 이 문서의 위치·정본 경계·판정 성격

- **정본은 Frozen specs/13-harness.md §3.2-B(상태 2종·전이 조건 4건)·§3.3(H-INV-6·H-INV-7)·§7(상태 판정 시연)·§8 예2다.** 이 문서는 그 전이 조건의 **v0.9 현 시점 인스턴스 대조·판정**이며, 상태 정의·전이 조건 문면·무결성 규칙을 **재정의·확장하지 않는다**. 계약 요소는 13 § 포인터·원문 인용으로만 참조한다.
- **판정 형식은 13 §8 예2 동형이다.** 예2는 각 조건에 대해 [정본 문면 대조 / 충족·미충족 / → 종합 판정(H-INV-7)]을 낸다. 본 문서 §3이 그 형식을 v0.9 실측 근거(산출물 § 포인터·파일 시스템 실측)로 채운다. 예2 자체는 v0.x 초기 스냅샷(관련 spec Draft/Review·환경 의존 규약 형태·Scaffold 조율 중)으로 4건 전건 미충족이었고, 본 v0.9 재판정은 그 이후 진전을 반영한다.
- **판정 성격(최종 승인 아님).** 본 문서가 산출하는 전이 판정은 13 §7 "상태 판정"의 출력 인스턴스다. 그러나 **이 산출 자체는 최종 승인이 아니다** — 13 §7은 "Verifier가 §3.2-B 전이 조건 4개를 관련 spec 상태와 대조해 Harness 상태를 판정한다. Advisor가 최종 승인한다"고 규정한다. 따라서 독립 판정(CP2 — Verifier)과 최종 승인(CP3 — Advisor)이 뒤따른다(02 §3.2-A). 상태 라인이 "CP2 대기"인 이유다. Worker(본 산출 주체)는 근거와 함께 판정을 제시하며 스스로 확정 승인하지 않는다.
- **조기 정식화 금지(H-INV-7).** 본 문서는 4건 전건 충족이 실측으로 확인되기 전에는 Formal을 선언하지 않는다. 아래 §3·§4의 판정은 조건 3 미충족으로 **Bootstrap 유지**를 결론지으며, 이는 H-INV-7("Harness는 규격이 확정되기 전에 자신을 정식이라 선언하지 않는다")과 정합한다.
- **실측 기반 상태 서술(L-07).** "충족/미충족·실재/부재" 주장은 파일 시스템·문서 정본 확인 후에만 기입한다. §3 각 조건의 근거·§6 실측 대조 표의 전 행은 2026-07-06 파일 시스템 직접 실측(status 라인 grep·디렉터리 열거)과 정본 § 원문 대조에 근거한다 — 미충족을 충족으로, 미도입을 도입으로 쓰지 않는다.
- 용어는 specs/00-glossary.md 정본만 사용한다. Harness 상태(Bootstrap/Formal, J-13)·최소 구성 집합·검증 게이트·Frozen·Baseline은 Glossary 정본이며, 본 문서는 새 용어를 신설하지 않는다. `형태 A`(문서·규약)·`형태 B`(실행 코드)는 structure.md §4의 서술 라벨 인용이며 Glossary 표제어가 아니다. `DP-4`·`DP-U1`은 Advisor 결정 라벨(본 문서는 참조·기록만 — 결정 주체는 Advisor)이다.

## §2. 판정 방법 (13 §7·§8 예2 동형)

13 §7 "상태 판정 시연"과 §8 예2의 형식을 따른다.

1. **정본 문면 인용.** 각 조건에 대해 13 §3.2-B의 전이 조건 원문을 그대로 인용한다(재정의 0).
2. **판정.** 인용한 문면의 성립 여부를 **충족 / 미충족**으로 판정한다. 근거가 부족하거나 검사 범위 한계로 확정 불가한 지점은 open_questions로 에스컬레이션하며 충족으로 위장하지 않는다(추측 금지 — 02 O4).
3. **근거.** 판정의 근거를 실측(파일 시스템 열거·status 라인 grep)과 산출물 § 포인터로 제시한다. 좁은 대리 지표 하나로 넓은 결론을 내지 않는다(06 V4) — 예: 조건 2의 Core AI 의존 0건은 단일 토큰이 아니라 C2 판정·경계 배치·CK-6 전수 스캔의 세 근거로 대조한다.
4. **종합.** 4건 전건 충족이면 Formal, 하나라도 미충족이면 Bootstrap 유지(13 §3.2-B·H-INV-7).

판정 대상은 "관련 spec 상태"(조건 1)·"환경 의존 실현의 격리와 Core 청정성"(조건 2)·"Runtime 호스팅 형태"(조건 3)·"Scaffold 설치 대상"(조건 4)이다. 각 조건의 근거 산출물은 §0 근거 정본의 확정본(Frozen specs·Baseline 자매 바인딩·r2/T4/T10 v0.9 산출물)이며, 미완성 산출물을 추측·인용하지 않았다(07 R2).

### §3.3 조건 3 — Runtime(01)의 정식 Module 구성으로 호스팅

**정본 문면(13 §3.2-B 조건 3, 원문 인용):**
> "Harness가 Runtime(01)의 정식 Module 구성으로 호스팅된다 (H-INV-6, 01 INV-2)."

대조 기준(13 §3.2-B 상태 표): Bootstrap 상태의 실현 형태는 "상위 규약 문서 + 역할 정의 + 위임·검증 관행. **Runtime의 정식 Module 구성으로 호스팅되지 않는다**." Formal 상태는 "**Runtime 정식 Module 구성** + Adapter 뒤로 격리된 환경 바인딩."

**판정: 미충족.**

**근거(정본 문면 대조·형태 A/B 실측 — 추측 없이):**

- **현 실현 = 형태 A(규약 문서·Manifest 문서·관행).** Harness의 호스팅은 현재 실행 코드가 아니라 규약·문서·관행으로 실현된다:
  - **Module Manifest는 6종 실재하나 형태 A 문서다.** 파일 시스템 실측(2026-07-06) — `framework/runtime/module-manifest.md`(01 §3.2-A Module Manifest 계약)와 5개 Module 구현 디렉터리의 인스턴스 `framework/{memory,verifier,loop,workflow,plugins}/module-manifest.md`, 합 **6종**이 실재한다(structure.md §8 트리). 그러나 이들은 **계약·규격 인스턴스 문서**이며, 실행되는 Module 정의가 아니다. runtime-binding.md §3.1 주 — "7필드 완전 직렬화 인스턴스는 형태 B."
  - **실행 Registry 미도입.** runtime-binding.md §3.2(Registry 4연산) — "Bootstrap 상태에서 등록부는 실행 코드가 아니라 **정의 파일 배치 + Advisor 오케스트레이션 규약**으로 실현된다(형태 A)." 같은 문서가 "형태 B(실행 코드) 도입 시, 위 규약 수행은 실행 Registry로 실현되며 … Runtime 정식 Module 호스팅의 진전 대상이다"라고 명시한다 — 즉 실행 Registry는 아직 도입되지 않았다.
  - **실행 Bootstrap 미도입.** runtime-binding.md §3.4 — Bootstrap/Shutdown은 "규약 실현(세션 개시/종료), 실행 Bootstrap/Shutdown은 형태 B." 세션/턴은 실행 컨테이너로 실재하나, Runtime Context를 산출하는 무인 실행 Bootstrap은 미도입이다.
  - **Module 구현 디렉터리는 형태 A 문서만 보유.** structure.md §8 트리 주 — `framework/{loop,memory,verifier,workflow,plugins}/`는 "형태 A(문서) 실현; 형태 B 시 실행 코드 실현(§4 C-2)." 실측상 각 디렉터리는 `module-manifest.md` + 프로토콜/스키마 인스턴스 문서만 보유하고 **실행 코드 0**이다.
  - **사이클 구동 실행 진입점·로더 미도입.** loop-binding.md §4(실측 대조) — "사이클 구동 실행 진입점·실행 로더 = 미도입(형태 B 예정) … `framework/loop/`는 계약 문서 4건만 실재(실행 코드 0)."
- **정본 문면 대조 결론.** 조건 3은 "Runtime(01)의 **정식 Module 구성으로 호스팅**"을 요구하고, 13 §3.2-B 상태 표는 이를 Formal 상태의 정의 요소로("Runtime 정식 Module 구성"), Bootstrap 상태를 그 부재로("호스팅되지 않는다") 규정한다. 현 실현은 규약·문서·관행(형태 A)으로 호스팅되며, 정식 Module 구성을 실행 호스팅하는 실행 Registry·실행 Bootstrap은 미도입(형태 B)이다. 따라서 조건 3의 정본 문면은 **성립하지 않는다 — 미충족**. (H-INV-6은 "Harness는 Runtime이 호스팅하는 구성의 최소 부분집합"으로 그 부분집합 "선택"만 Harness가 소유함을 규정하며, 호스팅 계약 자체는 01 소관이다. 현재 그 호스팅이 형태 B로 실현되지 않았다는 사실이 미충족의 근거다.)
- **harness-binding.md §5 정합.** harness-binding.md §5는 "13 §3.2-B 전이 조건 판정은 후속 Task(T11) 소관"으로 미루면서, 그 §2·§3의 형태 A/B 구분(위임/보고·게이트 운용·Wave 사이클 = 형태 A, 호스트 프로세스 실행 Bootstrap = 형태 B)을 본 판정의 실측 입력으로 남겼다(OQ-HB-1). 본 문서가 그 입력으로 조건 3을 미충족으로 판정한다 — harness-binding이 선취하지 않은 판정의 이행이다.

**미충족 잔여(조건 3 충족을 위한 미도입 작업 — Advisor 소관, 본 문서는 기록만):**

- **형태 B 실행 호스팅 도입.** 정식 Module 구성의 실행 호스팅(실행 Registry가 Module Manifest를 Register/Resolve, 실행 Bootstrap이 Runtime Context 산출)을 도입해야 조건 3이 충족된다.
- **DP-4 재상정.** 형태 B 실행 호스팅 도입 결정(DP-4)의 재상정이 선행 결정 사안으로 위임에 명시되었다(결정 주체 = Advisor·사용자). 본 문서는 이를 잔여로 기록만 한다(02 §3.2-A — Worker는 설계 결정을 하지 않는다).
- **형태 B 실행 코드 경계 분할 OQ.** 실행 코드를 어느 경계(각 Module 구현 디렉터리 vs `framework/adapters/claude/`)에 배치하는가의 경계 분할이 미해소다 — 위임이 명시한 참조: `OQ-M5-2`(memory)·`OQ-VB-2`(verifier-binding)·`OQ-LB-2`(loop-binding)·`OQ-WB-2`(workflow-binding)·`OQ-PB-2`(plugins-binding). 각 OQ의 상세 내용은 해당 자매 바인딩/spec 문서의 open_questions가 소유하며, 본 문서는 잔여 참조로만 기록한다(추측·재정의 0). (위임 본문의 "경계 분할 4건" 계수와 열거된 5종 라벨의 정합은 §7 OQ-TJ-2로 에스컬레이션 — 추측으로 조정하지 않는다.)
