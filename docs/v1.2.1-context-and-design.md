## 2. 북극성 — 최종 제품 목표 (사용자 진술)

UAHF/UAF는 궁극적으로 **부서 전원이 설치해서 쓰는 에이전틱 개발 도구**가 된다.

1. **설치형·프로젝트 비침투.** 도구를 각 프로젝트에 내려받는 게 아니라, **설치된 도구를 대상 프로젝트에서 호출**한다. 예: 새 계산기 프로젝트를 만들거나 수정할 때 `haf:<layer>` 명령으로 시작하면 그 구조대로 작업이 구동된다. (프로젝트 = 대상, 도구 = 적용자)
2. **Layer별 명령 호출.** `haf:<layer>` 형태(예: `haf:planning`). 현재는 진입 명령 `new`·`continue`만 존재(= `uaf-new`·`uaf-continue`). 나머지 Layer 명령은 각 Layer가 채워질 때 붙는다.
3. **독립 실행 + 체이닝.** 각 Layer를 단독으로 쓸 수 있고(uahf만/특정 Layer만), 동시에 최초 Layer→최후까지 연결된다.
4. **AI 비종속 + Layer별 LLM 선택.** 특정 LLM에 종속되지 않고, Layer별로 LLM을 고를 수 있다.
5. **최소 인간 개입.** 최종적으로 사람은 **승인 게이트에서만** 개입한다 — 지금처럼 컨텍스트가 차서 사람이 수동으로 handoff를 나르는 방식을 없앤다. (→ §5 오케스트레이션 모델)

> ※ 명령 프리픽스 명명(`haf`/`uaf`/`uahf`)은 Adapter 표면 확정 대상. LLM 선택·명령 표면·설치 패키징은 **미래 트랙**(§8).

## 3. 아키텍처 원리 — 두 개의 "Layer" 축

혼동 주의: 이 프로젝트에는 **서로 다른 두 "Layer" 축**이 있고, 직교(충돌 아님)한다.

| 축 | 무엇 | 정본 근거 |
|---|---|---|
| **UAF 파이프라인 축** (신규 최상위 Layer) | `entry / discovery / planning / runtime / knowledge` — 프로젝트를 이해→계약→실행하는 단계 | `uaf/ARCHITECTURE.md` §2.1 6요소 |
| **UAHF 6-Layer 축** (내부) | Presentation→Workflow→Agent→Runtime→Core→Adapter + Memory 횡단 | `ARCHITECTURE.md` §5 (현 root, 이동 후 `uahf/ARCHITECTURE.md`) |

- **UAHF는 최상위가 아니라 `uahf/` 아래 Runtime Layer의 구현체**다(사용자 원칙 11). uaf/ARCHITECTURE가 이미 "Entry·Discovery는 UAHF 6-Layer **외부**의 UAF 레벨 구조"라 선언 → 선례 있음, Glossary INV-3(Layer 정확히 6개) 무촉.
- **루트 `ARCHITECTURE.md` = 라우터.** 각 Layer의 `ARCHITECTURE.md`를 가리키고 Layer 관계(연결)만 서술. 각 Layer는 **독립 ARCHITECTURE**를 가진다.
- **`uaf/ARCHITECTURE.md`는 umbrella** — entry/discovery/project-contract 3 spec의 부모다(§8.1이 각 spec을 "상세 정본"으로 위임). 그래서 Phase 2에서 **통째 이동이 아니라 내용 분산**: 파이프라인 관계→루트 ARCHITECTURE, 요소별→각 Layer ARCHITECTURE. (`methodology-mapping.md`는 비정본 부록 — UAF-INV ⑥ "Framework는 방법론을 모른다"로 의도적 정본 배제 → planning/docs/appendix/.)
- **Knowledge는 Layer가 아니다** — 모든 Layer가 Consult하는 공용 Knowledge Base(사용자 원칙 10).

## 4. Layer 연결 설계 (A) — 타입 계약 파이프

**각 Layer는 입력 계약을 소비하고 출력 계약을 생산한다. 그 계약이 이음새다.** (Advisor 추천, 미확정 spec)

```
entry ──[Discovery Request]──▶ discovery ──[Project Contract]──▶ planning/uahf ──▶ execution
{mode,inputs,policy}            (Discovery 산출)                  (Stable Contract·유일 접점)

knowledge ◀──Consult── 모든 Layer   (횡단, 파이프 아님)
```

- **payload = 타입 계약(schema), narrative 아님.** 이유: LLM 교체·Layer 독립 실행 시 다음 Layer가 **안정적으로 파싱·소비**. → "AI 비종속 + Layer별 LLM 선택"과 직결.
- **저장 위치 = 대상 프로젝트의 `.claude/`** (`discovery-request/`·`project-contract/`). 도구는 설치형·무상태, 프로젝트별 상태는 그 프로젝트 `.claude/`에. **이미 contract-binding이 Project Contract를 소비 프로젝트 `.claude/project-contract/`에 두도록 확정 → 그 관례 확장.**
- **호출**: `haf:<layer>` = 입력 계약 읽기 → 실행 → 출력 계약 쓰기.
  - **체이닝**: `haf:new` → entry→…→execution 자동 연쇄, **사람 승인 게이트**(UAF-INV ⑤: Contract Ready)에서 정지.
  - **독립**: `haf:uahf` 단독 → Contract 있으면 소비, 없으면 기존 운용(**선택 입력**). `haf:discovery` 단독 → Discovery Request 주거나 생성.
- **독립+체이닝이 동시에 성립하는 근거**: 계약이 파일로 남으므로 앞 Layer 없이 계약만 있으면 뒤 Layer 실행 가능. Contract가 UAHF의 **선택 입력**(부재 시 운용 불변)이라 uahf 단독 실행이 이미 설계에 내장(uaf/ARCHITECTURE §2.1·UAF-INV ①).

**3개 메커니즘 구분(혼동 금지):** Memory=공유 지식(횡단) / Layer 계약=파이프(파이프라인축) / session handoff=시간축 연속.

## 5. 오케스트레이션·컨텍스트 모델 (B) — 최종 목표

**현재 session-handoff는 "메인 LLM이 모든 걸 컨텍스트에 든다"의 증상**이다 — 차면 사람이 수동으로 새 세션+handoff로 연속성을 나른다(사람이 컨텍스트 관리자 역할).

**목표: 연속성을 컨텍스트 창이 아니라 "디스크 아티팩트 + 위임"으로 옮겨 handoff를 사람 손에서 뗀다.** (§4와 같은 원리 — 상태를 머릿속이 아니라 파일에.)

- **오케스트레이터(메인 LLM)는 lean** — "파이프라인 위치 + 아티팩트 포인터"만 든다. 작업물 본체는 안 든다.
- **무거운 일은 sub-agent 위임** — 각자 컨텍스트에서 하고 소멸, **결과만 반환**(오케스트레이터 오염 없음).
- **상태는 디스크로 외부화** → 어떤 오케스트레이터 인스턴스든 재개 가능.
- **사람 = 승인 게이트만.**

**3-tier 영속:**

| tier | 무엇 | 대체 |
|---|---|---|
| Memory (`knowledge/`) | 장기 공유 지식(Lessons·패턴) | — |
| 계약 (Layer 경계) | 파이프라인 확정 상태(Discovery Request·Project Contract) | "무엇이 결정됐나" |
| Run 체크포인트 | 현재 실행 위치·진행(자동 기록·기계 재개) | **수동 session-handoff** |

- **결정적 전환**: session-handoff가 **사람 행위 → 자동 속성**. 구조화 체크포인트를 자동 생성·자동 소비.
- **정직한 단서**: 관건은 **위임의 철저함**. 요약이라도 오케스트레이터에 계속 쌓이면 다시 찬다 → 오케스트레이터조차 주기적 lean 체크포인트를 쓰고 거기서 재시작하도록 설계.
- **근거 원칙**: root `ARCHITECTURE.md` §3.6 Token Efficiency("항상 최소 Context만"). 이 목표는 그 원칙을 오케스트레이션 모델까지 확장한 것.
- **이 세션이 이미 proto**: Advisor 오케스트레이션 + Planner/Worker/Verifier 위임(무거운 컨텍스트 격리) + 브리프/Memory/git 외부화.
