## §0. 이 문서의 위치와 정본 경계

- **정본은 specs/07-workflow.md §3.1-C·§3.2-D다.** 이 문서는 그 Merge 연산 계약(§3.1-C)과 Merge Result 포맷(§3.2-D)의 **인스턴스**이며, 연산·데이터 포맷·불변 규칙을 **재정의·확장하지 않는다**. 계약 요소는 07의 해당 §를 § 포인터로 참조한다(framework/core/structure.md §7 확정 조건 C-1 정합 — 인스턴스는 계약 변경이 아니다; verifier-protocol.md §0·loop-protocol.md §0과 동형).
- 이 문서는 `framework/workflow/` 아래 **병합 규칙**을 확정한다 — Merge 연산(입력·출력·완료 조건·실패), Merge Result 4필드, 충돌 처리 순서의 단계별 검사·처리 규칙. 07 §3.1-C·§3.2-D의 계약을 이 경계 위에 배치·대조한다. work-graph.md §0이 "07 §3.2-D 소관 별도 인스턴스 문서(병합 규칙)"로 지목한 자리가 본 문서다.
- **연산 규칙 인스턴스로서의 소유 경계.** work-graph.md는 공통 Failure Report 포맷(07 §3.2-E)의 **포맷 인스턴스 소유 문서**이며, 각 `reason` 코드를 어느 연산이 언제 산출하는가(연산별 완료 조건과 실패 보고의 결합)는 **연산 규칙 인스턴스 문서 소관**이라고 명시했다(work-graph.md §0·§4). 본 문서가 그 규칙 인스턴스 중 **Merge 연산**을 담당한다 — Merge의 3종 `reason`(`UnverifiedResult`/`CrossReferenceMismatch`/`UnresolvedConflict`)이 어느 완료 조건 미충족에서 산출되는가의 **결합**을 소유하되, 공통 Failure Report의 4필드 구조·9종 `reason` 전체 열거는 **재게재하지 않고** work-graph.md §4를 § 포인터로 소비한다.
- **이 문서는 Module 구현 디렉터리 문서다.** `framework/workflow/`는 structure.md §2가 지정한 Module 구현 디렉터리 경계이며, work-graph.md(WF1)가 이 경계의 첫 실사용 인스턴스다. 이 문서 본문은 특정 AI 이름·모델명·제품 기능명·언어명·툴체인명·직렬화 형식명·물리 경로·확장자를 두지 않는다(structure.md §5 C-3 확장, 07 §3.3 INV-9).
- **인스턴스화 대상 경계 — Merge만.** 본 문서의 인스턴스화 대상은 Merge 연산(07 §3.1-C)과 Merge Result(07 §3.2-D) 및 충돌 처리 순서다. **Decompose(07 §3.1-A)·Dispatch(07 §3.1-B) 연산은 이 파일 소관이 아니다** — 각각 별도 인스턴스 문서 소관이며, 본 문서는 그 내용을 인용·추측하지 않고 "07 §3.1-A/§3.1-B 소관" 수준의 일반 포인터로만 가리킨다(07 R2, §6).

- **물리 실현 비서술(경계).** 병합 결과 수합·상호 참조 대조·충돌 중재 진입점의 **물리 채널·직렬화·물리 위치**는 이 문서가 서술하지 않는다. 이는 **Adapter Binding 문서 소관**이다(07 §4.1 상호 참조 정합성·충돌 중재 행·§4.2 이식 교체 지점 — 중재 진입점). 필요한 자리에는 "Adapter Binding 문서 소관(07 §4.1·§4.2)" 포인터만 둔다(§6).

## §1. 목적

`framework/workflow/`의 이 규격은 **완료·검증된 병렬 Task 결과를 어떻게 병합하고 충돌을 처리하는가**를 확정한다.

이 규격의 책임은 네 가지다.

- **Merge 연산 인터페이스** — Merge 연산(07 §3.1-C)의 입력(완료·검증된 Task 결과 집합)·출력(병합 결과 + 상호 참조 정합성 판정 + 충돌 목록)·완료 조건 3건·실패 reason 3종을 07 §3.1-C 정본의 인스턴스로 전개한다(§2).
- **Merge Result 포맷** — 병합 결과 4필드(`collected`/`crossRefStatus`/`conflicts`/`arbitration`)를 07 §3.2-D 정본 그대로 보존한 인스턴스 표로 확정한다(§3).
- **충돌 처리 규칙 전개** — 07 §3.2-D의 충돌 처리 순서(수합 → 상호 참조 정합성 검증 → 충돌 검출 → (충돌 시) Advisor 중재 → 병합 성립)를 보존하고, 각 단계를 **예/아니오 판정 가능한 검사·처리 규칙**으로 전개하며, 단계 ↔ Merge Result 필드 ↔ 완료 조건 ↔ 실패 reason의 결합을 확정한다(§4).
- **불변 준수와 판정 기준 참조 경계** — INV-5(검증 후 병합)·INV-6(중재자 = Advisor)를 준수하고, "개별 검증 통과 = 06 §3.2-C 최종 판정 Pass"를 § 포인터로만 참조하여 검증 판정 기준을 재정의하지 않음을 확정한다(§5).

경계·인스턴스 지위 선언은 §0(1벌)과 §6이 소유한다 — 본 절은 중복 선언을 두지 않는다.

## §2. Merge 연산 인터페이스 인스턴스 (정본: 07 §3.1-C)

Merge는 완료·검증된 Task 결과를 수합·정합성 검증·충돌 처리하는 연산이다(07 §3.1-C). 아래는 그 연산의 입력·출력·완료 조건·실패를 07 §3.1-C 정본과 일치하게 옮긴 인스턴스이며, 진위 판정 기준은 07 §3.1-C가 유지한다(§0). 본 절은 계약을 재정의하지 않는다(재정의·확장 0).

| 요소 | 값 (정본: 07 §3.1-C) |
|---|---|
| **입력** | 완료·검증된 Task 결과 집합 — 각 결과는 완료 보고(02 §3.2-C)를 동반한다. |
| **출력** | 병합 결과 + 상호 참조 정합성 판정 + (있다면) 충돌 목록. (출력의 포맷 인스턴스는 §3 Merge Result다.) |
| **완료 조건** | (1) 모든 Task 결과가 개별 검증을 통과했다(INV-5). (2) Task 간 상호 참조가 정합하다. (3) 충돌이 0건이거나, 발견된 충돌이 Advisor 중재로 해소되었다(INV-6). |
| **실패 보고 (reason 3종)** | `UnverifiedResult` \| `CrossReferenceMismatch` \| `UnresolvedConflict`. |

- **완료 보고 = 입력 동반물(참고 입력), 판정 근거 아님.** 각 Task 결과는 완료 보고(02 §3.2-C — `artifacts`/`self_check`/`failures`/`open_questions`/`verify_basis`, § 포인터·재정의 0)를 동반한다(07 §3.1-C 입력). 완료 보고의 5필드 정본은 02 §3.2-C가 소유하며 본 문서는 인용만 한다. Merge는 이 완료 보고를 동반물로 받되, **개별 검증 통과 여부의 판정 근거로 삼지 않는다** — 개별 검증은 Verifier 독립 판정(06 §3.1, CP2)의 산출이며 완료 보고의 `self_check`는 검사 대상(claim)이다(06 V1). Merge는 그 독립 판정의 최종 판정(Pass)을 선행 조건으로 요구할 뿐이다(§5).
- **개별 검증은 Merge가 수행하지 않는다.** "개별 검증을 통과했다"의 판정 기준은 06 §3.2-C 소관이며, Merge는 검증 통과 여부를 병합의 선행 조건으로 요구할 뿐 판정 자체를 정의하지 않는다(07 §3.1-C 주의, INV-8·Non-Goals). 본 표의 완료 조건 (1)은 그 선행 조건을 소비하는 지점이다(§5).
- **실패 보고 포맷.** Merge 실패 시 위 3종 `reason`은 공통 Failure Report(07 §3.2-E) 구조로 보고된다. 그 4필드 구조와 9종 `reason` 전체 열거의 **포맷 인스턴스는 work-graph.md §4가 소유**하며, 본 문서는 재게재하지 않고 § 포인터로 소비한다. Merge 실패의 `operation` 값은 `Merge`이고, 본 문서가 소유하는 것은 위 3종 `reason`이 **어느 완료 조건 미충족에서 산출되는가의 결합**이다(§4.1~§4.5 각 단계).
- **표 말미 면책(파일당 1곳 — §2·§3 공통 적용).** 두 표는 07 §3.1-C(연산)·§3.2-D(Merge Result) 정본을 그대로 보존한 인스턴스이며 계약을 재정의·확장하지 않는다(새 필드·새 열거 0, 정본 필수 열 부재 구조 보존). 상세 정본은 07 §3.1-C·§3.2-D가 유지한다.

## §3. Merge Result 포맷 인스턴스 (정본: 07 §3.2-D)

Merge Result는 병렬 결과의 수합·정합성 검증·충돌 처리 결과를 담는다(07 §3.2-D). 아래 필드·의미는 07 §3.2-D 정본을 **그대로 보존**한다(재정의 0, 새 필드 0, 새 열거 0). 정본 표는 필수 열을 두지 않으므로 본 인스턴스도 두지 않는다(정본 구조 보존).

| 필드 | 의미 |
|---|---|
| `collected` | 수합된 Task 결과 집합. 각 항목은 개별 검증을 통과한 결과만 포함한다 (INV-5). |
| `crossRefStatus` | 상호 참조 정합성 판정 — `Consistent` / `Mismatch`. 한 Task가 참조하는 다른 Task의 계약·산출물이 실제와 일치하는지. |
| `conflicts` | 충돌 목록. 두 Task가 같은 계약을 다르게 실현했거나 소유 경계가 사후 충돌한 경우. 각 항목은 중재 대상이다. |
| `arbitration` | 충돌 해소 결과. 중재자는 Advisor다 (INV-6). Workflow는 충돌을 검출·보고하고, 해소 결정은 Advisor가 내린다. |

- **`crossRefStatus` 열거(정본 보존).** `Consistent` / `Mismatch` 두 값이 전부다(07 §3.2-D). 새 값을 추가하지 않는다. 이 값은 §4.2(상호 참조 정합성 검증)의 검사 결과로 산출된다.
- **`arbitration` 중재자 = Advisor(정본 보존, INV-6).** Workflow는 충돌을 **검출·보고**하고 해소 **결정**은 Advisor 소관이다(07 §3.2-D, INV-6, 02 §3.2-A). 본 문서는 이 중재자 지정을 재정의하지 않는다(§5).
- **참조 대상 포맷의 소관.** `crossRefStatus`가 대조하는 계약은 Task의 `interfaceContract`, `conflicts`가 참조하는 소유 경계는 `ownedBoundary`이며 — 두 필드의 포맷 정본은 07 §3.2-B, 인스턴스 소유는 work-graph.md §3이다(재게재 0, § 포인터만).

## §4. 충돌 처리 순서 → 검사·처리 규칙 전개 (정본: 07 §3.2-D 순서 문면)

07 §3.2-D 정본은 충돌 처리 순서를 다음 문면으로 규정한다(정본 보존):

> 수합 → 상호 참조 정합성 검증 → 충돌 검출 → (충돌 시) Advisor 중재 → 병합 성립.

아래는 이 순서 문면을 보존하고, 각 단계를 **예/아니오 판정 가능한 검사·처리 규칙**으로 전개한 것이다. 전개는 07 §3.1-C 완료 조건·§3.2-D 필드·§6 실패 시나리오에 결합할 뿐 계약을 재정의·확장하지 않는다. 특히 **개별 검증의 판정 기준(무엇이 통과인가)은 전개하지 않는다** — 06 §3.2-C 소관이며 §5가 § 포인터로만 참조한다.

### §4.1 단계 1 — 수합 (Collect) → 산출: `collected`

- **검사(예/아니오).** 각 Task 결과에 대해: (a) 완료 보고(02 §3.2-C)를 동반하는가? **그리고** (b) 그 결과가 개별 검증을 통과했는가 — 즉 그 결과에 대한 독립 판정의 최종 판정이 Pass인가(INV-5; 판정 기준은 06 §3.2-C 소관, §5 포인터)?
- **처리.**
  - (a)·(b) **모두 예** → 그 결과를 `collected`에 포함한다. `collected`의 각 항목은 개별 검증을 통과한 결과만 포함한다(07 §3.2-D, INV-5).
  - (b)가 **아니오**(미검증·최종 판정이 Pass 아님) → 그 결과는 병합 대상이 아니다(INV-5). 미검증 결과를 병합하려는 시도는 완료 조건 (1) 미충족으로 Merge 실패이며 `reason` = `UnverifiedResult`이다(07 §3.1-C, §6).
- **경계.** Merge는 이 단계에서 검증을 **재수행하지 않는다**. 완료 보고는 참고 입력(동반물)이고, 개별 검증 통과 여부는 Verifier 독립 판정(06)의 최종 판정으로 주어진다(§2·§5). 이 단계는 그 최종 판정(Pass)을 선행 조건으로 확인·수합할 뿐이다.

### §4.2 단계 2 — 상호 참조 정합성 검증 (Cross-reference consistency) → 산출: `crossRefStatus`

- **검사(예/아니오).** `collected`의 각 Task가 참조하는 다른 Task의 계약·산출물(확정된 `interfaceContract`·산출물 — 07 §3.2-B·work-graph.md §3 포인터)이 **실제와 일치하는가**(07 §3.2-D `crossRefStatus` 의미)?
- **처리.**
  - **전부 일치** → `crossRefStatus` = `Consistent`. 완료 조건 (2)를 충족하고 다음 단계(충돌 검출)로 진행한다.
  - **하나라도 불일치** → `crossRefStatus` = `Mismatch`. 완료 조건 (2) 미충족으로 Merge 실패이며 `reason` = `CrossReferenceMismatch`이다. 이 불일치는 Advisor 중재로 넘긴다(07 §6 — 상호 참조 불일치 → Advisor 중재). 해소 결정은 Advisor 소관이다(INV-6).
- **경계.** 상호 참조 정합성은 **Workflow 자기 소관**의 판정이며(07 §3.1-C 출력 "상호 참조 정합성 판정", §3.2-D `crossRefStatus`), 개별 Task의 검증 판정 기준(06 소관, §5)과 **구분된다**. 이 단계는 Task 간 참조의 실제 일치 여부만 판정하며, 각 Task가 개별적으로 검증을 통과했는가는 단계 1이 다룬다.

### §4.3 단계 3 — 충돌 검출 (Conflict detection) → 산출: `conflicts`

- **검사(예/아니오).** 두 Task가 **같은 계약을 다르게 실현**했는가, 또는 **소유 경계(`ownedBoundary`)가 사후 충돌**하는가(07 §3.2-D `conflicts` 의미)?
- **처리.**
  - **그런 사례가 있으면** → 각 사례를 `conflicts` 목록에 추가한다. `conflicts`의 각 항목은 중재 대상이다(07 §3.2-D). 다음 단계(Advisor 중재)로 넘긴다.
  - **없으면** → `conflicts` = 0건. 완료 조건 (3)의 앞 분기(충돌 0건)를 충족한다.
- **경계.** Workflow는 이 단계에서 충돌을 **검출·보고만** 한다. 어느 실현을 채택할지의 **해소 결정은 내리지 않는다** — 그것은 단계 4의 Advisor 중재 소관이다(INV-6). 소유 경계의 사전 비중첩은 분해 시 보장되며(07 INV-2, Decompose 소관 — 비소관 포인터), 이 단계는 병합 시점의 **사후** 충돌만 검출한다.

### §4.4 단계 4 — (충돌 시) Advisor 중재 (Arbitration) → 산출: `arbitration`

- **검사(예/아니오).** `conflicts` 목록이 **0건 초과**인가(단계 2의 `Mismatch` 및 단계 3의 검출 충돌 포함)?
- **처리.**
  - **예(1건 이상)** → Advisor 중재로 넘긴다. Workflow는 충돌을 검출·보고하고, **해소 결정은 Advisor가 내린다**(INV-6, 02 §3.2-A — 설계·역할 충돌의 결정 권한은 Advisor). 각 충돌이 Advisor 중재로 해소되면 그 결과가 `arbitration`에 담기고 완료 조건 (3)의 뒤 분기(중재 해소)를 충족한다. 발견된 충돌이 **미해소로 남으면** 완료 조건 (3) 미충족으로 Merge 실패이며 `reason` = `UnresolvedConflict`이다(07 §3.1-C, §6 — Advisor가 중재한다).
  - **아니오(0건)** → 이 단계를 건너뛴다(`arbitration` 불필요).
- **경계.** 이 규격은 중재 **결정 권한을 갖지 않는다**(INV-6). 충돌의 검출·보고·중재 진입 라우팅까지가 Workflow 소관이고, 어떤 실현을 채택·기각할지의 재량 결정은 Advisor 소관이다(02 §3.2-A). 중재 진입점의 **물리 채널**은 이 문서가 서술하지 않는다 — Adapter Binding 문서 소관이다(07 §4.1 충돌 중재 행·§4.2 중재 진입점, §6).

### §4.5 단계 5 — 병합 성립 (Merge established)

- **검사(예/아니오).** 완료 조건 3건이 **모두 충족**되는가? — (1) `collected`의 모든 결과가 개별 검증 통과(INV-5), (2) `crossRefStatus` = `Consistent`, (3) `conflicts` = 0건이거나 발견된 전 충돌이 Advisor 중재로 해소(INV-6).
- **처리.**
  - **셋 다 예** → 병합이 성립한다. 출력은 병합 결과 + 상호 참조 정합성 판정 + (있다면) 충돌 목록이다(07 §3.1-C 출력, §3 Merge Result).
  - **하나라도 아니오** → 병합은 성립하지 않는다(완료가 아니다 — INV-5·ARCHITECTURE 3.4 정합). 미충족 조건에 대응하는 `reason`으로 Merge 실패를 보고한다(공통 Failure Report 포맷 — work-graph.md §4 포인터).

- **단계 ↔ 필드 ↔ 완료 조건 ↔ `reason` 결합.** 각 단계(§4.1~§4.5)가 자기 산출 필드·대응 완료 조건·미충족 시 `reason`을 함께 규정한다 — 별도 재집계 표를 두지 않는다(work-graph.md §0·§4가 규칙 인스턴스 문서 소관으로 지목한 결합의 소유 지점이 이 다섯 절이다). 이 결합은 07 §6 대표 실패 시나리오와 정합한다(미검증 결과 병합 → `UnverifiedResult` / 상호 참조 불일치 → `CrossReferenceMismatch` → Advisor 중재 / 충돌 미해소 → `UnresolvedConflict` → Advisor 중재).
- 각 단계의 **진위 판정 기준의 정본**은 07 §3.1-C(완료 조건·실패)·§3.2-D(필드·순서)가 유지한다.

## §5. INV-5·INV-6 준수 및 06 §3.2-C 판정 기준 참조 경계

Merge 연산이 준수하는 두 불변과, 검증 판정 기준을 06 §3.2-C에 § 포인터로만 위임하는 경계를 명문화한다. 검증 대조 지점이다.

### §5.1 INV-5 (검증 후 병합) — 판정 기준은 06 §3.2-C 참조 (재정의 0)

- **불변(07 §3.3 INV-5 보존).** 각 Task 결과는 개별 검증을 통과한 뒤에만 병합 대상이 된다. 검증 판정 기준은 이 규격이 정의하지 않는다(06-verifier 소관). 검증되지 않은 결과의 병합은 완료가 아니다(ARCHITECTURE.md 3.4).
- **"개별 검증을 통과했다" = 06 §3.2-C 최종 판정 Pass(§ 포인터 전용).** 그 판정 기준은 06 §3.2-C 최종 판정(통과/실패/조건부 도출 규칙)이 소유하며, "통과했다"는 최종 판정이 **Pass**인 상태를 뜻한다. 본 문서는 이를 07 §9 결정 기록("INV-5의 판정 기준은 06 §3.2-C 최종 판정 사용")과 정합하게 **§ 포인터로만 참조**하고, Pass/Fail/Conditional 도출 규칙을 **재서술하지 않는다**(판정 기준 재정의 0). 조건부(Conditional)·실패(Fail)는 Pass가 아니므로 개별 검증 통과가 아니며, 그 결과는 §4.1 단계 1에서 `collected`에 포함되지 않는다.
- **검증 리포트 스키마는 소비 지점 포인터만.** 개별 검증의 산출물인 검증 리포트의 스키마는 06 §3.2-A 정본이며 그 인스턴스는 framework/verifier/verification-report.md가 소유한다. 본 문서는 그 스키마를 재게재하지 않고 § 포인터로만 소비한다 — 병합 선행 조건이 요구하는 것은 그 리포트의 **최종 판정(Pass)** 결과이며, 리포트의 필드·구조는 06·verification-report.md 소관이다.
- **Merge는 검증을 수행하지 않는다.** 개별 검증(무엇이 통과인가의 판정)은 Verifier 독립 판정(06 §3.1, CP2) 소관이고, Merge는 그 최종 판정(Pass)을 병합의 **선행 조건**으로 소비할 뿐이다(07 §3.1-C 주의, INV-8·Non-Goals). 이 경계 위반(Merge가 검증 판정 기준을 정의해야만 성립하는 경우)이 발견되면 구현하지 않고 Advisor에게 보고한다.

### §5.2 INV-6 (중재자 = Advisor) — 검출·보고와 결정의 분리 (재정의 0)

- **불변(07 §3.3 INV-6 보존).** 충돌의 중재자는 Advisor다. Workflow는 충돌을 검출·보고하고, 해소 결정은 Advisor가 내린다. 설계·역할 충돌의 결정 권한은 Advisor에게 있다(02 §3.2-A 역할 경계).
- **검출·보고 = Workflow(이 규격) 소관 / 해소 결정 = Advisor 소관.** §4의 단계 2(상호 참조 불일치)·단계 3(충돌 검출)까지가 Workflow의 검출·보고이고, 단계 4의 **해소 결정**은 Advisor가 내린다. `arbitration`(§3)은 그 Advisor 결정의 결과를 담는다. 본 규격은 어떤 실현을 채택·기각할지의 재량 결정 권한을 갖지 않는다.
- **미해소 충돌의 귀결.** 발견된 충돌이 Advisor 중재로 해소되지 않으면 완료 조건 (3) 미충족으로 Merge 실패(`UnresolvedConflict`)이며, 병합은 성립하지 않는다(§4.4·§4.5). 재시도·재분해·재위임 등 후속 흐름의 오케스트레이션은 이 포맷 규격 밖이며 상위 오케스트레이션 소관이다(추측하지 않고 포인터만 — §6).

## §6. 경계와 비의존 (재정의 0 · 비소관 · 07 R2 · 금지 토큰 · Glossary)

본 문서가 준수하는 경계를 한자리에 모은다. 검증 대조 지점이다. 선언 1벌은 §0이며 본 절은 그 대조 항목만 열거한다.

- **07 계약 재정의·확장 0.** §2~§4의 연산 요소·Merge Result 필드·순서 단계는 07 §3.1-C·§3.2-D의 인스턴스이며 § 포인터로만 참조한다. 새 필드·새 열거·새 `reason`·새 완료 조건을 신설하지 않았다. 위반(형태 B가 07 §3 계약을 바꾸어야만 성립하는 경우)이 발견되면 구현하지 않고 Advisor에게 보고한다.
- **인스턴스화 대상 경계 — Merge만, Decompose·Dispatch 비소관.** 두 연산의 전개는 각 소관 별도 인스턴스 문서가 담당하며 본 문서는 "07 §3.1-A/§3.1-B 소관" 수준의 일반 포인터로만 가리킨다. 소유 경계 사전 비중첩(07 INV-2)도 Decompose 소관이며 본 문서는 병합 시점의 사후 충돌만 다룬다(§4.3).
- **검증 판정 기준 비정의(07 INV-8·Non-Goals).** "무엇이 개별 검증 통과인가"는 정의하지 않는다 — 06 §3.2-C 소관이며 최종 판정 Pass를 § 포인터로만 소비한다(§5.1). 상호 참조 정합성 판정(`crossRefStatus`)은 이와 구분되는 Workflow 자기 소관이다(§4.2).
- **포맷 소비 경로(재게재 0).** 공통 Failure Report(07 §3.2-E)·Work Graph(§3.2-A)·Task(§3.2-B) 포맷의 인스턴스는 work-graph.md §2·§3·§4가 소유한다. 본 문서는 저장소 문서 식별자 + § 포인터로만 소비하며, Merge 3종 `reason`이 어느 완료 조건 미충족에서 산출되는가의 **결합만** 소유한다(§4.1~§4.5).
- **위임 계약·완료 보고 인용 경계(07 INV-3).** 완료 보고(02 §3.2-C)·역할 경계(02 §3.2-A)는 02 소유이며 § 포인터로만 인용한다.
- **직렬화·물리 채널 비서술.** 병합 결과 수합·상호 참조 대조·충돌 중재 진입점의 물리 채널·직렬화·물리 위치는 서술하지 않고 **Adapter Binding 문서 소관**(07 §4.1·§4.2 중재 진입점) 포인터로만 처리한다. 특정 Adapter Binding 문서명·물리 진입점 토큰을 두지 않는다.
- **금지 토큰·Glossary 경계.** 금지 토큰 규칙과 정당 매치 분류(07 §3.1-C·§3.2-D 열거 값·06 최종 판정 열거·계약 필드명·Glossary §3.2-J J-07 표제어·역할 명칭·저장소 문서 식별자)의 판정 기준은 framework/core/structure.md §5 C-3 확장이 소유한다(07 INV-9). 용어는 specs/00-glossary.md §3.2-J(J-07) 정본과 07·06 정본 명칭만 사용하며 새 용어를 신설하지 않는다.
