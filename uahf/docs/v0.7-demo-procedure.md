## §0. 이 문서의 위치와 정본 경계

- **이 문서는 시연 절차서다.** 시연을 **어떻게 수행하고 무엇으로 판정하는가**의 절차·입력·기대 기록 명세·판정 문장·기록 포맷을 정의한다. 시연의 실제 **수행 기록**은 별도 산출물(후속 Task WF9 — docs/v0.7-demo.md 및 그 소산)이, **독립 판정**은 검증 단계(Verifier = CP2)가, **최종 승인**은 Advisor(CP3)가 담당한다. 이 절차서는 그 세 작업의 입력이다. 자기 점검은 최종 승인이 아니다 (02 §3.2-A).
- **정본은 specs/07-workflow.md(§3 Core Contract·§4 Adapter Binding·§7 완료 기준·§8 예2)와 확정 framework/workflow/ 5문서(WF1~WF5)·framework/adapters/claude/workflow-binding.md(WF6)·loop-binding.md(W3)·memory-binding.md(v0.4)이다.** 이 절차서는 그 계약·완료 기준·물리 구조를 **재정의·확장하지 않는다.** 계약 요소·판정 문장·필드·물리 구조는 § 포인터·원문 인용으로만 참조하고, 필수/선택 표기·열거 값은 정본 그대로 보존한다.
- **판정 문장은 인용이다.** 각 판정 문장은 07 §7 시연 가능 문장 또는 ROADMAP v0.7 완료 조건의 **원문 인용 또는 그 검증 가능 환원(예/아니오)**이며, 새 판정 기준을 창설하지 않는다. Work Graph 5필드·Task 7필드·Merge Result 4필드·공통 Failure Report 4필드+reason 9종·병렬 디스패치 R1~R4·분해 검사 C1~C4·충돌 처리 5단계는 전부 07 §3.2·framework/workflow/ 5문서 정본에서 인용한다.
- **기대 기록 명세는 정본 스키마의 인스턴스다 (재정의 0).** §8 (C)의 Work Graph 인스턴스·loop-data 전이표·Merge Result는 정본 스키마(work-graph.md §2·§3·§4 / loop-state-record §2·03 §3.2-A / merge-rules.md §3)를 이 시연 경로에 적용한 **기대 값 명세**이며, 필드·의미·필수 표기·열거 값을 재정의하지 않는다. loop-data의 `actor`·`trigger` 값은 03 §3.2-A 열거·02 §3.1 역할 책임에서 도출한다 — 각 전이의 `actor`는 그 전이를 유발한 역할이고, 첫 전이(from_stage 부재)의 actor는 사이클을 개시하는 Loop 호스트(Advisor 주 세션, §6)다.
- **물리 구조는 정본을 그대로 따른다 (OQ-WB-1 해소 반영).** Work Graph 인스턴스·Merge Result 기록의 물리 형태·위치·문서 구조는 workflow-binding §3.2(DP-W4 + Advisor 채택 확정 — 문서 형태·docs/ 시연 문서 내 구조화 섹션·새 백엔드 미신설)가 정본이다. 각 Task 사이클 loop-data의 물리 위치·구조·`at`/`ref` 표현은 loop-binding §3이 정본이다. ## §1. 목적과 범위

이 절차서의 책임은 세 가지다.

- v0.7 시연(픽스처 기반 소형 워크플로 — 07 §8 예2 동형)에 대해 **[절차 단계 / 입력(픽스처) / 기대 기록 명세 / 판정 문장(예/아니오 환원) / 기록 포맷]** 요소를 정의한다 (§8). v0.6-demo-procedure 관례와 동형이며, v0.7에서 중심 요소는 **Work Graph 인스턴스(분해 결과)·3 사이클 loop-data(병렬 디스패치·실행)·Merge Result(병합·충돌 처리)** 세 소산의 기대 구조다.
- 각 판정 문장을 **07 §7 시연 가능 문장 6건 + 검증 방법 5항목 + ROADMAP v0.7 완료 조건 3건 = 14건**의 해당 문장에 1:1 대응(배정)시키고, 재현이 아닌 정적·스캔형 판정(경계 시연 INV-8·AI 비의존 시연 INV-9)을 CP2 소관으로 명시 배정한다 (§2).
- 시연 수행 기록(후속 Task WF9)이 그대로 채우는 **공통 기록 포맷·기록 요건**(§3), **픽스처 명세**(§4), **물리 기록 명세**(§5), **수행 주체·역할 배치**(§6), **실패 처리 규칙**(§7)을 정의한다.

**시연 대상 (done 대상 — 절차 단계·입력·기대 기록 명세·판정 문장(예/아니오 환원)이 존재):**

큰 작업 1건 — **픽스처 기반 소형 워크플로**(07 §8 예2 동형)를 분해→병렬 디스패치→병합한다.

- **Decompose (분해).** Planner 초안 + Advisor 채택(workflow-binding §4.1 형태 A). 큰 작업을 3-Task로 분해한다 — **T1**(produces 계약 X) / **T2**(consumes X, produces 계약 Y) / **T3**(consumes Y). 계약 X·Y는 분해 시점에 픽스처로 확정되므로, 세 Task는 동시 진행 중인 형제 산출물이 아니라 **확정된 인터페이스 계약만 참조**하며(07 R2·INV-4), 상호 선행 의존 없이 **한 병렬 집합**을 이룬다(07 §3.2-A 도출 문면 — "선행 의존이 없는 Task들이 하나의 병렬 집합을 이룬다"). 각 Task의 `ownedBoundary` = 서로 다른 출력 파일 1개(쌍별 교집합 0 — 07 INV-2). 분해 완료 조건 검사 C1~C4(decompose-rules §3)를 통과한다. 산출 = Work Graph 인스턴스(문서 형태, workflow-binding §3.2). (§8-C.1)
- **Dispatch (병렬 디스패치).** Advisor(주 세션)가 한 병렬 집합의 3 Task를 서로 다른 Worker 서브에이전트에 02 §3.2-B 위임 메시지로 **동시 디스패치**한다(dispatch-protocol §2·§3, delegation-protocol §3.3). 착수 전 분해 검사 C1~C4 통과를 확인하고, 디스패치 중 R1(위임 메시지 전용)~R4(경계 준수)를 적용한다. (§8-A)
- **각 Task = Loop 사이클 실구동 (DP-W5).** T1·T2·T3 각각이 하나의 Loop 사이클(Consult→…→Complete, 03 §3.1)을 실구동하며, 사이클당 loop-data(`v07-demo-t1.jsonl`·`v07-demo-t2.jsonl`·`v07-demo-t3.jsonl`)에 전이 이벤트를 append-only로 기록한다(loop-binding §3). 각 Task의 CP2 = Verifier 서브에이전트 실위임(Task별 검증 리포트). 통과 케이스이므로 세 사이클 모두 CP2 Pass·`retry_count`=0·정상 Complete. (§8-C.2·C.3)
- **Merge (병합·충돌 처리).** Advisor가 완료·검증된(CP2 Pass) 세 결과를 수합(collected — 개별 검증 통과만, INV-5) → 상호 참조 정합성 검증(crossRefStatus) → **충돌 검출**(픽스처가 유도한 1건: T2가 산출한 계약 Y의 실현이 T3가 소비 시 참조한 확정 계약 Y 문면과 불일치 — 두 Task가 같은 계약을 다르게 실현, merge-rules §4.3) → **Advisor 중재**(arbitration, INV-6) → 병합 성립. Merge Result 기록(문서 형태, workflow-binding §3.2). (§8-C.4)
- **Learn→Memory Update.** 시연 유래 후보를 정식 memory-data에 append한다 — 성공한 병렬 분해·병합 패턴 → **Best Practice 후보(시연 네임스페이스 BPD-)**, 병합 충돌(중재 해소) → **Lesson 후보(시연 네임스페이스 LD-)** (07 §5, AGENT.md — 성공은 BP 후보·병합 충돌은 Lesson 후보). `source`=시연 유래·status=Candidate·기존 39건 무변경 append-only. (§5.4)

이 절차서는 위 시연의 **절차와 판정 기준**만 정의한다. 시연의 실제 수행·판정·승인은 시연 수행 Task WF9(수행 기록)·검증 단계(Verifier = CP2)·Advisor(최종 승인 = CP3)의 소관이다 (§7).

## §2. 배정 대응표 — 07 §7 시연 가능 문장 6건 + 검증 방법 5항목 + ROADMAP v0.7 3건 (done 1)

세 출처의 완료 기준을 **재정의 없이 인용**하고, 각 기준을 이를 실증하는 **시연 수행(WF9, 재현형)** 또는 **마일스톤 CP2 정적 판정**(정적·스캔형) 또는 **대조 절차**(Verifier가 Work Graph 인스턴스를 대상으로 밟는 필드 존재·경계 교집합 대조) 중 **최소 1곳**에 배정한다. §8 (D)의 판정 문장은 아래 표의 해당 문장을 **그대로 인용**한다.

### §2.1 방식·소관 구분

- **재현형** — Workflow 연산(07 §3.1 Decompose·Dispatch·Merge)과 각 Task 사이클 구동(03 §3.1)을 실제 수행·관측하는 시연. 본 절차서 소관(수행 = 시연 수행 Task WF9 / 판정 = CP2 검증 리포트).
- **마일스톤 CP2 정적 판정** — specs/07-workflow.md §3 본문을 스캔·정적 대조하는 방식. **검증 리포트(Verifier = CP2)**가 마일스톤 판정에서 직접 수행한다. 이는 v0.6-demo-procedure §2가 AI 비의존 전수 스캔을 CP2 소관으로 배정한 선례와 동형이다(경계 시연 INV-8·AI 비의존 시연 INV-9는 재현이 아니라 spec 본문의 정적 성질이므로 CP2 직접 판정).
- **대조 절차** — 산출된 Work Graph 인스턴스를 대상으로 각 Task 필수 필드(`done`·`interfaceContract`·`ownedBoundary`) 존재를 §3.2-B와 대조하고, 병렬 집합 내 소유 경계 쌍별 교집합이 0임을 확인하는 절차(07 §7 검증 방법 1·2). 수행 기록(WF9)이 절차를 밟고, CP2가 독립 재현한다.

### §3.2 기록 요건 (done 2 — 재발 방지·대조·Consult)

1. **실경로·실값 인용 ("수행했다" 서술 금지, L-07).** "근거 (관측한 것)"에는 추상 주장이 아니라 **실재 파일 경로와 실값**을 남긴다 — Work Graph 인스턴스의 실 필드 값, 각 Task 사이클 loop-data `v07-demo-t{1,2,3}.jsonl`의 실경로·전이 이벤트 **line 원문**(또는 필드 값 전건), Task별 CP2 리포트의 최종 판정, Merge Result의 실 필드 값, Memory Update가 append한 memory-data 항목의 실 id·`source`·`kind`·`stable_id`. "워크플로를 수행했다"·"병합이 성립했다" 류의 서술만으로는 근거가 불충분하다(L-07 — 상태 서술은 실측 후 기록). 파일이 실제로 존재하고 그 내용이 명세와 일치함을 실측으로 확인한 뒤 기입한다.
2. **`at`·시각 주장은 순서 값 / 실측 구분 (L-09).** 각 Task 사이클 loop-data의 `at` 필드는 **순서 값**이다(loop-binding §3.3 — 사이클 내 단조 증가하는 순서 값, 물리 벽시계 시각 아님). 수행 기록은 `at`을 "실제 수행 시각"으로 서술하지 않는다 — 순서 값과 물리 생성 시각(예: 파일·line의 mtime 실측)의 성격을 구분해 서술한다. 시각 주장을 넣지 않으면 넣지 않았음을 근거에 명시한다(L-09).
3. **분해·병합 재구성 확인 (07 §7 검증 방법 대응).** 수행 기록은 산출 소산만으로 시연을 재구성·검증할 수 있음을 아래로 확인한다:
   - **(가) 계약·경계 대조** — Work Graph 인스턴스의 각 Task 필수 필드(`done`·`interfaceContract`·`ownedBoundary`) 존재를 07 §3.2-B와 전수 대조하고(검증 방법 1), 병렬 집합 내 소유 경계 쌍별 교집합 0을 확인한다(검증 방법 2, decompose-rules §3.4 C3).
   - **(나) 병렬·검증 완결 확인** — 3 Task 사이클 loop-data가 각각 Consult→…→Complete를 `retry_count`=0·CP2 Pass로 완주함(개별 검증 통과)을 확인하고, 그 통과 결과만 Merge `collected`에 든다(INV-5, 검증 방법 3).
   - **(다) 충돌 처리 확인** — Merge Result에서 상호 참조 정합성 검증(crossRefStatus) 수행·충돌 1건 검출·Advisor 중재(arbitration)·병합 성립을 복원한다(검증 방법 4, merge-rules §4).
4. **시연 착수 시 Memory Consult 수행·회수 집합 기록.** 시연 수행 Task는 분해(Decompose) 착수 전과 각 Task 사이클 Consult 단계에서 Memory Service Interface로 회수(Recall)를 실제 수행한다 — `purpose`(예: "v0.7 Workflow 시연에 관련된 분해·간섭·병합 충돌 Active Lesson·BP 회수")와 `scope`(narrowing: `kind`=`lesson`/`best-practice`, `labels`: status=Active + 상황 투영), 기본 `detail`=index를 명시한다. 회수된 집합(회수 건수·매칭 라벨·회수된 `id` 목록)을 수행 기록에 남기고, **그 회수 집합 참조(mi-id 배열)를 해당 Task 사이클 Consult 전이 이벤트의 `ref`에 기록**한다(loop-state-record §6 DP-L5, loop-binding §3.3). 회수·기록이 단일 Port(Recall) 경유·우회 0건임을 확인한다(07 INV-7).

## §4. 픽스처 명세 (done 3, v0.6-demo-fixtures 관례 동형)

시연은 격리된 픽스처를 대상으로 워크플로를 구동한다. 이 절은 그 픽스처의 **명세**를 확정한다 — **픽스처의 실물 생성은 이 절차서 소관이 아니라 시연 수행 Task WF9 소관이다** (constraint, §0). 픽스처는 저장소 실계약 문서를 건드리지 않는 **자기완결** 대상물이다.

### §4.1 위치·격리 경계

- **위치.** 픽스처는 신규 디렉터리 **`docs/v0.7-demo-fixtures/`** 아래에 둔다. 이 디렉터리와 그 안의 파일은 **시연 수행 Task WF9가 생성한다** — 이 절차서는 생성하지 않는다(현 시점 미존재 — 본 작성 시 직접 실측).
- **자기완결(저장소 실계약 문서 무침범).** 시연 대상 큰 작업의 대상물은 전부 이 디렉터리 안에 자기완결로 둔다 — 각 Task 사이클의 Execute 산출물(T1·T2·T3의 출력 파일)도 이 경계 안에만 생성한다. `specs/`·`framework/`(workflow/loop/adapters 등 실계약 문서)·기존 memory-data 39건·기존 loop-data 3파일을 **읽거나 참조는 하되 수정하지 않는다**. 시연이 실계약 산출물을 변경하지 않게 하기 위함이다.
- **CP2 전수 스캔 제외 경계 (verifier_scope 관례).** 픽스처의 의도적 충돌 유도 지점(§4.3)은 `docs/v0.7-demo-fixtures/` 내부에만 존재한다. AI 비의존 전수 스캔(§2.2, CP2 소관 — specs/07-workflow.md §3 대상)이나 경계 시연 스캔(§2.2, CP2 소관)이 수행될 때, 픽스처 디렉터리는 **대상 경계에서 제외**하고 제외 사실을 `verifier_scope`에 명시한다(v0.6-demo-fixtures §4·criteria-catalog "정당 보유 지점 제외·제외 명시"와 동형). 픽스처의 의도적 충돌 지점이 실계약 경계의 위반으로 계상되지 않게 한다.

### §4.2 머리 명시 요건 (필수)

각 픽스처 파일의 **머리에 다음 두 문구를 명시**한다.

- **"시연 픽스처 — 실계약 문서 아님."** 픽스처가 검증 대상 계약 문서가 아니라 시연을 위해 구성된 대상물임을 표시한다.
- **"의도적 결함 정당 보유."** 충돌 유도 지점(§4.3)을 담은 픽스처는 그 불일치가 시연을 위해 **의도적으로 심긴 정당한 보유물**임을 명시한다 — 실계약 문서의 결함으로 오인되지 않게 한다. (v0.6-demo-fixtures "실계약 파일 아님·의도적 결함 정당 보유" 명시와 동형.)

### §4.3 픽스처 구성 (성격 수준 명세 — 실물·구체 내용은 WF9 생성)

세 Task spec은 시연 대상 큰 작업의 대상물(자기완결)이며, 충돌 유도 지점은 Merge 단계 3(충돌 검출)이 특정 결과를 내도록 설계된 **의도적 불일치**를 성격 수준으로만 규정한다(구체 내용은 WF9가 픽스처 디렉터리 내부에 생성).

| 픽스처 | 대상물 | 계약·done (성격 — WF9가 실물 구성) |
|---|---|---|
| **T1 spec** | 자기완결 대상 명세 + 위임 done. `ownedBoundary` = 출력 파일 1(예: `docs/v0.7-demo-fixtures/out-t1.md`). | `interfaceContract` = **produces: 계약 X**(분해 시점 확정). `done` = X를 실현한 산출이 T1 자기 spec을 충족(첫 산출로 충족 가능 — CP2 Pass 기대). 결함 없음. |
| **T2 spec** | 자기완결 대상 명세 + 위임 done. `ownedBoundary` = 출력 파일 2(예: `docs/v0.7-demo-fixtures/out-t2.md`). | `interfaceContract` = **consumes: 계약 X / produces: 계약 Y**(X·Y 분해 시점 확정). `done` = 확정된 X를 참조(R2 — 미완성 T1 산출 불추측)해 Y를 실현한 산출이 T2 자기 spec을 충족. **T2 자기 spec은 첫 산출로 충족 가능**하나, T2가 산출한 계약 Y의 실현이 **T3가 소비 시 참조하는 확정 계약 Y 문면과 불일치**하도록 설계된다(§4.3 충돌 유도 지점). |
| **T3 spec** | 자기완결 대상 명세 + 위임 done. `ownedBoundary` = 출력 파일 3(예: `docs/v0.7-demo-fixtures/out-t3.md`). | `interfaceContract` = **consumes: 계약 Y**(분해 시점 확정). `done` = 확정된 Y 문면을 참조(R2)해 소비한 산출이 T3 자기 spec을 충족(첫 산출로 충족 가능 — CP2 Pass 기대). |

**충돌 유도 지점 (1건 — merge-rules §4.3 단계 3 대상).**

- **성격.** 픽스처는 **두 Task(T2·T3)가 같은 인터페이스 계약 Y를 다르게 실현**하도록 설계된다 — T2는 계약 Y를 산출(produces)하며 자기 spec대로 실현하고(실현 A), T3는 확정된 계약 Y 문면을 소비(consumes)하며 참조한다(문면 B). 픽스처는 실현 A와 문면 B가 **불일치**하도록 구성한다. 각 Task는 **자기 spec에 대해서는 개별 검증(CP2)을 통과**하나(T2의 산출이 T2 자기 done을, T3의 산출이 T3 자기 done을 각각 충족), 두 Task가 실현한 같은 계약 Y의 **사후 불일치**는 **병합 시점에만** 드러난다. 이는 merge-rules §4.3 단계 3("두 Task가 같은 계약을 다르게 실현")의 인스턴스다.
- **검출 위치.** 이 불일치는 Merge 단계 3(충돌 검출)에서 `conflicts` 1건으로 검출되고, 단계 4에서 **Advisor 중재**(arbitration)로 넘어가 해소되며, 단계 5에서 병합이 성립한다(§8-C.4). 개별 검증(각 Task CP2)은 이 사후 충돌을 검출하지 않는다 — 각 Task는 자기 경계 내에서 자기 done만 판정하기 때문이며, 이것이 병합의 충돌 검출 단계가 존재하는 이유다.
- **결함의 지위.** 이 "의도적 불일치"는 **Workflow 병합·충돌 처리 메커니즘**을 실증하기 위한 구성물이며, 06의 판정 기준·검증 유형·거짓 완료 검출과 무관하다 — 각 Task는 자기 done을 진정으로 충족(CP2 Pass)하고, 충돌은 오직 Merge 수준의 사후 불일치다. 구체 내용은 픽스처 디렉터리 내부에만 존재하고, 본 절차서 본문에는 성격만 서술한다(§0 소유 경계).
- **음성 케이스 비시연.** Decompose 실패 4종(`MissingCompletionCriteria`·`MissingInterfaceContract`·`OwnershipOverlap`·`DependencyCycle`, decompose-rules §3)·Dispatch 실패 2종·Merge 미해소 실패(`UnresolvedConflict`)의 음성 케이스는 **시연하지 않는다**(07 §7 요구 없음). 본 시연은 정상 경로(분해 통과·병렬 검증 완료·충돌 검출→중재 해소→병합 성립)만 구동한다.

**claim(완료 보고)의 지위.** 각 Task 사이클의 Execute는 Worker 완료 보고(02 §3.2-C, self_check 포함)를 산출하나, 그 self_check "충족" 주장은 CP2 판정의 **참고 입력**일 뿐 판정 근거가 아니다(06 독립성). CP2는 각 Task 산출물을 근거로 독립 판정하여 Pass를 낸다(픽스처는 CP2 Pass가 기대되는 통과 케이스로 설계).

## §5. 물리 기록 명세 (done 2-C 물리 실현 — 정본 구조 그대로)

시연이 생성할 물리 소산 네 종의 명세다. **전부 후속 Task WF9가 생성할 예정**이며, 본 절차서는 명세만 한다(07 R2·L-07 — 실재 불주장; 현 시점 docs/v0.7-demo-fixtures/ 미존재·loop-data v07-demo-* 미생성·memory-data 39건 실측).

### §5.1 Work Graph 인스턴스 — 문서 형태 (workflow-binding §3.2 정본, OQ-WB-1 해소)

- **물리 형태·위치 (DP-W4 + Advisor 채택 확정).** Work Graph 인스턴스는 **문서 형태**로 직렬화한다 — `docs/` 아래 v0.7 시연 문서(수행 기록) 내 하나의 **구조화 섹션**으로 둔다. `framework/adapters/claude/workflow-data/` 등 새 데이터 백엔드 디렉터리를 신설하지 않는다(workflow-binding §3.1 DP-W4). Advisor가 이 구조를 채택 확정했다(OQ-WB-1 해소).
- **문서 구조 (workflow-binding §3.2).** Work Graph 인스턴스 섹션은 `goal`·`tasks`(각 Task의 `id`·`task`·`done`·`interfaceContract`·`ownedBoundary`·`dependsOn`·`delegation` — 7필드)·`dependencies`·`parallelSets`·`completion`의 **5필드**(work-graph.md §2)와 **Task 7필드**(work-graph.md §3)를 **전건 서술**한다. 병렬 집합 도출(선행 의존 없는 Task들이 한 병렬 집합)을 명시한다(work-graph.md §2 정본 문면). 필드·필수 표기는 정본 그대로 보존한다(재정의 0). 기대 값 명세는 §8-C.1.

### §5.2 루프 상태 기록 — 각 Task 사이클 loop-data (loop-binding §3 정본)

- **위치·구조 (loop-binding §3.1, DP-L4).** 각 Task 사이클의 전이 이벤트는 Adapter 경계 이하 `framework/adapters/claude/loop-data/`에 **사이클당 파일 1개**로 두고 **1 line = 1 전이 이벤트의 append-log**로 직렬화한다: `loop-data/<cycle_id>.jsonl`. 파일명 `<cycle_id>` = 전이 이벤트 `cycle_id`(하나의 위임/Task = 하나의 사이클). **본 시연 = 3파일** — `v07-demo-t1.jsonl`·`v07-demo-t2.jsonl`·`v07-demo-t3.jsonl`(cycle_id는 WF9가 사이클별로 배정, 예시 명 제안). **기존 3파일(`v06-demo-a/b/c.jsonl`)은 무변경 append-only**(수정·삭제 없음).
- **10필드 직렬화 (loop-binding §3.2 / 정본 loop-state-record §2·03 §3.2-A).** 각 line은 전이 이벤트 10필드를 JSON 객체로 직렬화한다. 필수 표기 보존 — 8필드(`cycle_id`·`seq`·`to_stage`·`trigger`·`outcome`·`retry_count`·`actor`·`at`)는 필수, 2필드(`from_stage`·`ref`)는 아니오. 첫 line(사이클 시작 전이)은 `from_stage` 생략. 열거 값 보존 — `outcome`(pass/fail/escalated)·`trigger`(완료 조건 충족 / Verify 실패 / 재작업 되돌림 / 에스컬레이션)·`actor`(Advisor/Planner/Worker/Verifier/human). **본 시연 3사이클은 전부 정상 사이클**이므로 `trigger`=완료 조건 충족·`outcome`=pass·`retry_count`=0·`actor`=human 0건이다(기대 전이표 §8-C.2).
- **`at` = 순서 값 (loop-binding §3.3, L-09).** `at`은 사이클 내에서 **단조 증가하는 순서 값**으로 직렬화한다 — 물리 벽시계 시각이 아니다(§3.2 요건 2). 순서 값의 구체 형식은 Adapter 선택이며 WF9가 정본 구조 내에서 배정한다.
- **`ref` = 경량 참조 (loop-binding §3.3, DP-L5).** `ref`은 관련 산출물·보고의 **식별 참조**만 담는다 — 위임/완료 보고·검증 리포트의 식별 참조, **Consult 전이 이벤트는 회수 집합 참조**(그 사이클 Consult에서 회수된 memory-data store id 배열; §3.2 요건 4). 원문 중복 저장 금지(경량 id 참조).
- **append-only·재구성 (loop-binding §3.2 / loop-state-record §5·03 INV-3).** 기존 line은 재작성·삭제하지 않는다. 각 사이클 파일의 line 집합만으로 그 사이클의 단계 경로·회수 참조가 복원돼야 한다(§3.2 요건 3).

### §5.3 Merge Result 기록 — 문서 형태 (workflow-binding §3.2 / merge-rules §3 정본)

- **물리 형태·위치 (DP-W4).** Merge Result 기록은 **문서 형태**로 직렬화한다 — `docs/` 아래 v0.7 시연 문서(수행 기록) 내 구조화 서술로 둔다. 새 데이터 백엔드 디렉터리를 신설하지 않는다(workflow-binding §3.1).
- **문서 구조 (workflow-binding §3.2 / merge-rules §3).** Merge Result 섹션은 `collected`(개별 검증 통과 결과만 — INV-5)·`crossRefStatus`(`Consistent`/`Mismatch`)·`conflicts`·`arbitration`(중재자 = Advisor)의 **4필드**(merge-rules §3)와 **충돌 처리 순서**(수합 → 상호 참조 정합성 검증 → 충돌 검출 → (충돌 시) Advisor 중재 → 병합 성립, merge-rules §4)를 서술한다. 필드·열거 값은 정본 그대로 보존한다(재정의 0). 기대 값 명세는 §8-C.4.

### §5.4 Memory Update 실기록 — 정식 memory-data append (memory-binding §3 / OQ-9 동형)

- **정식 append (OQ-9 동형, v0.6 M/L10 선례).** 시연의 Learn→Memory Update는 도출한 후보를 **정식 memory-data에 append**한다 — memory-binding §3.1 Record 물리 절차(`store/<id>.json` 쓰기 + `index/index.jsonl` line append 정합, 04 INV-7)로 단일 Port(memory-service §7) 경유. 우회 접근 0건(07 INV-7).
- **도출 후보 (07 §5, AGENT.md).** ⓐ **성공한 병렬 분해·병합 패턴** → **Best Practice 후보**(3-Task 병렬 집합 분해·동시 디스패치·개별 검증·병합 성립이 성공한 분해 패턴). ⓑ **병합 충돌(중재 해소)** → **Lesson 후보**(개별 검증이 통과한 두 Task가 같은 계약을 다르게 실현한 사후 충돌이 병합 시점에 검출·중재된 사례 — 07 §5 "병렬 작업 간 간섭·상호 참조 불일치·병합 충돌은 Lesson 후보").
- **시연 네임스페이스·`source` 표기 (OQ-9 동형).** append되는 각 항목의 `source`에 **시연 유래를 표기**하고(예: `source`="v0.7-demo-WF9" 또는 WF9가 확정하는 시연 유래 식별자), stable_id는 **실무 네임스페이스(L-/BP-)와 구분한 시연 네임스페이스**를 쓴다 — Best Practice 후보 = **BPD-**, Lesson 후보 = **LD-**(v0.6-demo BPD-/LD- 선례 동형, 회수 오염 방지). status=`Candidate`(승격 승인은 Advisor 전속, 05 INV-4 — 시연 Memory Update는 후보 등록까지). 라벨 투영은 memory-binding §5.4 정본 키(`situation`·`stable_id`·`status`·`verdict`·`matched_lesson_id`)를 따른다.
- **mi 번호 실측 순차 배정·기존 무변경 (OQ-9 동형).** `id`는 memory-binding §2 스킴(`mi-<정렬가능토큰>`)으로 **수행 시점 실측으로 순차 배정**한다. 현 시점 store·index는 **실측 39건**(`mi-0001`~`mi-0039` — 본 작성 시 직접 실측)이므로, 시연 append는 그 다음 순번(`mi-0040`부터)에서 시작하되 정확한 번호·건수는 WF9가 수행 시점에 실측해 배정한다(**선취 금지** — 구체 번호·건수를 본 절차서가 확정하지 않는다). **기존 39건은 무변경**이며 append-only만 수행한다.
- **loop-data ↔ memory-data 접속.** 각 Task 사이클 Consult 전이의 `ref`(회수 집합 mi-id 배열)가 두 백엔드를 잇는 지점이다. Workflow 수준 Learn→Memory Update(07 §5 Record — 단일 사이클 밖, 07 §9)가 도출한 시연 유래 후보(BPD-/LD-)를 memory-data에 실기록한다. 각 per-task 사이클의 Learn→Memory Update 전이(loop-data seq 6)는 성공 경로 Learn을 기록하며, 그 `ref`은 시연 유래 후보 참조를 담는다 — per-task 사이클과 Workflow 수준 후보의 정확한 append 건수·귀속은 WF9 수행 시점 실측(선취 금지, 기존 39건 무변경·append-only).

## §6. 수행 주체·역할 배치 (done 4 — Advisor 확정 시연 설계)

- **Advisor 주관 구동 (Workflow 오케스트레이션 = 주 세션).** 시연은 **Advisor(주 세션)**가 주관 구동한다 — Workflow 오케스트레이션(분해 채택 → 병렬 디스패치 → 각 Task 사이클 트리거 → 수합 → 상호 참조 정합성 검증 → 충돌 검출 → 중재 → 병합 성립, workflow-binding §4.1 형태 A)을 Advisor 주 세션이 구동한다. 분해 채택(Planner 초안 채택)·병렬 디스패치·수합·상호 참조 대조·충돌 중재(INV-6)·CP3 최종 승인은 Advisor가 수행한다(07 §3.2-D·INV-6, 02 §3.1, workflow-binding §5.3).
- **Planner·Worker·Verifier 실위임 (모의 시연 금지, L-07 실측 요건).** 시연은 기록물만 작성하는 **모의 시연이 아니다** — **Decompose 초안은 Planner 서브에이전트**(`.claude/agents/planner.md` — Wave 설계·분해·Worker 브리프 초안)에, **각 Task Execute는 Worker 서브에이전트**(`.claude/agents/worker.md`, 실측 `model: opus`)에, **각 Task CP2는 Verifier 서브에이전트**(`.claude/agents/verifier.md`)에 **실제 위임**한다(workflow-binding §5.1·§5.2·§5.4, loop-binding §5.1 역할 실행 = 서브에이전트 디스패치). 실 산출물이 생성되고 실 판정이 이뤄진 뒤에만 그 결과를 Work Graph 인스턴스·전이 이벤트·CP2 리포트·Merge Result로 남긴다(L-07 — "수행했다" 서술 금지, 실측 후 기록). Planner 초안은 Advisor 채택 대상이다(초안은 채택되기 전엔 계획이 아니다, 02 §3.1).
- **병렬 디스패치 = 서브에이전트 동시 위임 (delegation-protocol §3.3, R1~R4).** 주 세션 Advisor가 한 병렬 집합의 3 Task를 **서로 다른** Worker 서브에이전트에 **동시** 위임한다(dispatch-protocol §2.1 완료 조건 (iii) 서로 다른 Agent). 착수 전 분해 검사 C1~C4(decompose-rules §3) 통과를 확인하고, 디스패치 중 R1(위임 메시지 전용)·R2(미완성 산출물 불추측 — 확정된 `interfaceContract`만 참조)·R3(조율 필요 시 Advisor 에스컬레이션)·R4(경계 준수 — 각 Task는 자기 `ownedBoundary`만 수정)를 적용한다(dispatch-protocol §3).
- **역할 ↔ actor 대응.** 각 Task 사이클의 전이 이벤트 `actor`는 그 전이를 유발한 역할이다(§0) — CP1(Worker 자체 점검)은 Execute→Verify 전이의 근거, CP2(Verifier 독립 판정)는 Verify 전이의 판정, CP3(Advisor 최종 승인)는 Complete 진입 게이트. 본 시연 3사이클은 사람 개입이 없으므로 `actor`=human 0건이다. Merge 충돌의 중재는 Workflow 수준 Advisor 판단이며(loop-data 밖 — 07 §9 다중 사이클 오케스트레이션), Merge Result `arbitration`에 기록된다.
- **Worker(본 절차서 작성자)의 후속 담당.** 픽스처(docs/v0.7-demo-fixtures/) 준비·시연 수행 기록(docs/v0.7-demo.md)·loop-data 3파일·Merge Result·memory-data append 정리는 **후속 시연 Task WF9** 담당이다. 본 절차서(Task WF7)는 그 실행 명세만 확정하며, 픽스처·기록물·시연 실물을 생성하지 않는다(§0 소유 경계).

## §7. 실패 처리 규칙 (v0.6-demo-procedure §7 동형)

시연이 기대 관측과 **다르게 관측될 때**의 처리 규칙이다.

1. **은폐 없이 그대로 기록한다.** 관측이 기대와 달라도 실제 관측을 §3 기록 포맷의 "근거 (관측한 것)"에 그대로 남긴다. 실패·불일치를 숨기지 않는다(Worker 금지 사항 — 실패 은폐 금지, 02 O5). Work Graph 필드 값·loop-data line 원문·CP2 리포트·Merge Result 필드를 그대로 인용한다.
2. **판정 값으로 표기한다.** 기대와 다르게 관측되면 해당 판정의 "관측 결과"를 **위반**으로 표기한다. 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기하며, 판정 불가를 충족으로 위장하지 않는다.
3. **재작업 여부 판단은 게이트 소관이다.** 이 절차서와 수행 기록은 관측·기록까지만 한다. 위반·판정 불가의 **재작업 여부 판단**은 검증 단계(Verifier = CP2)와 Advisor(CP3)의 소관이다. 수행 기록·절차서가 스스로 통과 처리하거나 재작업을 결정하지 않는다.
4. **기대된 충돌과 예기치 못한 실패 구분.** 시연이 **기대**하는 것(충돌 유도 지점 1건이 Merge 단계 3에서 검출되어 Advisor 중재로 해소)과 예기치 못한 실패를 근거에 구분해 기록한다. 기대된 충돌이 정확히 검출·중재·해소되어 병합이 성립하면 충돌 처리 시연은 **충족**이다. 반대로 충돌이 검출되지 않거나 중재 없이 병합되면 **위반**이다.
5. **연산 실패와 정상 경로의 구분.** 시연 중 Workflow 연산 자체가 수행 불능(서브에이전트 디스패치 불가·loop-data 기록 불가·Work Graph/Merge Result 문서 기록 불가)이면 이는 **연산 실패**이며, 정상 경로(분해 통과·병렬 CP2 Pass·충돌 검출→중재→병합 성립)와 다르다. 둘을 혼동해 기록하지 않는다. 또한 Merge 충돌(중재 대상, 정상)과 각 Task 개별 검증 실패(본 시연은 미기대 — 통과 케이스)를 구분한다.

## §8. 시연 — 픽스처 기반 소형 워크플로 (07 §8 예2 동형)

목표: 큰 작업 1건을 3-Task(T1 produces X / T2 consumes X·produces Y / T3 consumes Y)로 분해해 **한 병렬 집합**으로 동시 디스패치하고, 각 Task가 Loop 사이클을 CP2 Pass로 완주(개별 검증 완료)한 뒤, 병합에서 상호 참조 정합성 검증·충돌 1건 검출·Advisor 중재·병합 성립을 보인다. 근거: 07 §7 병렬·계약·간섭 금지·충돌 처리 시연·§8 예2, ROADMAP v0.7 3건, decompose-rules §3·§4, dispatch-protocol §2·§3, merge-rules §3·§4, workflow-binding §3.2·§4.1·§5, loop-binding §3·§5, loop-protocol §3.

### (A) 절차 단계 (workflow-binding §4.1 형태 A + loop-protocol §3)

1. **Decompose 착수·회수.** Advisor(주 세션)가 큰 작업 1건(목표·범위 — 픽스처 기반 소형 워크플로)을 수령한다. Memory Consult 회수(Recall)를 수행하고(§3.2 요건 4 — 분해 패턴·간섭·병합 충돌 관련 Active Lesson·BP), 회수 집합을 기록한다.
2. **Decompose 구동 (Planner 초안 + Advisor 채택).** Planner 서브에이전트(planner.md)가 큰 작업을 3-Task Work Graph로 분해한 **초안**을 제출한다 — T1·T2·T3 각각 `id`·`task`·`done`·`interfaceContract`·`ownedBoundary`·`dependsOn`·`delegation`(7필드), `dependencies`·`parallelSets`·`completion`. 계약 X·Y는 분해 시점에 확정한다. Advisor가 분해 검사 C1(완료 조건 보유)·C2(인터페이스 계약 보유)·C3(소유 경계 쌍별 비중첩)·C4(의존 비순환)를 대조하고(decompose-rules §3), 병렬 집합 도출(D1 상호 비의존·D2 경계 비중첩, decompose-rules §4)을 확인해 **채택**한다. 산출 = Work Graph 인스턴스(문서 형태, §5.1). (기대 구조 §8-C.1)
3. **Dispatch 구동 (서브에이전트 동시 위임, R1~R4).** Advisor가 병렬 집합 {T1,T2,T3}의 각 Task를 02 §3.2-B 위임 메시지로 **서로 다른 Worker 서브에이전트에 동시 디스패치**한다(dispatch-protocol §2, delegation-protocol §3.3). 착수 전 C1~C4 통과를 재확인하고, R1(위임 메시지 전용)~R4(경계 준수)를 적용한다. 각 위임의 context에는 **확정된** 계약(X·Y)·픽스처 spec만 넣고, 동시 진행 중인 형제 Task의 미완성 산출물은 넣지 않는다(R2).
4. **각 Task Loop 사이클 실구동 (T1·T2·T3 병렬, DP-W5).** 각 Task는 하나의 Loop 사이클을 구동한다(Consult→Plan→Execute→Verify→Learn→Memory Update→Complete, loop-protocol §3):
   - **Consult** — 회수(Recall) 수행, 회수 집합을 Consult 전이 `ref`에 기록(DP-L5). → Plan 전이 append.
   - **Plan** — 계획 구성. → Execute 전이 append.
   - **Execute (Worker 실위임)** — Worker 서브에이전트(worker.md)가 확정된 `interfaceContract`(T1: produces X / T2: consumes X·produces Y / T3: consumes Y)를 참조해 자기 `ownedBoundary` 출력 파일 1개를 산출 + 자체 점검(CP1, self_check). → Verify 전이 append.
   - **Verify (Verifier 실위임, CP2)** — Advisor가 입력{산출물 + criteria}을 구성해 Verifier 서브에이전트(verifier.md)에 실위임 → CP2 독립 판정. 통과 케이스이므로 **CP2 Pass**(Task별 검증 리포트). → Learn 전이 append.
   - **Learn** — 성공 경로 Learn(03 §3.2-C). → Memory Update 전이 append.
   - **Memory Update** — (Workflow 수준 후보와의 접속은 §5.4). → Complete 전이 append.
   - **Complete** — Advisor CP3 최종 승인(게이트) → 사이클 정상 종료, 완료 보고 산출. `retry_count`=0, actor=human 0건. 각 사이클 = `v07-demo-t{1,2,3}.jsonl` 7 line(§8-C.2).
5. **Merge 구동 (수합→상호 참조 정합성 검증→충돌 검출→중재→성립).** Advisor가 완료·검증된 세 결과를 Merge한다(merge-rules §4):
   - **단계 1 수합** — 각 결과가 완료 보고 동반 + 개별 검증 통과(CP2 Pass)임을 확인해 `collected`를 채운다(INV-5 — Pass만).
   - **단계 2 상호 참조 정합성 검증** — 각 Task가 참조하는 다른 Task의 확정된 계약·산출물의 실제 일치를 대조해 `crossRefStatus`를 판정한다.
   - **단계 3 충돌 검출** — 두 Task가 같은 계약을 다르게 실현한 사후 충돌을 검출한다 → **충돌 1건**(T2의 계약 Y 실현 ↔ T3가 참조한 확정 계약 Y 문면 불일치)을 `conflicts`에 담는다(§4.3 충돌 유도 지점).
   - **단계 4 Advisor 중재** — `conflicts` 1건을 Advisor가 중재(INV-6)해 해소 결정을 `arbitration`에 담는다.
   - **단계 5 병합 성립** — 완료 조건 3건(개별 검증 통과·상호 참조 정합·충돌 중재 해소) 충족 → 병합 성립. Merge Result 기록(문서 형태, §5.3). (기대 값 §8-C.4)
6. **Learn→Memory Update (Workflow 수준, 07 §5).** 성공한 병렬 분해·병합 패턴 → Best Practice 후보(BPD-), 병합 충돌(중재 해소) → Lesson 후보(LD-)를 정식 memory-data에 append(§5.4 — `source` 시연 유래·status=Candidate, 단일 Port). 기존 39건 무변경.
7. **시연 최종 승인 (CP3).** Advisor가 시연 전체(분해·병렬 검증·병합·충돌 처리)의 판정(§8-D)을 최종 승인한다(CP3 — 마일스톤 게이트). 경계 시연·AI 비의존 시연은 CP2가 specs/07-workflow.md §3 정적 스캔으로 직접 판정한다(§2.2).

#### §8-C.2 3 사이클 loop-data 기대 전이표 (loop-binding §3 정본 — 각 사이클 7 line)

각 Task 사이클(`v07-demo-t1.jsonl`·`v07-demo-t2.jsonl`·`v07-demo-t3.jsonl`)이 loop-data 파일에 append할 **기대 전이 이벤트**다(필드 값 수준). 세 사이클은 전부 **정상 사이클**이므로 아래 표를 **동형으로 3회 인스턴스화**한다(cycle_id·`at` 순서 값·`ref` 실 참조·Execute/Verify 산출 참조는 WF9가 사이클별 실값으로 채운다). 필드·열거 값 정본 = loop-state-record §2·loop-binding §3.2·03 §3.2-A; `actor`·`trigger`는 03 §3.2-A 열거·02 §3.1 역할 책임에서 도출(§0). **새 필드·새 열거 0.**

| seq | from_stage | to_stage | trigger | outcome | retry_count | actor | ref | at |
|---|---|---|---|---|---|---|---|---|
| 1 | (없음) | Consult | 완료 조건 충족 | pass | 0 | Advisor | **회수 집합 참조 = 회수된 mi-id 배열**(DP-L5) | 1 |
| 2 | Consult | Plan | 완료 조건 충족 | pass | 0 | Advisor | (Plan 초안 참조) | 2 |
| 3 | Plan | Execute | 완료 조건 충족 | pass | 0 | Advisor | (채택된 계획 참조) | 3 |
| 4 | Execute | Verify | 완료 조건 충족 | pass | 0 | Worker | 완료 보고(self_check, CP1) + 산출 파일 참조 | 4 |
| 5 | Verify | Learn | 완료 조건 충족 | pass | 0 | Verifier | 검증 리포트(CP2 Pass) 참조 | 5 |
| 6 | Learn | Memory Update | 완료 조건 충족 | pass | 0 | Verifier | (성공 경로 후보 참조 — §5.4) | 6 |
| 7 | Memory Update | Complete | 완료 조건 충족 | pass | 0 | Advisor | 완료 보고(02 §3.2-C) 참조 | 7 |

- **필드 값 근거.** `trigger`=완료 조건 충족(성공 경로 선형 전이, 03 §3.2-A 열거). `outcome`=pass(각 단계 완료 조건 충족). `retry_count`=0(재작업 되돌림 0회 — 통과 케이스). `actor` — Consult/Plan/CP3는 Advisor, Execute 완료(CP1)는 Worker, Verify(CP2 Pass)·Learn 입력 제공은 Verifier(03 §3.1-A). 첫 line `from_stage` 부재(loop-state-record §2). **actor=human 0건**(사람 개입 없음 — 개입 최소).
- **Consult `ref` = 회수 집합 참조.** 각 사이클 seq 1의 `ref`에 그 사이클 Consult에서 회수된 memory-data store id 배열을 경량 참조로 기록한다(DP-L5, §3.2 요건 4). content 원문은 담지 않는다.
- **3사이클 동형·개별 검증 완결.** T1·T2·T3 사이클은 위 7전이를 동형으로 밟으며, 각 사이클의 seq 5(Verify→Learn, CP2 Pass)가 그 Task의 **개별 검증 통과**(INV-5)를 실현한다 — 이 통과 결과만 Merge `collected`에 든다(§8-C.4). 사이클 간 차이는 Execute 산출물 내용(T1: X 실현 / T2: Y 실현 / T3: Y 소비)과 cycle_id·`ref` 실값이며, 전이 구조·필드 값은 동형이다.
- **기존 파일 무변경.** `v06-demo-a/b/c.jsonl` 3파일은 수정·삭제하지 않는다(append-only — §5.2).

#### §8-C.3 Task별 CP2 검증 리포트 기대 (06 / verifier-binding 정본 참조 — 재정의 0)

각 Task의 CP2는 Verifier 서브에이전트 실위임으로 수행되며, 그 산출은 Task별 검증 리포트다(픽스처 경계 내 — 예: `verify-t1`·`verify-t2`·`verify-t3`, WF9 명명).

| Task | 검증 대상 | 기대 최종 판정 | verifier_scope |
|---|---|---|---|
| **T1** | T1 Execute 산출물 ↔ T1 `done`(자기 spec) | **Pass** — 산출이 자기 done 전 항목 충족 | `docs/v0.7-demo-fixtures/out-t1.md`. 픽스처 경계·타 Task 산출 제외. |
| **T2** | T2 Execute 산출물 ↔ T2 `done`(자기 spec) | **Pass** — 산출이 자기 done 전 항목 충족(계약 Y 실현이 T2 자기 spec은 충족; T3와의 사후 불일치는 개별 검증 범위 밖 — Merge 소관) | `docs/v0.7-demo-fixtures/out-t2.md`. 픽스처 경계 제외. |
| **T3** | T3 Execute 산출물 ↔ T3 `done`(자기 spec) | **Pass** — 산출이 자기 done 전 항목 충족 | `docs/v0.7-demo-fixtures/out-t3.md`. 픽스처 경계 제외. |

- **개별 검증 범위 경계.** 각 CP2는 그 Task의 산출물을 **자기 `done`(자기 spec)에 대해서만** 판정한다. T2의 계약 Y 실현이 T3가 참조한 확정 Y 문면과 불일치하더라도, T2의 산출은 T2 자기 done을 충족하므로 T2 CP2는 Pass다 — 이 사후 불일치(두 Task가 같은 계약을 다르게 실현)는 **개별 검증이 아니라 Merge 단계 3(충돌 검출)**이 잡는다(§8-C.4, merge-rules §4.3). 판정 기준(무엇이 통과인가)은 06 소관이며 본 절차서는 재정의하지 않는다(07 INV-8).
- **claim 독립성.** CP2는 Worker self_check "충족" 주장을 참고 입력으로만 받고, 산출물 근거로 독립 판정한다(06 독립성, 02 §3.2-A — 자기 점검은 최종 승인 아님).

#### §8-C.4 Merge Result 기대 (merge-rules §3·§4 정본 — 충돌 1건 검출→arbitration→성립)

Merge 산출 Merge Result의 **기대 값**이다(4필드, merge-rules §3). 값은 WF9가 실값으로 채운다.

| 필드 | 기대 값 (성격) |
|---|---|
| `collected` | T1·T2·T3 결과 3건 — **각각 CP2 Pass(개별 검증 통과)만 포함**(INV-5, §8-C.3). 미검증·Fail 결과 0건. |
| `crossRefStatus` | 상호 참조 정합성 판정(`Consistent`/`Mismatch`) — T2→T1(계약 X) 등 확정 계약 참조의 정합 대조 결과. (본 시연 충돌은 단계 3에서 검출되므로, 단계 2는 확정 계약 참조 정합을 판정한다 — Advisor 확정 설계.) |
| `conflicts` | **1건** — T2가 산출한 계약 Y의 실현 ↔ T3가 소비 시 참조한 확정 계약 Y 문면 불일치(두 Task가 같은 계약을 다르게 실현, merge-rules §4.3 단계 3). 각 항목은 중재 대상. |
| `arbitration` | 충돌 1건에 대한 **Advisor 중재** 해소 결과(INV-6, merge-rules §4.4 단계 4 — 중재자=Advisor). Workflow는 충돌을 검출·보고하고, 어느 실현을 채택·조정할지의 해소 결정은 Advisor가 내린다. |

- **충돌 처리 순서 (merge-rules §4).** 수합(단계 1, `collected`) → 상호 참조 정합성 검증(단계 2, `crossRefStatus`) → 충돌 검출(단계 3, `conflicts` 1건) → **(충돌 시) Advisor 중재**(단계 4, `arbitration`) → 병합 성립(단계 5 — 완료 조건 3건 충족). 시연은 이 5단계 전 과정을 Merge Result 기록으로 남긴다.
- **병합 성립 조건 (INV-5·INV-6).** 완료 조건 3건 — (1) `collected`의 모든 결과가 개별 검증 통과(CP2 Pass, INV-5), (2) 상호 참조 정합, (3) 충돌 1건이 Advisor 중재로 해소(INV-6) — 이 충족되어 병합이 성립한다. 미해소(`UnresolvedConflict`) 음성 케이스는 시연하지 않는다(§4.3 — 충돌은 중재로 해소).
- **경계 시연 실증 보강.** Merge는 개별 검증을 재수행하지 않고(merge-rules §4.1 경계), 개별 검증 판정 기준은 06 소관·단계 전이는 03 소관이다 — Workflow는 오케스트레이션(수합·상호 참조 대조·충돌 검출·중재 라우팅)만 수행한다(INV-8). 이것이 경계 시연(§2.2 ⑤)의 재현 보강이다.

### §10.2 결정 기록 (Advisor 확정 시연 설계 반영, 2026-07-06)

- **OQ-WB-1 해소 반영 — Work Graph·Merge Result 물리 구조 = 문서 형태.** workflow-binding §3.2(DP-W4 + Advisor 채택)가 확정한 문서 형태·docs/ 시연 문서 내 구조화 섹션 구조를 §5.1·§5.3·§8-C.1·§8-C.4가 그대로 따랐다(새 백엔드 미신설). 이는 07 §4.1 행 1·SP-1(계획·로드맵 문서 형태)의 인스턴스이며 계약 변경이 아니다.
- **DP-W5 반영 — 각 Task = Loop 사이클 실구동.** 각 Task(T1·T2·T3)가 하나의 Loop 사이클을 실구동하며 사이클당 loop-data(`v07-demo-t{1,2,3}.jsonl`, loop-binding §3 정본)를 기록한다(§5.2·§8-C.2). 기존 3파일 무변경 append-only. 각 Task CP2 = Verifier 서브에이전트 실위임(§8-C.3). 이는 03 §3.1 단일 사이클의 인스턴스이며 07 §9(다중 사이클 오케스트레이션은 03 밖)와 정합한다.
- **충돌 시연 설계 반영 — 사후 충돌 1건, Merge 단계 3 검출.** 픽스처가 유도하는 충돌 1건(T2의 계약 Y 실현 ↔ T3가 참조한 확정 Y 문면 불일치 — 두 Task가 같은 계약을 다르게 실현)이 Merge 단계 3(충돌 검출)에서 검출되고, 단계 4 Advisor 중재로 해소되어 병합이 성립한다(§4.3·§8-C.4). 각 Task는 자기 done에 대해 CP2 Pass하며, 충돌은 개별 검증이 아니라 병합의 사후 충돌 검출이 잡는다(merge-rules §4.3). Decompose 실패 4종·Merge 미해소 음성 케이스는 시연하지 않는다(07 §7 요구 없음).
- **OQ-9 동형 채택 반영 — Memory Update 시연 네임스페이스.** Learn→Memory Update 실기록은 정식 memory-data append(`source` 시연 유래·status=Candidate·시연 네임스페이스 BPD-/LD-)이며 기존 39건 무변경 append-only다(§5.4). mi 번호·건수는 WF9 수행 시점 실측 순차 배정(선취 금지). 이는 v0.6 M/L10 선례(BPD-/LD-·source=시연 유래)와 동형이다.

이 결정들은 07 §3·framework/workflow/ 5문서 계약의 인스턴스 확정이며 재정의가 아니다(§ 포인터 명시). 배정표(§2)·판정 문장(§8-D)은 07 §7·ROADMAP 원문 인용+환원만 쓴다.
