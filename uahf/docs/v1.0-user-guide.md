## §0. 이 문서의 위치·정본 경계

- 이 문서는 UAHF를 운용하는 사람을 위한 **안내**다 — 설치·세션 진입·핵심 루프·검증·Memory·이식의 절차를 정본 § 포인터로 엮는다.
- **정본은 이 문서가 아니다.** 계약·규칙·절차의 정본은 각 § 포인터가 가리키는 문서다. 이 문서는 재정의·확장하지 않으며, 충돌 시 정본이 우선한다. 충돌을 발견하면 Advisor에게 보고한다 (상위 규약 관행 — Architecture·Spec 충돌은 사용자 보고).
- **문서 역할 구분.** README.md = 저장소 소개·지도 / 리포 루트 docs/getting-started.md = 신규 참여자 세션 진입 / 이 문서 = 운용 안내. 세 문서는 서로 중복 정의하지 않는다.
- 용어의 정본은 specs/00-glossary.md다. 이 문서는 새 용어를 만들지 않는다.
- **하네스 상태.** 이 하네스는 현재 Bootstrap 상태다 (specs/13-harness.md §3.2-B, delegation-protocol.md §0) — 위임·보고·검증·Memory가 정식 실행 Module이 아니라 규약 문서·관행으로 실현된다.
- **범위 경계 (self-note).** 이 문서는 계약을 재정의·확장하지 않고 새 용어·필드·규칙·판정 기준을 만들지 않는다. **미확정 판정·시연 결과를 선취하지 않는다** — Adapter Conformance verdict·핵심 루프 통과 근거·Dogfooding 결과는 각 정본(Conformance 문서·검증 리포트·시연 기록)을 가리킨다.

## §1. 신규 프로젝트에 UAHF 설치

정본: specs/12-scaffold.md §3(설치 계약) / framework/adapters/claude/scaffold-binding.md(물리 실현) / `uahf/docs/v0.9-install-guide.md@cd9247b`(설치 절차 안내 — 아카이브; 열람: `git show cd9247b:uahf/docs/v0.9-install-guide.md`).

- **설치 절차:** Install → VerifyInstall → Runtime Bootstrap → Loop 1 사이클. 각 단계 상세는 아카이브 install-guide §2가 안내하며, 계약 정본은 specs/12 §3이다(가이드 부재 시에도 계약으로 설치가 성립한다).
- **최소 구성 집합** (설치가 성립시켜야 하는 것, specs/13-harness.md §3.2-A): 상위 규약 문서 · Agent 역할 정의 4종 · 위임·완료/실패 보고 프로토콜 · 검증 게이트(구현 주체와 검증 주체 분리) · 작업 추적.
- **moduleSelection**은 Bootstrap 필수 최소 집합(runtime·agent·verifier 등)을 반드시 포함한다. 선택 Module은 필요에 따라 추가한다 (Modular — 필요한 모듈만).
- **기존 프로젝트 설치**는 기존 파일 보존·멱등성을 지킨다 (specs/12 INV-3·INV-4).

이 절은 설치 연산·검사 항목을 재서술하지 않고 정본을 가리킨다.

## §3. 핵심 루프 운용 (위임·보고)

정본: specs/02-agent.md §3·§4, specs/07-workflow.md §3·§4. 운용 지침: 리포 루트 docs/delegation-protocol.md.

- **핵심 루프:** 위임 → 구현 → 검증 → 승인 (delegation-protocol.md §1).
- **위임 메시지 8필드** (from/to/task/input/output/done/context/constraints) 작성법은 delegation-protocol.md §2.1 (정본 specs/02 §3.2-B). 필수 필드(input/output/done/context) 중 하나라도 누락되면 수임 Agent는 착수하지 않고 반환·질의한다 (specs/02 INV-6, delegation-protocol.md §2.4).
- **완료 보고 5필드** (artifacts/self_check/failures/open_questions/verify_basis)는 Verify 단계를 통과한 뒤에만 작성한다 — delegation-protocol.md §2.2 (정본 specs/02 §3.2-C).
- **실패 보고 5필드** (reason/repro/attempted/lesson_candidate/blocking) — delegation-protocol.md §2.3 (정본 specs/02 §3.2-D).
- **병렬 Wave 운용(R1~R4)**과 에스컬레이션 경로는 delegation-protocol.md §2.5·§2.6 (정본 specs/07 §3.2-C). 소유 경계 밖 파일·미완성 산출물은 수정·추측하지 않는다.
- 이 프로젝트의 **물리 채널** 바인딩(위임 디스패치·보고 회수)은 delegation-protocol.md §3.
- **역할 빠른 참조:** 리포 루트 docs/roles-quick-reference.md (Advisor·Planner·Worker·Verifier).

이 절은 메시지 필드·규칙을 재정의하지 않고 정본을 가리킨다.

## §4. 검증 게이트

정본: specs/06-verifier.md §3(판정 계약), specs/03-loop.md §3.1-A(검증 게이트 CP1/CP2/CP3). 운용 체크리스트: 리포 루트 docs/verification-checklist.md.

- **구현 주체(Worker)와 검증 주체(Verifier/Advisor)는 분리**된다. Worker 완료 보고를 그대로 신뢰하지 않는다 (CLAUDE.md, verification-checklist.md §0).
- **검증 게이트 3단계** (specs/03 §3.1-A):
  - **CP1** — Worker 자체 점검 (자체 점검은 최종 승인이 아니다).
  - **CP2** — Verifier 독립 판정 (산출물 자체를 근거로).
  - **CP3** — Advisor 최종 승인 (Complete 진입 게이트).
- **Advisor 운용 게이트 A~D**(위임 발신 전 → 완료 보고 수령 → 산출물 독립 검증 → 최종 승인)의 점검 항목은 verification-checklist.md §3~§6.
- **판정 값**(충족/위반/판정 불가)과 **최종 판정 도출**(통과/실패/조건부)의 정본은 specs/06 §3.2-B/C. 조건부는 완료가 아니다.
- **검증 유형 VT-1~VT-5**는 specs/06 §3.2-E. 좁은 대리 지표 하나로 넓은 결론을 내지 않고 정직한 검사 범위를 명시한다 (verification-checklist.md §5.3).

이 절은 판정 기준을 재정의하지 않고 정본을 가리킨다.

## §5. Memory 사용 개요 (Consult / Update)

정본: specs/04-memory.md §3(Record/Recall), specs/05-lessons.md §3(Lessons), ARCHITECTURE.md §5.1(Memory Service · 단일 Port). 물리 실현: framework/adapters/claude/memory-binding.md §3.

- **단일 Port.** Memory는 Cross-cutting Service다. 모든 접근은 Memory Service Interface(단일 Port) 하나로만 이뤄진다 (ARCHITECTURE §5.1, specs/04 INV-1). 영속성 백엔드에 직접 접근하지 않는다.
- **Consult (회수, Recall).** 착수 전 관련 Lessons·이전 결정·컨텍스트를 목적·최소 범위로 회수한다 (Token Efficiency, specs/04 INV-3·INV-4). 물리 절차는 memory-binding.md §3.2.
- **Update (기록, Record).** 모든 실패는 Lesson 후보, 모든 성공은 Best Practice 후보다 (AGENT.md Memory). 기록은 append-only·정합 갱신이다 (specs/04 INV-6·INV-7). 물리 절차는 memory-binding.md §3.1.
- **Lessons·Best Practice·재발 판정**의 계약은 specs/05-lessons.md 소관이다.

이 절은 연산·포맷을 재정의하지 않고 정본을 가리킨다.

## §6. Adapter 이식 개요

정본: specs/11-adapters.md §3·§4.2.

- **이식 = Adapter 교체.** Core Contract(specs/11 §3)는 유지하고, §3.2-A 바인딩 지점의 값을 대상 환경 값으로 교체한다 (specs/11 §4.2).
- **Adapter 등급** (specs/11 §3.2-B): 완전 Adapter(Full) / 최소 구현 Adapter(Minimal). 최소 구현은 필수 바인딩 최소 부분집합(13개)만 제공하고 선택 바인딩(BP-6·12·16·17)은 생략할 수 있다.
- **Conformance(적합성 판정)**는 C1(필수 바인딩 완전성)·C2(Core Contract 불변)·C3(핵심 루프 1회 통과)를 모두 검사한다 (specs/11 §3.1).
- 현재 두 Adapter 경계가 실재한다: `framework/adapters/claude/`(첫 번째 — 완전 구현 목표)·`framework/adapters/generic/`(두 번째 — 환경 중립 최소 구현). 각 Adapter의 **Conformance verdict와 핵심 루프 통과 근거는 이 문서가 선취하지 않으며**, 각 Adapter 경계의 Conformance 문서·해당 검증 리포트를 정본으로 참조한다.

이 절은 바인딩 지점·판정 기준을 재정의하지 않고 정본을 가리킨다.
