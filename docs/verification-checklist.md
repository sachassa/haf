# 0. 사용 규칙

- 이 문서는 **운용 체크리스트**다. 판정 기준을 새로 정의하지 않는다. 판정 계약의 정본은 06·TEMPLATE이다.
- §1~§6의 체크 항목 본문은 **AI 비의존**으로 서술한다. 특정 AI·도구 사용법(검색·정독 실행 방법)은 §7 Adapter Binding에 분리한다 (ROADMAP 2.3, Core/Binding 분리).
- 각 체크 항목은 **예/아니오로 판정 가능한 문장**이다. 각 항목은 §1의 판정 값(충족/위반/판정 불가)으로 환원된다.
- 새 용어를 만들지 않는다. 이 문서의 "게이트 A~D"는 조직 편의 라벨이며 Glossary 정본 용어가 아니다. 실제 계약 용어는 검증 게이트(Glossary J-13)·CP1/CP2/CP3(03 §3.1-A)다.
- Advisor는 Worker 완료 보고를 그대로 신뢰하지 않는다. `self_check`는 검사 대상(claim)일 뿐 판정 근거가 아니다 (06 V1, INV-1).

# 1. 판정 규약 (요약 참조 — 정본: 06 §3.2-B/C)

이 절은 06의 판정 값과 도출 규칙을 **요약 참조**한다. 정의를 확장·수정하지 않는다.

**항목별 판정 값** (06 §3.2-B):
- **충족(Met)** — 기준이 산출물에서 만족됨을 근거로 확인했다.
- **위반(Violated)** — 기준이 산출물에서 만족되지 않음을 근거로 확인했다.
- **판정 불가(Undetermined)** — 근거 부족·검사 범위 한계로 확정 불가. 충족으로 취급하지 않는다 (06 V6).

**최종 판정 도출 규칙** (06 §3.2-C, 결정적):
- 모든 항목이 충족 → **통과(Pass)**.
- 하나라도 위반 → **실패(Fail)**.
- 위반은 없으나 판정 불가가 하나 이상 → **조건부(Conditional)**.

**조건부는 완료가 아니다.** 판정 불가 항목이 해소되어 통과로 전이하거나, 그 항목이 완료를 막지 않는다는 Advisor의 최종 판정(재량)을 받아야 한다. 재량 판정은 §6(게이트 D)에서만 한다. 독립 검증(게이트 C)에서 조건부 항목을 스스로 통과 처리하지 않는다 (06 §3.2-C, 02 §3.2-A Verifier 경계).

**모든 판정에 근거를 남긴다** (06 V3/INV-3). 근거 없는 "충족"은 무효다.
**모든 판정에 검사 범위를 명시한다** (06 V4/INV-4). 좁은 범위 검사로 넓은 결론을 내지 않는다.

# 2. 게이트 개요 (위임 발신 → 최종 승인)

Advisor는 한 위임 사이클에서 네 게이트를 순서대로 통과한다. 게이트 C·D는 03 §3.1-A 검증 게이트에 대응한다.

| 게이트 | 시점 | 점검 대상 | 03 §3.1-A 대응 |
|---|---|---|---|
| A. 위임 발신 전 | 위임 메시지 발신 직전 | 위임 메시지의 완전성 (02 §3.2-B, INV-6) | (사이클 진입 전) |
| B. 완료 보고 수령 시 | Worker 완료 보고 도착 시 | 완료 보고 필드 존재·정직성 예비 점검 (02 §3.2-C) | CP1 Worker 자체 점검 입력 확인 |
| C. 산출물 독립 검증 | 보고 수령 후 | 산출물 자체 근거의 독립 판정 (06 계약) | CP2 Verifier 독립 판정 |
| D. 최종 승인 | 독립 검증 통과 후 | CP2 통과 확인 + 조건부 재량 판정 | CP3 Advisor 승인 (Complete 게이트) |

게이트 C는 06의 Verifier 판정 계약을 적용하는 지점이다. 이 하네스에서 Advisor가 산출물을 정독해 이 판정을 구동·수행한다 (session-handoff §5.4). 게이트 D의 재량 판정은 Advisor 전속이다 (06 §3.2-C, TEMPLATE DoD-7). 게이트 C에서 게이트 D의 재량을 선점하지 않는다.

# 3. 게이트 A — 위임 발신 전 점검

기준: 02 §3.2-B 위임 메시지 필수 필드, 02 INV-6. 하나라도 누락되면 수임 Agent는 착수하지 않는다. 발신 전에 Advisor가 스스로 점검한다.

- [ ] `from` / `to`가 명시되어 있는가? (위임·수임 역할 확정)
- [ ] `task`가 작업 요약으로 존재하는가?
- [ ] `input`이 명확한가 — 무엇을 대상으로 하는지 확정되어 있는가?
- [ ] `output`이 명확한가 — 기대 산출물과 **위치(경로)**가 지정되어 있는가? (게이트 C의 VT-1 존재 검증 기준이 된다)
- [ ] `done`이 **검증 가능한 형태**로 열거되어 있는가 — 각 완료 조건이 예/아니오로 판정 가능한가? (게이트 C의 VT-2 대조 기준이 된다)
- [ ] `context`가 착수 전 읽을 문서 목록으로 존재하는가 — 상위 규약·Architecture·관련 spec·Memory 회수 범위를 포함하는가?
- [ ] `constraints`(경계·금지 사항)가 필요하면 명시되어 있는가? (선택 필드 — 병렬 위임 시 소유 경계·불추측 조율은 반드시 포함, 07 R2~R4)
- [ ] 위 필수 필드(input/output/done/context) 중 누락이 0건인가?

판정: 누락 항목이 있으면 해당 항목 **위반(Violated)** → 위임을 발신하지 않고 보완한다. 전 항목 충족 시 발신한다.

# 4. 게이트 B — 완료 보고 수령 시 점검

기준: 02 §3.2-C 완료 보고 필드. 이 게이트는 **필드 존재**와 **정직성 예비 점검**만 한다. 실제 판정은 게이트 C에서 산출물 근거로 한다.

## 4.1 필드 존재

- [ ] `artifacts`(산출물 경로 목록)가 존재하는가?
- [ ] `self_check`(완료 조건 항목별 충족 여부)가 존재하는가?
- [ ] `failures`가 존재하는가 — 없으면 "없음"이 **명시**되어 있는가?
- [ ] `open_questions`가 존재하는가 — 없으면 "없음"이 **명시**되어 있는가?
- [ ] `verify_basis`(Verify 통과 근거)가 존재하는가?

## 4.2 정직성 예비 점검 (게이트 C 입력 준비)

- [ ] `self_check`를 **판정 근거로 삼지 않겠다**고 확인했는가? (06 V1 — self_check는 검사 대상일 뿐이다)
- [ ] `verify_basis`가 근거로 든 검사 범위가 **좁은 대리 지표**(예: 단일 토큰 검색)에 머무는지 식별했는가? 좁으면 게이트 C에서 전수 재검사 대상으로 표시한다 (06 V4/VT-4, §5.3).
- [ ] `failures`가 "없음"이라는 주장이 게이트 C의 독립 판정에서 반증될 수 있음을 전제했는가? (06 §3.2-F)

판정: 필수 필드 누락은 **위반(Violated)**. 정직성 예비 점검은 게이트 C의 검사 범위를 설정하는 입력이며, 이 단계에서 "충족"을 확정하지 않는다.

# 5. 게이트 C — 산출물 독립 검증

기준: 06 판정 계약. 산출물 자체를 근거로 독립 판정한다 (06 V1/INV-1). 각 항목에 근거(evidence)와 검사 범위(scope)를 남긴다 (06 V3/V4). 검사한 범위와 제외한 범위를 함께 명시한다 (`verifier_scope`, 06 §3.2-A).

## 5.1 검증 유형 적용 (VT-1~VT-5 — 정본: 06 §3.2-E)

각 산출물에 대해 아래 다섯 유형을 적용한다. "무엇을 / 어떻게 검사하는가"를 각 유형별로 명시한다.

- [ ] **VT-1 산출물 존재.** *무엇* = 위임 `output`이 지정한 산출물. *어떻게* = 지정 경로의 산출물이 실제로 존재하고 접근 가능한지 확인한다. *충족* = 모든 지정 산출물이 존재. 부재 시 위반.
- [ ] **VT-2 완료 조건 대조.** *무엇* = 위임 `done`의 각 항목. *어떻게* = 각 완료 조건을 산출물과 **항목별로** 대조한다. *충족* = 모든 done 항목 충족. 하나라도 미충족이면 위반.
- [ ] **VT-3 규격 준수.** *무엇* = 산출물이 따라야 할 규격(spec이면 TEMPLATE DoD 8항목·대상 spec §7 완료 기준 / 비-spec이면 위임이 지정한 준용 규격, §5.2). *어떻게* = 규격의 각 항목을 산출물과 대조한다. *충족* = 규격 전 항목 충족.
- [ ] **VT-4 경계.** *무엇* = 불변 규칙·경계(예: AI 의존 요소 0건, 역할 경계 불침범, 소유 경계 밖 파일 미수정). *어떻게* = 금지 요소 후보 집합 **전체를 전수 스캔(exhaustive scan)** 하고 검사 범위를 산출물의 해당 경계 전 범위로 명시한다. *충족* = 금지 요소 0건. (§5.3에서 구체화)
- [ ] **VT-5 시연.** *무엇* = "시연 가능 문장"으로 표현된 완료 기준(대상 spec §7 또는 위임 done의 시연 항목). *어떻게* = 시연 시나리오를 실제로 재현하고 결과를 관측한다. *충족* = 시연이 기대대로 관측됨. (위임 완료 조건 "위임→구현→검증→승인 사이클 1회 시연"이 이에 해당)

각 항목의 판정에 `verification_type`을 붙인다 (06 §3.2-B). 한 항목은 하나 이상의 유형에 대응할 수 있다.

## 5.2 DoD 8항목 점검 (정본: TEMPLATE §3) — spec / 비-spec 산출물 준용

DoD 8항목은 spec의 Frozen 기준이다. spec이 아닌 산출물(문서·정의물·구현물)에는 아래 "준용" 지침으로 적용한다.

- [ ] **DoD-1 필수 섹션 §0~§9 존재.** *준용* = 비-spec 산출물은 자신이 따르는 구조 규약(있으면)의 필수 구성 요소가, 없으면 위임 `output`이 요구한 구성 요소가 전부 존재하는가.
- [ ] **DoD-2 완료 기준이 검증 가능 — 시연 시나리오로 환원.** *준용* = 산출물의 완료 조건이 예/아니오로 판정 가능하고 재현·시연 가능한 문장인가.
- [ ] **DoD-3 Core Contract에 AI 의존 요소 0건.** *준용* = 산출물의 AI 비의존이 요구되는 부분(체크 항목 본문, 이식 대상 계약 등)에 특정 AI 이름·모델명·제품 기능명이 0건인가 — **전수 스캔**한다 (§5.3, VT-4).
- [ ] **DoD-4 Memory 접근 시 Memory Service Interface만 참조.** *준용* = 산출물이 Memory 접근을 서술한다면 단일 Port(Memory Service Interface)만 참조하는가. 접근이 없으면 "해당 없음"으로 명시.
- [ ] **DoD-5 상호 참조가 실제 파일과 일치, 순환 의존 없음.** *준용* = 산출물이 인용·참조하는 모든 경로·§ 포인터가 실재하고 정확한가. 순환 참조가 없는가.
- [ ] **DoD-6 Glossary에 없는 용어 신설 안 함.** *준용* = 산출물이 `uahf/specs/00-glossary.md` 밖의 새 용어를 정본처럼 만들지 않았는가.
- [ ] **DoD-7 Open Questions가 비었거나 남은 항목이 완료를 막지 않음(Advisor 판정).** *준용* = 산출물의 미확정·Open Question이 없거나, 남은 것이 완료를 막지 않는다고 판정 가능한가. (막는지 불확실하면 **판정 불가(Undetermined)** → 게이트 D 재량 대상)
- [ ] **DoD-8 Verifier 검증 + Advisor 승인 통과.** *준용* = 독립 검증(게이트 C)과 최종 승인(게이트 D)을 통과했는가. (게이트 C 시점에는 미확정 — 게이트 D에서 최종 확인)

## 5.3 검사 범위 정직 (V4) — 전수 스캔 항목

이 절은 06 V4/VT-4/INV-4를 운용 항목으로 구체화한다. v0.1에서 실제 검출된 결함 유형이다 (session-handoff §1.4 Wave 1: 자체 점검이 특정 AI 이름 단일 토큰만 검사해 §3의 모델명을 놓침 → Advisor 재검증에서 검출·교정. 06 §8 예1로 편입).

### AI 비의존(DoD-3) 전수 스캔

- [ ] AI 의존 검사를 **단일 토큰 하나**로 대체하지 않았는가? (단일 토큰만 검색하면 위반)
- [ ] 금지 요소 후보 집합을 **전체**로 잡았는가 — 특정 AI 이름 + 모델명 + 제품 기능명을 모두 포함하는가? (구체 토큰 목록은 §7 바인딩)
- [ ] 검사 범위를 산출물의 AI 비의존 대상 경계 **전 범위**로 명시했는가? (`scope`에 기록)
- [ ] Worker `verify_basis`가 좁은 범위였다면, 그 범위를 **넘어** 재검사했는가?

판정: 잔존 금지 요소가 1건이라도 있으면 DoD-3 **위반(Violated)** → 최종 판정 Fail. 후보 집합·검사 범위가 좁아 확정 불가면 **판정 불가(Undetermined)**.

### 문서 내 상태 서술 ↔ 실제 상태 전수 대조

v0.1 Frozen 직후 교정 사례에서 도출된 항목이다 (session-handoff §5.3-4: Glossary 표의 낡은 "미작성" 표기가 실제 상태와 불일치 → 즉시 교정. Lesson 후보).

- [ ] 산출물이 서술하는 **모든 상태 표기**(파일 존재 여부, Status 값, 개수, "미작성/작성" 표기, dependents 목록 등)를 열거했는가?
- [ ] 열거한 각 상태 서술을 **실제 상태와 전수 대조**했는가 — 일부만 표본 대조하지 않았는가?
- [ ] 서술과 실제가 불일치하는 항목이 0건인가?

판정: 불일치 1건이라도 있으면 **위반(Violated)**. 대조 범위가 산출물 전체를 덮지 못하면 **판정 불가(Undetermined)**.

## 5.4 거짓 완료 보고 검출 (정본: 06 §3.2-F)

Worker 완료 보고의 주장과 실제 산출물의 불일치를 검출한다.

불일치 성립 케이스 (06 §3.2-F):
- [ ] `self_check`가 "충족"이라 주장하는 기준이, 독립 판정에서 **위반**은 아닌가?
- [ ] `artifacts`가 지정한 산출물이 **부재**하지는 않은가? (VT-1)
- [ ] `failures`가 "없음"이라 주장하나 독립 판정에서 **위반이 존재**하지는 않은가?
- [ ] `verify_basis`가 든 검사가 실제 필요한 범위를 **덮지 못한 좁은 범위**는 아닌가? (§5.3)

검출 절차 (06 §3.2-F):
- [ ] 완료 보고의 주장을 신뢰하지 않고, 동일 기준을 산출물에 대해 **충분한 범위로 독립 재판정**했는가? (06 V1·V4)
- [ ] 재판정 결과가 완료 보고 주장과 **모순**되면 거짓 완료 보고로 판정하고 `final_verdict = Fail`을 산출하는가?
- [ ] Fail 시 **재작업 지시**(06 §3.2-D: `violated_items` / `expected_state` / `revalidation_criteria` / `evidence_gap`)를 리포트에 포함했는가?

주의: `self_check`가 정직해도 검사 범위가 좁으면 거짓 완료가 통과할 수 있다. V4·VT-4가 그 범위를 넘어 전수 검사함으로써 검출한다 (06 §6, §8 예1).

## 5.5 게이트 C 판정 집계

- [ ] 각 항목에 `criterion` / `verdict`(충족·위반·판정 불가) / `evidence` / `scope` / `verification_type`을 남겼는가? (06 §3.2-B)
- [ ] 최종 판정을 §1 도출 규칙으로 결정적으로 산출했는가? (전부 충족→Pass / 위반 있음→Fail / 위반 없고 판정 불가 있음→Conditional)
- [ ] 판정 불가를 충족으로 위장하지 않았는가? (06 V6)

Fail 시: 재작업 지시(06 §3.2-D)를 산출하고 재작업 루프(03 §3.1-B)로 되돌린다. 게이트 D로 진행하지 않는다.

# 6. 게이트 D — 최종 승인 게이트 (CP3)

기준: 03 §3.1-A CP3(Advisor 승인, Complete 진입 게이트). "Verify 통과"는 CP2(게이트 C) PASS로 정의된다 (03 §3.1-A 게이트-단계 매핑).

- [ ] 게이트 C(CP2)의 최종 판정이 **Pass**임을 확인했는가? Pass가 아니면 승인하지 않는다.
- [ ] 최종 판정이 **Fail**이면 승인을 보류하고 재작업 지시(06 §3.2-D) + 재작업 루프(03 §3.1-B)로 넘겼는가?
- [ ] 최종 판정이 **조건부(Conditional)**이면, 판정 불가 항목에 대해 **재량 판정**을 수행했는가? — 그 항목이 완료를 막지 않는다고 판정하거나(TEMPLATE DoD-7), 해소를 요구해 통과로 전이시킨다. **조건부를 근거 없이 통과 처리하지 않는다.**
- [ ] 승인 결정(승인 / 보류 / 재작업)과 그 근거를 기록했는가?
- [ ] 사람 승인 필요 조건(03 §3.1-D)이 발생했는지 점검했는가 — 특히 **상위 규약·Architecture와 Spec의 충돌**을 발견하면 자동 해석하지 않고 사용자에게 보고하는가? (CLAUDE.md, 03 §3.1-D 조건 4)
- [ ] 완료 보고는 Verify 통과(CP2 PASS) 이후에만 유효함을 확인했는가? (02 INV-4 — 조기 완료 보고는 무효)

판정: 위 항목이 모두 충족되고 최종 판정이 Pass(또는 재량으로 해소된 조건부)일 때만 승인한다. 검증되지 않은 결과는 완료로 승인하지 않는다 (06 INV-7, ARCHITECTURE 3.4).

# 7. Adapter Binding — Claude Code 도구 사용법 (환경 의존)

이 절은 §1~§6의 AI 비의존 체크 항목을 v0.x Claude Code 환경에서 **실행하는 방법**이다. 다른 환경으로 이식하면 이 절만 교체한다. §1~§6 Core 체크 항목은 유지된다 (06 §4.2 SP-3, TEMPLATE §4).

이 절의 검사 도구 사용법은 **검증 게이트 운용 지침**이며, 각 검증 유형(VT-1~VT-5) ↔ 검사 도구의 **물리 실현 정본**(어떤 도구로 각 유형을 실현하는가)은 `uahf/framework/adapters/claude/verifier-binding.md` §5(VT-1~VT-5 검사 도구 바인딩)다. 이 절은 그 물리 바인딩을 게이트 운용으로 적용하며 재정의하지 않는다 — 정본(물리 바인딩)/운용(게이트 사용법)의 소유 구분이다 (06 §4.1 검사 도구 바인딩 행).

- **산출물 정독** (VT-1~VT-5, DoD 대조): 파일 조회 도구로 산출물 파일을 **전체** 연다. 표본만 읽지 않는다.
- **전수 스캔** (VT-4, DoD-3, §5.3): 텍스트 검색 도구로 금지 토큰 후보 집합 **전체**를 검색한다. v0.x 후보 토큰(예시, 확장 가능): `Claude`, `Anthropic`, `Opus`, `Sonnet`, `Haiku`, `claude-*` 패턴, 그리고 특정 AI 제품·기능명. 단일 토큰 하나로 끝내지 않는다 (06 §8 예1의 결함 방지).
- **상태 서술 대조** (§5.3): 산출물 내 상태 표기를 검색으로 열거한 뒤, 각 대상 파일의 실재 상태를 파일 조회로 대조한다.
- **완료 보고 회수** (게이트 B): Worker 서브에이전트의 최종 응답을 완료 보고로 받는다 (02 §4.1, 06 §4.1).
- **재작업 지시 전달** (게이트 C·D): 06 §3.2-D 재작업 지시를 Worker 서브에이전트에게 재위임 메시지로 전달한다. 전달·전이 채널은 03-loop·02 §4 소관이다.
- **판정 기록 산출** (게이트 C): 검증 리포트를 Markdown 등 구조화 파일로 남긴다 (06 §4.1).

이식 교체 지점(06 §4.2 SP-3): 위 검사 도구(존재 확인·전수 스캔·시연 실행)는 대상 환경의 검사 도구로 교체된다. Core 체크 항목의 의미는 바뀌지 않는다.
