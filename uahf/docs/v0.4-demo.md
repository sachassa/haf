## §0. 이 문서의 위치와 정본 경계

- **이 문서는 시연 수행 기록(Task M7)이다.** 절차서(docs/v0.4-demo-procedure.md)가 정의한 절차 단계·판정 문장·기록 포맷을 **입력**으로 받아, 시연 6종을 실물 파일 연산으로 수행하고 관측한 결과를 기록한다. 절차·판정 문장·기록 포맷을 **재정의하지 않는다** (절차서 §0).
- **독립 판정·최종 승인은 이 문서 소관이 아니다.** 판정 값(충족/위반/판정 불가)의 **관측 기록**까지가 이 문서(M7)의 책임이며, 최종 판정(통과/실패/조건부) 도출은 Verifier 독립 판정(CP2), 최종 승인은 Advisor(CP3) 소관이다 (절차서 §3 말미·§6-3). 각 시연의 "관측 결과"는 관측 수준 판정이며 **스스로 통과 처리·최종 승인이 아니다**. 자기 점검(CP1)은 승격 근거·최종 승인이 아니다 (05 §3.2, 02 §3.2-A).
- **관측을 창작하지 않았다.** 아래 모든 "근거"는 §1의 물리 store/index에 대한 실제 Record/Recall/Promote-gate 연산에서 관측된 구체 값이다(store 파일 내용, index 라인, Recall Result 건수·`detail`, Failure Report `operation`·`reason`, 재발 판정 `verdict`, store↔index 대조 결과). 수행하지 않은 단계의 관측을 기록하지 않았다 (06 §3.2-F, 절차서 constraints). 수행 불가 단계는 없었다.
- **하네스 상태 전제 (형태 A).** 이 하네스는 현재 Bootstrap 상태다 (memory-binding.md §0, Glossary J-13). Record/Recall은 실행 코드(형태 B)가 아니라 **규약 실현(형태 A)** 으로 수행되며 — memory-binding.md §3 물리 절차에 따라 이 백엔드(memory-data/)를 대상으로 실물 파일 연산(store `<id>.json` 쓰기 + index.jsonl append, index-first 조회)으로 관측 가능하게 했다. 이 기록은 그 규약 실현의 관측이며 형태 B 실행 로더를 주장하지 않는다.
- **물리 실데이터는 임시물이 아니라 산출물이다.** v0.3-demo(§1)는 시연을 임시 샌드박스에서 수행하고 산출물이 문서 1건뿐이었으나, M7의 위임 output은 문서 + `framework/adapters/claude/memory-data/` 이하 **물리 실데이터**를 포함한다(초기 실데이터 등록). 따라서 store/index 파일은 artifacts다(§8 전수 명시).
- **용어.** 계약 용어(Memory Item / Memory Index / Index Entry / Record / Recall / Lesson / Best Practice / Register Candidate / Promote / applicability / provenance / kind / scope / status / verdict / recurrence-judgment 등)와 판정 값(충족/위반/판정 불가)은 전부 Glossary·04·05·framework/memory 4종·verification-checklist.md 정본에서 인용했다. 후보 라벨 L-01~L-08·BP-01은 promotion-review §2·§3의 서술 라벨이다.

## §1. 수행 환경 · 물리 백엔드 · 라벨 표기 방식

### §1.1 물리 백엔드 (memory-binding.md §2 구조 그대로)

- **백엔드 루트(산출물):** `framework/adapters/claude/memory-data/` — 수행 전 미존재(memory-binding.md §7 실측 대조와 일치), 본 시연에서 생성.
  - `memory-data/store/<id>.json` — Memory Item 1건 = JSON 파일 1개. append-only·불변(04 INV-6). create-if-absent(memory-binding.md §3.1 단계 2 — 기존 파일 재작성·삭제 0).
  - `memory-data/index/index.jsonl` — Index Entry append-log(1 line = 1 Index Entry, Record 순서 append). `content` 원문 없음(04 INV-4).
- **`id` 스킴(memory-binding.md §2 주):** `mi-0001` … `mi-0021` — 사전식 정렬 가능 토큰, index append 순서(= Record 순서)와 정합. 파일명 `<id>.json`이 유일성 매체(같은 이름 생성 실패 = DuplicateId).
- **`timestamp` 값의 성격 (r3 교정 — 실측 후 기록, L-07 자기 적용).** 각 Memory Item·Index Entry의 `timestamp`(`22:19:47.602`~`22:20:07.602+09:00`, 1초 간격)는 **파일별 실제 쓰기 시각이 아니다.** 수행 세션 중 생성기가 배정한 **단조 증가 순서 값**이며, Record 순서·index append 순서·`id` 정렬 순서(`mi-0001`…`mi-0021`)와 정합한다. 물리 파일 생성 자체는 실측 파일 mtime `2026-07-05 22:19:46±25ms`로 **일괄** 수행됐다(21 store + 1 index). 04 §3.2-A `timestamp`("기록 시점")가 계약상 요구하는 기능 — Record 순서 정합과 lessons.md §5.2 **최신 상태 해소**(같은 `stable_id` 중 최신 `timestamp` 항목 = 현재 상태; 본 데이터에서 Active 기록이 Candidate보다 뒤 순서 값) — 은 이 순서 값으로 성립한다(CP2 검증 리포트 확인). 초판·r2가 이 값을 "실제 수행 시각"으로 서술한 것은 실측↔서술 모순(L-07 유형 재발)이었고 r3에서 서술 계층만 교정했다(물리 파일 무수정, §8.3).
- **직렬화 형식:** store = JSON, index = JSON Lines(memory-binding.md §2 주 — Adapter 선택, 격리 지점).
- **Record 물리 절차(memory-binding.md §3.1):** 각 Record는 store/`<id>.json` 쓰기 **직후** index.jsonl에 대응 line 1개 append를 함께 완료(04 INV-7). 완료 후 store 파일명 집합 ↔ index id 집합 전수 대조로 정합 보증(§7).
- **Recall 물리 절차(memory-binding.md §3.2):** `purpose`·`scope` 확인 → bounded 확인 → index.jsonl line만 스캔해 scope narrowing(`kind`→`kind`, `labels`→`labels`, `source`→`source`, `timeRange`→`timestamp`; memory-store.md §5) 해소 → 기본 `detail=index`면 Index Entry만 반환(store 미로드), `detail=full`+scope 한정 시에만 매칭 `id`의 store 파일 로드 → 반환량 `min(요청 limit, recall.limit.max=20)` 절단.

### §8.3 실패 처리 (절차서 §6 — 기대 불일치 시 은폐 없이 기록)

- **시연 관측 불일치 없음.** 시연 6종 모두 절차서 §7-C/§8-C/§10-C/§11-C/§12-C/§13-C 기대 관측대로 관측됐다. 위반·판정 불가로 표기할 항목은 없다. 여섯 시연의 "관측 결과"는 모두 **충족**(관측 수준). 최종 판정(Pass/Fail)은 내리지 않는다 — CP2·CP3 소관(절차서 §6-3, constraint).
- **CP2 검출 서술↔실측 모순 1건 (r3 교정 — 은폐 없이 기록, 절차서 §6-1).** 초판·r2 demo.md는 물리 기록 21건의 `timestamp`를 "실제 수행 시각"으로 서술했으나, CP2 독립 판정(검증 리포트 item #31)이 서술↔실측 모순을 검출했다: 실측상 store 21파일 + index는 `2026-07-05 22:19:46±25ms`에 **일괄** 생성됐고, 기록 내 `timestamp`(22:19:47~22:20:07, 1초 간격)는 파일별 실제 쓰기 시각이 아니라 생성기가 배정한 **단조 증가 순서 값**이다. 이는 **L-07(상태 서술은 실측 후 기록) 유형 재발** — "실재/시각" 주장을 실측과 대조하지 않고 기입한 것 — 이다. r3에서 서술 계층(head 수행 일시·§1.1·§10 self-note)의 해당 주장만 사실대로 교정했고, **물리 store·index 파일은 기록 불변(04 INV-6, append-only)에 따라 무수정**이다. `timestamp`의 계약 기능(Record 순서 정합·lessons.md §5.2 최신 상태 해소)은 이 순서 값으로 성립함을 CP2 검증 리포트가 확인했다. 이 재발은 **v0.4 신규 Lesson 후보 근거**가 된다(모든 실패는 Lesson 후보 — AGENT.md; 정식 후보 등록·승격은 Advisor 심사 소관). 시연 6종의 관측 결과(충족)에는 영향이 없다 — 이 결함은 수행 기록의 **서술 정확성** 사안이다.
- **은폐 없이 기록한 관측 구분.** ⓒ 음성 시도(NotApproved)와 ⓑ 케이스 1~3 거부는 **의도된 음성 시연의 기대된 거부**이며 예기치 못한 실패가 아니다(절차서 §6-4). ⓑ 케이스 4에서 반환 Index Entry 16건은 `scope`={kind:lesson}만 지정한 결과(Candidate+Active 전 후보)로, 이 케이스의 관측 대상은 "기본 index → content 비반환"이며 최소 집합 관측은 ⓐ 소관이다 — 정책 위반이 아니다. reason 코드 소속은 04 Memory(ⓑ MissingPurpose/MissingScope/UnboundedScope = Recall)와 05 Lessons(ⓒ NotApproved = Promote)를 구분해 혼입하지 않았다(L-02 자기 적용).
