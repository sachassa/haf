## §0. 이 문서의 위치와 경계

- **이 문서는 CP2 검증 입력물 1건이다.** UAF v1.1 마일스톤 검증(CP2)에서 Verifier가 시나리오 관통성을 판정하는 대상이며, 승인 계획 §검증 완료 조건 6("시나리오 워크스루 3건 통과")의 입력물이다. `docs/` 소속 운용 문서이지 정본이 아니다.

- **정본 재정의 0 (핵심 경계).** 본 문서는 어떤 상태·전이·판정식·스키마도 **새로 정의하지 않는다**. 모든 값은 정본 § 포인터 인용이며, 인용값은 §5 종합표에서 대상 정본과 실측 대조된다. 정본과 본 문서가 어긋나면 정본이 우선한다. 특히 State Machine 단일 정본은 uaf/specs/02-discovery.md §3.3(DISC-INV-2)이고, 결정 테이블 정본은 uaf/specs/01-entry.md §3.2-D이며, Contract 스키마 정본은 uaf/specs/03-project-contract.md §3.2다.

- **병렬 경계 (07 R2·R4).** 본 문서는 같은 v1.1 W5 병렬 집합의 다른 Task 산출물(`uaf/appendix/methodology-mapping.md`·`ROADMAP.md`)을 참조·인용하지 않는다. 공유하는 확정 인터페이스는 위 4개 UAF 정본과 그 § 포인터뿐이다.

- **관통 구간의 종단은 UAHF 접점까지.** 본 워크스루는 사용자 진입에서 시작하여 UAHF가 Contract를 **선택 입력**으로 소비하는 지점(uaf/specs/03-project-contract.md §3.5)까지를 관통한다. UAHF 내부 Execution(핵심 루프 구동)은 UAHF 정본 소관이며 본 문서의 관통 대상이 아니다(uaf/ARCHITECTURE.md §2.1·§6 비담당 ⑤).

- **AI 비의존.** 본문에 특정 AI 이름·모델명·제품 기능명·방법론 고유명을 두지 않는다(uaf/ARCHITECTURE.md §0 Core 문서 관행 동형). `/new`·`/continue`·`/import`는 UAF 논리 식별자다(위 머리 논리 식별자 주의).

## §1. 목적과 읽는 법

### §1.1 목적

세 시나리오는 UAF v1.1 파이프라인이 **사용자 진입에서 UAHF 소비까지 하나의 흐름으로 성립함**을 정본 § 포인터만으로 실증한다.

- 시나리오 A·B는 **전 구간 관통**을 보인다 — 실제 발견이 `Ready` 종단에 도달하고 완전한 Project Contract를 산출하기까지.
- 시나리오 C는 **확장 무변경**을 보인다 — 신규 Entry(`/import`)가 Layer·엔진·State Machine·Event Model·Contract 스키마를 **바꾸지 않고** 데이터 추가만으로 동일 흐름을 완주함(완료 조건 6 C1, D6-C1).

### §1.2 공통 관통 구간 (A·B 공통 골격)

시나리오 A·B는 다음 8구간을 순서대로 관통한다. 각 구간의 소유 정본을 § 포인터로 고정한다.

| 구간 | 내용 | 소유 정본 |
|---|---|---|
| ① 사용자 진입 | 논리 Entry(name) 발화 + Workspace Evidence 관측 | 01 §3.1 |
| ② Entry Resolution | 결정 테이블 행 매칭 + Resolution 엔진 고정 5단계 | 01 §3.2-A·§3.2-D |
| ③ Discovery Request | {mode, inputs, policy} 산출 | ARCHITECTURE §8.2 / 01 §3.2-B |
| ④ State Machine 전이 시퀀스 | Initiated → … → 종단, T# 전이·Event 시퀀스 | 02 §3.3-B·§3.5 |
| ⑤ Execution Ready 2축 판정식 | Completeness ∧ Confidence ∧ 사용자 승인 | 02 §3.7 |
| ⑥ Ready 종단 도달 | `Ready` 종단(T19) | 02 §3.3-A·§3.6 |
| ⑦ 산출 Contract 논리 골격 | 9 필드 그룹·필수 코어 필드 충족 | 03 §3.2-A·§3.2-B |
| ⑧ UAHF 소비 지점 | 선택 입력·두 소비 지점 | 03 §3.5 |

### §1.3 State Machine·판정식의 인용 기준 (재정의 0)

- **전이 표기.** `T#`는 uaf/specs/02-discovery.md §3.3-B 전이 전수 열거표의 전이 번호다. 본 문서의 전이 시퀀스는 그 표의 부분경로이며 새 전이를 만들지 않는다.
- **Event 표기.** 인용하는 Event는 uaf/specs/02-discovery.md §3.5 Event Model 15종의 원소다.
- **2축 판정식.** uaf/specs/02-discovery.md §3.7 "Execution Ready 2축 판정"의 판정식을 그대로 인용한다.

```
Ready = Contract Completeness  ∧  Confidence  ∧  사용자 승인
        (축 1 — 필수 코어 필드 전건 충족)  (축 2 — 전 차원 임계 충족)  (축 3 — Preserve Human Authority)
```

축 1(Completeness)은 모든 Ready 종단에서 타협 불가이고, 축 2(Confidence)만 가정 대체가 허용되며, 축 3(사용자 승인)은 게이트다(02 §3.7 축 1·2·3, UAF-INV ⑤, DISC-INV-6). 이 세 결합이 §3.7이 "2축 판정"으로 명명한 판정식이며, 본 문서는 이를 재정의하지 않고 인용한다.

## §2. 시나리오 A — Greenfield `/new` (신규 프로젝트)

빈 워크스페이스에서 새 프로젝트를 시작하는 정상 경로. **결정 테이블 행 1**(01 §3.2-D)에 해소된다.

### §2.1 ① 사용자 진입

- 명시 Entry(name): `/new`
- Workspace Evidence(01 §3.2-C): `{ contract-presence: 무, repository-presence: 무 }`
- 의미: 계약도 저장소도 없는 순수 Greenfield. `/new`는 순수 Greenfield 전용 진입이다(01 §3.1 Entry 2종).

### §2.2 ② Entry Resolution — 결정 테이블 행 1 + 엔진 5단계

**결정 테이블 행 1(01 §3.2-D 실측):** `| 1 | /new | 무 | 무 | → greenfield | 기본 | P-C (순수 Greenfield — /new 정상 경로) |`

**Resolution 엔진 고정 5단계(01 §3.2-A):**

1. **매칭** — name `/new`으로 Entry Registry에서 Entry Descriptor를 찾는다.
2. **증거 수집** — Descriptor의 requiredEvidence(contract-presence·repository-presence)를 관측: `{무, 무}`. (관측만 — Entry는 Discovery를 수행하지 않는다, EN-INV 1.)
3. **우선순위 평가** — decisionRows 대조: 상충 증거 0 → 행 1(P-C, greenfield 정상 경로) 단일 매칭.
4. **결정성 검증** — 이 조합은 행 1에만 매칭(전수·상호배타 분할, EN-INV 3).
5. **방출** — Discovery Request를 방출한다(§2.3).

### §2.3 ③ Discovery Request {mode, inputs, policy}

ARCHITECTURE §8.2 추상에 정합(01 §3.2-B 채움 규칙):

```
Discovery Request {
  mode:   greenfield                                  (01 §3.2-E · ARCHITECTURE §8.2 초기 등재값)
  inputs: [ contract-presence(무), repository-presence(무) ]   (Evidence 참조 목록)
  policy: 기본 정책 참조                               (Policy as Data — 값 상세는 02 소관)
}
```

Entry는 여기서 멈춘다 — Discovery 수행·Contract 생성 없음(P1, UAF-INV ④; 01 EN-INV 1·2).

### §2.4 ④ State Machine 전이 시퀀스 (02 §3.3-B)

기계는 Discovery Request가 결속될 때 `Initiated`로 인스턴스화된다(생성은 전이가 아님, 02 §3.3-A).

| 순 | 전이 | From — Event[Guard] → To | 비고 |
|---|---|---|---|
| 1 | **T1** | `Initiated` — `DiscoveryStarted` → `Contextualizing` | Greenfield 프레이밍(신규 문맥 구성, 02 §3.3-A) |
| 2 | **T3** | `Contextualizing` — `ContextCaptured`[맥락 기준선 확보 — Greenfield 프레이밍 완료] → `Eliciting` | Greenfield 분기는 T2 증거 스캔을 거치지 않는다 |
| 3 | **T4~T9**(적응 질문 루프, self) | `Eliciting` — `QuestionAsked`(T4)·`AnswerReceived`(T5)·`EvidenceRecorded`(T6)·`ConfidenceUpdated`(T7)·`BudgetConsumed`[soft](T8)·`DimensionSaturated`[일부 차원 포화](T9) → `Eliciting`(self) | 5차원(Intent·Requirement·Constraint·Risk·Architecture, 02 §3.11) 확신을 끌어올림 |
| 4 | **T10** | `Eliciting` — `DimensionSaturated`[전 필수 차원 포화] → `Synthesizing` | 전 차원 임계 도달로 종합 진입 |
| 5 | **T13**(self, 선택) | `Synthesizing` — `ConfidenceUpdated` → `Synthesizing`(self) | 종합 중 확신 갱신 |
| 6 | **T14** | `Synthesizing` — `ValidationRequested`[필수 코어 필드 충족 가능(실측 ∨ 가정)] → `Validating` | 사용자 확인 요청 |
| 7 | **T16** | `Validating` — `AnswerReceived`[사용자 승인] → `Compiling` | 축 3 게이트 — 사용자 승인 수령(02 §3.7) |
| 8 | **T18**(self) | `Compiling` — `ContractCompiled`[Back-end가 Contract 컴파일] → `Compiling`(self) | Contract 컴파일 |
| 9 | **T19** | `Compiling` — `ExecutionReadyDeclared`[Completeness ∧ 전 차원 Confidence 임계 ∧ 사용자 승인] → `Ready` | 종단 도달 |

Event 시퀀스(append-only, 02 §3.5): `DiscoveryStarted` → `ContextCaptured` → (`QuestionAsked`·`AnswerReceived`·`EvidenceRecorded`·`ConfidenceUpdated`·`BudgetConsumed`·`DimensionSaturated`)* → `DimensionSaturated`[전 차원] → `ConfidenceUpdated` → `ValidationRequested` → `AnswerReceived`[승인] → `ContractCompiled` → `ExecutionReadyDeclared`.

### §2.5 ⑤ Execution Ready 2축 판정식 적용 (02 §3.7)

T19의 Guard가 판정식 전건을 충족한다:

- **축 1 — Completeness:** 필수 코어 필드(03 §3.2-B) 전건 **실측** 충족. Compiler는 불완전 출력을 내지 않는다(DISC-INV-5).
- **축 2 — Confidence:** 전 차원(5) Confidence 임계 충족(T10에서 전 차원 포화). 가정 대체 없음.
- **축 3 — 사용자 승인:** `Validating`에서 승인 수령(T16), Readiness 선언에 기록(UAF-INV ⑤, DISC-INV-6).

세 축 모두 충족 → `Ready`(T20 ReadyWithAssumptions가 아님 — 축 2 미달 없음).

### §2.6 ⑥ Ready 종단 도달

종단 `Ready`(02 §3.3-A 종단 5 중 하나) 도달. Termination 경로 ①(2축 게이트 충족, 02 §3.6, 전이 T19). Contract 산출 = **완전한 Contract**. Assumption Ledger는 비어 있다.

### §2.7 ⑦ 산출 Project Contract 논리 골격 (03 §3.2-A 9그룹)

| # | 필드 그룹 | 이 시나리오의 논리 골격 |
|---|---|---|
| 1 | **Meta** | `{ id: (인스턴스 식별자), schemaVersion, instanceVersion: 1, supersedes: 없음 }` — 신규 프로젝트 최초 인스턴스 |
| 2 | **Intent** | 프로젝트 의도 — 실측 충족 |
| 3 | **Requirements** | 기능 요구·품질 요구 — 실측 충족 |
| 4 | **Constraints** | 제약 목록 — 실측 충족(명시적 공집합도 충족) |
| 5 | **Risks** | 리스크 목록 — 실측 충족(명시적 공집합도 충족) |
| 6 | **Architecture Direction** | 결정·미결 — 실측 충족 |
| 7 | **Assumption Ledger** | 빔(가정 없음) |
| 8 | **Readiness** | Completeness 판정(전건 실측)·Confidence Vector(전 차원 임계)·미해결 질문 목록(없음)·사용자 승인 기록(승인됨) |

### §2.8 ⑧ UAHF 소비 지점 (03 §3.5 — 선택 입력)

- **선택 입력(03 §3.5-A, D2④):** Contract는 UAHF의 선택 입력이다. 존재하면 아래 두 지점에서 소비되고, 부재 시 UAHF는 기존 방식으로 운용된다(하위 호환).
- **소비 지점 (a) Advisor 착수 정독(03 §3.5-B):** UAHF Advisor의 Consult 단계에서 존재하는 Contract를 프로젝트 정의 정본 문서로 정독한다. UAHF 계약 무수정(문서 정독은 연산·필드·불변을 바꾸지 않음).
- **소비 지점 (b) 신규 프로젝트 설치 배치(03 §3.5-B):** UAHF Scaffold가 신규 프로젝트에 Contract를 정본 문서로 함께 배치한다. UAHF Scaffold 계약 무수정.
- 정식 등재(필수 입력·명명 산출물)는 구현 버전 확장 포인트다(03 §3.5-C). 여기서는 설계하지 않는다.

**A 관통 성립:** 진입 → 행 1 해소 → greenfield Discovery Request → State Machine `Ready` 완주(T19) → 완전한 Contract(instanceVersion 1) → UAHF 선택 입력 소비. 전 구간 정본 § 포인터로 성립.

## §3. 시나리오 B — Brownfield `/continue` 최초 도입 (기존 저장소·Contract 부재)

기존 저장소가 있으나 아직 Project Contract가 없는 **최초 도입**. `/new`가 아니라 `/continue`의 소관이다(D3 ②). **결정 테이블 행 6**(01 §3.2-D)에 해소되며, 최초 Contract를 생성한다.

### §3.1 ① 사용자 진입

- 명시 Entry(name): `/continue`
- Workspace Evidence(01 §3.2-C): `{ contract-presence: 무, repository-presence: 유 }`
- 의미: 저장소는 존재하나 계약이 없다. Brownfield Full Discovery로 최초 Contract를 생성한다(01 §3.1 `/continue`·D3 ②).

### §3.2 ② Entry Resolution — 결정 테이블 행 6 + 엔진 5단계

**결정 테이블 행 6(01 §3.2-D 실측):** `| 6 | /continue | 무 | 유 | → brownfield | 기본 | D3 ② (/continue + Contract 부재 + Repo 존재 → Brownfield Full Discovery, 최초 Contract 생성) |`

**Resolution 엔진 고정 5단계(01 §3.2-A):**

1. **매칭** — name `/continue`으로 Registry에서 Descriptor를 찾는다.
2. **증거 수집** — requiredEvidence 관측: `{ contract 무, repo 유 }`.
3. **우선순위 평가** — decisionRows 대조: Contract 부재 + Repo 존재 → 행 6(D3 ②, brownfield) 단일 매칭.
4. **결정성 검증** — 이 조합은 행 6에만 매칭(EN-INV 3).
5. **방출** — Discovery Request를 방출한다(§3.3).

(대조: 만약 Contract가 존재했다면 Contract 존재 우선으로 행 7·8 incremental이 된다 — D3 ③. 본 시나리오는 최초 도입이므로 Contract 무 → 행 6.)

### §3.3 ③ Discovery Request {mode, inputs, policy}

```
Discovery Request {
  mode:   brownfield                                  (01 §3.2-E · ARCHITECTURE §8.2 초기 등재값)
  inputs: [ contract-presence(무), repository-presence(유) ]   (Evidence 참조 목록)
  policy: 기본 정책 참조
}
```

### §3.4 ④ State Machine 전이 시퀀스 (02 §3.3-B) — Brownfield 특성 반영

Brownfield 특성 3건(done 3)이 이 시퀀스에서 드러난다: **(i) Contextualizing의 Brownfield 증거 스캔 분기(T2 self 포함)**, **(ii) 기존 저장소 증거의 Evidence 기준선**, **(iii) 최초 Contract 생성(instanceVersion 1)**.

| 순 | 전이 | From — Event[Guard] → To | 비고 |
|---|---|---|---|
| 1 | **T1** | `Initiated` — `DiscoveryStarted` → `Contextualizing` | Brownfield 증거 스캔 분기(02 §3.3-A) |
| 2 | **T2**(self, 1+회) | `Contextualizing` — `EvidenceRecorded`[Brownfield 증거 스캔 진행] → `Contextualizing`(self) | **Brownfield 특성 (i)·(ii)** — 기존 저장소 산출물을 스캔해 증거를 기록, Evidence 기준선 확보. Greenfield(A)에는 없는 전이 |
| 3 | **T3** | `Contextualizing` — `ContextCaptured`[맥락 기준선 확보 — Brownfield 스캔 완료] → `Eliciting` | 스캔으로 확보된 증거 기준선 위에서 질문 개시 |
| 4 | **T4~T9**(적응 질문 루프, self) | `Eliciting` — `QuestionAsked`(T4)·`AnswerReceived`(T5)·`EvidenceRecorded`(T6)·`ConfidenceUpdated`(T7)·`BudgetConsumed`[soft](T8)·`DimensionSaturated`[일부 차원 포화](T9) → `Eliciting`(self) | 저장소 증거로 이미 확보된 차원은 포화 스킵(02 §3.13), 갭 차원에 질문 집중 |
| 5 | **T10** | `Eliciting` — `DimensionSaturated`[전 필수 차원 포화] → `Synthesizing` | 전 차원 임계 도달 |
| 6 | **T14** | `Synthesizing` — `ValidationRequested`[필수 코어 필드 충족 가능] → `Validating` | 사용자 확인 요청 |
| 7 | **T16** | `Validating` — `AnswerReceived`[사용자 승인] → `Compiling` | 축 3 게이트 — 사용자 승인 |
| 8 | **T18**(self) | `Compiling` — `ContractCompiled` → `Compiling`(self) | Contract 컴파일 |
| 9 | **T19** | `Compiling` — `ExecutionReadyDeclared`[Completeness ∧ 전 차원 Confidence 임계 ∧ 사용자 승인] → `Ready` | 종단 도달 |

Event 시퀀스(02 §3.5): `DiscoveryStarted` → (`EvidenceRecorded`)+ [Brownfield 스캔] → `ContextCaptured` → (`QuestionAsked`·`AnswerReceived`·`EvidenceRecorded`·`ConfidenceUpdated`·`BudgetConsumed`·`DimensionSaturated`)* → `DimensionSaturated`[전 차원] → `ValidationRequested` → `AnswerReceived`[승인] → `ContractCompiled` → `ExecutionReadyDeclared`.

**A와의 대조(핵심 Brownfield 특성):** B는 T1 직후 **T2(self, Brownfield 증거 스캔)**를 1회 이상 거쳐 기존 저장소 증거의 Evidence 기준선을 확보한 뒤 T3로 수렴한다. A(Greenfield)는 T2를 거치지 않고 프레이밍만으로 T3에 이른다. 세 mode 분기(greenfield·brownfield·incremental)는 모두 `ContextCaptured`(T3)로 수렴한다(02 §3.3-A).

### §3.5 ⑤ Execution Ready 2축 판정식 적용 (02 §3.7)

- **축 1 — Completeness:** 필수 코어 필드 전건 충족. 저장소 증거 기준선 위에서 실측으로 채워지며, 최초 도입이므로 `supersedes`는 없음.
- **축 2 — Confidence:** 전 차원 임계 충족(T10).
- **축 3 — 사용자 승인:** `Validating`에서 승인 수령(T16).

세 축 충족 → `Ready`(T19).

**대안 종단(비주경로 주석):** Brownfield에서 예산 소진으로 일부 차원 Confidence가 임계 미달이면, 필수 코어 필드를 가정으로 충족하고 Assumption Ledger에 기재하여 `ReadyWithAssumptions`(T20, Termination 경로 ②)로 종단할 수 있다. 이때도 축 1 Completeness는 타협 불가이고 Assumption Ledger는 비어 있을 수 없다(02 §3.7, DISC-INV-5). 본 워크스루의 주경로는 `Ready`(T19)다.

### §3.6 ⑥ Ready 종단 도달

종단 `Ready`(T19, Termination 경로 ①). Contract 산출 = 완전한 Contract. **최초 Contract 생성**이므로 `instanceVersion: 1`, `supersedes: 없음`(Brownfield 특성 (iii); 03 §3.4 인스턴스 거버넌스 — 이어갈 이전 인스턴스가 없다).

### §3.7 ⑦ 산출 Project Contract 논리 골격 (03 §3.2-A 9그룹)

A(§2.7)와 동일한 9 필드 그룹·동일 필수 코어 필드 집합으로 산출된다(Strategy Invariance — 어떤 mode·Strategy든 동일 스키마, UAF-INV ③·DISC-INV-7). Brownfield 고유차는 **내용의 출처**(일부 필드가 저장소 증거 스캔에서 유래)와 **Meta**에 국한된다:

- **Meta:** `{ id, schemaVersion, instanceVersion: 1, supersedes: 없음 }` — 최초 도입.
- **Assumption Ledger:** 주경로(Ready)에서는 빔; 대안 종단(ReadyWithAssumptions)에서는 필수로 채워짐(§3.5).
- 나머지 그룹·필수 코어 필드 충족표는 §2.7과 동형(전건 충족). 필드 그룹 스키마 자체는 mode와 무관하게 불변이다(03 §3.2-C 역방향 의존 없음).

### §3.8 ⑧ UAHF 소비 지점 (03 §3.5 — 선택 입력)

§2.8과 동일 — 선택 입력(§3.5-A), 두 소비 지점 (a) Advisor 착수 정독·(b) Scaffold 배치(§3.5-B), 정식 등재는 확장 포인트(§3.5-C). 소비 방식은 mode·인스턴스 계보와 무관하게 동일하다(UAHF는 tolerant reader로 필수 코어 필드만 의존, 03 §3.3-C).

**B 관통 성립:** 진입 → 행 6 해소 → brownfield Discovery Request → State Machine `Ready` 완주(T2 증거 스캔 포함) → 최초 완전 Contract(instanceVersion 1·supersedes 없음) → UAHF 선택 입력 소비. Brownfield 특성 3건 전부 시퀀스에 반영.

## §4. 시나리오 C — 가상 `/import` 확장 (사용자 흐름 수준)

가상의 신규 Entry `/import`(외부 산출물을 Discovery 씨앗으로 도입)가 **Layer·엔진·State Machine·Event Model·Contract 스키마를 바꾸지 않고** 등록 데이터 추가만으로 동일 흐름을 완주함을 보인다. 등록 모델은 01 §8 예3이 소유하며, 본 절은 그 등록을 소비하여 **사용자 흐름 수준**으로 확장한다. 완료 조건 6 C1(D6-C1)의 판정 근거다.

### §4.1 등록 (01 §8 예3 소비 — 변경 목록)

`/import`를 Entry Registry에 등록하는 데 필요한 변경 목록은 01 §8 예3이 확정한다. 본 절은 그것을 인용한다(재정의 0):

| 변경 | 내용 | 소유 정본 |
|---|---|---|
| **변경 1 — Evidence Source 선언 추가** | `external-deliverable-presence`(capability: 외부 산출물 존재·접근 가능 관측 / valueDomain: 유·무) | 01 §3.2-C 확장 스키마·§8 예3 변경 1 |
| **변경 2 — Entry Descriptor 행 추가** | name `/import`; requiredEvidence [external-deliverable-presence, contract-presence]; decisionRows (external-deliverable 유 + Contract 무 → import 정상 / external-deliverable 유 + Contract 유 → 충돌·사용자 확인 / external-deliverable 무 → 판별 실패); modeMapping (external-deliverable 유 → mode `import`) | 01 §3.2-A Registry·§8 예3 변경 2 |

| **변경 4 — policy 데이터 추가** | `/import` 결정 행이 참조할 정책 번들(정상·충돌 게이트) | 01 §8 예3 변경 4 |

### §4.2 사용자 흐름 — 등록 후 `/import` 발화

등록이 끝난 뒤 사용자가 `/import`를 발화한다. 아래 흐름의 어떤 단계도 새 코드·새 상태·새 스키마를 요구하지 않는다.

**① 사용자 진입.** 명시 Entry(name): `/import`; Workspace Evidence: `{ external-deliverable-presence: 유, contract-presence: 무 }`.

**② Entry Resolution — 무변경 고정 5단계(01 §3.2-A).** 엔진 알고리즘은 A·B와 **동일한 5단계**다:

1. **매칭** — name `/import`으로 Registry에서 변경 2의 Descriptor를 찾는다.
2. **증거 수집** — requiredEvidence(external-deliverable-presence·contract-presence) 관측: `{유, 무}`.
3. **우선순위 평가** — 변경 2의 decisionRows 대조: external-deliverable 유 + Contract 무 → "import 정상" 단일 매칭.
4. **결정성 검증** — 등록 시점에 전수·상호배타 분할이 검증된 Registry(EN-INV 3·§3.2-A 4단계).
5. **방출** — Discovery Request 방출(③).

엔진은 새 Descriptor를 **기존 알고리즘 그대로** 처리한다 — 정책은 전부 변경 2·4의 데이터에 있고 엔진 코드에는 없다(Policy as Data, EN-INV 4).

**③ Discovery Request.**

```
Discovery Request {
  mode:   import                                      (변경 3 — 확장 네임스페이스 등재값 · 계약 불변)
  inputs: [ external-deliverable-presence(유), contract-presence(무) ]   (Evidence 참조 목록 — 일반화되어 불변)
  policy: import 정책 참조
}
```

Discovery Request 추상({mode, inputs, policy})은 무변경이다 — mode는 확장 네임스페이스이므로 `import` 값 추가에 스키마 변경이 없고, inputs는 Evidence 참조 목록으로 일반화되어 `external-deliverable-presence` 참조를 담아도 계약이 깨지지 않는다(ARCHITECTURE §8.2 닫힘 없음 원칙).

**④ State Machine 완주 — 동일 §3.3-B 전이표.** 새 상태·새 전이·새 Event가 0인 채로 동일 기계가 종단에 이른다:

| 순 | 전이 | From — Event[Guard] → To | 비고 |
|---|---|---|---|
| 1 | **T1** | `Initiated` — `DiscoveryStarted` → `Contextualizing` | `import` mode의 맥락 확보 — 외부 산출물을 증거로 도입 |
| 2 | **T2**(self, 1+회) | `Contextualizing` — `EvidenceRecorded` → `Contextualizing`(self) | 외부 산출물을 증거로 기록(증거 스캔형 맥락화, 02 §3.3-A "mode에 따라 분기") |
| 3 | **T3** | `Contextualizing` — `ContextCaptured` → `Eliciting` | 세 mode 분기와 동일하게 `ContextCaptured`로 수렴 |
| 4 | **T4~T9** | `Eliciting` 적응 질문 루프(self) | A·B와 동일 Event 집합 |
| 5 | **T10** | `Eliciting` — `DimensionSaturated`[전 차원 포화] → `Synthesizing` | 동일 |
| 6 | **T14** | `Synthesizing` — `ValidationRequested` → `Validating` | 동일 |
| 7 | **T16** | `Validating` — `AnswerReceived`[사용자 승인] → `Compiling` | 동일 축 3 게이트 |
| 8 | **T18**(self) | `Compiling` — `ContractCompiled` → `Compiling`(self) | 동일 |
| 9 | **T19** | `Compiling` — `ExecutionReadyDeclared`[Completeness ∧ 전 차원 Confidence ∧ 사용자 승인] → `Ready` | 동일 종단 |

State Machine 구조(02 §3.3-B의 6 비종단·5 종단·전이 T1~T25·15 Event)는 불변이다. `import` mode는 **기존 `Contextualizing` 상태의 mode 분기**(02 §3.3-A — "mode에 따라 분기")로 흡수되며, mode가 확장 네임스페이스이므로(ARCHITECTURE §8.2, 01 §3.2-E) 새 mode 값의 등재가 전이표를 바꾸지 않는다. 이후 `Eliciting`~`Ready`(T3~T19)는 완전히 mode 비의존이다.

**⑤ 2축 판정식·⑥ Ready 종단.** A·B와 동일한 §3.7 판정식(Completeness ∧ Confidence ∧ 사용자 승인)으로 `Ready`(T19) 종단.

**⑦ 동일 Contract 스키마 산출.** 산출 Contract는 03 §3.2-A의 **동일 9 필드 그룹·동일 필수 코어 필드**(03 §3.2-B)로 컴파일된다. `import`로 발견했다는 사실은 Provenance 불투명 부속·`instanceVersion`에만 반영되고 코어 스키마·`schemaVersion`에 도달하지 못한다(03 §3.2-D·§3.4·PC-INV 2·10). Contract 스키마는 무변경이다(Strategy Invariance, UAF-INV ③).

**⑧ UAHF 소비.** §2.8·§3.8과 동일 — 선택 입력, 두 소비 지점(03 §3.5). UAHF는 tolerant reader로 필수 코어 필드만 의존하므로 새 mode의 존재조차 알 필요가 없다(03 §3.3-C).

### §4.3 무변경 대조표 (완료 조건 6 C1 판정 근거)

`/import` 도입의 변경 목록과 무변경 항목을 대조한다. **변경 = 데이터 추가 4건뿐이고, 계약·엔진·기계·스키마는 전부 무변경**임이 C1(Entry Resolution 확장성·D6-C1)의 판정 근거다.

| 항목 | 변경 여부 | 근거 정본 |
|---|---|---|
| Entry Registry 행 | **추가**(변경 목록) | 01 §3.2-A·§8 예3 변경 2 |
| Policy 데이터(decisionRows·modeMapping·정책 번들) | **추가**(변경 목록) | 01 §8 예3 변경 2·4 |
| Evidence Source 선언(external-deliverable-presence) | **추가**(변경 목록) | 01 §3.2-C·§8 예3 변경 1 |
| mode 네임스페이스 등재값(`import`) | **값 추가**(열거 변경 아님) | 01 §3.2-E · ARCHITECTURE §8.2 |
| **Entry Layer** | **무변경** | 01 §8 예3(변경되지 않는 것)·EN-INV 4 |
| **Resolution 엔진(고정 5단계 알고리즘)** | **무변경** | 01 §3.2-A·§8 예3(변경되지 않는 것) |
| **Discovery Request 추상({mode, inputs, policy})** | **무변경** | ARCHITECTURE §8.2·01 EN-INV 5 |
| **State Machine(§3.3-B 전이표 — 6 비종단·5 종단·T1~T25)** | **무변경** | 02 §3.3·DISC-INV-2 |
| **Event Model(15 Event)** | **무변경** | 02 §3.5·DISC-INV-1 |
| **Execution Ready 2축 판정식** | **무변경** | 02 §3.7 |
| **Contract 스키마(9 필드 그룹·필수 코어 필드)** | **무변경** | 03 §3.2·PC-INV 2·4 |

**C 판정 성립:** 신규 Entry `/import` 도입의 변경 목록 = **Entry Registry 행 + Policy 데이터 + Evidence Source 선언의 추가뿐**이며, Entry Layer·Resolution 엔진·State Machine·Event Model·Contract 스키마는 전부 무변경이다. 동일 흐름(진입 → Resolution → Discovery Request → State Machine `Ready` 완주 → 동일 Contract 스키마 → UAHF 소비)이 새 코드 없이 성립한다 — D6-C1(Entry Resolution 확장성)이 사용자 흐름 수준에서 실증된다.

### §5.3 Event Model (02 §3.5) 및 종단 (02 §3.3-A)

- 인용 Event(전부 02 §3.5 Event Model 15의 원소): `DiscoveryStarted`·`ContextCaptured`·`QuestionAsked`·`AnswerReceived`·`EvidenceRecorded`·`ConfidenceUpdated`·`BudgetConsumed`·`DimensionSaturated`·`ValidationRequested`·`ContractCompiled`·`ExecutionReadyDeclared`. ### §5.4 Execution Ready 2축 판정식 (02 §3.7 실측)

`Ready = Contract Completeness(축 1 — 필수 코어 필드 전건 충족) ∧ Confidence(축 2 — 전 차원 임계 충족) ∧ 사용자 승인(축 3 — Preserve Human Authority)`. 축 1 타협 불가·축 2만 가정 대체 허용·축 3 게이트(02 §3.7 축 1·2·3).

### §5.5 Contract 필드 그룹·필수 코어 필드 (03 §3.2 실측)

- **필드 그룹 9종(03 §3.2-A):** Meta · Intent · Requirements · Constraints · Risks · Architecture Direction · Assumption Ledger · Readiness · Provenance(불투명 부속).
- **필수 코어 필드(03 §3.2-B):** `id` · `schemaVersion` · `instanceVersion` · Intent · Requirements · Constraints · Risks · Architecture Direction · Readiness · Assumption Ledger. (Provenance는 비-코어 — Completeness 판정·UAHF 소비 대상 아님.)
- **UAHF 소비(03 §3.5):** 선택 입력(§3.5-A) · (a) Advisor 착수 정독·(b) Scaffold 배치(§3.5-B) · 정식 등재는 확장 포인트(§3.5-C).
- **인스턴스 거버넌스(03 §3.4):** 최초 생성 = `instanceVersion: 1`·`supersedes: 없음`(A·B); Incremental 갱신 = 새 `instanceVersion` + `supersedes` 계보.
