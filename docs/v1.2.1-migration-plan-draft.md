**핵심 실측 발견 (모든 후속 판단의 전제):**

1. **저장소 전역에 마크다운 클릭형 링크 `[..](..)` 가 0건이다.** 실측: `grep -rnoI "\]([^)]*\.md[^)]*)"` = 0 (fixtures·dogfooding 제외). **모든 상호 참조는 "루트 상대 산문 포인터"**다 — 예: `` `specs/01-runtime.md` §3 ``, `framework/core/structure.md §8`, `uaf/specs/01-entry.md §3.1`. 이는 백틱 코드스팬 또는 평문 경로 문자열이며, 링크 체커가 아니라 **경로 문자열의 물리 정합**이 "깨짐"의 기준이다.
2. **이미지/자산 링크 0건** (png/jpg/svg/gif 참조 0). 이미지 링크 깨짐 위험은 실측상 없다.
3. **참조는 전부 "저장소 루트 = UAHF 루트" 가정으로 작성**되었다. 이동 후 이 가정이 유지되는지(= UAHF 워크스페이스 서브루트를 참조 기준으로 볼 것인지)가 **문서 수정 범위를 10배 이상 좌우하는 단일 최대 결정**이다 (§7 에스컬레이션 1).

### 4.0 "깨짐"의 정의 (핵심)

참조는 전부 **루트 상대 산문 포인터**이므로(§0), 이동 후 다음 두 해석 중 무엇을 채택하느냐가 수정 범위를 결정한다:

- **해석 (a) — UAHF 서브루트 기준** (Planner 추천): `runtime/uahf/`를 UAHF 워크스페이스 루트로 보고, uahf 내부 문서의 `framework/…`·`specs/…` 포인터를 그 서브루트 상대로 해석한다. → uahf 내부에 **머무는** 참조는 **무편집으로 유효 유지**. 편집 대상은 uahf **경계를 넘는** 참조뿐.
- **해석 (b) — 저장소 루트 절대**: 모든 포인터를 저장소 루트 절대로 본다. → `framework/…` 전건이 `runtime/uahf/framework/…`로, `specs/…` 전건이 `runtime/uahf/specs/…`로 바뀌어야 하며 **UAHF 정본 문서 본문을 대량 편집**해야 한다.

**해석 (b)는 브리프의 자체 제약 "기존 UAHF 수정 금지"·"UAHF 정본 무수정"과 정면 충돌한다** — framework 내부 자기참조만 1,362건(framework/), specs 내부 947건을 편집하면 곧 UAHF 정본 대량 개변이다. 따라서 Planner는 **해석 (a)를 강하게 추천**한다. 단, 이 채택은 Advisor 권한이다 (§7 에스컬레이션 1).

## §5. 위험 요소

### A. 비git 비가역성 (최우선) — 이동 실패 시 복구 불가

- 실측: `.git` 부재. mv/이동은 undo 없음. 부분 실패 시 트리가 반쯤 깨진 상태로 남는다.
- **완화(강력 추천, 사용자 승인 필요)**:
  - (A-1) **선(先) `git init` + 초기 커밋** — 이행 전 저장소를 버전관리에 넣으면 전 이동이 **완전 되돌림 가능**해진다. 어떤 기존 파일 내용도 바꾸지 않고 `.git/`만 추가하는 최소 침습 안전망. append-only 데이터의 MD5 추적과도 상충하지 않는다(오히려 이력 보증 강화). **단, 저장소에 VCS를 도입하는 것은 "디렉터리·마크다운 이동" 범위를 넘으므로 사용자 승인 항목**(§7 에스컬레이션 7).
  - (A-2) git 미도입 시 **전체 스냅샷 사본** — 이행 전 저장소 전체를 타임스탬프 백업 디렉터리로 복사(예: `../uahf-backup-2026-07-09/`). 최소 요구.
  - (A-3) **스테이징 이행** — 목표 트리를 새 디렉터리에 조립(복사) 후 검증 통과 시 교체. 원본은 검증 완료까지 보존.
  - (A-4) **단계 분리(phased)** — §대안 A 참조. 바이트-청정 이동(framework/specs/dogfooding/docs)을 먼저, uaf 분할(참조·데이터 stale 유발)을 나중 별도 승인 단계로.

### B. append-only 데이터 딜레마 (§4.2 실측)

- 레코드는 **바이트 무변경 블록 이동**이 원칙. 그러나 내부 stale 경로가 존재.
- 해석(a) 채택 시 `framework/…` 내부 자기참조는 유효 유지(무편집). **남는 문제는 `uaf/…` 참조**: memory store 6 + discovery-data 다수가 uaf 분할로 stale.
- **선택지(Planner 결정 아님 — Advisor 에스컬레이션)**: (i) stale 허용(데이터는 역사적 스냅샷이므로 당시 경로 그대로 두고 무편집·MD5 보존) / (ii) supersede 신규 레코드 append(구 레코드 불변 유지 + 신 경로 레코드 추가) / (iii) 데이터 편집(MD5 불변 포기 — **비추천**). → §7 에스컬레이션 1.

## §6. Architecture 검토 (현재 정본 정합/충돌)

### 6.1 두 개의 "Layer" 축 — 충돌이 아니라 직교

- **UAHF 6-Layer**(현 ARCHITECTURE v0.2 §5): Presentation→Workflow→Agent→Runtime→Core→Adapter + Memory Cross-cutting. 이는 **UAHF 내부** 아키텍처 축이다. Glossary INV-3 "Layer 정확히 6개".
- **사용자 신규 최상위 Layer**: entry/discovery/planning/runtime/knowledge. 이는 **UAF 파이프라인 단계** 축이다 — `uaf/ARCHITECTURE.md §2`의 6요소(Entry Layer→Entry Resolution→Project Discovery→Project Contract→UAHF→Execution)와 정합.
- **핵심 정합 논리**: 두 "Layer"는 **다른 축**이다. 신규 최상위 Layer는 UAHF의 6-Layer를 늘리지 않는다(INV-3 무촉). uaf/ARCHITECTURE는 이미 "Entry·Discovery는 UAHF 6-Layer **외부**의 UAF 레벨 구조"라고 선언 → **선례 있음, 충돌 아님**. 단 **"Layer"라는 동일 단어의 이중 사용**은 문서상 반드시 구분 서술 필요(위험 D와 연결).

### 6.2 원칙 11 "UAHF는 Runtime Layer의 구현체" ↔ pc-uahf-001

- pc-uahf-001 `architectureDirection`: "UAF 레벨 파이프라인은 UAHF 6-Layer **외부** — 접점은 Project Contract 하나". 사용자 제안(`runtime/uahf/`)은 이 결정을 **물리 구조로 구현**한다 — UAHF가 runtime/ 아래 uahf/로 귀속되고, Contract는 planning/ 경계로 분리. **정합.**

### 6.3 충돌 지점 — "무수정" 제약 vs 참조 정합

- pc-uahf-001 `constraints`: **"UAHF 정본 무수정 — UAF와의 접점은 Project Contract 하나(UAF-INV ①)"**, **"물리 데이터 append-only"**, **"Core 경계 금지 토큰 0(C-3)"**.
- 이동은 **내용 무수정**을 지키지만, **참조 정합**(깨지는 링크 0)을 동시에 요구하면 §4.1의 UAHF 정본 내부 `uaf/` 참조 121건 + append-only 데이터 내부 `uaf/` 참조를 편집해야 하고 → **무수정·append-only 제약 위반.** 이 두 요구(무수정 ∧ 무깨짐)는 uaf/ 분할 지점에서 **동시 충족 불가**. → §7 에스컬레이션 1·4. **이것이 이번 이행의 최대 아키텍처 긴장이다.**
- 반면 framework/·specs/ 이동은 해석(a) 하에서 **무수정·append-only·무깨짐을 동시 충족**한다(서브루트 내부 참조 유지). → 이 부분은 아키텍처적으로 청정.

### 6.4 structure.md §8의 지위

- `framework/core/structure.md §8`이 "현재 물리 정본 트리"다. 이동 후 이 트리는 `runtime/uahf/framework/…` 실재와 어긋난다. 해석(a) 하에서 structure.md는 uahf 서브루트를 기준으로 하므로 **§8 트리(framework/ 상대)는 그대로 유효**. 단 §8 line 232-234의 `uaf/specs/01·02·03` 참조는 uaf 분할로 stale → **UAHF 정본 무수정과 충돌**(§6.3). structure.md 자신이 "개정은 Advisor 승인 + §9 이력 기록으로만"이라고 명시하므로, 이 문서 편집은 반드시 Advisor 게이트를 거쳐야 한다.

## §대안 (Alternative Proposals — 사용자 명시 요구, 최소 1개)

### 대안 A (Planner 추천) — "자기완결 uahf 서브루트 + 2단계 이행"

**핵심**: 사용자 제안 구조를 **그대로 채택하되**, 두 가지를 확정·순서화한다.

1. **참조 기준 = UAHF 서브루트(해석 a) 공식 채택.** `runtime/uahf/`를 자기완결 워크스페이스 루트로 규정 → uahf 내부 문서·데이터의 `framework/…`·`specs/…` 포인터는 **무편집으로 유효**. 이로써 (i) UAHF 정본 무수정 준수, (ii) append-only MD5 보존, (iii) 원칙 2 "각 Layer 독립 사용 가능" 실현. **framework/·specs/·dogfooding/·docs(uahf-dev) 이동이 바이트-청정해진다.**
2. **2단계 이행으로 비가역성·충돌 격리**:
   - **Phase 1 (청정)**: `git init`(A-1) → framework/→runtime/uahf/framework/, specs/→runtime/uahf/specs/, dogfooding/→runtime/uahf/dogfooding/, docs(uahf-dev)→runtime/uahf/docs/. 신규 Layer 스켈레톤(runtime·knowledge·entry·discovery·planning의 .claude/README/ARCH/ROADMAP) **스텁** 생성. **UAHF 정본·데이터 무편집.** 여기까지 무깨짐·무수정 동시 충족.
   - **Phase 2 (충돌 해소)**: uaf/ → entry/discovery/planning 분할. 여기서 발생하는 UAHF 정본 내부 `uaf/` 참조(121)와 append-only 데이터 내부 `uaf/` 참조를 **어떻게 처리할지 Advisor 결정**(무수정 예외 승인 / supersede append / stale 허용) 후 실행.

**장점**: 위험 A·B·C·의 정본충돌을 Phase 경계로 격리. 대부분(framework/specs/dogfooding)이 무편집 이동으로 안전. 되돌림 가능(git).
**단점**: 2단계라 완결까지 시간 소요. "서브루트 기준" 규약을 root ARCHITECTURE에 신설해야 함(신규 저술).

### 대안 B — "uaf/ 미분할 보존(형제 유지)"

`framework/`·`specs/`만 `runtime/uahf/`로 이동하고, `uaf/`는 **분할하지 않고 uaf/를 그대로 최상위 유지**(또는 uaf/ 통째로 runtime/ 형제 위치에 보존). entry/discovery/planning은 **논리 뷰(README 포인터)**로만 표현.

**장점**: uaf/ 분할이 유발하는 정본·데이터 stale(§4.3 최난부)을 **원천 회피** — 무수정·append-only·무깨짐 전부 충족. 위험 B·C·§6.3 충돌이 사라진다.
**단점**: 사용자 원칙 1·2(Layer 중심·독립 사용)를 uaf 3분할로는 실현 못 함 — **사용자 제안의 명시적 형태와 어긋남.** 사용자 의도(entry/discovery/planning 독립 Layer)를 절반만 충족.

### 대안 C — "심볼릭 뷰/별칭" (기각)

이동 없이 새 Layer 경로를 심볼릭 링크로 구성. **기각 근거**: 비git·크로스플랫폼(Windows) 환경에서 심링크 이식성·안정성 낮고, "물리 재구성으로 다시 안 바꾼다"는 목적과 배치. append-only 추적과도 충돌.

### 추천 최종안

**대안 A**를 추천한다. 사용자 제안 구조를 **완전히 실현**하면서(대안 B의 한계 없음), 위험 A(git으로 가역화)·B·C·§6.3 충돌을 **Phase 2로 격리**해 통제한다. 단 **참조 기준 채택(해석 a)·git 도입·2단계 순서·Phase 2 정본충돌 처리방식**은 전부 **Advisor 채택·사용자 승인 사항**이다(§7).

## §7. Advisor 에스컬레이션 (사용자 결정 필요) — Planner 결정 금지 항목

O4(추측 금지) 준수. 아래는 Planner가 임의 확정하지 않고 상신한다.

1. **[최우선] 참조 기준 결정 — 해석(a) 서브루트 vs (b) 루트절대.** 문서 수정 규모를 10배 이상 좌우. 해석(b)는 "UAHF 무수정" 제약과 충돌. Planner 추천 = (a). → 이 결정이 §4·§5-B·§6.3 전부의 전제.
2. **[최우선] append-only 데이터 stale 경로 처리(위험 B).** uaf 분할로 stale되는 memory store 6·discovery-data 다수의 `uaf/` 참조. (i)stale 허용·무편집(MD5 보존) / (ii)supersede append / (iii)편집(MD5 포기·비추천) 중 택1. Planner 결정 금지.
3. **신규 Layer 문서 범위(위험 F).** entry·discovery·planning·runtime·knowledge의 .claude/README/ARCHITECTURE/ROADMAP + knowledge 8하위 = **신규 저술**. "Directory·Markdown 이동만" 범위 밖. **스텁 vs 완전 저술**, 그리고 이것을 v1.2.1에 포함할지 후속으로 뺄지.
4. **UAHF 정본 내부 `uaf/` 참조 121건 처리(위험 C-b·§6.3).** framework/{contract,entry,discovery}-binding.md·structure.md §8이 uaf/specs를 참조. "무수정"과 "무깨짐"이 여기서 동시 충족 불가. 무수정 예외 승인 여부. `uaf/ARCHITECTURE.md`의 귀속 Layer(GAP 1.2)도 여기서.
5. **빈 4디렉터리 모순(위험 E3).** design/templates/tests/research를 root 유지 / runtime/uahf 하위 / 양쪽 중 어디로. (전부 빈 디렉터리 — 저위험이나 정본 위치 확정 필요.)
6. **GAP 대상 확정**: specs/→runtime/uahf/specs/ (E1) · dogfooding/→runtime/uahf/dogfooding/ (E2) · runtime/uahf/memory·lessons 원천(E4) · planning/contracts 원천(E5) · knowledge/glossary 원천=specs/00-glossary 복사 vs 참조(E6) · docs 분할(§1.4). Planner 추천안 채택 여부.
7. **`git init` 안전망 도입(위험 A-1) 및 루트 디렉터리명 변경 여부.** VCS 도입은 "이동만" 범위를 넘으나 비가역성 최대 완화책. 승인 여부. 루트명 `Universal-Agentic-Framework`로 변경할지(현 물리 디렉터리명 유지 권장).

## §8. 위험 Top 3 (경영 요약)
