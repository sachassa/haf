## §0. 이 문서의 위치와 정본 경계

- **이 문서는 시연 절차서다.** 시연 3종을 **어떻게 수행하고 무엇으로 판정하는가**의 절차·입력·기대·판정 문장·기록 포맷을 정의한다. 시연의 실제 **수행 기록**은 별도 산출물(시연 수행 기록, Task A7)이, **독립 판정**은 검증 단계(Verifier, Task A8, verification-checklist.md 게이트 C = CP2)가 담당한다. 이 절차서는 그 두 작업의 입력이다.
- **정본은 specs/01-runtime.md §7(완료 기준)·§3(Core Contract)과 확정 Core 4종 문서다.** 이 절차서는 그 계약·완료 기준을 **재정의·확장하지 않는다**. 계약 요소·판정 문장·필드는 § 포인터로만 참조하고, 필수/선택 표기는 정본 그대로 보존한다 (Lesson 후보 — session-handoff-v0.2 §1.5 항목 2).
- **필드 소속 명시.** 인용하는 필드·reason 코드는 소속 계약을 § 포인터로 명시한다 — 유사한 실패 구조를 가진 다른 계약의 필드명을 끌어오지 않는다 (Lesson 후보 — session-handoff-v0.2 §1.5 항목 1). 예: Bootstrap 실패 reason(`MissingRequired`)과 Load Config 실패 reason(`SchemaViolation`)은 각각 01 §3.1-C·§3.1-B 소속이며 혼입하지 않는다.
- **물리 실현 지점 비하드코딩.** 시연 절차는 추상 Runtime 연산(Register/Resolve/Replace/Bootstrap/Load Config)만으로 성립한다. 각 연산이 물리적으로 실현·관측되는 지점(실제 파일·세션 표면 등)은 이 절차서에 **하드코딩하지 않는다**. 물리 실현 지점은 `framework/adapters/` 경계의 Adapter Binding 문서 소관이며 (01 §4·§4.1), 수행 기록(A7)이 그 문서를 참조해 각 절차 단계의 물리 지점을 기입한다 (§4).
- **동시 작성 산출물 불인용 (07 R2).** 같은 병렬 집합에서 동시 작성 중인 Adapter Binding 산출물(framework/adapters/ 경계)의 미완성 내용을 인용·추측하지 않는다. 물리 지점이 필요한 자리에는 "Adapter Binding 문서 소관" 포인터만 둔다 (§4, §0 위 항목).
- **토큰 절제.** 이 문서는 `docs/` 소속이라 Core 경계 금지 토큰 규칙(structure.md §5 C-3)의 직접 대상은 아니다. 그러나 시연 시나리오는 **추상 계약 수준**으로 구성하며 특정 AI·언어·툴체인·직렬화 형식 토큰을 넣지 않는다 — 절차가 오직 Core 계약만으로 성립함을 보이기 위함이다.
- **라벨 주의 (새 용어 신설 없음).** 본 문서가 쓰는 "시연 ①/②/③", "판정 문장", "기록 포맷", 기록 포맷의 필드 이름(관측 결과·근거·수행 단계 로그·수행 물리 지점)은 조직 편의를 위한 **서술 라벨**이며 Glossary 표제어가 아니다 — 정본 용어처럼 신설·확장하지 않는다 (verification-checklist.md §0의 "게이트 A~D" 라벨 처리와 동형). 계약 용어(Module / Module Manifest / Runtime Context / Config / 활성 바인딩 / effective config / state 등)와 판정 값(충족/위반/판정 불가)은 전부 Glossary·01·Core 4종 정본에서 인용한다.

## §1. 목적과 범위

이 절차서의 책임은 세 가지다.

- v0.3 시연 3종 각각에 대해 **절차 단계 / 사용할 입력 / 기대 결과 / 판정 문장 / 기록 포맷**을 정의한다 (§6·§7·§8).
- 시연의 판정 문장을 01 §7 완료 기준의 해당 문장과 **1:1 대응**시키고, 산출물 스캔·대조 방식인 나머지 2건이 검증 단계(Verifier, Task A8) 소관임을 명시한다 (§2).
- 시연 수행 기록(A7)이 그대로 채우면 되는 **공통 기록 포맷**(§3), 물리 수행 지점 경계(§4), 실패 처리 규칙(§5)을 정의한다.

시연 3종 (done 대상):

- **시연 ① 단독 기동** — 필수 계약만 만족하는 최소 Module 집합만 등록한 Runtime이 Bootstrap되어 state=Ready(또는 Degraded)로 기동됨을 보인다. 근거: lifecycle.md §2.1·§3.1(INV-2), module-registry.md §2.1·§2.2.
- **시연 ② 모듈 교체** — 한 contract의 Module A를 동일 contract의 Module B로 Replace해도 소비자 참조 변경 0으로 Resolve가 Module B를 반환함을 보인다. 근거: module-registry.md §2.3·§3.
- **시연 ③ Config 병합** — 3스코프(Global/Project/Module)가 우선순위대로 병합되어 effective config가 config-schema.md 규칙과 일치함을 보인다. 근거: config-schema.md §4·§6.

이 절차서는 위 세 시연의 **절차와 판정 기준**만 정의한다. 시연의 실제 관측·판정·승인은 A7(수행 기록)·A8(검증 단계)·Advisor(최종 승인)의 소관이다 (§5, verification-checklist.md 게이트 C·D).

## §2. 시연 3종과 01 §7 완료 기준의 1:1 대응 (done 2)

01 §7 완료 기준은 5건의 시연 가능 문장이다. 그중 3건은 Runtime 연산을 실제 수행·관측하는 **재현형 시연**이고(본 절차서 소관), 2건은 산출물을 스캔·대조하는 **검증형**이다(검증 단계 소관).

| 01 §7 완료 기준 (인용) | 방식 | 소관 | 본 절차서 대응 |
|---|---|---|---|
| **단독 사용 시연.** 필수 계약만 만족하는 최소 Module 집합만 등록한 Runtime이 Bootstrap되어 state=Ready(또는 Degraded)로 기동됨을 보인다 (INV-2). | 재현(Bootstrap·Resolve 수행·관측) | 본 절차서 (수행 A7 / 판정 A8) | **시연 ①** (§6) 판정 문장 |
| **교체 시연.** 한 contract의 Module A를 동일 contract의 Module B로 Replace해도, 계약 소비자의 코드·규격 변경 0으로 Resolve가 Module B를 반환하고 동작이 유지됨을 보인다 (INV-1, ARCHITECTURE 3.2 Modular 검증). | 재현(Replace 전후 Resolve 대조) | 본 절차서 (수행 A7 / 판정 A8) | **시연 ②** (§7) 판정 문장 |
| **Config 일치 시연.** 선언한 스코프(Global/Project/Module)가 우선순위(Module > Project > Global)대로 병합되어 effective config가 §3.2-B 규격과 일치함을 보인다 (INV-5). | 재현(Load Config 수행·대조) | 본 절차서 (수행 A7 / 판정 A8) | **시연 ③** (§8) 판정 문장 |
| **Core AI 비의존 시연.** Core 디렉터리 전체를 스캔해 AI 모델명·제품 기능 참조가 0건임을 보인다 (INV-4). | 스캔(전수 토큰 스캔) | **검증 단계 (Verifier, Task A8)** — verification-checklist.md §5.3 VT-4 전수 스캔 | 본 절차서 비대상 (아래 주) |
| **경계 시연.** Runtime이 Agent Lifecycle 7단계를 정의하지 않고 호스팅 계약만 노출함을 보인다 (INV-6). | 대조(산출물 규격·경계 대조) | **검증 단계 (Verifier, Task A8)** — verification-checklist.md §5.1 VT-4 경계 / VT-3 규격 준수 (lifecycle.md §4가 단계 전이 규칙 0건임을 대조; 정확한 검증 유형 지정은 A8 재량) | 본 절차서 비대상 (아래 주) |

**주 (2건이 본 절차서 비대상인 이유).** Core AI 비의존 시연·경계 시연은 Runtime 연산을 수행해 상태를 관측하는 재현형이 아니라, **산출물을 스캔·대조**하는 방식이다 (01 §7 검증 방법 3·5행). 따라서 이 절차서는 이 2건의 절차 단계를 두지 않고, verification-checklist.md의 검증 유형(VT-4 전수 스캔 / VT-3 규격 대조)으로 검증 단계(Verifier, Task A8)가 수행함을 명시한다. 세 재현형 시연의 판정 문장(§6·§7·§8-D)은 위 표의 해당 01 §7 문장을 **그대로 인용**하며 재정의하지 않는다.

## §4. 물리 수행 지점 경계 (done 4)

- 시연 절차(§6·§7·§8)의 모든 단계는 **추상 Runtime 연산**으로 서술된다. 어떤 단계도 실제 파일 경로·세션 표면·직렬화 형식 같은 물리 지점을 명시하지 않는다.
- 물리 실현 지점(Register/Resolve/Replace/Bootstrap/Load Config가 어디에서 어떻게 수행·관측되는가)은 `framework/adapters/` 경계의 **Adapter Binding 문서 소관**이다 (01 §4 Adapter Binding, §4.1 바인딩 표, structure.md §6 Adapter 경계 행).
- **수행 기록(A7)의 기입 방식.** A7은 §3 기록 포맷의 "수행 물리 지점" 필드에, 각 절차 단계가 물리적으로 실현된 지점을 **Adapter Binding 문서를 참조하여** 기입한다. 절차서는 그 지점을 미리 확정·하드코딩하지 않는다.
- **07 R2 준수.** 같은 병렬 집합에서 동시 작성 중인 Adapter Binding 산출물(framework/adapters/ 경계)의 미완성 내용을 이 절차서에서 인용·추측하지 않는다. 물리 지점이 필요한 자리는 위 포인터로만 처리한다.

이 경계로 인해, 이 절차서는 대상 환경이 바뀌어도 (01 §4.2 이식 교체 지점) 유지된다 — 바뀌는 것은 "수행 물리 지점"의 실현뿐이고, 절차 단계·판정 문장·기록 포맷은 그대로다.

## §5. 실패 처리 규칙 (done 6)

시연이 기대 결과와 **다르게 관측될 때**의 처리 규칙이다.

1. **은폐 없이 그대로 기록한다.** 관측이 기대와 달라도 실제 관측을 §3 기록 포맷의 "근거 (관측한 것)"에 그대로 남긴다. 실패·불일치를 숨기지 않는다 (Worker 금지 사항 — 실패 은폐 금지, 02 O5).
2. **판정 문장을 위반으로 표기한다.** 기대와 다르게 관측되면 해당 시연의 "관측 결과"를 **위반**으로 표기한다 (판정 값 정본: verification-checklist.md §1). 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기하며, 판정 불가를 충족으로 위장하지 않는다 (06 V6).
3. **재작업 여부 판단은 게이트 소관이다.** 이 절차서와 수행 기록(A7)은 관측·기록까지만 한다. 위반·판정 불가의 **재작업 여부 판단**은 검증 단계(Verifier, 게이트 C = CP2)와 Advisor(게이트 D = CP3)의 소관이다 (verification-checklist.md §5·§6, 03 §3.1-A/§3.1-B). A7·절차서가 스스로 통과 처리하거나 재작업을 결정하지 않는다.
4. **Runtime 연산 자체의 실패 보고.** 시연 중 Runtime 연산이 실패하면(예: Bootstrap이 필수 계약 미해소로 `MissingRequired`, Replace가 `ContractMismatch`), 그 실패는 01 §3.2-D 공통 Failure Report 구조(`operation`/`target`/`reason`/`location`)로 관측·기록한다. reason 코드의 소속 연산을 § 포인터로 명시한다 (Register/Replace reason은 module-registry.md §5·01 §3.1-A, Bootstrap reason은 lifecycle.md §2.1·01 §3.1-C, Load Config reason은 config-schema.md §5·01 §3.1-B). 이때 연산 실패가 시연의 기대였는지(음성 시연) 아니면 예기치 못한 실패인지를 근거에 구분해 기록한다.

## §6. 시연 ① 단독 기동 (Bootstrap → Ready/Degraded)

목표: 필수 계약만 만족하는 **최소 Module 집합**만 등록한 Runtime이 Bootstrap되어 부분 집합만으로 기동됨을 보인다 (부분 집합 기동, INV-2 / lifecycle.md §3.1). 근거 연산: Register(module-registry.md §2.1) · Resolve(§2.2) · Bootstrap(lifecycle.md §2.1).

### (A) 절차 단계

1. **최소 집합 등록.** 필수 계약을 만족하는 최소 Module 집합의 각 Manifest를 Register한다 (module-registry.md §2.1). 각 Manifest의 필수 필드(`id`·`contract`·`version`·`entrypoint`)를 확인하고 `id` 유일성을 확인한다.
2. **Bootstrap 호출.** effective config와 등록된 Module 집합을 입력으로 Bootstrap을 호출한다 (lifecycle.md §2.1 입력).
3. **필수 계약 Resolve 관측.** Bootstrap이 모든 **필수(required)** 계약을 Resolve하는지 관측한다 (lifecycle.md §2.1 완료 조건). 각 필수 계약의 Resolve가 활성 바인딩 정확히 1로 유일한 핸들을 반환하는지 확인한다 (module-registry.md §2.2, INV-3). `requires`가 있는 Module은 그 의존 contract가 재귀적으로 해소되는지 확인한다.
4. **state 관측.** 산출된 Runtime Context의 `state`를 관측한다 (lifecycle.md §3).
   - 필수 계약 전부 해소 + 선택 계약 누락 없음 → **`Ready`**.
   - 필수 계약 전부 해소 + 선택 계약 일부 누락 → **`Degraded`** (Ready에 준함, Failed 아님, INV-2 / lifecycle.md §3.1).
   - (대조) 필수 계약 미해소면 → `Failed`, Bootstrap 실패(reason=`MissingRequired`, lifecycle.md §2.1). 이 경우는 단독 기동 성공이 아니다.

### (B) 사용할 입력 (일반형 예시 — module-manifest.md §2 7필드, 필수/선택 표기 보존)

최소 집합 = 필수 contract를 만족하는 Module만. 예시 Manifest 2건(필수 4필드 + 필요한 선택 필드만; 선택 필드는 기본값이면 생략):

| `id` (필수) | `contract` (필수) | `version` (필수) | `requires` (선택·기본 없음) | `entrypoint` (필수) | `replaceable` (선택·기본 true) |
|---|---|---|---|---|---|
| `dispatcher` | `DispatchPort` | `1.0.0` | `StorageContract` | (추상 참조 — 구체 해소는 Adapter Binding 문서 소관, 01 §4) | (생략 = 기본 true) |
| `storage-provider` | `StorageContract` | `1.0.0` | (생략 = 기본 없음) | (추상 참조 — Adapter Binding 문서 소관) | (생략 = 기본 true) |

- 필수 계약: `DispatchPort`, `StorageContract` — 둘 다 위 최소 집합이 활성 바인딩을 제공한다.
- 선택 계약(선언되었으나 provider 미등록, 예시): `MetricsPort` — 이 계약의 provider를 등록하지 않으면 그 부재는 `Degraded`로 처리된다 (INV-2).
- `entrypoint`는 **추상 참조**다 — 물리 진입점은 Manifest에 하드코딩하지 않는다 (module-manifest.md §3 `entrypoint` 지침, §4 물리 지점 경계).
- 예시 식별자(`dispatcher`·`DispatchPort`·`StorageContract`·`MetricsPort`)는 일반형이며 module-manifest.md §3 예시 어휘 재사용이다. 특정 AI·언어·툴체인·제품 토큰이 아니다.

### (C) 기대 결과

- Bootstrap이 필수 계약(`DispatchPort`·`StorageContract`)을 전부 Resolve한다. 각 Resolve는 유일한 핸들을 반환한다 (활성 바인딩 1, INV-3).
- Runtime Context의 `state`가 **`Ready`**(선택 계약 누락 없음) 또는 **`Degraded`**(선택 계약 `MetricsPort` 미해소)로 산출된다 — 두 경우 모두 기동 성공이며 `Failed`가 아니다 (INV-2).
- 즉, 최소 Module 집합만으로 Runtime이 기동된다 — 단독 사용(부분 집합 기동)이 성립한다.

### (D) 판정 문장 (01 §7 "단독 사용 시연" 인용 — 1:1 대응)

> 필수 계약만 만족하는 최소 Module 집합만 등록한 Runtime이 Bootstrap되어 state=Ready(또는 Degraded)로 기동됨을 보인다 (INV-2).

### (E) 기록 포맷 (§3 인스턴스 — A7이 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §6-D 문장을 A7이 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (Resolve가 반환한 핸들·module id, `state` 값, 선택 계약 `MetricsPort` 해소 여부) |
| 수행 단계 로그 | (§6-A 단계 1~4의 수행·관측 로그) |
| 수행 물리 지점 | (Register/Bootstrap/Resolve가 실현·관측된 지점 — Adapter Binding 문서 참조로 기입, §4) |

## §7. 시연 ② 모듈 교체 (동일 contract Replace — 소비자 참조 변경 0)

목표: 한 contract의 Module A를 **동일 contract**의 Module B로 Replace해도 계약 소비자 참조가 변경 0으로 유지되고, 교체 후 Resolve가 Module B를 반환함을 보인다 (INV-1). 근거: module-registry.md §2.3(Replace) + §3(R-교체-1·R-바인딩-1·R-참조-1), 예시 어휘 01 §8 예1(동일 contract 백엔드 스왑).

### (A) 절차 단계 (module-registry.md §2.3·§3 규칙을 절차 단계로 이관)

1. **교체 전 Resolve 관측.** 대상 contract를 Resolve해 현재 활성 Module(A)의 핸들을 얻는다 — 활성 바인딩이 정확히 1임을 확인한다 (module-registry.md §2.2, INV-3 / R-바인딩-1).
2. **소비자 참조 대상 확인.** 소비자가 참조하는 것이 **contract id**이지 특정 module id가 아님을 확인한다 (module-registry.md §3 R-참조-1 규칙 1; 소비자의 `requires`는 contract에 건다 — module-manifest.md §4). 
3. **동일 contract 확인.** 새 Manifest(B)의 `contract`가 대상 contract와 **동일**한지 확인한다. 다르면 교체하지 않고 `ContractMismatch`로 거부된다 (module-registry.md §2.3 규칙 1, INV-1).
4. **교체 가능 확인.** 대상의 현재 활성 Module(A)이 `replaceable=false`가 아님을 확인한다. `false`면 `NotReplaceable`로 거부된다 (module-registry.md §2.3 규칙 2).
5. **Replace 수행.** Replace(대상 contract id, Manifest_B)를 호출한다. 새 Module B 활성화와 이전 Module A 비활성화가 **한 교체 단위**로 수행되어, 교체 중에도 활성 바인딩이 1을 유지하는지 확인한다 (module-registry.md §3 R-바인딩-1). 출력은 이전 module id → 새 module id 쌍이다 (§2.3 출력).
6. **교체 후 Resolve 관측.** 대상 contract를 다시 Resolve해 반환 핸들이 Module B인지 확인한다 (module-registry.md §2.3 규칙 4).
7. **소비자 참조 변경 대조.** 교체 전후로 소비자의 Resolve 대상(contract id)이 동일함을 대조한다 — contract id가 안정적이므로(INV-7) 소비자 경로는 변하지 않는다. 소비자 참조 변경이 **0**임을 확인한다 (module-registry.md §3 R-참조-1 규칙 2). 변경이 0이 아니면(소비자가 특정 module id에 직접 의존) INV-1 위반 신호이므로, 추측으로 우회하지 않고 §5 규칙에 따라 위반으로 기록하고 게이트(Advisor·Verifier)로 에스컬레이션한다 (R-참조-1 규칙 3).

### (B) 사용할 입력 (일반형 예시 — 01 §8 예1 백엔드 스왑 어휘 재사용)

| 역할 | `id` (필수) | `contract` (필수) | `version` (필수) | `replaceable` (선택·기본 true) |
|---|---|---|---|---|
| 교체 전 Module A | `memory-provider-a` | `MemoryServiceInterface` | `1.0.0` | (생략 = 기본 true) |
| 교체 후 Module B | `memory-provider-b` | `MemoryServiceInterface` | `2.0.0` | (생략 = 기본 true) |

- 소비자(예시): contract `MemoryServiceInterface`에 `requires`로 의존하는 임의의 Module. 소비자는 **contract id**만 참조하고 특정 module id를 참조하지 않는다.
- A와 B의 `contract`는 동일(`MemoryServiceInterface`)하다 — 교체는 동일 contract 내에서만 성립한다 (INV-1). `id`·`version`만 다르다.
- 예시 어휘는 01 §8 예1(MemoryServiceInterface 백엔드 스왑)의 재사용이다. `MemoryServiceInterface`는 Glossary §3.2-C의 계약 용어(추상)이며 특정 AI·언어·툴체인 제품 토큰이 아니다. 저장 백엔드 종류 같은 물리 실현은 Adapter Binding 문서 소관이다 (01 §5·§8 예1, §4).
- `entrypoint`(필수)는 위 표에서 생략 표기했으나 실제 Manifest에는 존재하며 추상 참조다 (module-manifest.md §2·§3). 교체 판정과 무관하므로 표에서 생략했다.

### (C) 기대 결과

- 교체 전 Resolve(`MemoryServiceInterface`) = `memory-provider-a` 핸들. 교체 후 Resolve(`MemoryServiceInterface`) = `memory-provider-b` 핸들 (module-registry.md §2.3 규칙 4).
- 활성 바인딩은 교체 전·중·후 항상 정확히 1 (INV-3 / R-바인딩-1).
- 소비자 참조 변경 = **0** — 소비자는 여전히 동일 contract id를 Resolve하며 코드·규격 변경이 없다 (INV-1 / R-참조-1).
- 소비자 동작이 유지된다 (동일 contract이므로 계약 표면 불변).

### (D) 판정 문장 (01 §7 "교체 시연" 인용 — 1:1 대응)

> 한 contract의 Module A를 동일 contract의 Module B로 Replace해도, 계약 소비자의 코드·규격 변경 0으로 Resolve가 Module B를 반환하고 동작이 유지됨을 보인다 (INV-1, ARCHITECTURE 3.2 Modular 검증).

### (E) 기록 포맷 (§3 인스턴스 — A7이 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §7-D 문장을 A7이 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (교체 전·후 Resolve 반환 module id, 활성 바인딩 수, 소비자 참조 대상 contract id의 전후 동일성, 소비자 참조 변경 건수) |
| 수행 단계 로그 | (§7-A 단계 1~7의 수행·관측 로그 — 특히 단계 5 Replace 출력 쌍, 단계 6 Resolve 반환, 단계 7 참조 대조) |
| 수행 물리 지점 | (Resolve/Replace가 실현·관측된 지점 — Adapter Binding 문서 참조로 기입, §4) |

## §8. 시연 ③ Config 병합 (3스코프 → effective config)

목표: 선언한 3스코프(Global/Project/Module)가 우선순위(Module > Project > Global)대로 결정적으로 병합되어 effective config가 config-schema.md 규칙과 일치함을 보인다 (INV-5). 근거: config-schema.md §4(로딩 순서·우선순위·결정성·누락 스코프) + §6(병합 예시) + §5(Load Config 시그니처), 예시 어휘 01 §8 예2 / config-schema.md §6.

### (A) 절차 단계 (config-schema.md §4·§6 규칙을 절차 단계로 이관)

1. **스코프별 소스 준비.** Global / Project / Module 세 스코프의 Config 소스를 준비한다. Module scope 소스에는 `target`(대상 module id)이 있고 그 entries는 해당 Module 네임스페이스에 국한된다 (config-schema.md §2·§3).
2. **Load Config 호출.** 스코프별 소스 집합을 입력으로 Load Config를 호출한다 (config-schema.md §5, 01 §3.1-B 입력).
3. **로딩 순서 확인.** 로딩 순서가 Global → Project → Module임을 확인한다 (config-schema.md §4.1).
4. **우선순위 병합 관측.** 같은 키가 여러 스코프에 겹치면 우선순위 **Module > Project > Global**에 따라 높은 우선순위 스코프 값이 이기는지 관측한다 (config-schema.md §4.2). 한 스코프가 특정 키를 미지정하면 그 스코프는 그 키에 기여하지 않고 차하위 우선순위 값이 적용됨을 확인한다 (config-schema.md §4.4 누락/미지정 처리).
5. **결정성 확인.** 동일 입력으로 다시 병합하면 동일한 effective config가 나오는지 확인한다 (config-schema.md §4.3, INV-5).
6. **규격 일치 대조.** 산출된 effective config가 config-schema.md §2 추상 스키마·§4 우선순위 규칙과 일치하는지, 그리고 01 §3.2-B 규격과 일치하는지 대조한다 (config-schema.md §6 도출 결과 대조).

### (B) 사용할 입력 (일반형 예시 — config-schema.md §6 / 01 §8 예2 재현)

키 `verify.strict`에 대해 (config-schema.md §6 첫 예 재현):

| 스코프 | 기여 값 | 우선순위 지위 (config-schema.md §3) |
|---|---|---|
| Global scope | `verify.strict = false` (Framework 기본값) | 최저 |
| Project scope | `verify.strict = true` (이 프로젝트는 엄격 검증) | 중간 |
| Module scope (`target` = 예시 Module) | (미지정) | 최고 |

동형 예 (config-schema.md §6 둘째 예): 위 Module scope가 같은 키를 `verify.strict = false`로 **지정**하는 경우.

- 예시 키 `verify.strict`와 값은 config-schema.md §6·01 §8 예2의 재현이다. Framework 수준 예시 키이며 특정 AI·언어·툴체인 제품 토큰이 아니다.
- Config 소스의 물리 파일 위치·직렬화 형식은 이 절차서가 정하지 않는다 — Adapter Binding 문서 소관이다 (config-schema.md §8, 01 §4). 절차는 스코프·우선순위·결정성 계약만으로 성립한다.

### (C) 기대 결과

- **첫 예:** Module scope가 `verify.strict`를 미지정 → 그 키에 Module 기여 없음(§4.4) → 남은 스코프 중 최고 우선순위 Project가 이김 → effective config의 `verify.strict` = **`true`** (config-schema.md §6, 01 §8 예2와 동일 도출).
- **동형 예:** Module scope가 `verify.strict = false`를 지정 → 우선순위 Module > Project > Global에 따라 Module 값이 이김 → effective config의 `verify.strict` = **`false`** (config-schema.md §6 둘째 예).
- 두 예 모두 동일 입력에 대해 항상 동일 결과를 낸다 (결정성, INV-5). effective config는 config-schema.md §2 스키마·§4 우선순위 규칙과 일치한다.

### (D) 판정 문장 (01 §7 "Config 일치 시연" 인용 — 1:1 대응)

> 선언한 스코프(Global/Project/Module)가 우선순위(Module > Project > Global)대로 병합되어 effective config가 §3.2-B 규격과 일치함을 보인다 (INV-5).

(위 인용의 "§3.2-B"는 정본 01 §3.2-B를 가리킨다 — config-schema.md는 그 계약의 인스턴스다.)

### (E) 기록 포맷 (§3 인스턴스 — A7이 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §8-D 문장을 A7이 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (effective config의 `verify.strict` 값, 각 스코프 기여 값, 우선순위 승자, 동일 입력 재병합 결과의 일치 여부) |
| 수행 단계 로그 | (§8-A 단계 1~6의 수행·관측 로그 — 특히 단계 4 우선순위 승자, 단계 5 결정성, 단계 6 규격 대조) |

## §10. 정본 경계·용어 self-note (done 7)

- **재정의 없음.** 본 절차서의 모든 판정 문장은 01 §7 완료 기준의 인용이고, 모든 절차 단계·예시 입력·기대 결과는 01 §3·§8과 확정 Core 4종 문서(module-manifest.md·module-registry.md·config-schema.md·lifecycle.md)의 계약·규칙 인스턴스다. 어떤 계약 요소도 이 문서에서 진위가 확정되지 않는다 — 판정 기준은 항상 정본 §이다.
- **필수/선택 표기 보존.** 예시 Manifest 표는 필드의 필수/선택 표기(예: `requires` 선택·기본 없음, `replaceable` 선택·기본 true, `id`·`contract`·`version`·`entrypoint` 필수)를 정본 module-manifest.md §2 그대로 복제했다 (Lesson 후보 준수 — §1.5 항목 2).
- **필드 소속 명시.** reason 코드·필드는 소속 연산·계약을 § 포인터로 명시했다(§5 규칙 4) — 다른 계약의 필드명을 끌어오지 않았다 (Lesson 후보 준수 — §1.5 항목 1).
- **새 용어 신설 없음 (Glossary INV-4).** 사용한 계약 용어(Module / Module Manifest / contract / Register / Resolve / Replace / Bootstrap / Load Config / Runtime Context / effective config / state / 활성 바인딩 / 소비자 참조 / Config / scope)와 판정 값(충족/위반/판정 불가)은 전부 Glossary §3.2-C·§3.2-I·01·Core 4종·verification-checklist.md 정본에서 인용했다. "시연 ①/②/③", "판정 문장", "기록 포맷" 및 그 필드 이름은 조직 편의용 서술 라벨이며 Glossary 표제어가 아니다 (§0 라벨 주의).
- **물리 토큰 0건.** 시연 시나리오는 추상 계약 수준으로 구성했고 특정 AI·언어·툴체인·직렬화 형식·물리 경로 토큰을 두지 않았다. 물리 실현이 필요한 자리는 "Adapter Binding 문서 소관" 포인터로 처리했다 (§0, §4).
- **동시 작성 산출물 불인용 (07 R2).** 같은 병렬 집합에서 동시 작성 중인 Adapter Binding 산출물(framework/adapters/ 경계)을 인용·추측하지 않았다.

## §11. 요약 (한눈에 보기)

- 재현형 시연 3종의 절차·입력·기대·판정 문장·기록 포맷을 정의한다 — ① 단독 기동(Bootstrap→Ready/Degraded, INV-2) · ② 모듈 교체(동일 contract Replace, 소비자 참조 0, INV-1) · ③ Config 병합(3스코프 우선순위, INV-5).
- 세 판정 문장은 01 §7 완료 기준 3건을 1:1 인용한다. 나머지 2건(Core AI 비의존·경계)은 스캔·대조 방식이라 검증 단계(Verifier, Task A8) 소관이다 (§2).
- 각 절차 단계는 확정 Core 4종의 계약·규칙만 사용한다 — 교체는 module-registry.md §2.3·§3, Config는 config-schema.md §4·§6, 단독 기동은 lifecycle.md §2.1·§3.1. 예시 어휘는 01 §8·config-schema.md §6·module-manifest.md §3 재사용.
- 물리 수행 지점은 하드코딩하지 않는다 — Adapter Binding 문서 소관이며, 수행 기록(A7)이 그 문서를 참조해 기입한다 (§4, R2).
- 기록 포맷(§3)은 시연별로 판정 문장 / 관측 결과 / 근거 / 수행 단계 로그 / 수행 물리 지점 5필드를 갖는 표 구조 — A7이 그대로 채운다.
- 기대와 다르게 관측되면 은폐 없이 기록하고 위반으로 표기하며, 재작업 여부는 게이트(Advisor·Verifier) 소관이다 (§5).
