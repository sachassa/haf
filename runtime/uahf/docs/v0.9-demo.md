## §0. 이 문서의 위치·정본 경계·오케스트레이션 사실

### §0.1 위치·정본 경계

- **이 문서는 수행 기록이다.** 시연 1건을 **실제로 어떻게 수행했고 무엇이 관측됐는가**를 실값으로 기록한다. **독립 판정**은 검증 단계(Verifier = CP2)가, **최종 승인**은 Advisor(CP3)가 담당한다 — 본 기록은 그 판정의 입력이며 스스로 최종 승인을 내지 않는다(02 §3.2-A). 상태 라인이 "CP2 대기"인 이유다.
- **판정 문장은 전재다(재정의 0).** 각 판정의 판정 문장은 docs/v0.9-demo-procedure.md §8-D의 원문(12 §7·§3.2-C·ROADMAP v0.9 완료 조건 인용 + 예/아니오 환원)을 **그대로 옮긴다**. 새 판정 기준을 창설하지 않는다.
- **Work Graph 인스턴스는 문서 형태 구조화 섹션이다(v0.8-demo 관례 동형).** 본 기록 §4.3이 그 구조화 섹션이다. 새 데이터 백엔드 디렉터리를 신설하지 않았다.
- **소유 경계 준수(07 R4).** 본 작업(Task T10)의 소유 경계는 3산출물 — `docs/v0.9-demo.md`(이 파일)·`docs/v0.9-demo-fixtures/` 이하·`framework/adapters/claude/loop-data/v09-demo-scaffold.jsonl`(신규 1파일)이다. 라이브 표면(라이브 `.claude/`·`framework/core`·`framework/runtime`·`framework/adapters` 바인딩·`specs/`)·기존 loop-data 9파일·기존 memory-data 56건·scaffold-template/ 원본은 **수정하지 않았다** — 읽거나(정독) 복사 원본으로만 참조했다(§6.6 전수 대조).

### §0.2 오케스트레이션 사실 (Advisor 제공 — 수행 주체·역할 배치)

- **수행 주체.** Advisor(주 세션)가 시연 오케스트레이션(위임 수령 → Consult → Plan(단일 Task 채택) → Execute(T10 Worker) → Verify(독립 Verifier CP2) → Learn → Memory Update → Complete(CP3), loop-protocol §3)을 주관했다. loop-data 물리 기록은 T10 Worker Execute 산출이다.
- **실위임(모의 시연 아님, L-07·절차서 §7).** ④ Loop 1사이클의 CP2는 **독립 Verifier 서브에이전트(`.claude/agents/verifier.md`, DP-E8 `model: opus`)에 실위임**했다 — 설치를 수행한 Execute 주체(T10 Worker)와 검증 주체(Verifier)가 분리되어, 구현자가 자신의 설치 산출물을 최종 판정하지 못함을 실증한다(13 §3.2-A 검증 게이트 — CK-5의 핵심 성질). Verifier가 산출물(설치본·Install Manifest·loop-data·Uninstall 결과)을 직접 정독·재스캔해 CP2 리포트(`verify-scaffold.md`)를 산출한 뒤에만 그 판정을 전이 이벤트 seq5·§7에 기록했다.
- **단일 Task 분해 채택.** 시연은 상호 선행 의존이 있는 순차 단계(①~⑤)의 단일 흐름이므로 Work Graph는 단일 Task(T-SD)·병렬 집합 1개로 채택했다(과분해 금지 — 절차서 §5, 07 §3.2-A). Planner 초안(단일 Task)은 자명하여 Advisor가 분해 검사(done·interfaceContract 보유·소유 경계·비순환) 대조 후 채택했다(§4.2).
- **CP3.** Advisor가 시연 전체(설치→Bootstrap→루프·멱등·보호·제거)의 판정을 최종 승인하는 게이트(CP3, seq7)를 담당한다 — 본 기록은 그 입력이며 상태는 CP2 대기다.
- **actor=human 0건.** 시연 사이클 7 line 전건 actor ∈ {Advisor, Worker, Verifier}, human 0건(§5.2 실측 — 사람 개입 없음).
- **Memory Update 소관 구분(Advisor 결정 — 위임 constraint).** 시연 사이클의 Learn 산출(성공 경로 BP 후보)은 본 기록에 **후보로 기재만** 하며, **물리 memory-data append는 후속 승격 심사(T13) 소관**이다(v0.8 관행). 따라서 본 시연은 memory-data에 append하지 않았고(기존 56건 무변경), loop-data seq7 `ref`는 `record:mi` 실 id를 주장하지 않는다(§8.1·L-07 — 하지 않은 것을 했다고 쓰지 않는다).
- **`at`·timestamp = 순서 값(L-09).** loop-data `at`(1..7)·Install Manifest `timestamp`(order:1/order:2)는 사이클/설치 순서 값이며 물리 벽시계 시각 주장이 아니다(§8.2).

## §3. 관측 결과 판정 방식 (실측 대조)

각 판정의 "관측 결과"는 실측 산출물(설치본 파일·Install Manifest 실값·CK 재현·Bootstrap state·loop-data 7 line·멱등 diff·Uninstall 결과·해시)을 절차서 §6 기대 기록 명세·§8-D 예/아니오 환원과 대조해 판정한다. **기대와 전건 일치**하면 **충족**, 다르면 **위반**, 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기한다(절차서 §8-F). 특정 판정이 본 재현 범위 밖(마일스톤 CP2 정적 스캔 소관 — §3 AI 비의존·CP3 최종 승인)이면 **판정 유보**로 표기하고 충족으로 위장하지 않는다(§8-F-2·절차서 §2.2 배정). 본 시연은 정상 경로(통과 케이스)를 기대하며, 그 기대대로 관측되면 시연은 충족이다(§8-F-5). 시연 중 Scaffold 연산 자체의 수행 불능(연산 실패)은 관측되지 않았다(§8-F-6). 판정 값의 **최종 독립 판정**은 CP2(verify-scaffold.md)가 수행한다 — 본 기록의 관측은 그 입력이다.

### §8.1 Memory Update — BP 후보 기재 (물리 append T13 유보)

- **도출 후보.** 성공한 신규 프로젝트 설치→Bootstrap→루프 구동 단일 흐름 패턴 → **Best Practice 후보(시연 네임스페이스, 잠정 라벨 BPD-11)**. 요지: "신규 프로젝트 픽스처에 scaffold-template 배치→CK-1~8 전 충족→Bootstrap Ready→핵심 루프 1사이클 완주(주체 분리)→멱등성 diff 0·기존 파일 보존·Uninstall 잔여물 0을 단일 흐름으로 실증, 라이브 표면 비오염." 본 통과 케이스는 실패가 없으므로 Lesson 후보(LD-) 0건.
- **물리 append 유보(Advisor 결정 — 위임 constraint).** 시연 사이클의 Learn 산출은 본 기록에 후보로 **기재만** 하며, **물리 memory-data append·최종 id 배정은 후속 승격 심사(T13) 소관**이다(v0.8 관행). 따라서 본 시연은 memory-data에 append하지 않았다 — **store 56건·index 56 line 무변경**(실측). loop-data seq6·7 `ref`도 이 유보를 명시(record:mi 미생성). 이는 "하지 않은 것을 했다고 쓰지 않는다"(L-07·02 O5)의 준수다.
- **잠정 라벨 근거.** 현 index 최신 BPD 시퀀스는 BPD-10(mi-0051)이므로 다음 후보의 잠정 라벨을 BPD-11로 적었으나, 실제 `id`·`stable_id`·status·source의 물리 배정은 T13이 수행 시점에 실측 순차 배정한다(선취 금지).

### §8.2 `at`·timestamp = 순서 값 (L-09)

- **loop-data `at`.** `v09-demo-scaffold.jsonl` `at`=1..7은 사이클 내 단조 증가 순서 값(seq와 동반)이며 **물리 벽시계 시각이 아니다**(loop-binding §3.3). 본 기록은 `at`을 "실제 수행 시각"으로 서술하지 않는다.
