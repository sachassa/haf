## §2. 배정 대응표 — 40건 전건 (done 1·2)

네 출처의 완료 기준을 **재정의 없이 인용**하고, 각 기준을 이를 실증하는 **시연 수행(EX-DH/EX-DS/EX-DP 재현)** 또는 **마일스톤 CP2 정적 판정**(정적·스캔형) 또는 **대조 절차**(Verifier가 산출 소산을 대상으로 밟는 필드 존재·경계 대조) 또는 **CP3**(Advisor 최종 승인) 중 **최소 1곳**에 배정한다. §8-D의 판정 문장은 아래 표의 해당 문장을 **그대로 인용**한다. 판정 기준의 창설은 없다(done 2).

### §2.1 방식·소관 구분

- **재현형 (EX-DH/EX-DS/EX-DP)** — 각 서브시스템의 확장 연산(등록·발견·호출·Install/Activate/Remove·Hook Dispatch)을 실제 수행·관측하는 시연. 본 절차서 소관(수행 = 시연 Task PS-4 / 판정 = CP2 검증 리포트). loop-data·CP2 리포트가 근거.
- **마일스톤 CP2 정적 판정** — specs/08·09·10 §3 본문을 스캔·정적 대조하는 방식. **검증 리포트(Verifier = CP2)**가 마일스톤 판정에서 직접 수행한다. ### §3.2 기록 요건 (done 5 — 재발 방지·대조·Consult)

1. **실경로·실값 인용 ("수행했다" 서술 금지, L-07).** "근거 (관측한 것)"에는 추상 주장이 아니라 **실재 파일 경로와 실값**을 남긴다 — PS-4 Work Graph 인스턴스의 실 필드 값, 각 Task 사이클 loop-data `v08-demo-{h,s,p}.jsonl`의 실경로·전이 이벤트 **line 원문**(또는 필드 값 전건), F-H1 감사 기록·Hook Failure Report `blocking` 값·Skill 로드/비로드 대조 결과·Plugin Install/Activate/Remove 검사 결과, Task별 CP2 리포트의 최종 판정, Merge Result의 실 필드 값, 본체 diff 0 측정 대조 목록, Memory Update가 append한 memory-data 항목의 실 id·`source`·`kind`·`stable_id`. "확장을 시연했다"·"본체 수정이 없다" 류의 서술만으로는 근거가 불충분하다(L-07 — 상태 서술은 실측 후 기록). 파일이 실제로 존재하고 그 내용이 명세와 일치함을 실측으로 확인한 뒤 기입한다.
2. **`at`·시각 주장은 순서 값 / 실측 구분 (L-09).** 각 Task 사이클 loop-data의 `at` 필드는 **순서 값**이다(loop-binding §3.3 — 사이클 내 단조 증가하는 순서 값, 물리 벽시계 시각 아님). 수행 기록은 `at`을 "실제 수행 시각"으로 서술하지 않는다. Hook Event Record `occurredAt`도 순서 값(논리 시각)이며(hooks-binding §5.2, 08 §3.2-C) 벽시계 시각이 아니다. 시각 주장을 넣지 않으면 넣지 않았음을 근거에 명시한다(L-09).
3. **확장·병합 재구성 확인.** 수행 기록은 산출 소산만으로 시연을 재구성·검증할 수 있음을 아래로 확인한다:
   - **(가) 추가만의 확장·본체 diff 0** — 시연 전 본체 스냅샷과 시연 후 재열거를 대조해, 추가분이 선언된 시연 산출물(라이브 표면 레퍼런스·픽스처 경계·loop-data 신규 3파일·memory-data append분)뿐이고 기존 파일 변경 0임을 전수 대조한다(§6.6, ROADMAP ②·각 spec INV-1).
   - **(나) 서브시스템별 계약 준수 확인** — Hooks: F-H1 Hook Binding 6필드·순서 08 §3.1-D·비차단 `blocking=false` / Skills: Skill Manifest 로드 계층·미선택 본문 비로드 INV-4·역할 경계 INV-2·우선순위 4단 INV-3 / Plugins: Plugin Manifest 6필드·네 연산 검사 I1~IG·잔여물 0 = 설치 이전 목록 전수 대조.
   - **(다) 병렬·검증 완결·병합 확인** — 3 Task 사이클 loop-data가 각각 Consult→…→Complete를 `retry_count`=0·CP2 Pass로 완주함(개별 검증 통과)을 확인하고, 그 통과 결과만 Merge `collected`(3/3)에 들며, crossRefStatus=Consistent·conflicts=0으로 단계 4 생략·병합 성립을 복원한다(§6.4, merge-rules §4).
4. **시연 착수 시 Memory Consult 수행·회수 집합 기록.** 시연 수행 Task는 분해(Decompose) 착수 전과 각 Task 사이클 Consult 단계에서 Memory Service Interface로 회수(Recall)를 실제 수행한다 — `purpose`(예: EX-DH="v0.8 Hooks 확장 시연에 관련된 본체 불가침·비차단·순서 결정성 Active Lesson·BP 회수")와 `scope`(narrowing: `kind`=`lesson`/`best-practice`, `labels`: status=Active + 상황 투영), 기본 `detail`=index를 명시한다(memory-binding §3.2 단계 1·2). 회수된 집합(회수 건수·매칭 라벨·회수된 `id` 목록)을 수행 기록에 남기고, **그 회수 집합 참조(mi-id 배열)를 해당 Task 사이클 Consult 전이 이벤트의 `ref`에 기록**한다(loop-binding §3.3 DP-L5 — v0.7 실측 `ref`={"recall_set":[...]} 동형). 회수·기록이 단일 Port(Recall) 경유·우회 0건임을 확인한다(각 spec INV — 08 INV-7·09 INV-8·10 INV-5).

## §4. 픽스처 명세 (done 3, DP-E7·DP-E2·OQ-5)

시연은 격리된 픽스처를 대상으로 세 서브시스템의 확장을 구동한다. 이 절은 그 픽스처의 **명세**를 확정한다 — **픽스처의 실물 생성은 이 절차서 소관이 아니라 후속 시연 Task PS-4 소관이다** (constraint, §0). 픽스처는 저장소 실계약 문서를 건드리지 않는 자기완결 대상물이다.

### §4.1 위치·격리 경계 (DP-E7 — 라이브 표면 vs 픽스처 경계 정직 구분)

- **라이브 표면 존치 (정상 레퍼런스만).** DP-E7에 따라 `.claude/hooks/`·`.claude/skills/` 라이브 표면에는 **정상 레퍼런스 F-H1·F-S1만 존치**한다 — F-H1은 `.claude/hooks/audit-complete/`(hooks-binding §4.1 자기완결 경계 구조)에, F-S1은 `.claude/skills/<skill-id>/`(skills-binding §3.1 자기완결 단위)에 물리 배치한다. 이 두 라이브 표면 레퍼런스는 후속 시연 Task PS-4가 생성하며, 본 절차서는 생성하지 않는다(현 시점 두 디렉터리는 실재하나 빈 디렉터리 — §0 실측).
- **픽스처 경계 (결함·보조 픽스처).** 의도적 결함 픽스처(F-H2 실패 Hook·F-S2 위반 Skill)·순서 시연 보조(F-H3/F-H4)·미선택 대조(F-S3)·레퍼런스 Plugin bundle 원본(F-P1)·모사 프로젝트 컨텍스트 2종의 정본 거주지는 신규 디렉터리 **`docs/v0.8-demo-fixtures/`** 격리 경계다(v0.5~v0.7-demo-fixtures 관례 동형·plugins-binding §3.1 DP-E6 ⓐ). 이 디렉터리와 파일은 후속 시연 Task PS-4가 생성한다(현 시점 미존재 — 본 작성 시 직접 실측).
- **형태 A 규약 등록 (라이브 하네스 오염 금지, DP-E7).** 결함·보조 픽스처(F-H2·F-H3·F-H4·F-S2·F-S3)는 시연 중 라이브 표면에 물리 배치하지 않고, hooks/skills-binding의 **형태 A 규약 등록**(등록 서술 기록 — hooks-binding §4.3 형태 A / skills-binding §2 행 2 형태 A)으로 실현한다. 즉 등록 사실을 시연 기록에 서술로 남기되 `.claude/hooks/`·`.claude/skills/` 라이브 표면을 이 픽스처들로 오염시키지 않는다.
- **CP2 전수 스캔 제외 경계 (verifier_scope 제외, DP-E7).** AI 비의존 전수 스캔(§2, CP2 소관 — specs/08·09·10 §3 대상)이나 spec 일치 정적 판정이 수행될 때, **픽스처 경계(`docs/v0.8-demo-fixtures/`)와 라이브 표면 레퍼런스 물리 토큰은 대상 경계에서 제외**하고 제외 사실을 `verifier_scope`에 명시한다(v0.7-demo-fixtures §4 관례 동형). 픽스처의 의도적 결함(F-H2·F-S2)이나 시연 물리 토큰이 실계약(08·09·10 §3) 경계의 위반으로 계상되지 않게 한다.

### §4.2 머리 명시 요건 (필수)

픽스처 경계(`docs/v0.8-demo-fixtures/`)의 각 픽스처 파일 **머리에 다음 두 문구를 명시**한다.

- **"시연 픽스처 — 실계약 문서 아님."** 픽스처가 검증 대상 계약 문서가 아니라 시연을 위해 구성된 대상물임을 표시한다.
- **"의도적 결함 정당 보유."** 결함 픽스처(F-H2·F-S2)는 그 결함(action 실패·역할 경계/우선순위 위반 지시)이 시연을 위해 **의도적으로 심긴 정당한 보유물**임을 명시한다 — 실계약 문서의 결함으로 오인되지 않게 한다(v0.7-demo-fixtures "실계약 파일 아님·의도적 결함 정당 보유" 동형). 결함 없는 보조 픽스처(F-H3·F-H4·F-S3·F-P1·모사 컨텍스트)는 "실계약 문서 아님"만 명시한다.

**결함의 지위와 경계 (정직).**

- **의도적 결함 2건(F-H2·F-S2)은 실계약 문서의 결함이 아니다.** F-H2의 action 실패는 비차단 격리(INV-2)를, F-S2의 위반 지시는 역할 경계·우선순위 차단(INV-2·INV-3)을 실증하기 위한 구성물이며, 08·09 §3 계약의 판정 기준을 침범하지 않는다. 두 픽스처는 픽스처 경계 내부에만 존재하고 verifier_scope에서 제외된다(§4.1).
- **DP-E2 인스턴스 값은 신조어 창설이 아니다.** F-P1의 `id`=`report-exporter`·contract=`ReportExporterInterface`는 10 §8 예1 정본 예시 값의 인스턴스이며(DP-E2), Glossary·spec에 없는 새 용어를 창설하지 않는다. `ReportExporterInterface`는 예1의 예시 contract 식별자 값이다.
- **음성 케이스 비시연.** Plugin 실패 reason 11종(`BodyMutation`·`IncompatibleFramework`·`MissingDependency`·`DuplicateId`·`NotSelfContained`·`ContractMismatch`·`UnresolvedContract`·`DeactivateIncomplete`·`ResidueDetected`·`DependentExists`·`IsolationViolation`)이나 Skill 실패 8사유의 음성 케이스(등록 거부·미해소 등)는 정상 경로 시연 밖에서는 **시연하지 않는다**(08·09·10 §7 요구 없음). 본 시연은 정상 경로(추가만의 확장·비차단·순서 결정성·지연 로드·역할 경계/우선순위 차단·Install→Activate→Remove 성립·병합 성립)와, 명시적으로 요구된 결함 실증(F-H2 비차단·F-S2 차단·F-S3 미선택 대조)만 구동한다.

**claim(완료 보고)의 지위.** 각 Task 사이클의 Execute는 Worker 완료 보고(02 §3.2-C, self_check 포함)를 산출하나, 그 self_check "충족" 주장은 CP2 판정의 **참고 입력**일 뿐 판정 근거가 아니다(06 독립성, 02 §3.2-A). CP2는 각 Task 산출물을 근거로 독립 판정하여 Pass를 낸다(픽스처는 CP2 Pass가 기대되는 통과 케이스로 설계).

- **필드 값 근거.** `trigger`=완료 조건 충족(성공 경로 선형 전이, 03 §3.2-A 열거). `outcome`=pass(각 단계 완료 조건 충족). `retry_count`=0(재작업 되돌림 0회 — 통과 케이스). `actor` — Consult/Plan/채택(Execute 진입)/CP3(Complete 진입)는 Advisor, Execute 완료(CP1)는 Worker, Verify(CP2 Pass)·Learn 입력 제공은 Verifier(03 §3.1-A). 첫 line `from_stage` 부재(loop-state-record §2). **actor=human 0건**(사람 개입 없음 — 개입 최소).
- **Advisor 확정 요지(DP-E4) 대응.** DP-E4의 "seq1 Consult(ref=recall_set) → Plan(draft) → Plan(adopted) → Execute → Verify(CP2 Pass) → Learn → Complete·Memory Update 반영"은 위 v0.7 동형 7전이로 실현된다 — **Plan(draft)** = seq2 `ref`(Work Graph 초안), **Plan(adopted)** = seq3 `ref`(채택된 계획, Plan→Execute 진입), **Verify(CP2 Pass)** = seq5(Verify→Learn, verify-h/s/p Pass), **Memory Update 반영** = seq6(Learn→Memory Update). `actor=human 0건`·`retry 0`은 위 표에 반영됐다(v0.7 §8-C.2 실측 loop-data 동형).
- **Consult `ref` = 회수 집합 참조.** 각 사이클 seq 1의 `ref`에 그 사이클 Consult에서 회수된 memory-data store id 배열을 경량 참조(`{"recall_set":[...]}`)로 기록한다(DP-L5, §3.2 요건 4, v0.7 실측 동형). content 원문은 담지 않는다.
- **3사이클 동형·개별 검증 완결.** EX-DH·EX-DS·EX-DP 사이클은 위 7전이를 동형으로 밟으며, 각 사이클의 seq 5(Verify→Learn, CP2 Pass)가 그 Task의 **개별 검증 통과**(INV-5)를 실현한다 — 이 통과 결과만 Merge `collected`(3/3)에 든다(§6.4). 사이클 간 차이는 Execute 산출물 내용(EX-DH: Hooks 확장 / EX-DS: Skills 확장 / EX-DP: Plugins 수명주기)과 cycle_id·`ref` 실값이며, 전이 구조·필드 값은 동형이다.
- **기존 파일 무변경.** `v06-demo-a/b/c.jsonl`·`v07-demo-t1/t2/t3.jsonl` 6파일은 수정·삭제하지 않는다(append-only — §5.3).

- **AI 비의존 정적 스캔은 마일스톤 CP2 소관.** 08·09·10 §3 AI 비의존 전수 스캔(§2 배정)은 위 Task별 CP2와 별개로 마일스톤 CP2가 specs 본문을 대상으로 직접 수행하며, 픽스처 경계·라이브 표면·설치본의 물리 토큰은 verifier_scope에서 제외한다(§4.1, DP-E7).

### §6.4 Merge Result 기대 (merge-rules §3·§4 정본 — 충돌 0건 → 단계 4 생략)

Merge 산출 Merge Result의 **기대 값**이다(4필드, merge-rules §3). 값은 PS-4가 실값으로 채운다.

| 필드 | 기대 값 (성격) |
|---|---|
| `collected` | EX-DH·EX-DS·EX-DP 결과 3건 — **각각 CP2 Pass(개별 검증 통과)만 포함**(INV-5, §6.3). 미검증·Fail 결과 0건. (3/3) |
| `crossRefStatus` | **`Consistent`** — 세 Task가 서로의 산출을 참조하지 않고 각자 확정 정본(08/09/10 §3·binding)만 참조하므로(R2), 상호 참조 정합성 검증에서 불일치가 없다. |
| `conflicts` | **0건** — Hooks·Skills·Plugins가 상호 독립 서브시스템이라 "두 Task가 같은 계약을 다르게 실현"하는 사후 충돌이 존재하지 않는다(OQ-6, merge-rules §4.3 "없으면 → conflicts = 0건"). |
| `arbitration` | **(불필요 — 단계 4 생략)** `conflicts`=0이므로 merge-rules §4.4 "아니오(0건) → 이 단계를 건너뛴다" 분기가 적용되어 Advisor 중재 단계가 생략된다. |

- **충돌 처리 순서 (merge-rules §4) — 0건 분기의 첫 실증.** 수합(단계 1, `collected` 3/3) → 상호 참조 정합성 검증(단계 2, `crossRefStatus`=Consistent) → 충돌 검출(단계 3, `conflicts`=0건) → **(충돌 0건) 단계 4 Advisor 중재 생략**(merge-rules §4.4 0건 분기) → 병합 성립(단계 5). **이는 v0.7 시연(충돌 1건 → 단계 4 중재 수행)과 대비되는, merge-rules §4.4 "아니오(0건) → 이 단계를 건너뛴다" 분기의 첫 실증이다**(OQ-6). 시연은 5단계 전 과정(단계 4 생략 포함)을 Merge Result 기록으로 남긴다.
- **병합 성립 조건 (INV-5).** 완료 조건 3건 — (1) `collected`의 모든 결과가 개별 검증 통과(CP2 Pass, INV-5), (2) 상호 참조 정합(Consistent), (3) 충돌 0건(단계 4 뒤 분기 불요) — 이 충족되어 병합이 성립한다(merge-rules §4.5). 미검증 병합(`UnverifiedResult`)·상호 참조 불일치(`CrossReferenceMismatch`)·미해소 충돌(`UnresolvedConflict`) 음성 케이스는 시연하지 않는다(정상 경로만).
- **경계.** Merge는 개별 검증을 재수행하지 않고(merge-rules §4.1 경계), 개별 검증 판정 기준은 06 소관·단계 전이는 03 소관이다 — Workflow는 오케스트레이션(수합·상호 참조 대조·충돌 검출)만 수행한다.

### §6.5 Memory Update 실기록 기대 (memory-binding §3 / v0.6·v0.7-demo 동형)

- **정식 append.** 시연의 Learn→Memory Update는 도출한 후보를 **정식 memory-data에 append**한다 — memory-binding §3.1 Record 물리 절차(`store/<id>.json` 쓰기 + `index/index.jsonl` line append 정합, 04 INV-7)로 단일 Port(memory-service §7) 경유. 우회 접근 0건.
- **도출 후보 (07 §5, AGENT.md).** ⓐ **성공한 3-서브시스템 병렬 확장·병합(충돌 0) 패턴** → **Best Practice 후보**(Hooks·Skills·Plugins를 한 병렬 집합으로 추가만 확장하고 병합이 충돌 0으로 성립한 패턴). 본 통과 케이스는 실패가 없으므로 Lesson 후보(LD-)는 기대 0건이나, 시연 중 예기치 못한 실패가 관측되면 은폐 없이 LD- 후보로 기록한다(§8-실패, 02 O5).
- **시연 네임스페이스·`source` 표기 (v0.6/v0.7-demo 동형).** append되는 각 항목의 `source`에 **시연 유래를 표기**하고(예: `source`="v0.8-demo" 또는 PS-4가 확정하는 시연 유래 식별자), stable_id는 **실무 네임스페이스(L-/BP-)와 구분한 시연 네임스페이스**를 쓴다 — Best Practice 후보 = **BPD-**, Lesson 후보 = **LD-**(v0.6/v0.7-demo BPD-/LD- 선례 동형, 회수 오염 방지). status=`Candidate`(승격 승인은 Advisor 전속, 05 INV-4 — 시연 Memory Update는 후보 등록까지). 라벨 투영은 memory-binding §5.4 정본 키(`situation`·`stable_id`·`status`·`verdict`·`matched_lesson_id`)를 따른다.
- **mi 번호 실측 순차 배정·기존 무변경.** `id`는 memory-binding §2 스킴(`mi-<정렬가능토큰>`)으로 **수행 시점 실측으로 순차 배정**한다. 현 시점 store·index는 **실측 47건**(`mi-0001`~`mi-0047` — 본 작성 시 직접 실측)이므로, 시연 append는 그 다음 순번(`mi-0048`부터)에서 시작하되 정확한 번호·건수는 PS-4가 수행 시점에 실측해 배정한다(**선취 금지** — 구체 번호·건수를 본 절차서가 확정하지 않는다). **기존 47건은 무변경**이며 append-only만 수행한다.
- **loop-data ↔ memory-data 접속.** 각 Task 사이클 Consult 전이의 `ref`(회수 집합 mi-id 배열)가 두 백엔드를 잇는 지점이다. Workflow 수준 Learn→Memory Update(성공 패턴 BPD-)가 도출한 시연 유래 후보를 memory-data에 실기록한다. per-task 사이클과 Workflow 수준 후보의 정확한 append 건수·귀속은 PS-4 수행 시점 실측(선취 금지, 기존 47건 무변경·append-only).

### §6.6 본체 diff 0 측정 절차 (ROADMAP ②·각 spec INV-1 — done 5)

"본체 코드/규격 수정 없이 확장"(ROADMAP v0.8 ②·08 INV-1·09 INV-1·10 INV-1)을 **예/아니오 판정 가능한 전수 대조 절차**로 확정한다.

1. **시연 전 본체 스냅샷.** 시연 착수 **전**, 본체(기존 전 파일) 목록·상태를 스냅샷으로 확보한다 — `specs/`·`framework/core/`·`framework/runtime/`·기존 Baseline 산출물·기존 memory-data 47건·기존 loop-data 6파일·framework/plugins/ 3문서·이미 등록된 Module. 이것이 "본체의 시연 이전 상태"다.
2. **시연 후 재열거.** 시연(EX-DH·EX-DS·EX-DP 전 사이클 + Merge + Memory Update) 수행 후 동일 경계를 다시 열거한다.
3. **전수 대조.** 두 목록의 차집합을 계산한다. **추가분이 선언된 시연 산출물뿐이고 기존 파일 변경 0**이면 본체 diff = 0(예). 허용되는 추가분(선언된 시연 산출물) = { 라이브 표면 레퍼런스(`.claude/hooks/audit-complete/`·`.claude/skills/<skill-id>/`) · 픽스처 경계(`docs/v0.8-demo-fixtures/` 신규 디렉터리·파일) · loop-data 신규 3파일(`v08-demo-h/s/p.jsonl`) · memory-data append분(mi-0048~) · 시연 수행 기록(docs/v0.8-demo.md 등) }. **EX-DP의 설치본(`framework/plugins/report-exporter/`)은 Install 시 추가되나 Remove 후 잔여물 0이므로 최종 상태에서 순증가 0**(설치본 경로가 시연 후 재열거에 남지 않음 — plugins-binding §3.3 전수 대조).
4. **전 부류 전수(정직).** 추가분의 **전 부류**(라이브 표면·픽스처·loop-data·memory-data·설치본)를 스캔한다 — 한 부류(예: 픽스처)만 확인하고 다른 부류(loop-data)를 통과로 간주하지 않는다(좁은 대리 지표 금지, 06 §8 예1 유형 회피). 기존 파일 중 하나라도 변경이 있으면 본체 diff ≠ 0(아니오), ROADMAP ② 위반이다.
5. **검증 정합.** 이 절차는 08·09·10 §7 검증 방법("Verifier가 (Hook 추가/Skill 등록/Install) 전후 본체 diff가 0임을 확인")의 물리 실현이며, 파일 시스템 목록 대조로 예/아니오가 결정된다. 이 대조가 ROADMAP v0.8 ②(본체 코드/규격 수정 없이 확장)와 세 spec INV-1(본체 불가침)의 공동 실증이다.

## §7. 수행 주체·역할 배치 (Advisor 확정 시연 설계)

- **Advisor 주관 구동 (Workflow 오케스트레이션 = 주 세션).** 시연은 **Advisor(주 세션)**가 주관 구동한다 — Workflow 오케스트레이션(분해 채택 → 병렬 디스패치 → 각 Task 사이클 트리거 → 수합 → 상호 참조 정합성 검증 → 충돌 검출(0건) → 병합 성립)을 Advisor 주 세션이 구동한다. 분해 채택(Planner 초안 채택)·병렬 디스패치·수합·상호 참조 대조·CP3 최종 승인은 Advisor가 수행한다(07 §3.2-D, 02 §3.1). 본 시연은 충돌 0건이므로 Advisor 중재(단계 4)는 발생하지 않는다(§6.4).
- **Planner·Worker·Verifier 실위임 (모의 시연 금지, L-07 실측 요건).** 시연은 기록물만 작성하는 **모의 시연이 아니다** — **Decompose 초안은 Planner 서브에이전트**(`.claude/agents/planner.md`)에, **각 Task Execute는 Worker 서브에이전트**(`.claude/agents/worker.md`, 실측 `model: opus`)에, **각 Task CP2는 Verifier 서브에이전트**(`.claude/agents/verifier.md`)에 **실제 위임**한다(loop-binding §5.1 역할 실행 = 서브에이전트 디스패치, delegation-protocol §3.1). 실 산출물(F-H1 등록·F-S1 로드·F-P1 Install/Remove 등)이 생성되고 실 판정이 이뤄진 뒤에만 그 결과를 Work Graph 인스턴스·전이 이벤트·CP2 리포트·Merge Result로 남긴다(L-07 — "수행했다" 서술 금지, 실측 후 기록). Planner 초안은 Advisor 채택 대상이다.
- **병렬 디스패치 = 서브에이전트 동시 위임 (delegation-protocol §3.3, R1~R4).** 주 세션 Advisor가 한 병렬 집합의 3 Task를 **서로 다른** Worker 서브에이전트에 **동시** 위임한다. 착수 전 분해 검사 C1~C4 통과를 확인하고, 디스패치 중 R1(위임 메시지 전용)·R2(미완성 산출물 불추측 — 각 Task는 자기 확정 정본 08/09/10만 참조, 형제 산출물 불인용)·R3(조율 필요 시 Advisor 에스컬레이션)·R4(경계 준수 — 각 Task는 자기 `ownedBoundary`만 수정, §5.3)를 적용한다.
- **역할 ↔ actor 대응.** 각 Task 사이클의 전이 이벤트 `actor`는 그 전이를 유발한 역할이다 — CP1(Worker 자체 점검)은 Execute→Verify 전이의 근거, CP2(Verifier 독립 판정)는 Verify 전이의 판정, CP3(Advisor 최종 승인)는 Complete 진입 게이트. 본 시연 3사이클은 사람 개입이 없으므로 `actor`=human 0건이다(§6.2).
- **후속 담당(PS-4).** 픽스처(docs/v0.8-demo-fixtures/)·라이브 표면 레퍼런스(F-H1·F-S1)·Plugin 설치본·시연 수행 기록(docs/v0.8-demo.md)·loop-data 3파일·Merge Result·memory-data append 정리는 **후속 시연 Task PS-4(EX-DH·EX-DS·EX-DP)** 담당이다. 본 절차서(Task EX-D1)는 그 실행 명세만 확정하며, 픽스처·기록물·시연 실물을 생성하지 않는다(§0 소유 경계).

## §8. 시연 — 절차 단계 · 입력 · 기대 기록 명세 · 판정 문장 · 기록 포맷 · 실패 처리

목표: 본 마일스톤 Work Graph 병렬 집합 PS-4를 3-Task(EX-DH Hooks·EX-DS Skills·EX-DP Plugins)로 분해해 **한 병렬 집합**으로 동시 디스패치하고, 각 Task가 Loop 사이클을 CP2 Pass로 완주(개별 검증 완료)한 뒤, 병합에서 상호 참조 정합성 검증(Consistent)·충돌 0건 검출·단계 4 생략·병합 성립을 보인다. 근거: 08·09·10 §7·§8, ROADMAP v0.8 3건, merge-rules §3·§4, loop-binding §3, plugins-binding·hooks-binding·skills-binding.

### (A) 절차 단계

1. **Decompose 착수·회수.** Advisor(주 세션)가 v0.8 시연(목표·범위)을 수령한다. Memory Consult 회수(Recall)를 수행하고(§3.2 요건 4 — 확장·본체 불가침·병렬 관련 Active Lesson·BP), 회수 집합을 기록한다.
2. **Decompose 구동 (Planner 초안 + Advisor 채택).** Planner 서브에이전트가 PS-4를 3-Task Work Graph로 분해한 **초안**을 제출한다 — EX-DH·EX-DS·EX-DP 각각 7필드(§5.2), `dependencies`·`parallelSets`·`completion`. Advisor가 분해 검사 C1(완료 조건 보유)·C2(인터페이스 계약 보유)·C3(소유 경계 쌍별 비중첩, §5.3)·C4(의존 비순환)를 대조하고 병렬 집합 도출(상호 비의존·경계 비중첩)을 확인해 **채택**한다. 산출 = PS-4 Work Graph 인스턴스(§5).
3. **Dispatch 구동 (서브에이전트 동시 위임, R1~R4).** Advisor가 병렬 집합 {EX-DH, EX-DS, EX-DP}의 각 Task를 02 §3.2-B 위임 메시지로 **서로 다른 Worker 서브에이전트에 동시 디스패치**한다. 각 위임의 context에는 자기 서브시스템의 **확정 정본**(08/09/10 §3·§7·§8, 대응 binding)만 넣고, 동시 진행 중인 형제 Task의 미완성 산출물은 넣지 않는다(R2).
4. **각 Task Loop 사이클 실구동 (EX-DH·EX-DS·EX-DP 병렬).** 각 Task는 하나의 Loop 사이클을 구동한다(Consult→Plan→Execute→Verify→Learn→Memory Update→Complete, §6.2):
   - **EX-DH Execute (Worker 실위임)** — F-H1(audit-complete·`lifecycle.complete`@after·감사 기록)을 `.claude/hooks/audit-complete/`에 등록만 하여 본체 diff 0으로 감사 로그가 실행됨을 보이고(08 §8 예1), F-H2 실패 Hook을 주입해 본 작업 완료·다른 Hook 계속·Hook Failure Report `blocking=false`를 보이며(08 §8 예2·INV-2), F-H3·F-H4(order 10/20)를 등록해 08 §3.1-D 3단 순서로 결정적 실행됨을 보인다(08 §8 예3·INV-5). Event Record 읽기 전용(INV-3)·`lifecycle.verify` 관찰만(판정 불침범, INV-7). F-H2·F-H3·F-H4는 형태 A 규약 등록(라이브 표면 미오염, DP-E7).
   - **EX-DS Execute (Worker 실위임)** — F-S1을 `.claude/skills/<skill-id>/`에 등록만 하여 능력이 확장됨을 보이고(09 §8 예1·INV-1), 발견·선택이 메타데이터(front-matter)만 사용하며 선택 F-S1 본문만 로드·미선택 F-S3 본문 비로드를 보이고(INV-4), F-S2가 역할 경계 밖(`RoleBoundaryViolation`)·상위 규약 충돌(`PrecedenceConflict`) 시 차단됨을 보이며(09 §8 예2·3·INV-2·3), 모사 프로젝트 컨텍스트 2종에 F-S1을 재등록만으로 부분 재현(Config/`input` 주입, INV-5)하고, 동일 컨텍스트 발견 반복 실행이 동일 후보를 냄을 보인다(INV-7). F-S2·F-S3·모사 컨텍스트는 형태 A 규약 등록.
   - **EX-DP Execute (Worker 실위임)** — F-P1(report-exporter) bundle 원본을 설치본 `framework/plugins/report-exporter/`로 Install(본체 diff 0·I1~I5·IG)하고, Activate로 provides Module을 Runtime Register·requires([]) Resolve해 반환 핸들을 얻으며(A1·A2·INV-2), Remove 후 설치 이전 파일 목록 전수 대조로 잔여물 0을 보인다(R1·INV-3). 격리(IG — Memory 단일 Port·Core AI 비의존·역할 경계 불재정의)·자기완결(I5)을 대조한다(plugins-binding §5).
   - 각 사이클: Verify(Verifier 실위임, CP2 Pass verify-h/s/p) → Learn → Memory Update → Complete(Advisor CP3). `retry_count`=0·actor=human 0건. 각 사이클 = `v08-demo-{h,s,p}.jsonl` 7 line(§6.2).
5. **Merge 구동 (수합→상호 참조 정합성 검증→충돌 검출(0건)→단계 4 생략→성립).** Advisor가 완료·검증된 세 결과를 Merge한다(merge-rules §4): 단계 1 수합(`collected` 3/3, CP2 Pass만) → 단계 2 상호 참조 정합성 검증(`crossRefStatus`=Consistent) → 단계 3 충돌 검출(`conflicts`=0건 — 상호 독립) → **단계 4 Advisor 중재 생략**(0건 분기, merge-rules §4.4의 첫 실증) → 단계 5 병합 성립. ### (F) 실패 처리 규칙 (v0.7-demo-procedure §7 동형)

시연이 기대 관측과 **다르게 관측될 때**의 처리 규칙이다.

1. **은폐 없이 그대로 기록한다.** 관측이 기대와 달라도 실제 관측을 §3 기록 포맷의 "근거 (관측한 것)"에 그대로 남긴다. 실패·불일치를 숨기지 않는다(Worker 금지 사항 — 실패 은폐 금지, 02 O5·INV-5). Work Graph 필드 값·loop-data line 원문·서브시스템 확장 산출·CP2 리포트·Merge Result 필드·본체 diff를 그대로 인용한다.
2. **판정 값으로 표기한다.** 기대와 다르게 관측되면 해당 판정의 "관측 결과"를 **위반**으로 표기한다. 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기하며, 판정 불가를 충족으로 위장하지 않는다.
3. **재작업 여부 판단은 게이트 소관이다.** 이 절차서와 수행 기록은 관측·기록까지만 한다. 위반·판정 불가의 **재작업 여부 판단**은 검증 단계(Verifier = CP2)와 Advisor(CP3)의 소관이다.
4. **본체 diff ≠ 0 = 위반.** 시연이 기대하는 것은 본체 diff 0(추가만의 확장)이다. 기존 파일이 하나라도 변경되면 ROADMAP ②·각 spec INV-1 **위반**으로 표기한다(§6.6). Plugin 설치본이 Remove 후에도 잔여로 남으면 `ResidueDetected`·INV-3 위반이다.
5. **충돌 0건 기대의 이탈.** 본 시연은 충돌 0건을 기대한다(상호 독립 서브시스템, OQ-6). 만약 Merge에서 `conflicts`≠0 또는 `crossRefStatus`=Mismatch가 관측되면 이는 예기치 못한 관측이며 은폐 없이 기록하고 위반/판정 불가로 표기한다 — 임의로 충족 처리하지 않는다. 통과 케이스인 각 Task CP2가 Fail로 관측되면 이 또한 은폐 없이 기록한다(본 시연 미기대).
6. **연산 실패와 정상 경로의 구분.** 시연 중 Workflow 연산 자체가 수행 불능(서브에이전트 디스패치 불가·loop-data 기록 불가·Hook/Skill 등록 불가·Plugin Install 불가)이면 이는 **연산 실패**이며, 정상 경로(추가만의 확장·비차단·순서·지연 로드·역할 경계/우선순위 차단·Install→Activate→Remove 성립·병합 성립)와 다르다. 둘을 혼동해 기록하지 않는다.
