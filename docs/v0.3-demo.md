## §0. 이 문서의 위치와 정본 경계

- **이 문서는 시연 수행 기록(Task A7)이다.** 절차서(docs/v0.3-demo-procedure.md)가 정의한 절차 단계·판정 문장·기록 포맷을 **입력**으로 받아, 시연 3종을 실제로 수행하고 관측한 결과를 기록한다. 절차·판정 문장·기록 포맷을 **재정의하지 않는다** (절차서 §0, §5).
- **독립 판정·최종 승인은 이 문서 소관이 아니다.** 판정 값(충족/위반/판정 불가)의 관측 기록까지가 이 문서(A7)의 책임이며, 최종 판정(통과/실패/조건부) 도출은 Verifier 독립 판정(A8, 게이트 C = CP2), 최종 승인은 Advisor(게이트 D = CP3) 소관이다 (절차서 §3 말미, §5 규칙 3). 이 기록의 "관측 결과" 필드는 관측 수준 판정이며 **스스로 통과 처리·최종 승인이 아니다**.
- **관측을 창작하지 않았다.** 아래 모든 "근거"는 실제 파일 연산·병합 수행에서 관측된 구체 값이다 (§1 샌드박스에서 수행). 수행하지 않은 단계의 관측을 기록하지 않았다 (06 §3.2-F). 수행 불가 단계는 없었다.
- **하네스 상태 전제 (형태 A).** 이 하네스는 현재 Bootstrap 상태다 (runtime-binding.md §0, Glossary J-13). Register/Resolve/Replace/Load Config는 실행 코드(형태 B)가 아니라 **규약 실현(형태 A)**으로 수행된다 — 실제 파일 배치·로딩·교체·스코프 소스 병합으로 관측 가능하게 했다 (runtime-binding.md §3.2·§3.3·§3.4). 이 기록은 그 규약 실현을 관측한 것이며, 형태 B 실행 Registry/로더를 주장하지 않는다.
- **용어.** 계약 용어(Module / Module Manifest / contract / Register / Resolve / Replace / Bootstrap / Load Config / Runtime Context / effective config / state / 활성 바인딩 / 소비자 참조 / Config / scope)와 판정 값(충족/위반/판정 불가)은 전부 Glossary·01·Core 4종·verification-checklist.md 정본에서 인용했다. 새 용어를 신설하지 않았다.

## §3. 시연 ② 모듈 교체 (동일 contract Replace — 소비자 참조 변경 0)

### 3.1 수행 단계 로그 (절차서 §7-A 단계 1~7, 실제 수행)

입력(절차서 §7-B 그대로): 교체 전 Module A = `memory-provider-a`(contract=`MemoryServiceInterface`, version=1.0.0), 교체 후 Module B = `memory-provider-b`(동일 contract, version=2.0.0). 소비자 = `consumer`(requires=[`MemoryServiceInterface`]).

- **단계 1 — 교체 전 Resolve 관측.** 등록부(교체 전) = { `consumer.md`, `memory-provider-a.md` }. Resolve(`MemoryServiceInterface`): 활성 바인딩 수 = **1** → 반환 핸들(module id) = `memory-provider-a` (INV-3 / R-바인딩-1).
- **단계 2 — 소비자 참조 대상 확인.** `consumer.requires=[MemoryServiceInterface]` → 소비자가 참조하는 것은 **contract id `MemoryServiceInterface`**이지 특정 module id(memory-provider-a/-b)가 아니다 (module-registry.md §3 R-참조-1 규칙 1, module-manifest.md §4).
- **단계 3 — 동일 contract 확인.** B.id=memory-provider-b, B.contract=`MemoryServiceInterface`, B.version=2.0.0. 대상 contract=`MemoryServiceInterface`; **B.contract 동일=True** → 교체 가능 (다르면 `ContractMismatch` 거부 — INV-1, module-registry.md §2.3 규칙 1).
- **단계 4 — 교체 가능 확인.** 현재 활성 Module A(memory-provider-a).replaceable=**true** → `replaceable=false` 아님 → 교체 허용 (아니면 `NotReplaceable` — module-registry.md §2.3 규칙 2).
- **단계 5 — Replace 수행 (Replace = 파일 교체; 한 교체 단위 = R-바인딩-1).**
  - [대조] R-바인딩-1이 금지하는 상태 확인: 이전 비활성화 없이 새 활성화만 하면(A·B 동시 존재) Resolve 활성 바인딩 수 = **2** = `DuplicateBinding`(INV-3 위반). 교체 단위는 이 상태를 만들지 않는다. (대조용 임시 B는 즉시 제거해 복귀 — 활성 바인딩 수 1.)
  - [실제 Replace] 새 B 활성화 + 이전 A 비활성화를 **한 교체 단위**로 실행(이전 A 파일 제거 + 새 B 파일 배치를 하나의 원자 블록으로). 교체 단위 커밋 후 활성 바인딩 수 = **1** → 2-바인딩(DuplicateBinding) 상태 미발생 → 중(during) = 1 유지 (R-바인딩-1).
  - Replace 출력(식별자 쌍) = **`memory-provider-a` → `memory-provider-b`** (module-registry.md §2.3 출력).
- **단계 6 — 교체 후 Resolve 관측.** 등록부(교체 후) = { `consumer.md`, `memory-provider-b.md` }. Resolve(`MemoryServiceInterface`): 활성 바인딩 수 = **1** → 반환 핸들 = `memory-provider-b` (module-registry.md §2.3 규칙 4: 새 Module B 반환).
- **단계 7 — 소비자 참조 변경 대조.** consumer.requires(후)=[MemoryServiceInterface] → 소비자 Resolve 대상 contract id **전=후 = `MemoryServiceInterface`**(동일). consumer.md SHA256 전 = 후 = `32FFE8516A27A0327EE0DC84E2D8EE315FD19C14214897C5123C62D02574D59C` (동일) → **소비자 코드·규격 변경 = 0 건** (INV-1 / R-참조-1 규칙 2). 변경 0이므로 R-참조-1 규칙 3(위반 신호) 에스컬레이션 불필요.

관측 요지 (소비자 참조 변경 0 대조): 교체 전·후 소비자의 Resolve 대상 contract id 동일(`MemoryServiceInterface`); 활성 바인딩 수 전·중·후 각 1(중=교체 단위로 유지, DuplicateBinding 미발생); Replace 출력 쌍 memory-provider-a → memory-provider-b; 소비자 정의(consumer.md) 해시 불변 → 참조 변경 0.

| **관측 결과** | **충족** (관측 수준 판정 — 최종 판정·승인은 A8/Advisor 소관). |
| **근거 (관측한 것)** | 교체 전 Resolve(MemoryServiceInterface)=`memory-provider-a`; 교체 후 Resolve=`memory-provider-b`. 활성 바인딩 수 전=**1**, 중=**1**(교체 단위 유지, DuplicateBinding=2 미발생), 후=**1**. Replace 출력 쌍 = `memory-provider-a → memory-provider-b`. 소비자 Resolve 대상 contract id 전=후=`MemoryServiceInterface`(동일). consumer.md SHA256 전=후 동일(32FFE8…D59C) → 소비자 참조 변경 = **0 건**. |
| **수행 단계 로그** | §3.1 단계 1~7 참조. 단계 5 Replace 출력 쌍(memory-provider-a → memory-provider-b), 단계 6 Resolve 반환(memory-provider-b), 단계 7 참조 대조(contract id 전=후 동일, 해시 불변) 포함. R-바인딩-1 금지 상태(2-바인딩=DuplicateBinding) 대조 관측 포함. |
| **수행 물리 지점** | 이 시연은 Bootstrap 상태(**형태 A**)의 규약 실현이다 (runtime-binding.md §0·§3.2). 실현·관측 물리 표면: **Resolve = 정의 파일 로딩/조회**(등록부에서 contract별 활성 파일 조회·활성 바인딩 수 집계, §3.2 Resolve 행) → **Replace = 파일 교체**(이전 A 파일 비활성화·제거 + 새 B 파일 활성화·배치를 한 교체 단위로, §3.2 Replace 행). 소비자 참조 불변은 소비자 정의 파일(consumer.md)의 해시 불변으로 관측. 형태 B(실행 Registry) 미도입, 01 §3.1-A 계약 변경 0으로 이식(§3.2 형태 열). |

## §4. 시연 ③ Config 병합 (3스코프 → effective config)

### 4.1 수행 단계 로그 (절차서 §8-A 단계 1~6, 실제 수행)

입력(절차서 §8-B 그대로): 키 `verify.strict`. Global scope = `false`(Framework 기본값, 최저) / Project scope = `true`(엄격 검증, 중간) / Module scope(target=example-module, 최고) = 첫 예 **미지정**, 동형 예 **`false` 지정**.

- **단계 1 — 스코프별 소스 준비.** 세 스코프 소스를 물리 파일로 배치(runtime-binding.md §3.3: Config 3스코프 물리 소스). 파싱된 entries의 `verify.strict` 기여 값:
  - Global(`global.config`): verify.strict = **false**.
  - Project(`project.config`): verify.strict = **true**.
  - Module 첫 예(`module-case1.config`, target=example-module): verify.strict = **(미지정 — 이 스코프는 이 키에 기여 없음, config-schema.md §4.4)**.
  - Module 동형 예(`module-case2.config`, target=example-module): verify.strict = **false**.
- **단계 2 — Load Config 호출.** 스코프별 소스 집합을 입력으로 병합 수행 (config-schema.md §5, 01 §3.1-B). (runtime-binding.md §3.3: Load Config 실행 로더는 형태 B이며, 여기서는 스코프 소스 로딩·우선순위 병합을 규약 실현(형태 A)으로 수행.)
- **단계 3 — 로딩 순서 확인.** 로딩 순서 = **Global → Project → Module** (config-schema.md §4.1). 이 순서는 우선순위 오름차순과 일치하여 로딩 순서대로 덮어쓰면 최고 우선순위가 최종 승자가 된다(§4.2 정합 관찰).
- **단계 4 — 우선순위 병합 관측 (Module > Project > Global, config-schema.md §4.2).**
  - 첫 예: Module scope가 `verify.strict` 미지정 → Module 기여 없음(§4.4) → 남은 스코프 중 최고 우선순위 **Project**가 이김 → effective `verify.strict` = **`true`** [우선순위 승자 = Project].
  - 동형 예: Module scope가 `verify.strict=false` 지정 → 우선순위 Module > Project > Global에 따라 **Module** 값이 이김 → effective `verify.strict` = **`false`** [우선순위 승자 = Module].
- **단계 5 — 결정성 확인.** 동일 입력으로 재병합(각 예 2회):
  - 첫 예: 재병합 값 동일 = **True** (값1=true, 값2=true).
  - 동형 예: 재병합 값 동일 = **True** (값1=false, 값2=false).
  - → 동일 입력은 항상 동일 effective config 산출 (결정성, config-schema.md §4.3 / INV-5).
- **단계 6 — 규격 일치 대조.** 산출된 effective config가 config-schema.md §6 도출 결과 및 01 §8 예2와 일치:
  - 첫 예 도출 `verify.strict=true`(승자 Project) = config-schema.md §6 첫 예("Module 미지정 → Project가 이긴다") = 01 §8 예2. **일치.**
  - 동형 예 도출 `verify.strict=false`(승자 Module) = config-schema.md §6 둘째 예("Module이 지정 → Module이 이긴다"). **일치.**

관측 요지: 3스코프가 우선순위(Module > Project > Global)대로 결정적으로 병합됨. 첫 예(Module 미지정)→Project 승자→true, 동형 예(Module=false)→Module 승자→false. 동일 입력 재병합 결과 동일(결정적). config-schema.md §6·01 §8 예2 규격과 일치.

### 4.2 기록 포맷 (절차서 §3·§8-E 인스턴스)

## §5. 불일치 여부 (절차서 §5 실패 처리 규칙 — done 7)

- **불일치 없음.** 시연 3종 모두 절차서 §6-C/§7-C/§8-C 기대 결과대로 관측되었다. 기대와 다르게 관측된 항목은 없으며, 위반·판정 불가로 표기할 항목이 없다. 세 시연의 "관측 결과"는 모두 **충족**이다(관측 수준).
- **은폐 없이 기록한 비-계약 관측 1건 (계약 불일치 아님).** 시연 ③ 최초 병합 실행 시, 콘솔 코드페이지와 UTF-8 소스 파일 인코딩 불일치로 소스 파일의 **한글 주석·라벨 텍스트**가 콘솔에서 깨져 표시되었다(mojibake). 이는 **표시(display) 계층의 인코딩 아티팩트**이며, 병합 대상 데이터(키 `verify.strict`의 값 = ASCII)와 병합 결과(첫 예 true/승자 Project, 동형 예 false/승자 Module, 결정성 True/True)는 두 실행 모두에서 정확했다. UTF-8 출력 인코딩으로 재실행하여 파싱 값·병합 결과가 동일함을 확인했다. **Config 병합·우선순위·결정성 계약의 불일치가 아니다.** 실패 은폐 금지(02 O5, 절차서 §5 규칙 1)에 따라 관측 그대로 기록한다.
- **Runtime 연산 실패 보고 (절차서 §5 규칙 4).** 시연 중 예기치 못한 Runtime 연산 실패(Bootstrap `MissingRequired` 등)는 관측되지 않았다. 시연 ①의 MetricsPort 미해소(활성 바인딩 0)와 시연 ②의 DuplicateBinding(2-바인딩) 대조는 각각 **의도된 관측**(선택 계약 부재 → Degraded, INV-2 / R-바인딩-1이 금지하는 상태 대조)이며 예기치 못한 실패가 아니다.

## §6. 정본 경계·용어 self-note

- **재정의 없음.** 세 판정 문장은 절차서 §6/§7/§8-D(=01 §7 완료 기준 3건)를 전재했고, 모든 절차 단계·예시 입력·기대 결과는 절차서 §6/§7/§8과 Core 4종 문서(module-manifest.md·module-registry.md·config-schema.md·lifecycle.md)·01 §3·§8의 계약·규칙 인스턴스다. 어떤 계약 요소도 이 문서에서 진위가 확정되지 않는다 — 판정 기준은 정본 §이며, 이 기록의 "관측 결과"는 관측 수준 입력이고 최종 판정·승인은 A8·Advisor 소관이다.
- **필수/선택 표기 보존.** 예시 Manifest는 필드의 필수/선택 표기(`requires` 선택·기본 없음, `replaceable` 선택·기본 true, `id`·`contract`·`version`·`entrypoint` 필수)를 정본 module-manifest.md §2 그대로 반영했다 (Lesson 후보 준수 — session-handoff-v0.2 §1.5 항목 2).
- **필드 소속 명시.** reason 코드·필드는 소속 연산·계약을 § 포인터로 명시했다 — Register/Resolve/Replace reason(ContractMismatch/DuplicateBinding/NotReplaceable 등)은 module-registry.md §5·01 §3.1-A 소속, Bootstrap reason(MissingRequired)은 lifecycle.md §2.1·01 §3.1-C 소속, Load Config reason(SchemaViolation)은 config-schema.md §5·01 §3.1-B 소속. 다른 계약의 필드명을 끌어오지 않았다 (Lesson 후보 준수 — §1.5 항목 1).
- **관측 창작 없음.** 모든 근거는 §1 샌드박스의 실제 파일 연산·병합에서 관측된 구체 값이다(등록부 디렉터리 목록, Resolve 활성 바인딩 수, Replace 출력 쌍, consumer.md SHA256, effective config 값·승자·재병합 일치). 수행하지 않은 단계의 관측을 기록하지 않았다 (06 §3.2-F, 절차서 constraints).
- **동시 작성 산출물 불인용 (07 R2).** 이 기록은 확정 문서(절차서 게이트 C Pass, runtime-binding.md r2, Core 4종, 01)만 참조했다. 동시 작성 중인 미완성 산출물을 인용·추측하지 않았다. "수행 물리 지점"은 확정된 runtime-binding.md의 해당 § 참조로만 기입했다.
