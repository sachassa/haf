## §2. 채택 아키텍처 (모델 P 수정 채택 — 판정 B)

**planning/을 rename 없이 "Project Contract 스키마 소유자 + Solution Design 단계 소유자"의 이중 책임으로 진화**시킨다.

```
Discovery ──▶ Contract 인스턴스 vN (Ready | ReadyWithAssumptions)
                  │
                  ▼  복잡도 게이트 (단순하면 스킵 — vN이 곧 최종 소비 대상)
            Solution Design  [planning/ 소유 · UAF 레벨 활동]
              복잡도 판정 → 동적 역할 할당(Capability 개방 네임스페이스)
              → 협업 설계(Proposal → Conflict → Trade-off → Integrated Review)
              → 사용자 승인 게이트(UAF-INV ⑤ 동형)
                  │
                  ▼
            Contract 인스턴스 v(N+1) (supersedes vN · append-only) ──▶ UAHF
```

기각 대안(재론 금지 — 근거는 계획 정본): (b) Discovery 확장 = P2·UAF-INV ③ 파괴 / (c) UAHF 내부 단계화 = UAF-INV ① 직접 위반 / (a) contract/ rename + solution-design/ top-level 신설 = 종국 지향점으로는 우월하나 v1.3 부적합 → **04 spec 확장 포인트로 퇴로만 기록**.

## §4. 선행 확정 인터페이스 (W1 저술의 고정 입력 — v1.1 W1 Discovery Request 선례 동형)

### §4.1 단계 정의 (한 문장)

Solution Design은 **Ready 종단 Contract 인스턴스를 입력으로, 프로젝트 복잡도에 따라 동적으로 구성된 전문가 역할 협업으로 솔루션 설계 결정을 성숙시켜, 사용자 승인 하에 superseding Contract 인스턴스를 재발행하는 UAF 레벨 활동**이다. 소유 = `planning/`. UAHF 구현 Planning과 별개 네임스페이스(C2 3항 구분).

### §4.2 입출력 추상

- **입력**: Ready 또는 ReadyWithAssumptions 종단의 Project Contract 인스턴스 vN (+ 선택: 대상 워크스페이스 증거). 비종단·비Ready 인스턴스는 입력이 될 수 없다.
- **출력 (두 경로 — 둘 다 사용자 게이트 통과)**:
  - **성숙 경로**: superseding Contract 인스턴스 v(N+1)(supersedes=vN·append-only·vN 문면 불변) + 선택된 Projection 산출 목록(대상 프로젝트 워크스페이스 귀속).
  - **스킵 경로**: 무산출 — vN이 곧 UAHF 소비 대상. 스킵 판정 기록 + 경량 사용자 확인(D6).

### §4.3 루트 §12 신규 용어 4건 (문안 초안 — W2b에서 §12.1에 등재)

- **Solution Design** — §4.1 정의 문장.
- **Expert Role** — Solution Design에서 Capability 선언으로 정의되는 논리 역할. 고정 Agent Class가 아니며 개방 네임스페이스다. 프로젝트 특성·복잡도에 따라 최소 필요 역할만 동적으로 구성된다. 실행 주체 매핑은 Adapter 소관(코어는 역할 추상까지 — M5).
- **Projection** — Project Contract를 Source of Truth로 하여 파생 생성되는 프로젝트별 산출 문서(예: PRD·ARCHITECTURE·ADR·UI Guide). 대상 프로젝트 워크스페이스에 귀속되며, 유형 목록은 개방 레지스트리(비정본 부록)다. 모든 프로젝트에 모든 유형을 강제하지 않는다.
- **Contract Maturation(성숙)** — Ready 인스턴스 vN을 기준선으로 새 설계 결정을 반영한 v(N+1)을 supersedes 계보로 재발행하는 것. 단일 문서의 상태 변경이 아니라 **완결 인스턴스의 재발행**이다(PC-INV 7·9 무촉).

### §4.4 경계 기준 (vs discovery/specs/02 §3.11 Architecture Dimension — 04가 소유할 문안)

> **Discovery는 아키텍처 방향·기존 결정·미결 사항을 이해로 기록하고, 미결의 해소와 신규 설계 결정의 창출은 Solution Design 소관이다.**

Discovery Strategy가 설계를 심화하는 스코프 크리프, G2에서 승인된 결정을 성숙 단계가 무단 번복하는 권위 충돌을 이 기준 + supersedes 계보 + 사용자 게이트로 차단한다. `discovery/specs/02-discovery.md`는 **무수정**(경계 기준은 04와 루트가 소유).

### §4.5 SP-INV 축 (최소 후보 8 — 확정·문면화는 04 저술 소관, 축 자체는 고정)

① 입력 Ready 불변(비Ready 인스턴스 성숙 금지) ② 성숙 내부 개념의 Contract 코어 필드 유입 금지(PC-INV 2 동형) ③ 성숙 실행 메타 불투명(PC-INV 3 동형 — 역할 구성·Proposal·충돌 기록은 코어 밖) ④ 사용자 승인 게이트 없이 성숙 종단 없음(UAF-INV ⑤ 동형·스킵 포함 D6) ⑤ 방법론·역할 카탈로그 불인지(UAF-INV ⑥ 동형 — Provider·비정본 부록만 앎) ⑥ UAHF 무수정·하류 역참조 금지(§2.5 폐쇄성 — 코어는 역할 추상까지) ⑦ 산출물 대상 워크스페이스 귀속(Framework 상태 오염 금지) ⑧ 최소 할당(필요 역할만 — 불필요 Multi-Agent 비용 방지).
