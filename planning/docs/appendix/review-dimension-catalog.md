## §1. 목적

Integrated Design Review(`Reviewing`, 04 §3.4-D ④)가 역할별 부분 설계를 **하나의 시스템으로 통합 검토**할 때 쓸 수 있는 **관점 차원의 예시**를 보인다. 부분 설계가 개별적으로 옳더라도 통합하면 충돌할 수 있고, 이 차원들은 그 통합 수준 결함을 드러내기 위한 관찰 각도다. 리뷰의 산출("단일 일관 결정 집합" 수렴·잔여 충돌 재노출 시 `Reconciling` 회귀)은 04 §3.4 소유다.

## §2. 관점 차원 예시 표 (8종 — 예시일 뿐 강제 목록 아님)

| 차원 (예시) | 무엇을 보는가 | 통합 수준에서 드러나는 전형 결함 |
|---|---|---|
| 아키텍처 일관성 | 역할별 결정이 하나의 아키텍처 방향과 정합하는가 | 부분 설계마다 다른 구조 전제·중복 책임 |
| 인터페이스 호환성 | 경계를 넘는 호출·계약이 양쪽 설계에서 일치하는가 | 시그니처·프로토콜·버전 불일치 |
| 데이터 흐름 일관성 | 데이터의 생산·소유·변환·소비 경로가 닫히는가 | 소유자 없는 데이터·이중 진리원천 |
| 보안 | 신뢰 경계·권한·비밀 취급이 전 구간에서 유지되는가 | 경계 한 곳의 우회 경로·권한 확대 |
| 운영성 | 배포·관측·장애 대응이 설계에 담겼는가 | 운영 불가능한 결합·관측 사각 |
| 시험성 | 결정들이 검증 가능한 형태인가 | 실행 가능한 수용 기준 부재 |
| 기술 호환성 | 선택 기술들이 상호 운용 가능한가 | 런타임·버전·라이선스 상충 |
| 횡단 관심사 (cross-cutting) | 어느 단일 역할에도 속하지 않는 관심사가 누락되지 않았는가 | 역할 경계 사이에 떨어진 요구(국제화·감사 추적 등) |

- **동적 선택.** 8종은 예시이며 전 차원 강제가 아니다 — 검토 차원의 선택 자체가 프로젝트 특성·복잡도에 따른다(04 §3.2).
- **충돌 검출과의 관계.** 차원 검토 중 발견된 상충은 새 결정이 아니라 **충돌**로 다루고 T7로 `Reconciling`에 되돌린다(04 §3.4-B). 어떤 차원 검토도 확정 권한을 갖지 않는다 — 확정 게이트는 사용자 승인(T8·UAF-INV ⑤)이다.

## §3. 산출 취급 (포인터만)

차원별 검토 기록은 **코어 밖 실행 메타**이며 Contract 코어 필드로 유입되지 않는다(04 §3.8 SP-INV 2·3). 저장은 대상 프로젝트 워크스페이스 귀속이고(04 §3.7·SP-INV 7) 물리 배치는 Adapter 소관이다(04 §4).
