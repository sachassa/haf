## §3. 관측 결과 판정 방식 (실측 대조)

각 판정의 "관측 결과"는 실측 산출물(Work Graph 인스턴스 필드 값·loop-data 21 line·CP2 리포트·Merge Result 4필드·memory-data 항목)을 절차서 §6 기대 기록 명세·§8-D 예/아니오 환원과 대조해 판정한다. **기대와 전건 일치**하면 **충족**, 다르면 **위반**, 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기한다(절차서 §8-F). 특정 판정이 본 재현 범위 밖(마일스톤 CP2 정적 스캔 소관 — AI 비의존·카탈로그 도출·spec 일치·CP3 최종 승인)이면 **판정 유보**로 표기하고 충족으로 위장하지 않는다(절차서 §8-F-2·§2.2 배정). 본 시연은 충돌 0건을 기대하며(상호 독립 서브시스템, OQ-6), 그 기대대로 관측되면 병렬·병합 시연은 충족이다(절차서 §8-F-5). 시연 중 Workflow 연산 자체의 수행 불능(연산 실패)은 관측되지 않았다(절차서 §8-F-6).

## §5. 병렬 디스패치 + 3 Task 사이클 loop-data 수행 기록 (§6.2)

### §5.1 병렬 디스패치 수행 (절차서 §8-A 단계 3~4, R1~R4)

Advisor가 병렬 집합 {ex-dh, ex-ds, ex-dp}의 각 Task를 02 §3.2-B 위임 메시지로 **서로 다른 Worker 서브에이전트에 동시 디스패치**했다(dispatch-protocol §2, delegation-protocol §3.3). 착수 전 C1~C4 통과를 재확인하고, 다음을 적용했다:

- **R1(위임 메시지 전용).** 세 Task 전부 02 §3.2-B 위임 메시지로만 위임(§0.2 실위임 6회 중 Execute Worker 3).
- **R2(미완성 산출물 불추측).** 각 위임 context에 **자기 서브시스템의 확정 정본**(08/09/10 §3·§7·§8, 대응 binding)만 넣고, 동시 진행 중인 형제 Task의 미완성 산출물은 넣지 않았다. 세 완료 보고가 R2 준수(형제 실물 불참조) 명시(§0.2). Merge crossRefStatus=Consistent가 이 준수를 사후 확인(§6.2).
- **R3(조율 필요 시 Advisor 에스컬레이션).** 세 서브시스템 확정 정본이 분해 시점에 고정됐고 상호 독립이므로 조율 필요 사항이 발생하지 않았다(각 Worker open_questions — EX-DH만 F-H1 contract 인스턴스 값의 채택 거버넌스를 참고 명기, §0.2). ⓑ planner.md·verifier.md 동시 변경은 각 CP2가 EX-R3 귀속으로 정직 에스컬레이션·해소(§7.8).
- **R4(경계 준수).** 각 Task는 자기 `ownedBoundary`(§5.6)만 산출했다 — 세 CP2 리포트가 경계 밖 수정 0을 실측 확인(verify-h I5·verify-s item 9·verify-p C-5).

### §6.3 merge-rules §4.4 "0건 → 단계 4 생략" 분기의 첫 실증 (OQ-6)

v0.7 시연은 충돌 1건이 병합 단계 3에서 검출→단계 4 Advisor 중재→해소됐다(v0.7-demo §6.3). v0.8 시연은 상호 독립 서브시스템이라 **conflicts=0건**이 관측되어 merge-rules §4.4의 다른 분기 — "아니오(0건) → 이 단계를 건너뛴다" — 가 적용됐다. 이는 그 0건 분기의 **첫 실증**이다(절차서 OQ-6):

- **§4.4 검사(예/아니오).** "`conflicts` 목록이 0건 초과인가?" → **아니오(0건)**.
- **§4.4 처리.** "아니오(0건) → 이 단계를 건너뛴다(`arbitration` 불필요)." → Advisor 중재 미발생, `arbitration` 필드 값 = 생략.
- **§4.5 병합 성립.** 완료 조건 3건(collected 전건 Pass·Consistent·충돌 0건) 전부 충족 → 병합 성립.

### §8.2 `at`·timestamp 성격 구분 (L-09 — 순서 값 / 물리 시각 구분)

L-09(기록 `at`/timestamp의 성격 구분, 물리 시각 주장은 실측 대조 후에만)에 따라 본 기록은 loop-data `at`·memory-data timestamp를 **순서 값**으로 서술하고 **물리 벽시계 시각으로 주장하지 않는다**.

- **loop-data `at` = 순서 값(loop-binding §3.3).** 세 파일의 `at`은 정수 서수로 seq와 동반 단조 증가(각 1..7, §5.2 line 원문 `at`=`seq` 위치). 전이 순서를 확정할 뿐 물리 시각이 아니다. 본 기록은 `at`을 "실제 수행 시각"으로 서술하지 않는다.
- **memory-data timestamp = 생성기 배정 단조 순서 값(기존 시퀀스 연속).** mi-0048~0051의 timestamp는 각각 `2026-07-05T22:20:34.602+09:00`·`...35.602`·`...36.602`·`...37.602`로, 직전 기존 항목 mi-0047(`2026-07-05T22:20:33.602+09:00`)에서 **+1초씩 연속**하는 생성기 배정 순서 값이다(실측). 이는 mi 시퀀스의 단조 순서를 나타낼 뿐 물리 생성 시각이 아니다.
- **실측 대조(L-09 — 물리 시각은 실측값으로만 별도 공개).** timestamp 필드 값(2026-07-05T22:20:3x)과 파일의 **물리 mtime**은 서로 다르다 — 본 작성 시 직접 실측한 물리 mtime(LastWriteTime): loop-data v08-demo-h.jsonl `2026-07-06 16:56:42`·s `16:56:42`·p `16:56:43`; store mi-0048.json `2026-07-06 16:57:44`·mi-0049 `16:57:44`·mi-0050 `16:57:44`·mi-0051 `16:57:44`; index.jsonl `2026-07-06 16:57:44`. 물리 mtime은 **2026-07-06**(그 다음 날)로 timestamp 필드 값(2026-07-05T22:20:3x)과 **불일치**한다. 이 불일치가 timestamp 필드가 물리 시각이 아니라 생성기 배정 순서 값임을 직접 실증한다(v0.7-demo §8.2 실증 동형). 본 기록은 timestamp/`at`을 시연의 물리 수행 시각으로 주장하지 않으며, 물리 시각은 위 mtime 실측값으로만 별도 공개한다.
