## §0. 이 문서의 위치·정본 경계·오케스트레이션 사실 (Advisor 제공)

### §0.1 위치·정본 경계

- **이 문서는 수행 기록이다.** 시연 3종을 **실제로 어떻게 수행했고 무엇이 관측됐는가**를 실값으로 기록한다. **독립 판정**은 검증 단계(Verifier = CP2)가, **최종 승인**은 Advisor(CP3)가 담당한다 — 본 기록은 그 판정의 입력이며 스스로 최종 승인을 내지 않는다(02 §3.2-A). 관측 결과의 "충족/위반/판정 불가"는 실측 대조 관측이며, 게이트 통과의 최종 확정이 아니다.
- **판정 문장은 전재다(재정의 0).** 각 시연의 판정 문장은 docs/v0.6-demo-procedure.md §8/§10/§11 (D)의 원문(03 §7 시연 가능 문장·ROADMAP v0.6 완료 조건 인용 + 예/아니오 환원)을 **그대로 옮긴다**. 새 판정 기준을 창설하지 않는다.
- **소유 경계 준수(07 R4).** 본 작업의 소유 경계는 이 1파일(docs/v0.6-demo.md)이다. loop-data/·memory-data/·픽스처를 **수정하지 않았고**, 전부 읽기 전용 실측으로만 인용했다. framework/·specs/·기존 memory-data 30건 무변경.

### §0.2 오케스트레이션 사실 (Advisor 제공 — 수행 주체·역할 배치, OQ-7)

- **수행 주체.** Advisor(주 세션)가 Loop 호스팅·오케스트레이션을 구동했다(OQ-7). 각 사이클에서 Advisor는 위임 수령·위임 완전성 확인 → Consult 회수 주도 → Plan 채택 → Execute 위임 → Verify 트리거 → Learn → Memory Update → Complete/에스컬레이션을 오케스트레이션했다(loop-protocol §3).
- **실서브에이전트 위임(모의 아님, L-07).** Planner가 계획 초안을, **Worker 서브에이전트**(`.claude/agents/worker.md`, `model: opus`)가 Execute를(ⓐ 1회·ⓑ 2회·ⓒ 3회), **Verifier 서브에이전트**(`.claude/agents/verifier.md`)가 CP2 독립 판정을(ⓐ 1회·ⓑ 2회·ⓒ 3회) **실제 수행**했다. 실 산출물(output-*.md)·실 판정 리포트(verify-*.md)가 생성된 뒤에만 전이 이벤트로 기록됐다.
- **사이클 위임(Advisor 발신 8필드).** task=각 픽스처 §A 이행 / input=fixture §0·§A / output=output-*.md / done=fixture §B / context·constraints 포함(02 §3.2-B).
- **CP3 최종 승인.** ⓐ·ⓑ는 CP2 Pass 후 Advisor가 CP3 최종 승인 → **사이클 완료 보고 산출**(각 사이클 §4·§5에 02 §3.2-C 5필드 수록). **ⓒ는 완료 보고 미생성** — 대신 에스컬레이션 산출(실패 보고 요지, 02 §3.2-D; §6에 수록).
- **사람 개입(ⓒ seq 11).** Advisor가 주 세션에서 사용자에게 에스컬레이션을 제시 → 사용자가 "확인 — 에스컬레이션 종료 승인" 실응답(2026-07-06) → `actor`=human 전이(v06-demo-c.jsonl seq 11)로 기록됐다. 이 개입은 03 §3.1-D 조건 1(재시도 한도 초과)의 **정당 개입**(개입 최소 INV-6 위반 아님)이다. ⓐ·ⓑ는 `actor`=human **0건**(§7 grep 실측).
- **Learn 도출 → Memory Update.** ⓐ→BPD-01(mi-0031), ⓑ→LD-01(mi-0032)+BPD-02(mi-0033), ⓒ→LD-02(mi-0034). 전부 status=Candidate·source="v0.6-demo-L10"(OQ-9). 시연 유래 stable_id는 실무 네임스페이스(L-/BP-)와 구분한 **시연 네임스페이스(LD-/BPD-)**다(회수 오염 방지).

## §2. Consult 회수 기록 (done 4 — §3.2 요건 4, DP-L5 실증)

세 사이클 모두 착수 Consult 단계에서 Memory Service Interface(단일 Port Recall)로 회수를 실제 수행했고, 회수 집합 참조를 각 사이클 loop-data seq 1 전이 이벤트의 `ref`에 기록했다(loop-state-record §6 DP-L5, loop-binding §3.3).

- **회수 집합(3사이클 공통, seq 1 `ref` 실측).** v06-demo-a·b·c.jsonl seq 1의 `ref` 필드가 전부 동일하다:

  ```json
  "ref":{"recall_set":["mi-0013","mi-0015","mi-0016","mi-0018","mi-0028"]}
  ```

  이는 content 원문이 아니라 **경량 mi-id 배열**이다(원문 필요 시 그 id로 Memory 백엔드 Recall — 경량 참조, §5.1 loop-binding §3.3). memory content를 loop-data에 중복 저장하지 않았다.

- **purpose.** "v0.6 Loop 시연 사이클에 관련된 Active Lesson·Best Practice 회수" — 착수 전 관련 Lessons·이전 결정·컨텍스트 회수(Consult).

- **scope(narrowing).** `kind`∈{lesson, best-practice} + `labels.status`=Active + `situation` 4태그 투영 + 기본 `detail`=index(index-first, memory-binding §3.2). 회수된 5건은 전부 status=Active이며 kind∈{lesson, best-practice}임을 index.jsonl 실측으로 확인했다:

  | 회수 id | stable_id | kind | status(실측) | situation(실측) |
  |---|---|---|---|---|
  | mi-0013 | L-05 | lesson | Active | completion-report-authoring, artifacts-listing |
  | mi-0015 | L-07 | lesson | Active | existence-claim-authoring, file-resource-status-description |
  | mi-0016 | L-08 | lesson | Active | delegation-message-authoring, done-clause-specification |
  | mi-0018 | BP-01 | best-practice | Active | rework-execution, defect-class-full-audit |
  | mi-0028 | L-11 | lesson | Active | delegation-message-authoring, artifact-text-specification, pointer-notation |

- **situation 4태그(투영 — Active 풀에서 회수 집합을 정확히 산출하는 4태그).** {`completion-report-authoring`, `existence-claim-authoring`, `delegation-message-authoring`, `rework-execution`}. index.jsonl Active lesson/BP 풀(mi-0009~0018·mi-0026~0029) 전수에 이 4태그 합집합을 적용하면 정확히 {mi-0013(L-05), mi-0015(L-07), mi-0016(L-08), mi-0018(BP-01), mi-0028(L-11)} 5건이 선택된다 — 4태그 중 어느 것도 회수 집합 밖 Active 항목을 매칭하지 않는다(실측 대조). 이는 시연 사이클 수행의 상황(완료 보고 작성·존재 주장·위임 작성·재작업 이행)을 투영한 것이다.

- **단일 Port·우회 0(INV-7).** 회수·기록은 Memory Service Interface(Recall) 경유이며 영속성 백엔드 직접 접근이 없다. seq 1 `ref`에 회수 집합 참조를 기록함으로써 DP-L5(Consult 전이 `ref` = 회수 집합 참조)를 실증했다.

## §3. 관측 결과 판정 방식 (done 1 — 실측 대조)

각 시연의 "관측 결과"는 실측 loop-data line을 절차서 §8/§10/§11 (C) **기대 전이 이벤트 명세**와 필드 단위(seq·from_stage·to_stage·trigger·outcome·retry_count·actor·ref·at)로 대조해 판정한다. **기대 전이표와 전건 일치**하면 충족, 다르면 위반, 근거 부족·검사 범위 한계면 판정 불가로 표기한다(§7 절차서 실패 처리 규칙 1·2). 기대된 되돌림(ⓑ·ⓒ)·에스컬레이션(ⓒ)이 정확히 관측되면 충족이다(절차서 §7-4 음성/양성 구분). 시연 중 Loop 구동 연산 자체의 수행 불능(연산 실패)은 관측되지 않았다(절차서 §7-5).

## §8. `at`·timestamp 성격 구분 (done 3 — L-09, 순서 값 / 물리 시각 구분)

L-09(기록 timestamp/순서 값의 성격 구분, 물리 시각 주장은 실측 대조 후에만)에 따라 본 기록은 loop-data `at`·memory-data timestamp를 **순서 값**으로 서술하고 **물리 벽시계 시각으로 주장하지 않는다**.

- **loop-data `at` = 순서 값(loop-binding §3.3).** 각 파일 `at`은 정수 서수 1..N으로 seq와 동반 단조 증가(ⓐ 1..7·ⓑ 1..9·ⓒ 1..11). 전이 순서를 확정할 뿐 물리 시각이 아니다. 본 기록은 `at`을 "실제 수행 시각"으로 서술하지 않는다.
- **memory-data timestamp = 생성기 배정 단조 순서 값(기존 시퀀스 연속).** mi-0031~0034의 timestamp는 각각 `2026-07-05T22:20:17.602+09:00`·`...18.602`·`...19.602`·`...20.602`로, 직전 기존 항목 mi-0030(`2026-07-05T22:20:16.602+09:00`)에서 **+1초씩 연속**하는 생성기 배정 순서 값이다. 이는 mi 시퀀스의 단조 순서를 나타낼 뿐 물리 생성 시각이 아니다.
- **실측 대조(L-09 — 물리 시각 필요 시 실측 후 별도 공개).** timestamp 필드 값(2026-07-05T22:20:x)과 파일의 **물리 mtime**은 서로 다르다 — 실측한 물리 mtime: loop-data v06-demo-a.jsonl `2026-07-06 09:54:42`·b `2026-07-06 10:05:56`·c `2026-07-06 10:26:51`; store mi-0031.json `2026-07-06 09:54:29`·mi-0032 `10:05:30`·mi-0033 `10:05:37`·mi-0034 `10:18:57`; index.jsonl `2026-07-06 10:19:08`. 물리 mtime은 **2026-07-06**(그 다음 날)로 timestamp 필드 값(2026-07-05T22:20:x)과 **불일치**한다. 이 불일치가 timestamp 필드가 물리 시각이 아니라 생성기 배정 순서 값임을 직접 실증한다. 본 기록은 timestamp/`at`을 시연의 물리 수행 시각으로 주장하지 않으며, 물리 시각은 위 mtime 실측값으로만 별도 공개한다.
