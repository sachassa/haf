## §0. 이 문서의 위치와 정본 경계

- **이 문서는 시연 절차서다.** 시연 6종을 **어떻게 수행하고 무엇으로 판정하는가**의 절차·입력·기대 관측·판정 문장·기록 포맷을 정의한다. 시연의 실제 **수행 기록**은 별도 산출물(시연 수행 기록, Task M7)이, **독립 판정**은 검증 단계(Verifier = CP2, 검증 리포트)가 담당한다. 이 절차서는 그 두 작업의 입력이다.
- **정본은 specs/04-memory.md·specs/05-lessons.md(§3 Core Contract·§7 완료 기준)와 확정 framework/memory/ 4종 문서다.** 이 절차서는 그 계약·완료 기준을 **재정의·확장하지 않는다**. 계약 요소·판정 문장·필드는 § 포인터로만 참조하고, 필수/선택 표기는 정본 그대로 보존한다 (필수/선택 표기 보존 — L-03, session-handoff-v0.2 §1.5-2).
- **필드 소속 명시(혼입 방지).** 인용하는 필드·reason 코드는 소속 계약을 § 포인터로 명시한다 — 유사한 실패 구조를 가진 다른 계약의 필드명을 끌어오지 않는다 (필드 계약 혼입 방지 — L-02, session-handoff-v0.2 §1.5-1). 특히 **Memory Failure Report reason(04 §3.2-D — SchemaViolation/DuplicateId/IndexInconsistent/MissingPurpose/MissingScope/UnboundedScope/ScopeUnresolvable/PortBypass)** 와 **Lessons Failure Report reason(05 §3.2-F — InvalidSource/MissingProvenance/PromotionCriteriaUnmet/NotApproved/PortReadFailed/PortWriteFailed/ScopeExceeded/SignatureUnmatchable)** 은 서로 다른 계약의 코드 집합이며 혼입하지 않는다 (§6-4).
- **물리 실현 지점 비하드코딩(done 3).** 시연 절차는 추상 Memory Service Interface 연산(Record·Recall)과 그 위에 올라탄 Lessons 특화 연산(Register Candidate·Promote·Recall·Judge Recurrence·Register Best Practice)만으로 성립한다. 물리 store·index·직렬화·실행 절차가 실현·관측되는 지점은 이 절차서에 하드코딩하지 않는다 — `framework/adapters/claude/memory-binding.md`(Adapter Binding 문서)가 정본이며 (04 §4·§4.1, 05 §4), 수행 기록(M7)이 그 문서를 참조해 각 절차 단계의 물리 지점을 기입한다 (§4).
- **동시 작성 산출물 불인용 (07 R2).** 같은 v0.4 Wave에서 동시 작성 중인 Adapter Binding 산출물(memory-binding.md)의 미완성 내용을 인용·추측하지 않는다. 물리 지점이 필요한 자리에는 "Adapter Binding 문서 소관" 포인터만 둔다 (§4). 확정 입력 문서(framework/memory/ 4종·docs/v0.4-promotion-review.md)만 참조한다.
- **Lesson 후보 본문 비복제(constraint).** 초기 실데이터 Lesson 후보 8건과 Best Practice 후보 1건의 확정 필드 본문은 이 절차서에 전문 복제하지 않는다. 식별 라벨(L-01~L-08·BP-01)과 출처 § 포인터·승인 참조(docs/v0.4-promotion-review.md §2·§3)만 둔다. 전문 필드값의 실제 등록은 시연 수행 기록(M7)의 소관이며, M7은 그 확정 필드값을 그대로 등록한다(추측·개작 금지 — promotion-review §4).
- **라벨 주의 (새 용어 신설 없음).** 본 문서가 쓰는 "시연 ⓞ/ⓐ/ⓑ/ⓒ/ⓓ/ⓔ", "판정 문장", "기록 포맷", 기록 포맷 필드 이름(관측 결과·근거·수행 단계 로그·단일 Port 경유·수행 물리 지점), 후보 라벨(L-01~L-08·BP-01)은 조직 편의를 위한 **서술 라벨**이며 Glossary 표제어가 아니다 — 정본 용어처럼 신설·확장하지 않는다 (v0.3-demo-procedure §0 라벨 처리 동형). 계약 용어(Memory Item / Memory Index / Index Entry / Record / Recall / Lesson / Best Practice / applicability / provenance / kind / scope / status / verdict 등)와 판정 값(충족/위반/판정 불가)은 전부 Glossary·04·05·framework/memory 4종·verification-checklist.md 정본에서 인용한다.
- **토큰 절제.** 이 문서는 `docs/` 소속이라 Core 경계 금지 토큰 규칙(structure.md §5 C-3)의 직접 대상은 아니다. 그러나 시연 시나리오는 **추상 계약 수준**으로 구성하며 특정 AI·언어·툴체인·직렬화 형식·매칭 알고리즘·물리 경로 토큰을 넣지 않는다 — 절차가 오직 04·05 계약만으로 성립함을 보이기 위함이다 (mention/use 경계 — L-04).

## §2. 시연 6종과 완료 기준 17건의 1:1 대응 (done 2)

세 출처의 완료 기준을 **재정의 없이 인용**하고, 각 기준을 이를 실증하는 시연(재현형) 또는 검증 리포트(정적·스캔형)에 1:1 대응시킨다. 각 시연의 판정 문장(§7~§13의 (D))은 아래 표의 해당 문장을 **그대로 인용**한다.

### §2.1 방식·소관 구분

- **재현형** — Memory Service Interface·Lessons 연산을 실제 수행·관측하는 시연. 본 절차서 소관(수행 M7 / 판정 검증 리포트).
- **정적·스캔형** — 산출물 본문을 스캔하거나 정적 값을 대조하는 방식. **검증 리포트 소관**으로 배정한다(배정 명시). 이는 v0.3-demo-procedure §2가 스캔형 2건(Core AI 비의존·경계)을 검증 단계로 배정한 것과 동형이다.

## §4. 물리 수행 지점 경계 (done 3)

- 시연 절차(§7·§8·§10·§11·§12·§13)의 모든 단계는 **추상 Memory Service Interface 연산(Record·Recall)** 과 그 위에 올라탄 **Lessons 특화 연산(Register Candidate·Promote·Recall·Judge Recurrence·Register Best Practice)** 으로 서술된다. 어떤 단계도 실제 파일 경로·store·index·직렬화 형식·매칭 알고리즘 같은 물리 지점을 명시하지 않는다.
- 물리 실현 지점(store·index·직렬화·실행 절차가 어디에서 어떻게 수행·관측되는가)은 `framework/adapters/claude/memory-binding.md`(**Adapter Binding 문서**)가 정본이다 (04 §4·§4.1 — Memory Item 직렬화·Store 물리 저장·Index 물리 구현·백엔드 격리; 05 §4 SP-1 레코드 직렬화·저장 위치·SP-2 매칭 구현).
- **수행 기록(M7)의 기입 방식.** M7은 §3 기록 포맷의 "수행 물리 지점" 필드에, 각 절차 단계가 물리적으로 실현된 지점을 **memory-binding.md를 참조하여** 기입한다. 절차서는 그 지점을 미리 확정·하드코딩하지 않는다.
- **07 R2 준수.** 같은 v0.4 Wave에서 동시 작성 중인 memory-binding.md의 미완성 내용을 이 절차서에서 인용·추측하지 않는다. 물리 지점이 필요한 자리는 위 포인터로만 처리한다.

이 경계로 인해, 이 절차서는 대상 환경이 바뀌어도 (04 §4.2·05 §4.2 이식 교체 지점) 유지된다 — 바뀌는 것은 "수행 물리 지점"의 실현뿐이고, 절차 단계·판정 문장·기록 포맷은 그대로다.

## §5. 단일 Port 경유·우회 접근 0건 관측 (done 4)

이 절은 전 시연(ⓞⓐⓑⓒⓓⓔ)에 공통으로 적용되는 횡단 관측 단계를 정의한다. ROADMAP v0.4 "모든 Memory 접근이 Memory Service Interface를 경유한다" / 04 §7·05 §7 "단일 Port 시연"을 실증한다.

### §5.1 연산 → 단일 Port 매핑

Lesson·Best Practice·재발 판정 레코드는 별도 저장 경로를 갖지 않는다. 셋 모두 Memory Item의 `kind`로 단일 Port 위에 올라탄다 (04 §3.4, 05 INV-1, lessons.md §5·§6). 각 시연의 연산은 다음과 같이 Memory Service Interface 연산으로 해소된다 — 이 매핑을 M7이 연산별로 관측·기록한다.

| 시연 연산 (05 §3.1) | 단일 Port 연산 (04 §3.1) | kind / scope |
|---|---|---|
| Register Candidate (ⓞ) / Promote (ⓞ) | Record — Memory Item 기록 + Index Entry 생성(INV-7) | kind=`lesson` (lessons.md §5.1) |
| Recall (ⓐ·ⓑ) | Recall — index-first, scope 해소(INV-4) | scope: `kind`=`lesson`, `labels`=상황 투영 (lessons.md §5.2, 04 §3.2-B) |
| Judge Recurrence 입력 조회 (ⓓ) / 판정 레코드 기록 (ⓓ) | Recall(매칭 Lesson 조회) + Record(판정 레코드) | 조회 scope `kind`=`lesson`; 기록 kind=`recurrence-judgment` (lessons.md §5.1) |
| Register Best Practice Candidate / Promote (ⓔ) / Recall (ⓔ) | Record + Recall | kind=`best-practice` (lessons.md §5.1) |

### §5.2 관측·우회 0건 확인 단계 (전 시연 공통)

1. **연산별 Port 경유 관측.** 각 시연의 모든 연산이 §5.1 매핑대로 Memory Service Interface(단일 Port)의 Record 또는 Recall로 수행됨을 관측한다. 소비자(Agent·Loop·Workflow·Verifier)는 백엔드에 직접 접근하지 않는다 (04 §3.4, memory-service.md §7).
2. **우회 접근 0건 확인.** 어떤 연산도 영속성 백엔드에 직접 접근하지 않았음을 확인한다. 직접 접근은 `PortBypass` 위반이다 (04 INV-1·§3.2-D reason, memory-service.md §5.3). M7은 PortBypass 건수가 **0**임을 §3 기록 포맷의 "단일 Port 경유 · 우회 0건" 필드에 기록한다.
3. **contract id 노출 확인(배정 명시).** 접근 계약 id가 `MemoryServiceInterface`임을 정적으로 확인하는 절(04 §7 "이때 contract id가 `MemoryServiceInterface`임을 보인다")은 **검증 리포트 소관**이다(§2.3). 대조 기준은 module-manifest.md §2 `contract` 값과 01 §8 예1이다. 본 절차서·M7은 연산의 단일 Port 경유(1·2)만 관측하고, contract id 정적 대조는 검증 리포트가 수행한다.

## §6. 실패 처리 규칙 (done 5, v0.3-demo-procedure §5 동형)

시연이 기대 관측과 **다르게 관측될 때**의 처리 규칙이다.

1. **은폐 없이 그대로 기록한다.** 관측이 기대와 달라도 실제 관측을 §3 기록 포맷의 "근거 (관측한 것)"에 그대로 남긴다. 실패·불일치를 숨기지 않는다 (Worker 금지 사항 — 실패 은폐 금지, 02 O5).
2. **판정 문장을 위반으로 표기한다.** 기대와 다르게 관측되면 해당 시연의 "관측 결과"를 **위반**으로 표기한다 (판정 값 정본: verification-checklist.md §1). 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기하며, 판정 불가를 충족으로 위장하지 않는다.
3. **재작업 여부 판단은 게이트 소관이다.** 이 절차서와 수행 기록(M7)은 관측·기록까지만 한다. 위반·판정 불가의 **재작업 여부 판단**은 검증 단계(Verifier, CP2)와 Advisor(CP3)의 소관이다. M7·절차서가 스스로 통과 처리하거나 재작업을 결정하지 않는다.
4. **연산 자체의 실패 보고 — reason 코드 소속 명시(혼입 방지).** 시연 중 연산이 실패하면 공통 Failure Report 구조로 관측·기록하되, **reason 코드의 소속 계약을 § 포인터로 명시한다** (L-02 필드 계약 혼입 방지 적용).
   - **Memory 연산 실패** → 04 §3.2-D 구조(`operation`/`reason`/`target`/`location`). reason은 Record 소속(SchemaViolation/DuplicateId/IndexInconsistent — 04 §3.1-A) 또는 Recall 소속(MissingPurpose/MissingScope/UnboundedScope/ScopeUnresolvable — 04 §3.1-B) 또는 단일 Port 우회(PortBypass — 04 INV-1). 소속 정본: memory-service.md §5.3 표.
   - **Lessons 연산 실패** → 05 §3.2-F 구조(`operation`/`reason`/`target`/`location`). reason은 InvalidSource/MissingProvenance/PromotionCriteriaUnmet/NotApproved/PortReadFailed/PortWriteFailed/ScopeExceeded/SignatureUnmatchable. 소속 정본: lessons.md §2.6.
   - 두 집합은 서로 다른 계약의 코드이며 섞지 않는다. 예: ⓑ의 MissingPurpose/MissingScope/UnboundedScope는 **04 Recall** 소속이고, ⓒ의 NotApproved는 **05 Promote** 소속이다.
   - **음성 시연 구분.** 연산 실패가 시연의 기대였는지(음성 시연 — ⓑ 회수 정책 거부, ⓒ NotApproved 거부)와 예기치 못한 실패인지를 근거에 구분해 기록한다. 음성 시연에서는 "기대된 거부가 정확한 reason으로 발생"이 **충족**이다.

5. **포맷 일치 관측.** 등록·승격된 각 Lesson(Memory Item kind=`lesson`)이 04 §3.2-A(Memory Item)·05 §3.2-A(Lesson 8필드) 스키마와 일치하고, 대응 Index Entry가 04 §3.2-C 스키마와 일치함을 대조한다 (04 §7 포맷 일치 시연; memory-store.md §2·§3). 필수/선택 표기 보존을 대조한다 (L-03).

## §8. 시연 ⓐ — 실패→Lesson→회수 사이클 (Active Lesson 최소 집합 회수)

목표: ⓞ가 승격한 Active Lesson이 **다음 작업의 Consult**에서 applicability 매칭(labels·kind 투영)으로 **최소 집합**만 회수됨을 끊김 없이 보여, 실패 → Lesson 생성 → 회수의 사이클을 완성한다. 근거: 05 §3.1-B·§7 학습 사이클·최소 회수, lessons.md §5.2, 04 §3.1-B·§8 예1.

### (A) 절차 단계

1. **다음 작업 상황 서술자 준비.** 회수를 유발할 다음 작업의 상황 서술자(situation descriptor)를 준비한다 (05 §3.2-C). 예: "기존 문서의 상태·결정 서술을 개정하는 작업"(L-06 applicability와 매칭되는 상황). 상황 서술자는 시연 입력이다.
2. **Recall 호출 (Consult).** `purpose`(예: "이 개정 작업에 관련된 Active Lesson 회수")와 `scope`(narrowing: `kind`=`lesson`, `labels`=상황 투영)를 갖는 Recall Request로 회수한다 (04 §3.1-B, memory-service.md §5.2). `detail`은 기본값 `index`다.
3. **applicability 매칭 (labels·kind 투영).** Port가 `kind`/`labels` 범위 조회로 후보를 좁힌 뒤, 상황 서술자 ↔ `applicability` 대조로 관련성을 산출한다 (lessons.md §5.2, 04 §9 결정 기록 "applicability는 labels·kind로 투영"). 매칭 계약 표면은 05 소유, 매칭 알고리즘은 Adapter 소관이며 절차서는 규정하지 않는다.
4. **최소 집합 관측.** 회수 결과가 ⓞ의 Active 8건 전량이 아니라 상황에 매칭되는 **최소 집합**(예: L-06 중심의 소집합)임을 관측한다 (05 INV-6, 04 INV-3). 기본 `detail=index`이므로 Index Entry(참조)만 반환되고 content 원문은 로드되지 않는다 (04 INV-4). 필요 시 특정 `id`에 대해 `detail=full`로 재회수한다 (04 §8 예1).
5. **사이클 완결 관측.** 회수된 Lesson의 `lesson`(실행 지시)이 다음 작업에 적용되어 같은 실패를 회피하는 경로가 성립함을 관측한다 (05 §8 예1 — 끊김 없는 사이클). ⓞ(생성·승격) → ⓐ(회수)가 이어져 실패 → Lesson 생성 → 회수 사이클이 완결된다.

### (B) 입력

- ⓞ가 승격한 Active Lesson 집합(8건, kind=`lesson`).
- 다음 작업 상황 서술자(시연 입력, (A)-1).
- Recall Request: `purpose` + `scope`{`kind`=`lesson`, `labels`=상황 투영}, `detail`=`index`(기본), `limit` 미지정(시스템 상한 `recall.limit.max`=20 적용 — module-manifest.md §2, memory-service.md §3.2).

### (C) 기대 관측

- 회수 결과가 상황에 매칭되는 **최소 집합**(전량 아님, 8건 미만)이다 (05 INV-6).
- 기본 `detail=index` — Index Entry만 반환, content 원문 비반환 (04 INV-4). 반환 Index Entry가 04 §3.2-C 스키마와 일치한다.
- 매칭이 상황 서술자 ↔ `applicability` 대조로 산출된다 (lessons.md §5.2).
- 회수가 단일 Port(Recall)로 수행되고 우회 0건이다 (§5).
- ⓞ→ⓐ 사이클이 끊김 없이 완결된다 (05 §7 학습 사이클).

### (D) 판정 문장 (인용 — §2 대응)

> (05 §7 학습 사이클 시연 인용) 한 작업의 실패 보고 `lesson_candidate`(여부=예) → Register Candidate → Verifier Learn 입력 → Advisor 승격 → Active Lesson → **다음 작업 Consult에서 적용 조건 매칭으로 회수**됨을, 실패 → Lesson 생성 → 회수의 끊김 없는 사이클로 보인다.

> (ROADMAP v0.4 인용) 실패 → Lesson 생성 → 다음 작업에서 회수 사이클을 시연한다 (Learn from Failure 검증).

> (05 §7 최소 회수 시연 인용) 회수가 전량이 아니라 적용 조건이 매칭되는 최소 집합만 반환함을 보인다 (INV-6, Token Efficiency).

### (E) 기록 포맷 (§3 인스턴스 — M7이 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §8-D 세 문장을 M7이 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (Recall Request의 purpose·scope, 회수된 Index Entry 집합·건수(최소 집합), detail=index로 content 비반환 여부, 매칭된 라벨(예: L-06), Index Entry 스키마 대조) |
| 수행 단계 로그 | (§8-A 단계 1~5의 수행·관측 로그 — 특히 단계 4 최소 집합, 단계 5 사이클 완결) |
| 단일 Port 경유 · 우회 0건 | (Recall이 단일 Port로 수행됨 · PortBypass 0건, §5) |
| 수행 물리 지점 | (Recall이 실현·관측된 지점 — memory-binding.md 참조로 기입, §4) |

## §10. 시연 ⓑ — 회수 정책 거부 3케이스 (MissingPurpose / MissingScope / UnboundedScope + 기본 index)

목표: 회수 정책이 Port에서 강제됨을 세 거부 케이스와 기본 회수 세분도로 보인다 — `purpose`/`scope` 없는 Recall 거부, 전량 로드 겨냥 scope 거부, 기본 `detail=index`(content 원문 비반환). 근거: 04 §3.1-B·§3.1-C·INV-2/3/4, memory-service.md §5.2·§5.3.

### (A) 절차 단계 (음성 시연 3케이스 + 기본 index 관측)

1. **케이스 1 — MissingPurpose.** `purpose`를 누락한 Recall Request로 회수를 시도한다. `MissingPurpose`로 거부됨을 관측한다 (04 §3.1-B, INV-2; memory-service.md §5.2-1·§5.3). Failure Report는 04 §3.2-D 구조이며 reason 소속은 **Recall**이다 (§6-4).
2. **케이스 2 — MissingScope.** `scope`를 누락한 Recall Request로 시도한다. `MissingScope`로 거부됨을 관측한다 (04 §3.1-B, INV-2; §5.3).
3. **케이스 3 — UnboundedScope.** narrowing 차원(`kind`/`labels`/`timeRange`/`source`)도 finite `limit`도 없이 전체 store를 겨냥하는 scope로 시도한다. `UnboundedScope`로 거부됨을 관측한다 (04 §3.1-B, INV-3; §5.3). 전량 로드가 인터페이스 수준에서 차단된다.
4. **기본 detail=index 관측.** narrowing 차원을 갖춘 정상 Recall(예: `scope`{`kind`=`lesson`})을 `detail` 미지정으로 호출하면 기본값 `index`가 적용되어 **Index Entry(참조)만 반환**되고 content 원문이 반환되지 않음을 관측한다 (04 INV-4, memory-service.md §5.2-4). content가 필요하면 `detail=full`+scope 한정으로 명시 요청해야 함을 대조한다.

### (B) 입력 (04 §8 예2 재현 어휘)

| 케이스 | Recall Request | 기대 reason (소속) |
|---|---|---|
| 1 | `purpose` 누락 (+ 임의 `scope`) | `MissingPurpose` (Recall — 04 §3.1-B) |
| 2 | `scope` 누락 (+ 임의 `purpose`) | `MissingScope` (Recall — 04 §3.1-B) |
| 3 | `purpose` 有 + `scope`=전체 store(narrowing·limit 없음) | `UnboundedScope` (Recall — 04 §3.1-B) |
| 4 (양성 대조) | `purpose` 有 + `scope`{`kind`=`lesson`} + `detail` 미지정 | 성공 — Index Entry만 반환(기본 index) |

- reason 코드는 전부 **04 Recall** 소속이다 (05 Lessons reason과 혼입 금지 — §6-4, L-02).
- 예시 scope 값·키는 04 §3.2-B·§8 예2 재현이며 특정 AI·언어·툴체인 토큰이 아니다.

### (C) 기대 관측

- 케이스 1~3이 각각 정확한 reason(`MissingPurpose`/`MissingScope`/`UnboundedScope`)으로 거부된다 — **음성 시연의 기대된 거부** (§6-4).
- Failure Report가 04 §3.2-D 구조(`operation`=Recall·`reason`·`target`·`location`)와 일치한다.
- 케이스 4에서 기본 `detail=index`로 Index Entry만 반환되고 content 원문이 반환되지 않는다 (04 INV-4).
- 회수 시도가 전부 단일 Port(Recall)로 수행되고 우회 0건이다 (§5).

### (D) 판정 문장 (인용 — §2 대응)

> (04 §7 회수 정책 시연 인용) `purpose` 또는 `scope`가 없는 Recall이 거부되고(INV-2), 전체 store를 겨냥한 Recall이 거부되며(INV-3), 기본 회수가 Index Entry만 반환함(INV-4)을 보인다. 즉 Memory가 필요할 때만·목적을 명시하고·최소 범위로만 읽힘을 시연한다.

> (ROADMAP v0.4 인용) Memory는 필요한 경우에만 읽는다 — 회수 규칙이 최소 Context 원칙을 지킨다 (Token Efficiency 검증).

## §11. 시연 ⓒ — 승격 권한 차단 (승인 기록 없는 승격 → NotApproved, 음성 케이스)

목표: Advisor 승인 기록 참조 없는 승격 시도가 `NotApproved`로 거부됨을 보여, 승격 권한이 Advisor 전속임을 실증한다 (음성 케이스). 근거: 05 INV-4·§3.1-A·§3.2-F, lessons.md §3.2.

### (A) 절차 단계 (음성 시연)

1. **Candidate 준비.** 승격 대상 Lesson Candidate 1건을 준비한다 (예: ⓞ에서 등록만 하고 승격 전 상태로 둔 후보 하나, 또는 별도 Candidate). status=`Candidate`이며 5필드·provenance는 채워져 있다(승격 3조건 중 1·2는 만족).
2. **승인 기록 없는 승격 시도.** **docs/v0.4-promotion-review.md의 해당 승인 기록 참조를 첨부하지 않고** Promote(Candidate → Active)를 시도한다 (승격 3조건 중 3 — Advisor 승인 — 미충족).
3. **NotApproved 거부 관측.** 승격이 거부되고 Failure Report reason이 `NotApproved`임을 관측한다 (05 §3.1-A Promote 실패 보고, INV-4; lessons.md §3.2). Failure Report는 05 §3.2-F 구조이며 reason 소속은 **Promote(Lessons)** 이다 (§6-4 — 04 Memory reason과 혼입 금지).
4. **양성 대조.** 같은 Candidate에 promotion-review 승인 기록 참조를 첨부하면 Active로 승격됨을 대조한다 (ⓞ-4와 동일 경로) — 승격 성립 조건은 승인 기록 참조 첨부다 (Advisor 결정 (b), 05 INV-4).

### (B) 입력

| 시도 | 승인 기록 참조 첨부 | 기대 결과 (reason 소속) |
|---|---|---|
| 음성 (차단 대상) | 없음 | 거부 — `NotApproved` (Promote — 05 §3.1-A) |
| 양성 (대조) | docs/v0.4-promotion-review.md 해당 행 | 승격 — status=`Active` |

- reason `NotApproved`는 **05 Lessons(Promote)** 소속이다 (04 Memory reason과 혼입 금지 — §6-4, L-02).
- Worker는 후보를 제출하고 Verifier는 Learn 입력을 제공하나, 승격 결정 권한은 Advisor에 있다 (05 INV-4, lessons.md §3.2). 자기 점검은 승격 근거가 아니다.

### (C) 기대 관측

- 승인 기록 참조 없는 승격 시도가 `NotApproved`로 거부된다 — **음성 시연의 기대된 거부** (§6-4).
- Failure Report가 05 §3.2-F 구조(`operation`=Promote·`reason`=`NotApproved`·`target`·`location`)와 일치한다.
- 양성 대조에서 승인 기록 참조 첨부 시 status=`Active`로 승격된다.
- 승격 시도가 단일 Port로 수행되고 우회 0건이다 (§5).

### (D) 판정 문장 (인용 — §2 대응)

> (05 §7 승격 권한 시연 인용) Advisor 승인 없는 승격이 차단됨(reason=NotApproved)을 보인다 (INV-4).

### (E) 기록 포맷 (§3 인스턴스 — M7이 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §11-D 문장을 M7이 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (음성 시도의 Failure Report `operation`=Promote·`reason`=`NotApproved`, 양성 대조의 status=Active, reason 소속=Promote(05) 대조) |

## §12. 시연 ⓓ — 재발 판정 3분류 (Novel / RecallGap / Recurrence)

목표: 새 실패를 세 결과 중 정확히 하나로 분류함을 케이스로 보여, "같은 실수를 반복하지 않는다"를 검증 가능화한다. 회수 이력은 03-loop 미구현이므로 **수동 제공 입력**이다. 재발 판정 레코드(kind=`recurrence-judgment`)를 기록한다. 근거: 05 §3.1-C·§7, lessons.md §4·§5.1.

### (A) 절차 단계 (3케이스)

1. **입력 준비.** 각 케이스에 대해 (i) 새 실패의 `failure_signature`(실패 보고에서 도출), (ii) 그 작업의 **회수 이력(작업별 회수 집합)** — 03-loop 미구현이므로 **시연 입력으로 수동 제공** (05 §9·04 §9 결정 기록: 회수 이력은 03 소관, 05는 입력으로 받음), (iii) `applicability` 매칭 기존 Active Lesson(Port 조회 — 단일 Port Recall) 을 준비한다 (05 §3.1-C).
2. **케이스 Novel.** 매칭되는 기존 Active Lesson이 없는 새 실패 → `Novel`로 판정됨을 관측한다 (05 §3.1-C, lessons.md §4). 후속: 신규 후보 등록 대상 (실패 아님).
3. **케이스 RecallGap.** 매칭되는 Lesson이 존재했으나 그 작업의 (수동 제공) 회수 집합에 **없었던** 실패 → `RecallGap`로 판정됨을 관측한다. 이는 회수 규칙/적용 조건의 결함이며 Lesson 내용 결함이 아니다 (lessons.md §4).
4. **케이스 Recurrence.** 매칭되는 Lesson이 존재하고 (수동 제공) 회수 집합에 **있었음에도** 같은 실패가 발생 → `Recurrence`로 판정됨을 관측한다. 이는 "같은 실수 반복"이며 Lesson 효과 미달이다 (05 INV-7, lessons.md §4).
5. **판정 레코드 기록.** 각 케이스의 재발 판정 레코드(05 §2.5 5필드: `failure_signature`·`matched_lesson_id`·`was_recalled`·`verdict`·`follow_up`)를 kind=`recurrence-judgment`로 Record한다 (lessons.md §5.1, 단일 Port). 레코드가 05 §3.2-E 스키마와 일치함을 대조한다.

### (B) 입력 (수동 제공 회수 이력 명시)

| 케이스 | 매칭 기존 Active Lesson | 회수 집합(수동 제공)에 포함? | 기대 verdict |
|---|---|---|---|
| Novel | 없음 | (해당 없음) | `Novel` |
| RecallGap | 있음 | 아니오 | `RecallGap` |
| Recurrence | 있음 | 예 | `Recurrence` |

- **회수 이력은 시연 입력으로 수동 제공한다** — 03-loop 루프 상태 기록이 미구현이므로 (Advisor 결정 (c); 05 §9 "회수 이력은 03 소관, 05는 입력으로 받는다"). M7은 각 케이스의 회수 집합을 입력으로 명시 제공하고, 이것이 수동 제공 입력임을 근거에 기록한다.
- 매칭 기존 Active Lesson은 ⓞ의 Active 집합에서 취할 수 있다(예: RecallGap·Recurrence 케이스는 L-06·L-07 등과 매칭되는 실패를 구성).

### (C) 기대 관측

- 세 케이스가 각각 정확히 `Novel`/`RecallGap`/`Recurrence`로 분류된다 (05 §3.1-C 정확히 하나).
- 회수 이력이 수동 제공 입력임이 근거에 명시된다.
- 각 재발 판정 레코드(kind=`recurrence-judgment`)가 05 §3.2-E 5필드 스키마와 일치하고, 단일 Port(Record)로 기록된다 (§5).
- 매칭 Lesson 조회(Recall)·판정 레코드 기록(Record)이 단일 Port로 수행되고 우회 0건이다 (§5).

### (D) 판정 문장 (인용 — §2 대응)

> (05 §7 재발 판정 시연 인용) 같은 실패가 (a) 회수된 Lesson과 겹치면 `Recurrence`, (b) 존재하나 미회수면 `RecallGap`, (c) 매칭 없으면 `Novel`로 분류됨을 케이스로 보인다 (INV-7 — "같은 실수를 반복하지 않는다"의 검증 가능화).

### (E) 기록 포맷 (§3 인스턴스 — M7이 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §12-D 문장을 M7이 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (케이스별 verdict 값, 매칭 여부, 회수 집합(수동 제공) 포함 여부, 재발 판정 레코드 5필드·kind=recurrence-judgment 스키마 대조) |
| 수행 단계 로그 | (§12-A 단계 1~5의 수행·관측 로그 — 3케이스 판정·레코드 기록) |
| 단일 Port 경유 · 우회 0건 | (매칭 조회 Recall·판정 레코드 Record가 단일 Port로 수행됨 · PortBypass 0건, §5) |
| 수행 물리 지점 | (Recall·Record가 실현·관측된 지점 — memory-binding.md 참조로 기입, §4) |

## §13. 시연 ⓔ — Best Practice 대칭 (성공 완료 보고 → BP → 회수, Lesson과 동일 계약)

목표: v0.3 §1.4 모범 사례 기반 Best Practice 1건(BP-01)이 Candidate → 승격 → 회수를 Lesson과 **동일한 계약**으로 통과함을 보여, 실패↔성공 대칭을 실증한다. 근거: 05 §3.1-D·INV-8·§7, lessons.md §3.3, docs/v0.4-promotion-review.md §3.

### (A) 절차 단계

1. **출처 확인.** Best Practice 후보 BP-01의 출처를 확인한다: docs/session-handoff-v0.3.md §1.4의 기록된 모범 사례(재작업 시 지시 범위 밖 동종 결함을 자가 검출·교정·공개; v0.2 §1.4 동종 사례 병기). Verify 통과 완료 보고 기반이므로 provenance가 실재한다 (Advisor 결정 (a), 05 §3.1-D). 확정 필드값 원본·승인: docs/v0.4-promotion-review.md §3 BP-01.
2. **Register Best Practice Candidate.** BP-01을 Register Best Practice Candidate로 등록한다 (05 §3.1-D, lessons.md §3.3). 입력은 02 §3.2-C 완료 보고(Verify 통과) 계열이며, status=`Candidate`, provenance 4필드(05 §2.4)를 실기입한다(promotion-review §3 확정값 그대로). 등록은 단일 Port의 Record다 (Memory Item kind=`best-practice`, §5.1).
3. **승인 기록 참조 첨부 → Active 승격.** BP-01을 Promote한다. Lesson과 **동일한 권한·절차**를 따른다 (05 INV-4·INV-8) — docs/v0.4-promotion-review.md §3 BP-01 참조를 승인 기록으로 첨부하는 것이 승격 성립 조건이다 (Advisor 결정 (b)). 승격 시 status=`Active`, 안정 `id`·매칭 `applicability`를 갖는다.
4. **회수 (Lesson과 동일 계약).** BP-01을 다음 유사 작업의 Consult에서 회수한다 (05 §3.1-B). scope는 `kind`=`best-practice`, `labels`=상황 투영 (lessons.md §5.2). 회수가 Lesson 회수(ⓐ)와 **동일한 Recall 계약·회수 정책**(최소 범위·기본 index)으로 동작함을 대조한다 (05 INV-8).
5. **대칭 관측.** BP-01의 스키마(05 §3.2-B 7필드)가 Lesson(05 §3.2-A 8필드)과 대칭임을 대조한다: `Lesson.failure`↔`BestPractice.success`, `Lesson.cause`+`Lesson.lesson`↔`BestPractice.practice`, `id`·`status`·`applicability`·`provenance` 공유 (lessons.md §2.2).

### (B) 입력

- Best Practice 후보 BP-01. 출처: docs/session-handoff-v0.3.md §1.4 (v0.2 §1.4 동종 사례 병기). 확정 필드값 원본: docs/v0.4-promotion-review.md §3 (M7이 그대로 등록).
- Advisor 승격 승인 기록: docs/v0.4-promotion-review.md §3 BP-01 (승인, promotion-review §4) — 시연 착수 전 제공 (Advisor 결정 (b)).
- kind 값: `best-practice` (lessons.md §5.1). 회수 상황 서술자(시연 입력).

### (C) 기대 관측

- BP-01이 status=`Candidate`로 Register되고 provenance 4필드가 실기입된다(Verify 통과 완료 보고 기반 — provenance 실재).

- 회수가 Lesson 회수와 동일한 Recall 계약·회수 정책(최소 범위·기본 index)으로 동작한다 (05 INV-8).
- BP 스키마가 Lesson과 대칭임이 대조된다.
- 모든 저장·회수가 단일 Port로 수행되고 우회 0건이다 (§5).

### (D) 판정 문장 (인용 — §2 대응)

> (05 §7 Best Practice 대칭 시연 인용) 성공 완료 보고 → Best Practice 생성 → 회수가 Lessons와 동일 계약으로 동작함을 보인다 (INV-8).

## §14. 정본 경계·용어 self-note

- **재정의 없음.** 본 절차서의 모든 판정 문장은 04 §7·05 §7·ROADMAP v0.4 완료 조건의 인용이고, 모든 절차 단계·입력·기대 관측은 04·05 §3 Core Contract와 확정 framework/memory 4종 문서(memory-service·memory-store·lessons·module-manifest)의 계약·규칙 인스턴스다. 어떤 계약 요소도 이 문서에서 진위가 확정되지 않는다 — 판정 기준은 항상 정본 §이다 (04·05 계약 재정의 0).
- **필드 소속 명시·혼입 방지 (L-02).** reason 코드·필드는 소속 계약을 § 포인터로 명시했다. **04 Memory Failure Report reason(§3.2-D)** 과 **05 Lessons Failure Report reason(§3.2-F)** 을 혼입하지 않았다 — ⓑ의 MissingPurpose/MissingScope/UnboundedScope는 04 Recall, ⓒ의 NotApproved는 05 Promote 소속으로 구분했다 (§6-4, §10-B·§11-B 표).
- **필수/선택 표기 보존 (L-03).** Recall Request `detail`("아니오(기본 `index`)")·`limit`("아니오")·`purpose`/`scope`("예") 등 필드의 필수/선택 표기를 정본(04 §3.2-B, memory-service.md §4.2) 그대로 보존했다. Lesson `supersedes`("아니오") 등 선택 표기도 05 §3.2-A 그대로다.
- **Lesson 후보 본문 비복제 (constraint).** Lesson 후보 8건(L-01~L-08)·Best Practice 후보 1건(BP-01)의 확정 필드 본문을 이 절차서에 전문 복제하지 않았다 — 식별 라벨·출처 § 포인터·승인 참조(docs/v0.4-promotion-review.md §2·§3)만 두었다. 전문 등록은 M7 소관이며 M7은 promotion-review 확정값을 그대로 등록한다.
- **새 용어 신설 없음 (Glossary INV-4).** 계약 용어(Memory Item / Memory Index / Index Entry / Record / Recall / Lesson / Best Practice / applicability / provenance / kind / scope / status / verdict / recurrence-judgment 등)와 판정 값(충족/위반/판정 불가)은 전부 Glossary·04·05·framework/memory 4종·verification-checklist.md 정본에서 인용했다. "시연 ⓞ~ⓔ", "판정 문장", "기록 포맷"과 그 필드 이름, 후보 라벨 L-01~L-08·BP-01은 조직 편의용 서술 라벨이며 Glossary 표제어가 아니다 (§0 라벨 주의).
- **물리 토큰 0건 · memory-binding.md 불인용 (done 3, 07 R2, L-04).** 시연 시나리오는 추상 계약 수준으로 구성했고 특정 AI·언어·툴체인·직렬화 형식·매칭 알고리즘·물리 경로 토큰을 두지 않았다. 물리 실현이 필요한 자리는 "Adapter Binding 문서(memory-binding.md) 소관" 포인터로만 처리했고, 동시 작성 중인 memory-binding.md의 내용을 인용·추측하지 않았다.
- **contract id·AI 비의존 배정 명시 (done 2).** 04 §7의 contract id 노출 확인과 04 §7·05 §7의 AI 비의존 시연은 정적·스캔형이므로 검증 리포트 소관으로 배정하고 §2.3·§2.4·§5.2-3에 명시했다.
- **상태 서술 전수 대조 (L-01·L-06) 자기 적용.** ⓞ-1에서 후보 8건을 출처 §에서 전수 재열거해 건수를 확정하는 단계를 두어, 이 절차서 자신이 L-01(상태 서술 전수 대조)·L-06(부분 개정 잔여 방지) 교훈을 적용했다.
