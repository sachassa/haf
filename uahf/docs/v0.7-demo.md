## §0. 이 문서의 위치·정본 경계·오케스트레이션 사실 (Advisor 제공)

### §0.1 위치·정본 경계

- **이 문서는 수행 기록이다.** 시연 1건을 **실제로 어떻게 수행했고 무엇이 관측됐는가**를 실값으로 기록한다. **독립 판정**은 검증 단계(Verifier = CP2)가, **최종 승인**은 Advisor(CP3)가 담당한다 — 본 기록은 그 판정의 입력이며 스스로 최종 승인을 내지 않는다(02 §3.2-A). 관측 결과의 "충족/위반/판정 불가/판정 유보"는 실측 대조 관측이며, 게이트 통과의 최종 확정이 아니다.
- **판정 문장은 전재다(재정의 0).** 각 판정의 판정 문장은 docs/v0.7-demo-procedure.md §8-D의 원문(07 §7 시연 가능 문장·ROADMAP v0.7 완료 조건 인용 + 예/아니오 환원)을 **그대로 옮긴다**. 새 판정 기준을 창설하지 않는다.
- **Work Graph 인스턴스·Merge Result는 문서 형태 구조화 섹션이다(workflow-binding §3.2 정본, OQ-WB-1 해소).** 본 기록 §4.3(Work Graph 인스턴스)·§6.2(Merge Result)가 그 구조화 섹션이다. 새 데이터 백엔드 디렉터리를 신설하지 않았다.
- **소유 경계 준수(07 R4·append-only).** 본 작업의 소유 경계는 이 1파일(docs/v0.7-demo.md)이다. 픽스처(docs/v0.7-demo-fixtures/)·loop-data/·memory-data/를 **수정하지 않았고**, 전부 읽기 전용 실측으로만 인용했다. framework/·specs/·기존 memory-data 39건·기존 loop-data 3파일(v06-demo-*) 무변경.

## §3. 관측 결과 판정 방식 (실측 대조)

각 판정의 "관측 결과"는 실측 산출물(Work Graph 인스턴스 필드 값·loop-data 21 line·CP2 리포트·Merge Result 4필드·memory-data 항목)을 절차서 §8-C 기대 기록 명세·§8-D 예/아니오 환원과 대조해 판정한다. **기대와 전건 일치**하면 **충족**, 다르면 **위반**, 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기한다(절차서 §7-1·§7-2). 특정 판정이 WF9 재현 범위 밖(CP2 마일스톤 정적 스캔 소관)이면 **판정 유보**로 표기하고 충족으로 위장하지 않는다(절차서 §7-2·§2.2 배정). 기대된 충돌(충돌 유도 지점 1건이 Merge 단계 3에서 검출→중재→해소)이 정확히 관측되면 충돌 처리 시연은 충족이다(절차서 §7-4). 시연 중 Workflow 연산 자체의 수행 불능(연산 실패)은 관측되지 않았다(절차서 §7-5).

1. **Decompose 착수·회수.** Advisor(주 세션)가 큰 작업 1건(용어 카드 3부작 — 픽스처 기반 소형 워크플로)을 수령하고 Workflow 수준 Consult 회수(§2.1 [mi-0029])를 수행했다.

- **경계(merge-rules §4.1).** Merge는 개별 검증을 재수행하지 않았다 — 개별 판정 기준은 06 소관·단계 전이는 03 소관이며, Workflow는 수합·상호 참조 대조·충돌 검출·중재 라우팅(오케스트레이션)만 수행했다(INV-8, §7.5 경계 시연 보강).
- **단계 2·3 구분(Advisor 확정 설계 반영).** 단계 2(crossRefStatus)는 각 Task가 참조한 **확정 계약**(X 문면·Y 문면)의 실물 정합을 판정하고(Consistent), 단계 3(conflicts)은 **두 Task가 같은 계약 Y를 다르게 실현**한 사후 불일치를 검출한다 — wf-t2가 실제 산출한 Y(등장 순)와 확정 Y 문면(가나다 순)의 상이. 두 판정은 대상이 다르므로 crossRefStatus=Consistent와 conflicts=1건이 양립한다(절차서 §8-C.4).

### §6.2 Merge Result (구조화 섹션 — merge-rules §3 정본, 4필드 실값)

| 필드 | 실값 |
|---|---|
| `collected` | [wf-t1(v07-demo-t1, CP2 Pass 3/0/0), wf-t2(v07-demo-t2, CP2 Pass 4/0/0), wf-t3(v07-demo-t3, CP2 Pass 4/0/0)] — **3건, 개별 검증 통과만**(INV-5). 미검증·Fail 0건. |
| `crossRefStatus` | **Consistent** — wf-t2→확정 계약 X(out-t1.md가 X 문면 그대로 실현) · wf-t3→확정 계약 Y 문면(out-t3.md 9행 인용이 확정 문면과 문자 단위 일치). 확정 계약 참조의 실물 정합 판정. |
| `conflicts` | **1건** — wf-t2가 실현한 계약 Y(out-t2.md 데이터 행 순서 베타→알파→감마, 9~11행) ↔ wf-t3가 소비 시 참조한 확정 계약 Y 문면(가나다 순 감마→베타→알파). 두 Task가 같은 계약 Y를 다르게 실현(merge-rules §4.3). 중재 대상 1건. |
| `arbitration` | **Advisor 중재로 해소**(INV-6, 중재자=Advisor). 결정 전문 §6.3. Workflow는 충돌을 검출·보고하고 어느 실현을 채택·조정할지의 해소 결정은 Advisor가 내렸다. |

병합 성립 조건 3건(collected 전건 CP2 Pass·상호 참조 정합·충돌 1건 중재 해소) 충족 → 병합 성립. 미해소(`UnresolvedConflict`) 음성 케이스는 시연하지 않았다(절차서 §4.3 — 충돌은 중재로 해소).

### §6.3 arbitration 결정 전문 (Advisor 제공, INV-6)

Advisor가 충돌 1건을 다음과 같이 중재해 해소했다:

1. **계약 Y 정본 확정.** 계약 Y의 정본 = **분해 시점 확정 문면**(가나다 순 감마→베타→알파). wf-t3가 이 확정 문면을 소비했고 crossRefStatus에서 실물 정합(Consistent)이 확인됐으므로, 병합본의 Y 소비 기준은 확정 문면이다.
2. **wf-t2 실현 A의 지위.** wf-t2 실현 A(등장 순 베타→알파→감마)는 **자기 spec 지시(fixture-t2-spec §A)에 기인한 계약 이탈 실현**이다. 이 불일치가 픽스처의 의도적 보유물임을 fixture-t2-spec 머리("본 spec의 Y 실현 지시 … 는 확정 계약 Y 문면 … 과 의도적으로 불일치한다 — Merge 단계 3(충돌 검출) 시연 유도 지점")에서 확인했다. wf-t2는 자기 done을 충족하므로 개별 CP2는 Pass다(verify-t2) — 위반이 아니라 계약 이탈 실현이다.
3. **해소 결정.** 병합본의 Y 소비 기준 = 확정 문면(가나다 순)으로 확정한다. out-t2.md 표는 **시연 경계 내 존치**(픽스처 의도적 보유물, 무수정). **실계약 상황이라면 wf-t2가 재작업(정렬 교정 — 표를 가나다 순으로) 라우팅 대상**임을 기록한다. → 충돌 1건 해소, 병합 성립(단계 5).

이 중재는 Workflow 수준 Advisor 판단이며(loop-data 밖 — 07 §9 다중 사이클 오케스트레이션), Merge Result `arbitration`에 기록됐다. Learn→Memory Update가 이 사례를 Lesson 후보 LD-03(mi-0044)으로 도출했다(§8.1).

### §8.2 `at`·timestamp 성격 구분 (L-09 — 순서 값 / 물리 시각 구분)

L-09(기록 `at`/timestamp의 성격 구분, 물리 시각 주장은 실측 대조 후에만)에 따라 본 기록은 loop-data `at`·memory-data timestamp를 **순서 값**으로 서술하고 **물리 벽시계 시각으로 주장하지 않는다**.

- **loop-data `at` = 순서 값(loop-binding §3.3).** 세 파일의 `at`은 정수 서수로 seq와 동반 단조 증가(각 1..7, §5.2 line 원문 `at`=`seq` 위치). 전이 순서를 확정할 뿐 물리 시각이 아니다. 본 기록은 `at`을 "실제 수행 시각"으로 서술하지 않는다.
- **memory-data timestamp = 생성기 배정 단조 순서 값(기존 시퀀스 연속).** mi-0040~0044의 timestamp는 각각 `2026-07-05T22:20:26.602+09:00`·`...27.602`·`...28.602`·`...29.602`·`...30.602`로, 직전 기존 항목 mi-0039(`2026-07-05T22:20:25.602+09:00`)에서 **+1초씩 연속**하는 생성기 배정 순서 값이다(실측). 이는 mi 시퀀스의 단조 순서를 나타낼 뿐 물리 생성 시각이 아니다.
- **실측 대조(L-09 — 물리 시각은 실측값으로만 별도 공개).** timestamp 필드 값(2026-07-05T22:20:x)과 파일의 **물리 mtime**은 서로 다르다 — 본 작성 시 직접 실측한 물리 mtime(LastWriteTime): loop-data v07-demo-t1.jsonl `2026-07-06 13:38:54`·t2 `13:39:01`·t3 `13:39:09`; store mi-0040.json `2026-07-06 13:39:24`·mi-0041 `13:39:33`·mi-0042 `13:39:40`·mi-0043 `13:39:49`·mi-0044 `13:39:59`; index.jsonl `2026-07-06 13:40:19`. 물리 mtime은 **2026-07-06**(그 다음 날)로 timestamp 필드 값(2026-07-05T22:20:x)과 **불일치**한다. 이 불일치가 timestamp 필드가 물리 시각이 아니라 생성기 배정 순서 값임을 직접 실증한다(v0.6-demo §8 실증 동형). 본 기록은 timestamp/`at`을 시연의 물리 수행 시각으로 주장하지 않으며, 물리 시각은 위 mtime 실측값으로만 별도 공개한다.
