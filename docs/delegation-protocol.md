# 1. 핵심 사이클

위임 → 구현 → 검증 → 승인 (핵심 루프, Glossary J-11).

- Advisor가 위임 메시지(§2.1)로 작업을 넘긴다.
- 수임 Agent가 구현하고 완료 보고(§2.2) 또는 실패 보고(§2.3)를 남긴다.
- Verifier가 독립 판정한다. 완료 보고를 그대로 신뢰하지 않는다.
- Advisor가 검증 통과 후 최종 승인한다.

이 문서는 이 사이클의 **위임과 보고 작성·운용**을 규율한다. 판정·승인의 상세는 06·03 소관이다.

# 2. Core 운용 지침 (AI 비의존)

정본: uahf/specs/02-agent.md §3.2, uahf/specs/07-workflow.md §3.2-C. 이 섹션은 그 계약을 채우는 법이다.

## 2.1 위임 메시지 작성 (02 §3.2-B)

위임 시 8개 필드를 전달한다. 필수 필드(from/to/task/input/output/done/context)가 하나라도 누락되면 수임 Agent는 착수하지 않는다 (INV-6 — §2.4). constraints는 선택이다.

각 필드를 무엇으로 채우고, 무엇을 피하는가.

### from — 위임하는 역할

- 채우는 법: 위임 주체의 **역할** 하나 (Advisor / Planner / Worker / Verifier). 사람·실행 단위가 아니라 역할 경계(02 §3.2-A) 대조가 가능한 역할명.
- 좋은 예: `from: Advisor`
- 나쁜 예: `from: 나` — 역할이 아니면 위임 권한(위임은 Advisor 권한)을 대조할 수 없다.

### to — 수임하는 역할

- 채우는 법: 수임 역할 하나. 작업 성격에 맞는 역할인가 확인한다 — 구현은 Worker, 계획 초안은 Planner, 검증은 Verifier.
- 좋은 예: `to: Worker`
- 나쁜 예: `to: 담당자` — 역할 미지정. 역할 경계 대조 불가, INV-6 누락.

### task — 작업 요약

- 채우는 법: 대상과 동작이 드러나는 한 문장. "무엇을 어떻게 한다".
- 좋은 예: `task: docs/delegation-protocol.md 신규 작성`
- 나쁜 예: `task: 프로토콜 개선` — 대상 파일·동작이 불명확해 완료를 판정할 수 없다.

### input — 명확한 입력

- 채우는 법: 작업이 대상으로 삼는 **확정된** 입력. 파일 경로·계약을 정본 § 포인터까지 지정한다.
- 좋은 예: `input: uahf/specs/02-agent.md §3.2-B/C/D (메시지 계약 정본), uahf/specs/07-workflow.md §3.2-C (병렬 규칙)`
- 나쁜 예: `input: 관련 문서들` — 범위가 없으면 수임 Agent가 대상을 추측하게 되어 O4(추측 금지)를 유발한다.

### output — 명확한 출력

- 채우는 법: 기대 산출물의 **개수와 정확한 위치**. 절대 경로로 지정한다.
- 좋은 예: `output: C:\...\docs\delegation-protocol.md 1개`
- 나쁜 예: `output: 문서 하나` — 경로가 없으면 산출물 위치를 검증할 수 없다.

### done — 완료 조건

- 채우는 법: **검증 가능한** 항목의 목록. "~가 존재한다 / ~가 0건이다 / ~와 일치한다"처럼 대조로 참·거짓이 갈리게 쓴다. 완료 보고 self_check가 이 항목에 1:1로 대응한다.
- 좋은 예: `done: (1) 8필드 각각 작성 지침 존재 (2) Core 섹션에 AI 의존 토큰 0건 (3) 정본을 § 포인터로만 참조`
- 나쁜 예: `done: 문서를 잘 작성한다` — 시연 시나리오로 환원되지 않아 검증 불가.
- **접합부 왕복 (2026-07-26 신설)**: 위임 대상이 다른 컴포넌트·문서와의 접합부(생산→소비 계약 경계)를 만들거나 변경하면, done에 왕복 항목을 포함한다 — "생산 산출 실물을 소비자 절차에 실제로 통과시켜 불일치 0을 확인한다". 접합부 결함은 양쪽 단위 검증을 모두 통과하므로 단위 done만으로는 잡히지 않는다. 판정 운용 = `docs/verification-checklist.md` §5.7.
- **축 도출 (2026-07-26 신설)**: done의 검증 항목은 정본 열거(계약 §·spec·정책 데이터)에서 도출하고 좌표를 병기한다. 위임자가 발명한 축만으로 done을 채우면 명세가 쓰지 않은 축은 검증에서도 빠진다 — "명세가 안 쓴 축은 검증기도 안 봤다"(실측 2026-07-25). 판정 운용 = `docs/verification-checklist.md` §5.8.

### context — 착수 전 읽어야 할 문서 목록

- 채우는 법: 착수 전 정독할 파일 경로 목록 — 상위 규약, Architecture, 관련 spec, Memory 회수 범위. **확정(Frozen/실재) 문서만** 넣는다. 동시 작성 중인 산출물은 넣지 않는다 (R2 — §2.5).
- 좋은 예: `context: uahf/specs/02-agent.md 전체, uahf/specs/07-workflow.md, AGENT.md(상위 규약), uahf/specs/00-glossary.md`
- 나쁜 예: `context: 알아서 참고` — 회수 범위 부재. 미완성 산출물을 나열하는 것도 나쁜 예다 — 추측·인용을 유발한다.

### constraints — 금지·경계 (선택)

- 채우는 법: 하지 말아야 할 것. 소유 경계 밖 파일 수정 금지, 계약 재정의 금지 등. 선택 필드지만, 병렬 집합(§2.5)에서는 소유 경계 명시를 강하게 권장한다.
- 좋은 예: `constraints: 이 한 파일만 생성. 다른 파일 수정 금지. 정본 계약 재정의 금지.`
- 나쁜 예: 병렬 작업인데 `constraints: 없음`으로 소유 경계를 비운다 — 간섭 위험을 열어 둔다 (R4 — §2.5).

## 2.2 완료 보고 작성 (02 §3.2-C)

Verify 단계를 통과한 **뒤에만** 작성한다 (INV-4). 검증 전 완료 보고는 무효다.

- **artifacts** — 실제로 생성·변경한 산출물의 경로 목록. 절대 경로. 만들지 않은 것을 나열하지 않는다.
- **self_check** — 위임 done의 각 항목에 1:1로 대응해 충족 여부와 **근거**를 쓴다. 검사 범위를 정직하게 명시한다 — "무엇을 어디까지 확인했는가". "0건" 주장은 전수 스캔 근거를 함께 남긴다.
- **failures** — 실패·미완성 사항. **없으면 "없음"을 명시**한다. 은폐하지 않는다 (INV-5). 빈칸은 은폐로 간주된다.
- **open_questions** — 추측하지 않고 남긴 확인 필요 사항 (§2.6 에스컬레이션의 비차단 채널). **없으면 "없음"을 명시**한다.
- **verify_basis** — Verify 통과의 근거. 무엇을 어떤 방법으로 확인했는가. done 항목·정본 § 대조 방식을 적는다.

### 보고 전문 파일 우선 기록 + 최종 응답 한정 형식 (2026-07-27 신설 — 절차 비례화 트랙 W3-b)

회수 채널의 물리 수명은 세션이다(§3.2) — 최종 응답에만 둔 보고 전문은 세션이 끝나면 남지 않는다. 따라서 수임 Agent는 ① 위 5필드 전문을 **파일에 먼저 쓰고** ② 최종 응답을 아래 7블록으로 한정한다. 5필드 자체와 "없으면 없음을 명시"는 무변이며, 이 항은 전문의 **물리 위치**만 규정한다(정본 = `.claude/AGENT.md` §Communication Rules · 재정의 0).

- **보고 전문 파일 위치 — §2.7 승격 위치 2분기를 그대로 승계한다(새 위치 규칙 발명 0).** 원장 run 이 있으면 그 run 디렉터리 하위 `reports/<unit>-<role>-<attempt>.md`, 하네스 자체 작업이면 해당 트랙 문서 옆에 둔다. 최종 응답에는 그 절대경로를 **1건** 남긴다 — 경로 0건은 전문 소실이며 위임 산출 유실 금지 위반이다.
- **보고 파일의 지위 = 원장이 가리키는 artifact 1건.** `ArtifactRecord`의 `location`·`contentHash`가 지시하는 산출물이며(정본 = `orchestration/specs/05-project-orchestration.md` §3.6), 새 원장 트리·새 레코드 종류·새 스키마·제2 진리원천은 **0**이다. 수명 등급 = **evidence**(정본 = `docs/artifact-lifecycle-policy.md` §2·§3·§5 · 이 절에서 재정의하지 않는다).
- **최종 응답 7블록 — 전부 필수.**
  1. `[착수 전 점검]` 필수 필드 7/7 존재 · done N/N 이진 판정 가능 · context M/M 실재 (§2.4)
  2. `[이탈 선언]` 병렬 집합 보고만 — 없으면 "없음" 명시 (§2.5)
  3. `[판정]` 이진 1줄 (역할별 판정 어휘 — 수임 Agent = 완료 \| 실패, Verifier = `final_verdict`)
  4. `[요약]` 3~5줄 — 결론·근거 종류·산출물 개수
  5. `[보고 파일]` 전문 파일 절대경로 1건
  6. `[failures]` 없음 \| N건 → 전문 파일의 해당 절 지시
  7. `[open_questions]` 없음 \| N건 → 전문 파일의 해당 절 지시
- **"없음까지 명시" 불변의 충족 층.** `failures`·`open_questions`의 **존재·부재는 최종 응답에 이진으로** 남기고 내용은 전문 파일에 둔다. 즉 불변은 최종 응답 층에서 충족되며 삭제·약화되지 않는다. `artifacts`·`self_check`·`verify_basis`는 전문 파일에만 둔다 — 5필드는 **보고**의 필드이고 보고의 물리 위치를 규정하지 않는다(재정의 0).
- **최종 응답 상한 = 문자 5,000자 AND 40줄**(두 상한을 동시에 충족한다) · **보고 전문 파일 절대경로 1건 필수**. 확정값 = 사용자 게이트 Q-6(2026-07-26). 줄 수만 세면 긴 줄로 우회되고 문자 수만 세면 형식 붕괴를 못 막으므로 AND 로 결합한다.
- **상한은 필수 블록을 줄이지 못한다.** 상한은 `[요약]`의 길이를 줄이는 레버이며, 7블록 중 어느 것도 상한을 이유로 생략할 수 없다. 생략은 은폐로 귀결된다.
- **컨텍스트 절감은 Pass 경로 한정이다.** Pass 경로에서는 절감이 실현된다 — CP3의 정독 대상은 **산출물**이며 보고 전문 정독은 요구가 아니다(`.claude/AGENT.md` §Verification & Gate CP3). Fail·반려 경로에서는 절감이 실현되지 않는다 — 결함 귀속 판정(`docs/verification-checklist.md` §5.6)이 위임 문면과 보고 전문을 요구하므로 **Advisor가 전문 파일을 연다**. 절감을 두 경로 공통으로 과대 주장하지 않는다.

`uaf-verified:` 위 항의 근거 = `.claude/AGENT.md` §Communication Rules·§Invariants·§Verification & Gate, 본 문서 §2.7·§3.2, `docs/artifact-lifecycle-policy.md` §2·§3·§5, `orchestration/specs/05-project-orchestration.md` §3.6, `docs/verification-checklist.md` §5.6 직독. **검색 범위** = 그 6개 문서의 해당 절이며, 소비 프로젝트 트리·`uahf/specs/` 전문은 범위 밖이다.

## 2.3 실패 보고 작성 (02 §3.2-D)

착수 불능·차단 시 작성한다. 모든 실패는 Lesson 후보다.

- **reason** — 실패 이유. 근본 원인 한 문장.
- **repro** — 재현 조건. 어떤 입력·상태에서 재현되는가.
- **attempted** — 시도한 것과 그 결과 (선택). 대체 경로를 탐색했다면 무엇을 왜 접었는지.
- **lesson_candidate** — Lesson 후보 여부(예/아니오)와 한 줄 요약. 다음 작업에서 회수될 교훈 문장.
- **blocking** — 차단 여부. 계속 진행 가능한가, 차단되었는가. 차단이면 사이클이 멈춘다.

### 보고 전문 파일 우선 기록 + 최종 응답 한정 형식 (2026-07-27 신설 — 절차 비례화 트랙 W3-b)

실패 보고도 완료 보고와 동일하게 전문을 파일에 먼저 쓰고 최종 응답을 7블록으로 한정한다. 형식 열거·상한 판정 술어는 §2.2 동명 항이 소유하며 여기서 재정의하지 않는다(문면 갈림 0).

- **보고 전문 파일 위치 — §2.7 승격 위치 2분기를 그대로 승계한다(새 위치 규칙 발명 0).** 원장 run 이 있으면 그 run 디렉터리 하위 `reports/<unit>-<role>-<attempt>.md`, 하네스 자체 작업이면 해당 트랙 문서 옆에 둔다. 최종 응답에는 그 절대경로를 **1건** 남긴다 — 경로 0건은 전문 소실이며 위임 산출 유실 금지 위반이다.
- **최종 응답 상한 = 문자 5,000자 AND 40줄**(두 상한을 동시에 충족한다) · **보고 전문 파일 절대경로 1건 필수**. 확정값 = 사용자 게이트 Q-6(2026-07-26).
- 실패 보고의 `reason`·`blocking`은 최종 응답의 `[판정]`(= 실패)과 `[failures]`에 이진으로 드러나고, `repro`·`attempted`·`lesson_candidate`의 내용은 전문 파일에 둔다. 위 5필드는 삭제·약화 없이 유지된다(정본 = `.claude/AGENT.md` §Communication Rules · 재정의 0).
- 착수 전 반환(§2.4 3단계)도 실패 보고 형태이므로 이 항이 그대로 적용된다.

`uaf-verified:` 위 항의 5필드 유지 주장은 개정 전후 §2.3 필드 목록(reason·repro·attempted·lesson_candidate·blocking)을 같은 자리에서 대조해 얻었다. **검색 범위** = 본 문서 §2.3 과 `.claude/AGENT.md` §Communication Rules 이며 그 밖은 범위 밖이다.

## 2.4 필수 필드 누락 위임의 반환 (INV-6 운용)

명확한 입력·출력·완료 조건·컨텍스트 중 하나라도 누락되면 수임 Agent는 착수하지 않는다 (02 INV-6). 반환 절차는 다음과 같다.

1. **착수 전 점검.** 수임 Agent는 작업 시작 전 위임 메시지의 필수 7필드(from/to/task/input/output/done/context) 존재와 명료성을 점검한다.
2. **착수 보류.** 누락·모호한 필드가 하나라도 있으면 구현에 착수하지 않는다. 누락 필드를 추측으로 메우지 않는다 (O4).
3. **반환·질의.** 위임자(Advisor)에게 반환한다. **무엇이 누락·모호한지**와 **무엇을 확정해 달라는지**를 명시한다. 반환은 실패 보고(§2.3)의 blocking=차단 형태를 쓴다 — reason에 "위임 필수 필드 누락"과 누락·모호 필드의 목록을, repro에 어떤 위임 메시지에서 재현되는가(해당 위임의 식별)를 적는다.
4. **재착수.** 보완된 위임을 받은 뒤에만 착수한다.

물리 반환 채널은 §3.4다.

### 점검 산출 의무 (2026-07-26 신설 — 위임 규율 B-1 강제 배선)

1단계 점검은 수행 주장만으로는 검증 불가다 — 2026-07-21 실측: 브리프의 done이 검증 가능 목록이 아니었는데 병렬 5조 중 반환 0건(5/5 미작동). 점검을 산출물로 강제한다.

- **보고 서두 블록.** 수임 Agent(Worker·Planner)는 완료 보고(§2.2)·실패 보고(§2.3) 어느 쪽이든 **서두 첫 블록**으로 착수 전 점검 결과를 제출한다. 형식(3항 전부 이진):
  `[착수 전 점검] 필수 필드 7/7 존재 · done N/N 이진 판정 가능 · context M/M 실재`
- **판정 술어 3종.** ① 필수 7필드(from/to/task/input/output/done/context)가 각각 존재하는가 ② done 각 항목이 대조로 참·거짓이 갈리는 문장인가(§2.1 done 지침의 판정식 — "~가 존재한다 / ~가 0건이다 / ~와 일치한다") — **모호한 done은 누락과 동급**이다 ③ context 각 경로가 실재하는가(열어서 확인). 하나라도 0이면 착수하지 않고 3단계 반환으로 간다.
- **부재 = 보고 무효.** 점검 블록이 없는 보고는 Advisor가 수리하지 않고 반려·재보고를 요구한다(§3.2).
- **강제 지점** — ① 수임 Agent 역할 정의의 입력·보고 형식 요건: 역할 정의 문서는 수임 시마다 수임 Agent에 자동 주입되는 층이다(물리 위치·주입 메커니즘 = §3.1) ② Advisor 회수 반려(§3.2). 자동 차단 장치 미도입 — 사유: 위임·보고는 도구 호출이 아니어서 도구 호출 차단 장치가 개입할 표면이 없다(AGENT.md §Invariants 강제 없는 규율 신설 금지의 미도입 사유 기록·물리 수단 상세는 §3 소관).

## 2.5 병렬 Wave 운용 (07 §3.2-C R1~R4)

한 병렬 집합(Parallel Set)의 여러 Task를 동시에 위임할 때, 각 수임 Agent가 지키는 실무 규칙이다. 규칙 정본은 07 §3.2-C다.

- **R1 (위임 메시지 전용).** 병렬 Task는 오직 02 §3.2-B 위임 메시지(§2.1)로만 착수한다. 구두·암묵 합의로 착수하지 않는다. 위임 메시지에 없는 지시는 지시가 아니다.
- **R2 (미완성 산출물 불추측).** 같은 Wave에서 동시 작성 중인 다른 Task의 미완성 산출물을 인용·추측하지 않는다. 오직 확정된 인터페이스 계약(Interface Contract)만 참조한다.
  - 실무: 위임 context 필드(§2.1)에는 Frozen/확정 문서만 넣는다. 인용은 context에 명시된 확정 문서로 한정한다. 동시 작성 파일이 필요하면 인용하지 말고 R3로 에스컬레이션한다.
- **R3 (조율 에스컬레이션).** 계약 불명확·경계 충돌 조짐·의존 계약 미확정을 발견하면 추측하지 않고 Advisor에게 에스컬레이션한다 (§2.6).
- **R4 (소유 경계 준수).** 자신의 소유 경계(Ownership Boundary — 위임 output/constraints로 지정된 파일) 밖의 파일·계약을 수정하지 않는다. 같은 병렬 집합의 다른 Task 파일을 건드리지 않는다.

### 동료 계약·이탈 선언 (2026-07-26 신설 — 위임 규율 B-4 배선 · 07 R1~R4 재정의 아님·운용 층 추가)

병렬 집합에서 한 조의 **정당한** 이탈이 동료 조의 전제를 무너뜨릴 때 알릴 채널이 없었다 — 2026-07-21 실측: 한 조의 정당한 이탈(FR-5b 신설)이 병렬 동료에게 전달되지 않아 동료 산출물이 거짓 사실 주장을 보유한 채 완료됐다.

- **동료 계약 블록(브리프 측).** 병렬 집합의 각 위임 메시지는 동료 계약 블록을 포함한다 — 같은 집합의 동료 Task 목록 + 이 Task의 산출 중 동료가 전제로 소비하는 계약 문면(교차 소비 지점; 없으면 "없음" 명시). 병렬 분해 초안은 Planner 소관이므로(AGENT.md §Roles Advisor 이진 판별) 이 블록은 Planner 브리프 초안의 완료 조건이다.
- **이탈 선언 블록(보고 측).** 병렬 집합의 수임 Agent는 보고 서두(착수 전 점검 블록 다음)에 이탈 선언 블록을 제출한다 — 위임 문면·전제에서 벗어난 결정의 목록(없으면 "없음" 명시). 동료 계약 블록의 교차 소비 지점에 닿는 이탈은 `[동료 영향]`과 해당 Task를 지목한다.
- **실행 중 전파 채널의 존재는 환경 의존이며, 본 프로젝트의 물리 채널에는 없다**(§3.3 — 수임 Agent 사이의 직접 채널 부재). 전파 시점은 **회수 직후**로 고정한다(§2.7 승격과 같은 시점): Advisor가 이탈 교차 대조를 수행한다 — 각 조의 이탈 선언 × 동료 계약 블록 → 영향 유/무 이진 판정 → 영향 있으면 해당 동료 산출물을 CP2 전에 재검 또는 재브리프. 대조 결과는 §2.7 원장에 기록한다.
- **강제 지점** — ① 수임 Agent 역할 정의의 보고 형식 요건 + Planner 초안 완료 조건(역할 정의 문서의 물리 위치 = §3.1) ② Advisor 회수 반려(블록 부재 보고 무효·§3.2) ③ §2.7 원장 구성 ④항(교차 대조 결과 기록 의무). 자동 차단 장치 미도입 — 사유는 §2.4 점검 산출 의무와 동일(위임·보고는 도구 호출이 아니다).

## 2.6 에스컬레이션 경로

추측 대신 에스컬레이션한다 (O4, AGENT.md 추측 금지). 경로는 다음으로 고정된다.

| 요소 | 값 |
|---|---|
| **누가** | 수임 Agent — Worker / Planner / Verifier (R3 포함). |
| **무엇을** | 계약 갭(필드 누락·모호) / 조율 필요(병렬 간섭 조짐·의존 계약 미확정) / 불확실(추측 대상). |
| **어떤 채널로** | 착수 전 필수 필드 누락 → **반환·질의**(§2.4). 차단되어 진행 불능 → **실패 보고**(02 §3.2-D). 진행은 가능하나 확인 필요 → **완료 보고의 open_questions**(02 §3.2-C). |
| **누구에게** | **Advisor** — 설계·역할·조율 충돌의 결정·중재 권한을 가진다 (07 INV-6, 02 §3.2-A). |

Verifier도 판정 중 발견한 계약 갭·불일치를 같은 채널로 Advisor에게 올린다. 물리 채널은 §3.4다.

## 2.7 보고 산출의 원장 승격 (AGENT.md §Invariants 위임 산출 유실 금지 운용)

완료 보고의 open_questions와 실패 보고의 lesson_candidate는 **회수 채널에만 두면 소멸한다**. 회수 직후 원장으로 승격한다.

- **승격 대상** — 완료 보고의 `open_questions` · 범위 이탈과 그 사유 · 위임자가 제시한 기본값 중 수임 Agent가 적용한 것 · `verify_basis`의 검사 범위와 한계. 실패 보고의 `reason`·`lesson_candidate`·`blocking`.
- **승격 시점** — **보고 회수 직후**. 병렬 집합(§2.5)이면 마지막 보고를 회수한 직후 한 번에 옮긴다. 사이클 마감까지 미루지 않는다.
- **승격 위치** — 작업 대상 트리 안의 원장 파일. 소비 프로젝트 작업이면 그 프로젝트 트리에, 하네스 자체 작업이면 해당 트랙 문서 옆에 둔다.
- **수명 등급** — **evidence**(게이트 판정 근거). 수명·삭제·아카이브·인용 규칙의 정본은 `docs/artifact-lifecycle-policy.md` §2·§3·§5이며 이 절에서 재정의하지 않는다.
- **원장이 담을 것** — ① 위임자(사용자·Advisor) 결정이 필요한 항목 ② 적용된 기본값과 사유 ③ 이탈과 사유 ④ 병렬 집합 간 교차 확인 대기 항목과 **이탈 교차 대조 결과**(§2.5 동료 계약·이탈 선언 — 병렬 집합이면 대조 수행·기록이 필수) ⑤ 회수 근거(무엇을 읽어 옮겼는가). ⑤에는 **이 원장이 검증 결과가 아니라 수임 Agent의 주장을 회수한 것**임을 명시한다 — 판정은 Verify(§1) 소관이다.
- **금지** — 개수만 기록하는 것. "미결 N건"으로 내용을 갈음하지 않는다. 다음 사이클은 개수에서 내용을 복원할 수 없다.
- **보고 전문 파일과 승격분의 층위 구분 (2026-07-27 신설 — 절차 비례화 트랙 W3-b).** §2.2·§2.3의 보고 전문 파일과 이 절의 승격분은 **다른 층**이다. 전문 파일 = 보고 원문 전량, 수명 등급 `evidence`(아카이브·삭제 대상 — `docs/artifact-lifecycle-policy.md` §3). 승격분 = **다음 사이클이 소비할 것**으로 한정된 압축(미결·이탈·기본값과 사유·검사 범위 한계). 전문 파일 도입으로 이 절의 승격이 대체·축소되지 않는다 — 승격 = **1(필수)**, 전문 파일 경로로 갈음 = **0(금지)**. 전문이 evidence 로 아카이브·삭제되면 승격하지 않은 미결은 함께 사라진다.

원장 승격은 검증을 대체하지 않는다. 승격은 **소실 방지**이고 판정은 별개다 — 승격된 주장도 CP2에서 산출물로 재판정된다(INV-4).

# 3. Adapter 바인딩 — 이 프로젝트의 물리 채널 (Claude Code)

정본: uahf/specs/02-agent.md §4.1, uahf/specs/07-workflow.md §4.1. §2의 추상 계약을 이 프로젝트 표면에 바인딩하는 지점만 명시한다. 이식 시 이 섹션만 교체된다 (02 §4.2, 07 §4.2).

## 3.1 위임 디스패치

- Advisor는 Claude Code의 서브에이전트 위임으로 §2.1 위임 메시지를 Worker / Planner / Verifier에게 전달한다 (02 §4.1).
- 위임 메시지의 context 필드는 읽어야 할 파일 경로 목록으로 전달된다.
- 각 역할은 `.claude/agents/*.md`로 정의되고, 상위 규약은 `.claude/AGENT.md`, Advisor 진입점은 `.claude/CLAUDE.md`가 바인딩한다 (02 §4.1). Worker의 기본 실행 모델은 Opus다 (02 §4.1, SP-3).

## 3.2 보고 회수

- §2.2 완료 보고와 §2.3 실패 보고는 서브에이전트의 **최종 응답**으로 회수된다 (02 §4.1).
- Advisor는 회수한 보고를 그대로 신뢰하지 않고 독립 재검증한다 (검증 게이트, 13 §3.2-A / 02 INV-4).
- **서브에이전트 최종 응답은 세션 컨텍스트에만 존재한다.** 이 프로젝트에서 회수 채널의 물리 수명은 세션이며, 세션이 끝나면 응답 본문은 남지 않는다. 따라서 Advisor는 회수 직후 **§2.7에 따라 원장 파일로 승격**한다 — 승격하지 않은 미결·이탈은 다음 세션에서 복원되지 않는다(AGENT.md §Invariants 위임 산출 유실 금지).
- **점검·이탈 블록 반려 (2026-07-26 신설).** 회수한 보고에 착수 전 점검 블록(§2.4 점검 산출 의무)이 없거나, 병렬 집합 보고에 이탈 선언 블록(§2.5 동료 계약·이탈 선언)이 없으면 보고를 수리하지 않고 반려·재보고를 요구한다. 반려 시 어느 블록이 부재인지 명시한다.
- **반려 사유 3항 (2026-07-27 — 3항째 신설·절차 비례화 트랙 W3-b).** 회수한 보고의 수리 거부 사유는 아래 **3항**으로 닫힌다. 각 항은 이진 술어이며 회수 시점에 참·거짓이 갈린다.
  1. **점검 블록 부재** — 보고 서두 첫 블록에 `[착수 전 점검]`이 존재하는가(1) 부재인가(0). **0 = 반려**(§2.4 점검 산출 의무 — 위 항).
  2. **이탈 선언 블록 부재** — 병렬 집합 보고의 점검 블록 다음에 `[이탈 선언]`이 존재하는가(1) 부재인가(0). **0 = 반려**(§2.5 — 위 항). 병렬 집합이 아니면 이 항은 판정 대상에서 제외된다.
  3. **상한 초과 — 신설.** 세 술어를 AND 로 판정한다. ① 최종 응답 문자 수 ≤ 5,000 인가(1) 아닌가(0) ② 최종 응답 줄 수 ≤ 40 인가(1) 아닌가(0) ③ 보고 전문 파일 절대경로가 정확히 1건 존재하는가(1) 0건인가(0). **어느 하나라도 0 = 반려**(§2.2·§2.3 · 확정값 = 사용자 게이트 Q-6 2026-07-26). 문자 수·줄 수는 회수한 응답을 세어 판정하므로 블록 존재·부재와 동급의 결정적 판정이다.
  - 반려 시 **어느 항이 0 인지** 명시한다. 반려는 재보고 요구이며 판정(CP2)이 아니다. 7블록 중 `[판정]`·`[failures]`·`[open_questions]` 부재도 1항과 동급으로 반려한다 — 상한은 필수 블록을 줄이지 못한다(§2.2).
  - **강제 지점** — ① 수임 Agent 역할 정의(`.claude/agents/worker.md`·`verifier.md`·`planner.md`의 "출력" 절)의 보고 형식·상한 요건 — 역할 정의는 수임 시마다 자동 주입되는 층이다(§3.1) ② 본 절의 Advisor 회수 반려. **자동 차단 장치 미도입** — 사유는 §2.4 점검 산출 의무·§2.5 동료 계약과 동일하다: 위임·보고는 도구 호출이 아니어서 도구 호출 차단 장치가 개입할 표면이 없다(`.claude/AGENT.md` §Invariants 강제 없는 규율 신설 금지의 미도입 사유 기록). 신규 차단 스크립트·훅 신설 = **0**.

## 3.3 병렬 Wave 물리 실현

- Advisor가 서브에이전트 **동시 위임**으로 한 병렬 집합의 Task들을 여러 Worker에게 동시에 전달한다 (07 §4.1).
- 각 Worker의 결과는 각 서브에이전트 최종 응답으로 회수·수합되고, Advisor가 상호 참조 정합성을 대조하며 충돌을 중재한다 (07 §4.1, INV-6).
- 이 프로젝트의 spec 병렬 작성 Wave가 이 구조의 실사용 형태다 (07 §8 예1).

## 3.4 반환·에스컬레이션 물리 채널

- §2.4 반환과 §2.6 에스컬레이션은 서브에이전트 최종 응답으로 Advisor에게 회수된다 — 차단 시 실패 보고(§2.3), 비차단 확인 필요 시 완료 보고 open_questions(§2.2).
- 이식 시 이 회수 채널만 교체된다 (02 §4.2 SP-4·SP-5, 07 §4.2). §2의 필드·규칙은 유지된다.
