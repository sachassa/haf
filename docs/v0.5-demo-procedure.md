## §0. 이 문서의 위치와 정본 경계

- **이 문서는 시연 절차서다.** 시연 6종을 **어떻게 수행하고 무엇으로 판정하는가**의 절차·입력·기대 관측·판정 문장·VT 사상·기록 포맷을 정의한다. 시연의 실제 **수행 기록**은 별도 산출물(시연 수행 기록, 후속 Task)이, **독립 판정**은 검증 단계(Verifier = CP2, 검증 리포트)가, **최종 승인**은 Advisor(CP3)가 담당한다. 이 절차서는 그 세 작업의 입력이다. 자기 점검은 최종 승인이 아니다 (02 §3.2-A).
- **정본은 specs/06-verifier.md(§3 Core Contract·§7 완료 기준·§8 예1)와 확정 framework/verifier/ 5종 문서(V1~V5)다.** 이 절차서는 그 계약·완료 기준을 **재정의·확장하지 않는다**. 계약 요소·판정 문장·필드는 § 포인터로만 참조하고, 필수/선택 표기는 정본 그대로 보존한다.
- **판정 문장은 인용이다.** 각 시연의 판정 문장은 06 §7 시연 가능 문장 또는 ROADMAP v0.5 완료 조건의 **원문 인용 또는 그 검증 가능 환원(예/아니오)**이며, 새 판정 기준을 창설하지 않는다 (done 7). 판정 값(충족/위반/판정 불가)·최종 판정(통과/실패/조건부)은 06 §3.2-B/C·verification-report.md §3/§4 정본에서 인용한다.
- **필드 소속 명시(혼입 방지).** 인용하는 필드는 소속 계약을 § 포인터로 명시한다 — 검증 리포트 6필드·항목별 판정 5필드는 06 §3.2-A/B(V1 §2/§3), 재작업 지시 4필드는 06 §3.2-D(V4 §2), 검증 유형 VT-1~VT-5·대조 기준 부류는 06 §3.2-E/§3.2-A(V5 §2/§4), 완료 보고 필드(self_check·verify_basis·failures·artifacts)는 02 §3.2-C(delegation-protocol §2.2)다. 판정 대상의 완료 보고 필드와 판정 산출물의 리포트 필드를 섞지 않는다.
- **물리 실현 지점 비하드코딩(§5).** 시연 절차는 추상 판정 연산(Verify — 06 §3.1)과 그 5단계(verifier-protocol §2)·검증 유형(VT-1~VT-5 — criteria-catalog §2)만으로 성립한다. 검사 도구(존재 확인·전수 스캔·시연 실행에 쓰는 도구)·리포트 직렬화·물리 진입점 해소 같은 물리 지점은 이 절차서에 하드코딩하지 않는다 — Adapter Binding 문서(framework/adapters/claude/verifier-binding.md)가 정본이며 (06 §4.1·§4.2 SP-3, criteria-catalog §5), 시연 수행 기록(후속 Task)이 그 문서(확정 후)를 참조해 각 단계의 물리 지점을 기입한다 (§5).
- **동시 작성 산출물 불인용 (07 R2).** 같은 Wave에서 동시 작성 중인 Adapter Binding 산출물(framework/adapters/claude/verifier-binding.md, V6)의 미완성 내용을 인용·추측하지 않는다. 물리 지점이 필요한 자리에는 "Adapter Binding 문서 소관" 포인터만 둔다 (§5). 확정 입력 문서(06·framework/verifier/ 5종·ROADMAP·docs/v0.4-demo-procedure·docs/session-handoff-v0.4)만 참조한다.
- **픽스처 실물 비생성·금지 토큰 비나열 (constraint, done 3·done 7).** 이 절차서는 픽스처를 **명세**만 하고 **생성하지 않는다** — 픽스처 파일·디렉터리(docs/v0.5-demo-fixtures/)의 생성은 시연 수행 Task 소관이다. 픽스처에 심을 금지 토큰의 **구체 예시를 이 절차서 본문에 나열하지 않는다** — 명세는 "금지 토큰 후보 **부류** 중 택1을 심는다" 수준으로만 서술한다(실물은 시연 수행 Task가 생성). 심은 구체 토큰이 픽스처 디렉터리 밖(이 절차서 포함)으로 누출되지 않게 하기 위함이다 (§4 격리 조건).
- **라벨 주의 (새 용어 신설 없음).** 본 문서가 쓰는 "시연 ⓐ/ⓑ/ⓒ/ⓓ/ⓔ/ⓕ", "판정 문장", "VT 사상", "기록 포맷"과 그 필드 이름(관측 결과·근거·수행 단계 로그·수행 물리 지점·Memory Consult 기록), "픽스처(대상 파일·claim 파일)"는 조직 편의를 위한 **서술 라벨**이며 Glossary 표제어가 아니다 — 정본 용어처럼 신설·확장하지 않는다 (v0.4-demo-procedure §0 라벨 처리 동형). 계약 용어(검증 리포트 / 항목별 판정 / 검증 유형 / 재작업 지시 / 거짓 완료 보고 / target / criteria_basis / items / final_verdict / verifier_scope / rework / criterion / verdict / evidence / scope / verification_type 등)와 판정 값(충족/위반/판정 불가)·최종 판정(통과/실패/조건부)은 전부 Glossary §3.2-J·06 §3.2·framework/verifier/ 정본에서 인용한다.
- **토큰 절제.** 이 문서는 `docs/` 소속이라 Core/Module 경계 금지 토큰 규칙(structure.md §5 C-3 확장, 06 INV-8)의 직접 대상은 아니다. 그러나 시연 시나리오는 **추상 계약 수준**으로 구성하며 특정 AI·언어·툴체인·직렬화 형식·검사 도구·물리 경로 토큰을 넣지 않는다 — 절차가 오직 06 §3·V1~V5 계약만으로 성립함을 보이기 위함이다(mention/use 경계). 픽스처에 심을 금지 토큰은 §4에서 부류로만 서술한다.

## §1. 목적과 범위

이 절차서의 책임은 세 가지다.

- v0.5 시연 6종 각각에 대해 **[절차 단계 / 입력 / 기대 관측 / 판정 문장(예/아니오 환원) / VT 사상 / 기록 포맷]** 요소를 정의한다 (§8·§10·§11·§12·§13·§14). v0.4-demo-procedure 관례와 동형이며, 판정 문장별 적용 VT 명시(§ (E))가 v0.5에서 추가된 요소다 (done 4).
- 각 시연의 판정 문장을 **ROADMAP v0.5 완료 조건 3건 + 06 §7 시연 가능 문장 8건**의 해당 문장에 1:1 대응(배정)시키고, 재현이 아닌 정적·스캔형 판정을 검증 리포트(CP2)·규격 Task 산출물 done으로 명시 배정한다 (§2, done 2).
- 시연 수행 기록(후속 Task)이 그대로 채우는 **공통 기록 포맷**(§3, done 6), **픽스처 명세**(§4, done 3), **물리 수행 지점 경계**(§5), **역사 실사례 인용**(§6, done 5), **실패 처리 규칙**(§7)을 정의한다.

- **시연 ⓑ 리포트 스키마 완전성 + 결정적 생성** — 임의의 판정에 대해 검증 리포트 6필드·항목별 판정 5필드가 전건 존재하고(스키마 완전성), 동일 입력{산출물+criteria}을 2회 수행하면 문면 동일 리포트를 냄(결정적 생성, DP-V3 실증)을 보인다. 근거: 06 §7 검증 리포트 스키마 시연·ROADMAP v0.5 "검증 리포트 자동 생성", verification-report §2/§3, verifier-protocol §2/§4(DP-V3). (§10)
- **시연 ⓒ 검증 유형 VT-1~VT-5 적용** — VT-1(산출물 존재)·VT-2(완료 조건 대조)·VT-3(규격 준수)·VT-4(경계)·VT-5(시연) 각각이 최소 1개 판정 항목에 적용되고, 유형별 판정 방법대로 `verdict`가 도출됨을 보인다. 근거: 06 §7 검증 유형 적용 시연·§3.2-E, criteria-catalog §2. (§11)
- **시연 ⓓ 최종 판정 결정성 3집합** — 전부 충족 집합→통과(Pass), 위반 포함 집합→실패(Fail), 위반 없이 판정 불가 포함 집합→조건부(Conditional)의 3분기가 06 §3.2-C 규칙으로 전부 결정적으로 도출됨을 보인다. 근거: 06 §7 최종 판정 결정성 시연·§3.2-C·INV-5·§8 예2, verification-report §4. (§12)
- **시연 ⓔ 재작업 지시 필드 완전성** — Fail 리포트·Conditional 리포트의 `rework` 4필드(violated_items·expected_state·revalidation_criteria·evidence_gap)가 모두 채워지고, Pass 리포트의 `rework`가 "없음"임을 보인다. 근거: 06 §7 재작업 지시 시연·§3.2-D·§3.2-A, rework-instruction §2/§3/§4. (§13)
- **시연 ⓕ 독립성** — 완료 보고 `self_check` "충족" 주장과 무관하게 판정이 산출물 근거로만 이루어져 위반으로 도출됨(주장 반대 사례)을 보인다. 근거: 06 §7 독립성 시연·§3.1 V1·INV-1, verifier-protocol §2.2/§5. (§14)

이 절차서는 위 여섯 시연의 **절차와 판정 기준**만 정의한다. 시연의 실제 관측·판정·승인은 시연 수행 Task(수행 기록)·검증 단계(Verifier = CP2)·Advisor(최종 승인 = CP3)의 소관이다 (§7).

## §3. 공통 기록 포맷 (시연 수행 기록용) (done 6, v0.4-demo-procedure §3 동형)

시연 수행 기록(후속 Task)이 여섯 시연 각각에 대해 **그대로 채우면 되는** 기록 포맷이다. 시연별로 아래 필드를 갖는 표 구조를 사용한다. 각 시연 절차의 (F)에는 이 포맷의 **빈 인스턴스**를 판정 문장이 채워진 채로 embed한다.

| 필드 | 의미 | 채우는 주체 |
|---|---|---|
| **판정 문장** | 이 시연의 성립을 판정하는 기준 문장(예/아니오 환원 포함). 06 §7·ROADMAP v0.5 완료 조건 문장의 인용이며 절차서가 확정한다. 수행 기록은 그대로 옮긴다. | 절차서(확정) → 수행 기록(전재) |

**기록 요건 (done 6 — 재발 방지·Consult):**

1. **관측 값·수행 물리 지점 기록.** "근거 (관측한 것)"에는 추상 주장이 아니라 실제 관측 값·상태를 남긴다. "수행 물리 지점"에는 각 단계가 실현·관측된 물리 지점을 verifier-binding.md(확정 후) 참조로 기입한다(§5).
2. **기록 내 timestamp·시각 주장은 실측 대조 후에만 기입 (L-07 재발 방지, session-handoff-v0.4 §1.4·§1.5-1).** 기록에 timestamp나 "실제 수행 시각" 류의 시각 주장을 넣을 때는 **실측 대조 후에만** 기입한다. **순서 값(생성기 배정 순서 등)과 물리 생성 시각(실측)의 성격을 구분해 서술한다** — 둘을 혼동해 순서 값을 "실제 수행 시각"으로 서술하지 않는다. 이는 v0.4 CP2 Fail 실사례(demo.md가 기록 timestamp를 "실제 수행 시각"으로 서술했으나 실측상 순서 값이었던 서술↔실측 모순 — Verifier가 검출, L-07 유형 재발)의 재발 방지 요건이다. 시각 주장을 넣지 않는다면 넣지 않았음을 근거에 명시한다.
3. **시연 수행 착수 시 Memory Consult 수행·회수 집합 기록 (handoff §3.4).** 시연 수행 Task는 착수 시 Memory Service Interface로 회수(Consult)를 실제 수행한다 — `purpose`(예: "v0.5 Verifier 시연 수행에 관련된 Active Lesson·BP 회수")와 `scope`(narrowing: `kind`=`lesson`/`best-practice`, `labels`: status=Active + 상황 투영), 기본 `detail`=index를 명시한다. 회수된 집합(회수 건수·매칭 라벨·회수된 `id` 목록)을 수행 기록에 남긴다. 물리 Consult 절차는 memory-binding.md §3.2(확정 v0.4 Baseline — index 조회 → 대상 store 파일만 로드) 소관이다. 회수·기록이 단일 Port(Recall) 경유·우회 0건임을 확인한다 (04 INV-1). Consult 기록은 시연별 (F) 표와 별개로 수행 기록 머리에 1회 둔다.

## §4. 픽스처 명세 (done 3, Advisor 픽스처 결정 OQ-f 반영)

시연 ⓐ(거짓 완료 보고 검출)와 ⓕ(독립성)는 06 §8 예1 동형 구성의 픽스처를 입력으로 쓴다. 이 절은 그 픽스처의 **명세**를 확정한다 — **픽스처의 실물 생성은 이 절차서 소관이 아니라 시연 수행 Task 소관이다** (constraint, §0).

### §4.1 위치·구성

- **위치.** 픽스처는 신규 디렉터리 **`docs/v0.5-demo-fixtures/`** 아래에 둔다(Advisor 픽스처 결정). 이 디렉터리와 그 안의 파일은 **시연 수행 Task가 생성한다** — 이 절차서는 생성하지 않는다.
- **구성 (06 §8 예1 동형 — 2파일).**
  - **(a) 대상 파일** — 금지 토큰이 **잔존하는** "Core류 문서 역할" 파일. 06 §8 예1의 "어떤 spec 파일"에 대응하는 판정 대상이다. 이 파일은 Core/Module 경계 문서가 준수해야 할 금지 토큰 규칙(structure.md §5 C-3 확장, 06 INV-8)을 **의도적으로 위반**하도록 구성한다 — 즉 금지 토큰 후보 부류 중 하나를 본문에 심는다.
  - **(b) claim 파일** — Worker 완료 보고(02 §3.2-C) claim이다. `artifacts`=대상 파일 (a), `self_check`="§3(또는 대상 경계) AI 의존 0건 (충족)", `failures`="없음", `verify_basis`="단일 토큰 검색으로 특정 AI 이름을 찾음 → 0건"에 해당하는 **좁은 범위 검사 주장**을 담는다(06 §8 예1의 완료 보고 동형). 이 claim은 판정의 **참고 입력**일 뿐 판정 근거가 아니다(06 V1).

### §4.2 머리 명시 요건·격리 조건

- **머리 명시 요건(필수).** 각 픽스처 파일((a)·(b))의 **머리에 "시연 픽스처 — 실계약 문서 아님"을 명시**한다. 이는 픽스처가 검증 대상 계약 문서가 아니라 시연을 위해 구성된 대상물임을 표시한다.
- **"Core류 문서 역할" 구성물 명시.** 대상 파일 (a)는 "Core류 문서 역할"을 하는 **구성물**이며 **실제 Core/Module 경계 파일이 아니다**. framework/core/·framework/verifier/ 등 실제 경계 산출물이 아니라, 금지 토큰 규칙의 적용을 시연하기 위해 그 역할을 흉내 내는 픽스처임을 (a) 머리에 명시한다. 실계약 문서(06·V1~V5·framework/ 산출물)는 픽스처가 아니며, 픽스처 검출 결과가 실계약 문서의 판정으로 오인되지 않게 한다.
- **격리 조건(필수).** 픽스처에 **심은 금지 토큰은 `docs/v0.5-demo-fixtures/` 디렉터리 내부에만 존재해야 한다.** 그 구체 토큰이 이 절차서를 포함한 디렉터리 밖 어떤 저장소 파일에도 나타나지 않게 한다. 이 격리로 인해, 06 §7-⑧ Core AI 비의존 전수 스캔(§2.3, CP2 소관)이 실계약 산출물을 대상으로 수행될 때 픽스처의 심은 토큰이 실계약 경계의 위반으로 계상되지 않는다(픽스처 디렉터리는 전수 스캔의 대상 경계에서 제외하고, 제외 사실을 명시 — criteria-catalog §3 절차 2의 "정당 보유 지점 제외·제외 명시"와 동형).

### §4.3 심을 금지 토큰 — 부류 수준 명세 (done 7 — 구체 토큰 비나열)

- 대상 파일 (a)에 심는 금지 토큰은 **금지 요소 후보 부류 중 택1**이다(criteria-catalog §3 절차 1의 후보 부류). 후보 부류는 다음을 포함한다 — ① 특정 AI 의존 요소(특정 AI 이름·모델명·제품 기능명), ② 특정 언어·툴체인 의존 요소(프로그래밍 언어명·툴체인명), ③ 직렬화 형식명·확장자·OS 토큰, ④ 물리 경로·인스턴스 누출. **06 §8 예1의 실패 유형(단일 토큰 검색이 놓친 "모델명" 잔존)을 재현하려면 ① 부류의 한 토큰을 심는 것이 정본 예 동형**이다.
- **구체 토큰은 이 절차서 본문에 나열하지 않는다.** 어느 부류의 어떤 토큰을 심을지 실물 선택은 시연 수행 Task가 수행하며, 심은 실물 토큰은 §4.2 격리 조건에 따라 픽스처 디렉터리 내부에만 존재한다. 이 명세는 "부류 중 택1을 심는다" 수준으로만 규정한다(§0 픽스처 실물 비생성·금지 토큰 비나열).
- **좁은 범위 검사와의 대비.** claim 파일 (b)의 `verify_basis`가 주장하는 검사 범위는 "단일 토큰 검색"(좁은 범위)이며, 심은 금지 토큰은 그 단일 토큰 검색이 **놓치도록** 구성한다(예: (b)가 검색한 토큰과 다른 부류·다른 표기의 토큰을 (a)에 심는다). 이 대비가 ⓐ에서 VT-4 전수 스캔이 좁은 범위를 넘어 검출하는 지점이다(06 §8 예1, criteria-catalog §3 절차 6, verifier-protocol §5).

## §5. 물리 수행 지점 경계 (07 R2 — Adapter Binding 문서 소관 포인터)

- 시연 절차(§8·§10·§11·§12·§13·§14)의 모든 단계는 **추상 판정 연산(Verify — 06 §3.1)** 과 그 실행 절차 5단계(verifier-protocol §2)·검증 유형(VT-1~VT-5 — criteria-catalog §2)·재작업 지시 포맷(rework-instruction §2)으로 서술된다. 어떤 단계도 검사 도구(존재 확인·전수 스캔·시연 실행에 쓰는 도구)·리포트 직렬화 형식·물리 진입점·물리 경로 같은 물리 지점을 명시하지 않는다.
- 물리 실현 지점(검사 도구가 무엇이고, 전수 스캔·시연 재현·리포트 산출이 어디에서 어떻게 수행·관측되는가)은 **Adapter Binding 문서 `framework/adapters/claude/verifier-binding.md`** 가 정본이다 (06 §4.1 검사 도구 바인딩 행·재작업 지시 전달 행, §4.2 SP-2·SP-3·SP-5; criteria-catalog §5).
- **수행 기록의 기입 방식.** 시연 수행 기록(후속 Task)은 §3 기록 포맷의 "수행 물리 지점" 필드에, 각 절차 단계가 물리적으로 실현된 지점을 **verifier-binding.md(확정 후)를 참조하여** 기입한다. 절차서는 그 지점을 미리 확정·하드코딩하지 않는다.
- **07 R2 준수.** 같은 Wave에서 동시 작성 중인 verifier-binding.md(V6)의 미완성 내용을 이 절차서에서 **인용·추측하지 않는다.** 물리 지점이 필요한 자리는 위 포인터로만 처리한다. 이는 v0.4-demo-procedure §4가 동시 작성 중인 memory-binding.md를 불인용하고 소관 포인터로만 처리한 선례와 동형이다.

이 경계로 인해, 이 절차서는 대상 환경이 바뀌어도(06 §4.2 이식 교체 지점) 유지된다 — 바뀌는 것은 "수행 물리 지점"의 실현(검사 도구·직렬화·전달 채널)뿐이고, 절차 단계·판정 문장·VT 사상·기록 포맷은 그대로다(06 §4.2 유지 목록).

## §7. 실패 처리 규칙 (v0.4-demo-procedure §6 동형)

시연이 기대 관측과 **다르게 관측될 때**의 처리 규칙이다.

1. **은폐 없이 그대로 기록한다.** 관측이 기대와 달라도 실제 관측을 §3 기록 포맷의 "근거 (관측한 것)"에 그대로 남긴다. 실패·불일치를 숨기지 않는다 (Worker 금지 사항 — 실패 은폐 금지, 02 O5).
2. **판정 값으로 표기한다.** 기대와 다르게 관측되면 해당 시연의 "관측 결과"를 **위반**으로 표기한다 (판정 값 정본: 06 §3.2-B, verification-report §3). 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기하며, 판정 불가를 충족으로 위장하지 않는다 (06 V6, INV-3).
3. **재작업 여부 판단은 게이트 소관이다.** 이 절차서와 수행 기록은 관측·기록까지만 한다. 위반·판정 불가의 **재작업 여부 판단**은 검증 단계(Verifier, CP2)와 Advisor(CP3)의 소관이다. 수행 기록·절차서가 스스로 통과 처리하거나 재작업을 결정하지 않는다.
4. **연산 실패와 판정 대상 final_verdict=Fail의 구분 (verifier-protocol §6).** 시연 중 Verify 연산 자체가 수행 불능(산출물 접근 불가·대조 기준 부재)이면 이는 **연산 실패**이며, 판정 대상이 기준을 충족하지 못한 **`final_verdict = Fail`**(정상 출력)과 다르다(06 §3.1 주의). 둘을 혼동해 기록하지 않는다 — 연산 실패는 실패 보고로, `final_verdict = Fail`은 정상 리포트로 기록한다.
5. **음성/양성 구분.** 시연이 위반·Fail·거부를 **기대**하는 경우(ⓐ 위반 검출, ⓓ Fail·Conditional 분기)와 예기치 못한 실패를 근거에 구분해 기록한다. 기대된 검출·거부가 정확히 관측되면 그 시연은 **충족**이다.

## §8. 시연 ⓐ — 거짓 완료 보고 검출 (06 §8 예1 동형)

목표: 픽스처 대상 파일 (a)에 대해 VT-4 경계 검증 전수 스캔을 수행해, claim 파일 (b)의 `self_check` "AI 의존 0건 충족" 주장에 반해 잔존 금지 토큰을 검출하고, `verdict`=위반(Violated) → `final_verdict`=Fail + 재작업 지시 4필드를 산출한다. 근거: 06 §7 거짓 완료 보고 검출 시연·§8 예1·§3.2-F, verifier-protocol §5, criteria-catalog §3, rework-instruction §2, verification-report §2/§3/§4.

### (A) 절차 단계

1. **입력 수령 (verifier-protocol §2.2).** 판정 대상 = 픽스처 대상 파일 (a) + 대조 기준(criteria). Worker 완료 보고 = claim 파일 (b)를 **참고 입력으로만** 받는다 — `self_check`·`failures`·`verify_basis` 주장은 검사 대상(claim)일 뿐 판정 근거가 아니다 (06 V1, INV-1).
2. **기준 확인 (verifier-protocol §2.3).** 대조 기준 `criteria_basis` = **경계 규칙** 부류 — "대상 파일 (a)의 해당 경계에 금지 요소가 0건이어야 한다"(criteria-catalog §4 경계 규칙 부류, 06 §3.2-A). 기준이 명시되므로 판정을 진행한다.
3. **항목별 판정 — VT-4 전수 스캔 (verifier-protocol §2.4, criteria-catalog §3 절차 1~5).** 완료 보고 주장을 신뢰하지 않고 동일 기준을 산출물 (a)에 대해 **충분한 범위로 재판정**한다(06 §3.2-F, verifier-protocol §5). `scope` = 대상 파일 (a) 본문 전체 + 금지 요소 후보 부류 전체(단일 토큰 검색보다 넓음, §4.3). 전수 스캔에서 심은 금지 토큰이 검출되면 `verdict`=위반(Violated), `evidence`=잔존 위치 인용, `verification_type`=VT-4로 항목별 판정을 산출한다. 산출물을 수정하지 않는다 (06 V5, INV-6).
4. **최종 판정 도출 (verifier-protocol §2.5).** 위반 항목이 1건 이상이므로 06 §3.2-C 규칙으로 `final_verdict`=**실패(Fail)** 를 결정적으로 도출한다(verification-report §4).
5. **리포트 산출 + 재작업 지시 (verifier-protocol §2.6, rework-instruction §2).** 검증 리포트 6필드를 산출하고, Fail이므로 `rework` 4필드를 채운다 — `violated_items`=[경계 규칙 기준 + verdict=위반], `expected_state`=대상 경계에 금지 요소 후보 전부 0건, `revalidation_criteria`=전수 스캔 재실행 후 0건(라이브 본문 기준 — rework-instruction §4), `evidence_gap`=없음(판정 불가 0건). `verifier_scope`에 검사한 범위와 제외 범위(픽스처 디렉터리 외 실계약 경계는 이 시연 대상 아님)를 명시한다 (06 V4).

### (B) 입력

- 픽스처 대상 파일 (a) — 금지 토큰 후보 부류 중 택1이 잔존, "Core류 문서 역할" 구성물(§4). 실물 생성·토큰 선택은 시연 수행 Task 소관.
- claim 파일 (b) — `self_check`="AI 의존 0건 충족", `verify_basis`="단일 토큰 검색 → 0건"의 좁은 범위 검사 주장(§4).
- 대조 기준 criteria — 경계 규칙(금지 요소 0건, criteria-catalog §4).

### (C) 기대 관측

- claim (b)의 단일 토큰 검색이 놓친 금지 토큰이 대상 파일 (a)에 잔존함이 VT-4 전수 스캔으로 검출된다.
- 항목별 판정: `verdict`=위반(Violated), `evidence`=잔존 위치, `verification_type`=VT-4.
- 최종 판정: `final_verdict`=Fail (위반 1건 이상, 06 §3.2-C).
- `rework` 4필드가 채워진다(evidence_gap="없음").
- 거짓 완료 보고로 판정된다 — claim (b)의 `self_check` "충족" ↔ 독립 판정 위반의 모순(06 §3.2-F).

### (D) 판정 문장 (인용 + 예/아니오 환원 — §2 대응)

> (06 §7 거짓 완료 보고 검출 시연 인용) 완료 보고가 "AI 의존 0건 충족"이라 주장하나 산출물에 금지 요소가 잔존하는 케이스에서, VT-4 전수 스캔이 위반을 검출하고 `final_verdict = Fail`을 산출함을 보인다(§8 예1).

> (ROADMAP v0.5 인용) 거짓 완료 보고를 검출하는 케이스를 1개 이상 시연한다 (Verify Everything 검증).

**예/아니오 환원:** 픽스처 대상 파일 (a)의 전수 스캔에서 claim (b)가 놓친 잔존 금지 토큰이 검출되어 `verdict`=위반이고 `final_verdict`=Fail이며 `rework` 4필드가 채워졌는가? (예 → 충족 / 아니오 → 위반)

### (E) VT 사상 (done 4 — criteria-catalog 유형·기준 부류)

- **적용 VT:** VT-4 경계 검증 (criteria-catalog §2 VT-4 행, §3 전수 스캔 절차 1~6). 검출 연결 = 06 §3.2-F(criteria-catalog §3 절차 6, verifier-protocol §5).
- **대조 기준 부류:** 경계 규칙 (criteria-catalog §4 — "경계 Y에 금지 요소가 0건이다"). 주 대응 VT = VT-4.
- **리포트 필드 사상:** `criteria_basis`←경계 규칙, `criterion`←"대상 경계에 금지 요소 0건", `verification_type`←VT-4, `verdict`←위반, `evidence`←잔존 위치, `final_verdict`←Fail, `rework`←4필드(criteria-catalog §4 사상 사슬).

### (F) 기록 포맷 (§3 인스턴스 — 시연 수행 Task가 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §8-D 두 문장 + 예/아니오 환원을 수행 Task가 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (전수 스캔 매치·잔존 토큰 위치, 항목별 판정 verdict=위반·evidence·scope·VT-4, final_verdict=Fail, rework 4필드 값, claim self_check↔독립 판정 모순 확인) |
| 수행 단계 로그 | (§8-A 단계 1~5의 수행·관측 로그 — 특히 단계 3 전수 스캔, 단계 5 rework 산출) |
| 수행 물리 지점 | (전수 스캔·리포트 산출이 실현·관측된 지점 — verifier-binding.md 참조로 기입, §5) |

## §10. 시연 ⓑ — 리포트 스키마 완전성 + 결정적 생성 (DP-V3 실증)

목표: 임의의 판정에 대해 검증 리포트 6필드·항목별 판정 5필드가 전건 존재하고(스키마 완전성), 동일 입력{산출물+criteria}을 2회 수행하면 문면 동일 리포트를 냄(결정적 생성)을 보여, 06 §7 검증 리포트 스키마 시연과 ROADMAP v0.5 "검증 리포트 자동 생성"(DP-V3 해석)을 실증한다. 근거: 06 §7 검증 리포트 스키마 시연·ROADMAP v0.5·§3.2-A/B·INV-5, verification-report §2/§3, verifier-protocol §2/§4(DP-V3).

### (A) 절차 단계

1. **판정 대상 준비.** 임의의 판정 대상{산출물 + criteria}을 준비한다 — 확정 산출물(예: framework/verifier/ 문서 1종) 또는 픽스처. 통과 케이스(전 항목 충족)로 두면 `rework`="없음" 관측이 함께 성립한다.
2. **1회차 Verify 수행 (verifier-protocol §2 5단계).** 입력 수령→기준 확인→항목별 판정→최종 판정 도출→리포트 산출을 수행하여 검증 리포트 1건을 낸다.
3. **스키마 완전성 대조 (verification-report §2/§3).** 산출된 리포트에 6필드(`target`·`criteria_basis`·`items`·`final_verdict`·`verifier_scope`·`rework`)가 전건 존재하고(rework는 조건부 — Pass면 "없음"), 각 항목별 판정에 5필드(`criterion`·`verdict`·`evidence`·`scope`·`verification_type`)가 전건 존재함을 대조한다. 필수/조건부 표기를 정본(06 §3.2-A) 그대로 대조한다.
4. **2회차 Verify 수행 (동일 입력).** **동일 입력{산출물+criteria}** 으로 Verify를 1회 더 수행한다.
5. **결정성 대조 (DP-V3 — verifier-protocol §4).** 1회차·2회차 리포트의 **문면이 동일**함을 관측한다 — 필드 전건이 규정 절차만으로 도출되고 재량 개입이 0이므로, 동일 입력은 동일 리포트를 낸다(06 INV-5의 연산 수준 인스턴스, DP-V3). 문면 차이가 있으면 위반으로 표기한다(§7).

### (B) 입력

- 임의의 판정 대상{산출물 + criteria} 1건 (통과 케이스 권장 — rework="없음" 동시 관측).
- 동일 입력 2회 수행 지시(결정성 실증).

### (C) 기대 관측

- 리포트 6필드 전건 존재 — `target`·`criteria_basis`·`items`·`final_verdict`·`verifier_scope` 존재, `rework`는 조건부(Pass면 "없음").
- 항목별 판정 5필드 전건 존재 — `criterion`·`verdict`·`evidence`·`scope`·`verification_type`.
- 동일 입력 2회 수행 → **문면 동일 리포트**(DP-V3 결정성).

### (D) 판정 문장 (인용 + 예/아니오 환원 — §2 대응)

> (06 §7 검증 리포트 스키마 시연 인용) 임의의 판정에 대해 `target`·`criteria_basis`·항목별 판정(충족/위반/판정 불가)·`evidence`·`final_verdict` 필드가 모두 존재함을 보인다(§3.2-A/B).

> (ROADMAP v0.5 인용 + DP-V3) Worker 결과물에 대해 검증 리포트가 자동 생성된다 — DP-V3 해석상 "자동 생성" = 동일 입력{산출물+criteria}이 규정 절차만으로 동일 리포트를 냄(결정적·재량 무개입).

**예/아니오 환원:** 산출된 검증 리포트에 6필드(및 항목별 판정 5필드)가 전건 존재하고, 동일 입력{산출물+criteria} 2회 수행이 문면 동일 리포트를 냈는가? (예 → 충족 / 아니오 → 위반)

### (E) VT 사상 (done 4 — criteria-catalog 유형·기준 부류)

- **적용 VT:** VT-3 규격 준수 검증 (criteria-catalog §2 VT-3) — "산출된 리포트가 검증 리포트 스키마 규격(06 §3.2-A/B, verification-report §2/§3)의 각 필드와 일치"를 셀 단위 대조. 결정성(문면 동일)은 VT 밖 불변 관측이며 06 INV-5·DP-V3(verifier-protocol §4)에 사상된다.
- **대조 기준 부류:** 규격 (criteria-catalog §4 — "규격 항목 X가 산출물과 셀 단위로 일치한다"). 결정성 근거는 경계 규칙 부류의 불변(INV-5)이다.
- **리포트 필드 사상:** 이 시연의 판정 대상은 "리포트 산출물 자체"이며, 대조 기준은 06 §3.2-A/B 스키마 규격 + INV-5/DP-V3 결정성이다.

### (F) 기록 포맷 (§3 인스턴스 — 시연 수행 Task가 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §10-D 두 문장 + 예/아니오 환원을 수행 Task가 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (리포트 6필드 존재·값, 항목별 판정 5필드 존재, 1회차·2회차 리포트 문면 동일 여부(결정성), rework 조건부(Pass면 "없음") 확인) |
| 수행 단계 로그 | (§10-A 단계 1~5의 수행·관측 로그 — 특히 단계 3 스키마 대조, 단계 5 결정성 대조) |
| 수행 물리 지점 | (Verify 수행·리포트 산출이 실현·관측된 지점 — verifier-binding.md 참조로 기입, §5) |

## §11. 시연 ⓒ — 검증 유형 VT-1~VT-5 적용

목표: VT-1(산출물 존재)·VT-2(완료 조건 대조)·VT-3(규격 준수)·VT-4(경계)·VT-5(시연) 각각이 최소 1개 판정 항목에 적용되고, 유형별 판정 방법대로 `verdict`가 도출됨을 보인다. 근거: 06 §7 검증 유형 적용 시연·§3.2-E, criteria-catalog §2, verification-report §3.

### (A) 절차 단계

각 유형에 대해 판정 대상의 해당 항목을 유형별 판정 방법(criteria-catalog §2 정본 셀)대로 판정하고, 항목별 판정 5필드(criterion·verdict·evidence·scope·verification_type)를 남긴다.

1. **VT-1 산출물 존재 검증.** 위임 output이 지정한 산출물이 실제로 존재하고 접근 가능한지 확인한다 → 존재하면 충족(Met).
2. **VT-2 완료 조건 대조 검증.** 위임 완료 조건(done) 항목을 산출물과 항목별로 대조한다 → 전 항목 충족이면 충족.
3. **VT-3 규격 준수 검증.** 산출물이 따라야 할 규격(예: 대상 spec §7 완료 기준, 스키마 필수/선택 표기)의 각 항목을 산출물과 셀 단위 대조한다 → 규격 전 항목 충족이면 충족.
4. **VT-4 경계 검증.** 금지 요소 후보 부류 전체를 대상 경계 전 범위로 전수 스캔한다(criteria-catalog §3) → 금지 요소 0건이면 충족. (실계약 산출물을 대상으로 하면 충족이 기대되고, 픽스처 (a)를 대상으로 하면 위반이 도출된다 — 유형별 판정 방법은 대상과 무관하게 전수 스캔이다.)
5. **VT-5 시연 검증.** "시연 가능 문장"으로 표현된 완료 기준의 시연 시나리오를 실제로 재현하고 결과를 관측한다 → 기대대로 관측되면 충족.

### (B) 입력

- VT-1~VT-5 각각을 적용할 항목을 포함하는 판정 대상 — 확정 산출물(VT-1 존재·VT-2 위임 done 대조·VT-3 스키마/§7 규격 대조·VT-4 경계 전수 스캔) + 시연 재현 대상(VT-5). 구체 판정 대상 바인딩은 시연 수행 Task가 수행한다.

### (C) 기대 관측

- VT-1·VT-2·VT-3·VT-4·VT-5 각각이 **최소 1개** 판정 항목에 적용된다.
- 각 유형의 `verdict`가 유형별 판정 방법(criteria-catalog §2 정본 셀)대로 도출된다.
- 한 항목이 하나 이상 유형에 대응할 수 있다(예: 규격 대조이자 시연인 항목은 VT-3·VT-5 병기 — criteria-catalog §2 다중 유형 대응).

### (D) 판정 문장 (인용 + 예/아니오 환원 — §2 대응)

> (06 §7 검증 유형 적용 시연 인용) VT-1 ~ VT-5 각각이 한 판정 항목에 적용되고, 유형별 판정 방법대로 verdict가 도출됨을 보인다(§3.2-E).

**예/아니오 환원:** VT-1~VT-5 각각이 최소 1개 판정 항목에 적용되고 유형별 판정 방법대로 `verdict`가 도출됐는가? (예 → 충족 / 아니오 → 위반)

### (E) VT 사상 (done 4 — criteria-catalog 유형·기준 부류)

- **적용 VT:** VT-1·VT-2·VT-3·VT-4·VT-5 전부 (criteria-catalog §2 카탈로그).
- **대조 기준 부류 (criteria-catalog §4):** VT-1·VT-2 → 위임 완료 조건, VT-3 → 규격, VT-4 → 경계 규칙, VT-5 → 시연 기준.
- **리포트 필드 사상:** 각 항목의 `verification_type`←해당 VT, `criterion`←대조 기준 검증 가능 문장, `verdict`←유형별 판정 방법 결과(criteria-catalog §4 사상 사슬).

## §12. 시연 ⓓ — 최종 판정 결정성 3집합 (Pass / Fail / Conditional)

목표: 세 가지 항목별 판정 집합에서 06 §3.2-C 도출 규칙이 항상 동일한 `final_verdict`를 내고, 통과(Pass)·실패(Fail)·조건부(Conditional) 3분기가 규칙대로 전부 결정적으로 도출됨을 보인다. 근거: 06 §7 최종 판정 결정성 시연·§3.2-C·INV-5·§8 예2, verification-report §4, verifier-protocol §2.5.

### (A) 절차 단계

1. **집합 1 준비·도출 (Pass).** 전 항목이 충족(Met)인 항목별 판정 집합을 구성한다 → 06 §3.2-C 규칙(모든 항목 충족 → 통과)으로 `final_verdict`=**통과(Pass)** 도출을 관측한다(verification-report §4). `rework`="없음".
2. **집합 2 준비·도출 (Fail).** 위반(Violated)이 하나 이상 포함된 집합을 구성한다 → 규칙(하나라도 위반 → 실패)으로 `final_verdict`=**실패(Fail)** 도출을 관측한다. `rework` 4필드 채움.
3. **집합 3 준비·도출 (Conditional).** 위반은 없고 판정 불가(Undetermined)가 하나 이상 포함된 집합을 구성한다(예: 06 §8 예2 유형 — Open Question 해소 여부가 근거 부족으로 판정 불가) → 규칙(위반 없고 판정 불가 존재 → 조건부)으로 `final_verdict`=**조건부(Conditional)** 도출을 관측한다. `rework`에 `evidence_gap` 유내용(rework-instruction §3).
4. **결정성 대조 (INV-5).** 각 집합을 반복 적용하면 항상 동일한 `final_verdict`가 나옴을 관측한다 — 위반의 경중을 재량으로 감면하지 않는다(06 INV-5). 최초 Fail과 재검증 Pass 같은 차이는 판정 집합 자체가 변한 결과이지 도출 규칙의 변경이 아니다(verifier-protocol §2.5).
5. **재량 경계 관측 (06 §8 예2).** 집합 3(Conditional)은 Verifier가 스스로 통과 처리하지 않고 Conditional로 두어 Advisor 최종 판정(재량)에 넘김을 관측한다 — 재량 판정은 Verifier가 하지 않는다(06 §3.2-C, 02 §3.2-A).

### (B) 입력

- 세 항목별 판정 집합 — 집합 1(전부 충족), 집합 2(위반 ≥1 포함), 집합 3(위반 0·판정 불가 ≥1 포함). 각 집합은 06 §3.2-C 도출 규칙의 대상이며, 구성은 시연 수행 Task가 수행한다(합성 집합 가능 — 도출 규칙 실증이 목적).

### (C) 기대 관측

- 집합 1 → 통과(Pass), 집합 2 → 실패(Fail), 집합 3 → 조건부(Conditional) — 3분기 전부 규칙대로 도출.
- 동일 집합 반복 적용 시 항상 동일 `final_verdict`(결정성, 06 INV-5).
- 집합 3(Conditional)은 재량 처리 없이 Advisor 최종 판정에 넘겨진다(06 §8 예2).

### (D) 판정 문장 (인용 + 예/아니오 환원 — §2 대응)

> (06 §7 최종 판정 결정성 시연 인용) 동일한 항목별 판정 집합에서 §3.2-C 규칙이 항상 동일한 `final_verdict`를 내고, Pass/Fail/Conditional이 규칙대로 도출됨을 보인다(INV-5).

**예/아니오 환원:** 전부 충족 집합→통과(Pass), 위반 포함 집합→실패(Fail), 위반 없이 판정 불가 포함 집합→조건부(Conditional)의 3분기가 06 §3.2-C 규칙으로 전부 결정적으로 도출됐는가? (예 → 충족 / 아니오 → 위반)

### (E) VT 사상 (done 4 — criteria-catalog 유형·기준 부류)

- **적용 VT:** 이 시연의 판정 대상은 "최종 판정 도출 규칙 자체"이며 개별 VT가 아니라 06 §3.2-C 도출 규칙·INV-5 결정성(verification-report §4)에 사상된다. 도출 규칙 일치 대조는 규격 준수(VT-3) 성격이다(criteria-catalog §2 VT-3 — 규격 = 도출 규칙).
- **대조 기준 부류 (criteria-catalog §4):** 규격(도출 규칙 06 §3.2-C) + 경계 규칙(결정성 불변 INV-5).
- **리포트 필드 사상:** 각 집합의 `items`(항목별 판정) → `final_verdict`(06 §3.2-C 규칙), Fail·Conditional 집합의 `rework`(조건부).

### (F) 기록 포맷 (§3 인스턴스 — 시연 수행 Task가 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §12-D 문장 + 예/아니오 환원을 수행 Task가 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (집합 1·2·3의 항목별 판정 구성, 각 집합의 도출 final_verdict(Pass/Fail/Conditional), 반복 적용 결정성, Conditional의 Advisor 재량 이관 확인) |
| 수행 단계 로그 | (§12-A 단계 1~5의 수행·관측 로그 — 3집합 도출·결정성·재량 경계) |
| 수행 물리 지점 | (도출 규칙 적용이 실현·관측된 지점 — verifier-binding.md 참조로 기입, §5) |

## §13. 시연 ⓔ — 재작업 지시 필드 완전성 (Fail·Conditional rework 4필드)

목표: Fail 리포트·Conditional 리포트의 `rework` 4필드(violated_items·expected_state·revalidation_criteria·evidence_gap)가 모두 채워지고, Pass 리포트의 `rework`가 "없음"임을 보인다. 근거: 06 §7 재작업 지시 시연·§3.2-D·§3.2-A, rework-instruction §2/§3/§4, verification-report §2.

### (A) 절차 단계

1. **Fail 리포트 rework 대조.** ⓐ의 Fail 리포트(또는 ⓓ 집합 2)에서 `rework` 4필드 존재를 대조한다(rework-instruction §2) — `violated_items`(위반 항목 criterion+verdict), `expected_state`(기대 상태), `revalidation_criteria`(재검증 기준), `evidence_gap`(판정 불가 0건이면 "없음"). 위반 항목·기대 상태·재검증 기준이 모두 포함됨을 확인한다(06 §7 재작업 지시 시연).
2. **Conditional 리포트 rework 대조.** ⓓ 집합 3(Conditional)의 `rework`에서 `violated_items`에 판정 불가 항목이, `evidence_gap`에 그 판정을 막은 근거 부족·검사 범위 한계가 유내용으로 채워짐을 대조한다(rework-instruction §3, 06 §8 예2).
3. **Pass 리포트 rework 대조.** 통과 케이스(ⓑ 또는 ⓓ 집합 1)에서 `rework`="없음"임을 대조한다(06 §3.2-A 조건부 표기, rework-instruction §3).
4. **재검증 기준 적용 범위 규칙 대조 (rework-instruction §4).** `revalidation_criteria`·`expected_state`의 "잔존 서술 0건" 류 기준이 **라이브 본문**에 적용되고, 시점-스코프 기록(이력 행·인용·교정 경위)은 제외되며, 이력 행 문면은 append-only 불변임을 확인한다.

### (B) 입력

- Fail 리포트 1건(ⓐ 또는 ⓓ 집합 2), Conditional 리포트 1건(ⓓ 집합 3), Pass 리포트 1건(ⓑ 또는 ⓓ 집합 1).

### (C) 기대 관측

- Fail 리포트 `rework` 4필드 채움 — 위반 항목·기대 상태·재검증 기준 포함, evidence_gap="없음".
- Conditional 리포트 `rework` 4필드 채움 — violated_items에 판정 불가 항목, evidence_gap 유내용.
- Pass 리포트 `rework`="없음".
- 재검증 기준이 라이브 본문에 적용되고 시점-스코프 기록은 제외된다.

### (D) 판정 문장 (인용 + 예/아니오 환원 — §2 대응)

> (06 §7 재작업 지시 시연 인용) Fail 리포트의 `rework`에 위반 항목·기대 상태·재검증 기준이 모두 포함됨을 보인다(§3.2-D).

**예/아니오 환원:** Fail·Conditional 리포트의 `rework` 4필드가 모두 채워지고(Fail은 위반 항목·기대 상태·재검증 기준 포함, Conditional은 evidence_gap 유내용), Pass 리포트의 `rework`가 "없음"인가? (예 → 충족 / 아니오 → 위반)

### (E) VT 사상 (done 4 — criteria-catalog 유형·기준 부류)

- **적용 VT:** VT-3 규격 준수 검증 (criteria-catalog §2 VT-3) — "산출된 재작업 지시가 재작업 지시 4필드 스키마 규격(06 §3.2-D, rework-instruction §2)의 각 필드와 일치·조건부 규칙(06 §3.2-A/C) 준수"를 대조.
- **대조 기준 부류 (criteria-catalog §4):** 규격(재작업 지시 4필드 스키마·발행 조건).
- **리포트 필드 사상:** `rework`←4필드(rework-instruction §2), 발행 조건←`final_verdict`(Fail/Conditional 필수, Pass면 "없음", 06 §3.2-A/C).

### (F) 기록 포맷 (§3 인스턴스 — 시연 수행 Task가 채운다)

| 필드 | 내용 |
|---|---|
| 판정 문장 | (위 §13-D 문장 + 예/아니오 환원을 수행 Task가 전재) |
| 관측 결과 | (충족 / 위반 / 판정 불가) |
| 근거 (관측한 것) | (Fail rework 4필드 값, Conditional rework(판정 불가 항목·evidence_gap 유내용), Pass rework="없음", 재검증 기준 라이브 본문 적용·시점-스코프 제외 확인) |
| 수행 단계 로그 | (§13-A 단계 1~4의 수행·관측 로그 — Fail·Conditional·Pass rework 대조, 적용 범위 규칙) |

## §14. 시연 ⓕ — 독립성 (self_check "충족" 주장과 무관한 산출물 근거 판정)

목표: 완료 보고 `self_check` "충족" 주장과 무관하게 판정이 산출물 근거로만 이루어져 위반으로 도출됨(주장 반대 사례)을 보인다. 근거: 06 §7 독립성 시연·§3.1 V1·INV-1, verifier-protocol §2.2/§5, criteria-catalog §3 절차 6.

### (A) 절차 단계

1. **완료 보고 참고 입력 수령 (verifier-protocol §2.2).** claim 파일 (b)의 `self_check`="충족" 주장을 **참고 입력으로만** 받는다 — 판정 근거로 삼지 않는다(06 V1, INV-1).
2. **산출물 근거 독립 판정 (verifier-protocol §2.4/§5).** 판정을 대상 파일 (a) **자체와 그 실측**을 근거로만 수행한다. 완료 보고 주장을 신뢰하지 않고 동일 기준을 산출물에 충분한 범위로 재판정한다(VT-4 전수 스캔, criteria-catalog §3 절차 6).
3. **주장 반대 사례 관측.** claim (b)의 `self_check` "충족" 주장에도 불구하고, 산출물 근거 판정이 **위반(Violated)** 으로 도출됨을 관측한다 — 완료 보고 주장이 판정을 바꾸지 못함(주장 반대 사례). 판정이 오직 산출물 근거로만 이루어짐이 실증된다(06 INV-1).

### (B) 입력

- claim 파일 (b) — `self_check`="충족" 주장(§4).
- 대상 파일 (a) — 실제로는 금지 토큰 잔존(위반 근거, §4). ⓐ 픽스처를 재사용할 수 있다.
- 대조 기준 criteria — 경계 규칙(criteria-catalog §4).

### (C) 기대 관측

- 완료 보고 `self_check` "충족"과 독립 판정 `verdict`=위반이 모순된다.
- 판정 근거가 완료 보고 주장이 아니라 산출물 (a)의 실측(잔존 위치)임이 `evidence`에 남는다.
- 완료 보고 주장이 판정을 바꾸지 못함(독립성, 06 INV-1).

### (D) 판정 문장 (인용 + 예/아니오 환원 — §2 대응)

> (06 §7 독립성 시연 인용) `self_check` "충족" 주장과 무관하게 판정이 산출물 근거로만 이루어짐을 보인다(INV-1).

**예/아니오 환원:** 완료 보고 `self_check` "충족" 주장에도 불구하고 판정이 산출물 (a) 근거로만 이루어져 `verdict`=위반으로 도출됐는가(주장 반대 사례)? (예 → 충족 / 아니오 → 위반)

### (E) VT 사상 (done 4 — criteria-catalog 유형·기준 부류)

- **적용 VT:** VT-4 경계 검증 (criteria-catalog §2/§3) — 완료 보고 `self_check`·`verify_basis`가 근거로 든 좁은 검사 범위를 **넘어** 전수 재검사(criteria-catalog §3 절차 6). 독립성 자체는 06 §3.1 V1·INV-1 불변에 사상된다.
- **대조 기준 부류 (criteria-catalog §4):** 경계 규칙(독립성 불변 — 판정은 산출물 근거, 완료 보고는 검사 대상).
- **리포트 필드 사상:** `evidence`←산출물 (a) 실측(완료 보고 주장 아님), `verdict`←위반(완료 보고 self_check "충족"과 무관), 완료 보고는 참고 입력(claim)일 뿐(06 V1).

### (F) 기록 포맷 (§3 인스턴스 — 시연 수행 Task가 채운다)

| 필드 | 내용 |

## §15. 정본 경계·용어 self-note (재정의 0 — done 7)

- **재정의 없음 (done 7).** 본 절차서의 모든 판정 문장은 06 §7 시연 가능 문장·ROADMAP v0.5 완료 조건의 **인용 또는 그 검증 가능 환원(예/아니오)**이고, 모든 절차 단계·입력·기대 관측·VT 사상은 06 §3 Core Contract와 확정 framework/verifier/ 5종(V1~V5)의 계약·규칙 인스턴스다. 어떤 계약 요소도 이 문서에서 진위가 확정되지 않는다 — 판정 기준은 항상 정본 §(06 §3·V1~V5)이다. **새 판정 기준·새 검증 유형·새 판정 값·새 필드를 창설하지 않았다.**
- **필드 소속 명시·혼입 방지.** 검증 리포트 6필드·항목별 판정 5필드는 06 §3.2-A/B(V1 §2/§3), 재작업 지시 4필드는 06 §3.2-D(V4 §2), 검증 유형 VT-1~VT-5·대조 기준 부류는 06 §3.2-E/§3.2-A(V5 §2/§4), 완료 보고 필드(self_check·verify_basis·failures·artifacts)는 02 §3.2-C(delegation-protocol §2.2)로 소속을 § 포인터로 명시했다 — 판정 대상의 완료 보고 필드와 판정 산출물의 리포트 필드를 섞지 않았다.
- **연산 실패 vs final_verdict=Fail 구분 (verifier-protocol §6).** 시연에서 관측되는 `final_verdict = Fail`(정상 출력)과 Verify 연산 실패(산출물 접근 불가·대조 기준 부재)를 §7-4에서 구분했다 — 새 실패 사유 코드를 신설하지 않았다.
- **픽스처 실물 비생성·금지 토큰 비나열 (constraint, done 3·done 7).** 픽스처(docs/v0.5-demo-fixtures/)를 **명세**만 하고 생성하지 않았다(시연 수행 Task 소관). 픽스처에 심을 금지 토큰의 **구체 예시를 본문에 나열하지 않았다** — §4.3에서 후보 부류로만 서술했고, 실물 토큰 선택·심기는 시연 수행 Task 소관이며 격리 조건(픽스처 디렉터리 내부에만)으로 절차서 본문 누출을 차단했다.
- **소유 경계 준수 (07 R4).** 본 작업의 소유 경계는 이 1파일(docs/v0.5-demo-procedure.md)이다. 픽스처 파일·디렉터리를 생성하지 않았고, framework/verifier/·06·다른 저장소 파일을 수정하지 않았다.
- **동시 작성 산출물 불인용 (07 R2).** 같은 Wave에서 동시 작성 중인 framework/adapters/claude/verifier-binding.md(V6)의 미완성 내용을 인용·추측하지 않았다 — 물리 수행 지점은 "Adapter Binding 문서 소관" 포인터로만 처리했다(§5). 참조한 확정 입력은 06·framework/verifier/ 5종(V1~V5)·ROADMAP·docs/v0.4-demo-procedure·docs/session-handoff-v0.4뿐이다.
- **새 용어 신설 없음 (Glossary §3.2-J).** 계약 용어(검증 리포트·항목별 판정·검증 유형·재작업 지시·거짓 완료 보고 및 그 필드명)와 판정 값(충족/위반/판정 불가)·최종 판정(통과/실패/조건부)은 전부 Glossary §3.2-J·06 §3.2·framework/verifier/ 정본에서 인용했다. "시연 ⓐ~ⓕ", "판정 문장", "VT 사상", "기록 포맷", "픽스처(대상 파일·claim 파일)"는 조직 편의용 서술 라벨이며 Glossary 표제어가 아니다(§0 라벨 주의).
- **적용 Lesson 반영.** L-07(상태 서술 실측 후 — 기록 내 timestamp 성격 구분, §3 기록 요건 2), L-08(판정 문장 예/아니오 환원 — 각 시연 (D)의 예/아니오 환원), BP-01(자가 검출·교정·공개 — 경계·재정의 0을 self-note로 투명 공개)의 취지를 반영했다.
