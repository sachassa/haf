# Solution Design — 운송관리시스템(TMS)

> 이 문서는 Solution Design 성숙 run `maturation-tms-001`의 **설계 근거 문서(Projection)**다.
> **Source of Truth는 Project Contract v2**(`.claude/project-contract/project-contract.v2.md`)이며,
> 이 문서는 그 파생이다(04 §3.5 — Contract 코어 스키마 재정의 0). 상세 코드·ERD·화면은 없다(구현 Planning 하류).

## 1. 개요

### 1.1 입력 (기준선 v1)

성숙의 입력은 Project Contract **v1**(`instanceVersion:1`, 종단 ReadyWithAssumptions)이다.
v1은 국내 화물자동차 운송주선업(3인 사업장) TMS를 방향 수준으로 확정했으나, 다음이 미결이었다.

- 화물정보망 연동 실현 방식(자동 vs 반자동) — 대상 정보망별 검증 필요.
- 배차 상세 기준(누가·어떤 우선순위로 어느 채널).
- 회계/ERP·화물정보망 대상 제품 미확정.
- 상세 설계(화면·ERD·API·Wireframe)는 Discovery 범위 밖.
- 가정 6건(A1~A6) 전부 미해결(기업 화주·클라우드·백업·감사이력·WHEN-WHERE·대상 제품).

### 1.2 성숙 개요

Solution Design은 v1을 입력으로 복잡도 판정 → 역할 협업(Proposing/Reconciling/Reviewing) →
사용자 게이트(Validating) → **Matured** 종단으로 진행했다. 산출은 superseding **Contract v2**와
이 Projection 문서다. 성숙의 핵심 성과:

- 정산 도메인을 **청구(AR)/지급(AP) 라인 분리 모델**로 재구조화(2자·3자 단일 흡수, 마진=파생).
- 화물정보망 의존을 **채널 불가지 어댑터**로 격리하고 실현성을 법적으로 판정(반자동 폴백·크롤링 배제).
- 감사이력·백업을 **확정 요구**로 승격, 4개 사용자 결정(정보망 정책·우리 전용·기업 화주·TS 풀스택)을 수렴.
- 가정 6건 중 4건 해소(잔여 3건 SA1·SA2·SA3).

## 2. 설계 결정 (SD-D1~D17 상세)

- **SD-D1 모듈러 모놀리스 단일 백엔드.** 정산 트랜잭션 일관성을 최우선으로, 단일 백엔드 내 모듈 경계로
  구성한다. 3인 소규모 운영 부담을 고려해 마이크로서비스를 지양하되, 확장 시 모듈 단위 분리 여지를 남긴다.
- **SD-D2 3접점 프런트.** 내부 웹은 리치 SPA(배차·정산·마스터), 기사용은 경량 PWA(수락·상태·인수증 사진),
  화주 포털은 조회 전용·데이터 격리. 접점별로 화면 복잡도와 권한 표면이 다르므로 분리한다.
- **SD-D3 클라우드 SaaS·국내 리전 매니지드.** 3인 사업장 운영 부담·다접점 접근성·데이터 주권(국내 리전).
- **SD-D4 정산 = 청구(AR)/지급(AP) 라인 분리.** 오더 1건에 화주 청구 라인과 차주/용차 지급 라인을 분리 부착.
  2자 정산(직배차)은 지급 라인이 실차주, 3자 정산(용차)은 지급 라인이 협력사가 되어 **단일 모델로 흡수**된다.
  마진은 저장 값이 아니라 **청구−지급 파생**으로 계산 → 단가 변경 시 일관성 자동 유지.
- **SD-D5 3자 장부 경계 = 2라인.** 장부화는 화주 청구/협력사(용차) 지급 2라인까지. 협력사↔실차주 관계는
  **참조만** 보관(사고·클레임 대비 실차주 식별정보 보관)하되 우리 장부의 정산 대상은 아니다.
- **SD-D6 단가표 청구용/지급용 분리.** 청구용·지급용 단가표를 분리하고, 노선·거래처·조건으로 **우선순위 자동
  제안** + 건별 **오버라이드**를 허용한다. 표단가와 실제 적용단가를 **둘 다 기록**(사후 대사·감사).
- **SD-D7 정산 원장=건별, 월마감=파생.** 원장의 단일 진실은 건별 정산 라인이며, 월마감·세금계산서는
  월·거래처 단위 **집계 파생**이다 → 정정·재발행 시 원장만 갱신, 파생은 재계산.
- **SD-D8 세금계산서=독립 엔티티·N:M.** 세금계산서를 정산건과 **N:M**으로 연결(월 합산 발행 가능),
  대행 API(팝빌/바로빌급) 경유로 정발행/역발행 처리.
- **SD-D9 정산건 상태머신.** 발생→확정→마감→발행→수납/지급. **확정 후 변경은 수정/재발행 이력**으로
  남기고 직접 덮어쓰기를 금지 → 감사 추적·정산 이의 대응.
- **SD-D10 권한 = 내부 얇은 RBAC + 외부 행 단위 소유권 스코핑.** 내부는 운영/관리자 얇은 역할,
  외부(화주·기사)는 **행 단위 소유권**을 **서버에서 강제**(클라이언트 불신)하고 정산 정보를 은닉.
- **SD-D11 감사이력=append-only 변경로그(확정).** 정산·배차·오더 변경을 이전값→이후값으로 append-only 기록.
  (v1 A4 가정 → 확정 요구.)
- **SD-D12 백업=자동 스냅샷+PITR(확정).** 매니지드 DB 자동 스냅샷 + 시점복구. (v1 A3 가정 → 확정 요구.)
- **SD-D13 배차 채널 불가지 어댑터.** 직배차/화물정보망/용차 세 채널을 **단일 배차 진입점**으로 흡수하는
  어댑터로 설계 → 화물정보망 의존을 격리하고, 연동 방식(자동/반자동)이 바뀌어도 상위 배차 로직 불변.
- **SD-D14 연동 방식 확정.** 세금계산서=대행 API / 알림=카카오 공식 딜러사+SMS 폴백 /
  회계=더존 반자동(전표 내보내기·단방향) 기본·제품 확정 시 API / 화물정보망=반자동 폴백+운영사 공식
  문의 병행·**크롤링 배제**. (§4 실현성 판정표 참조.)
- **SD-D15 멀티테넌시=tenant_id-ready + 단일 테넌트.** 현재 우리 전용 단일 테넌트 배포이나 데이터 모델에
  tenant_id 경계를 예약해 향후 SaaS 확장에 대비.
- **SD-D16 기술스택=TS 풀스택.** Node/NestJS(백) + React/Next.js(내부 웹·화주 포털) + 기사 PWA +
  PostgreSQL + 국내 리전 매니지드. 언어 통일·3인 팀 생산성·트랜잭션 신뢰.
- **SD-D17 단계화.** Phase 1(마스터+수주+기본배차+정산코어) → 1.5(세금계산서) →
  2(운송추적+기사앱+예외) → 3(리포트+화주포털) → 4(알림·회계·화물정보망 조건부). (§5 로드맵.)

## 3. ADR (Architecture Decision Records)

각 ADR = {맥락 · 대안 · 선택 · 이유}.

### ADR-1 — 모듈러 모놀리스
- 맥락: 정산이 최우선이며 트랜잭션 일관성이 핵심. 운영 인력 3인.
- 대안: (a) 마이크로서비스, (b) 모듈러 모놀리스, (c) 단순 모놀리스.
- 선택: (b) 모듈러 모놀리스.
- 이유: 정산 트랜잭션 일관성·운영 부담 최소화. 마이크로서비스의 분산 트랜잭션 비용 회피. 확장 시 모듈 분리 여지 확보.

### ADR-2 — tenant_id-ready 단일 테넌트
- 맥락: 현재 우리 전용이나 사용자가 향후 확장 가능성을 언급.
- 대안: (a) 순수 단일 테넌트(테넌트 개념 없음), (b) tenant_id 예약 단일 테넌트, (c) 풀 멀티테넌트.
- 선택: (b).
- 이유: 현 시점 단일 테넌트 운영 단순성 + 미래 SaaS 전환 시 데이터 재설계 회피. 풀 멀티테넌트는 현재 과잉.

### ADR-3 — 기사앱 = PWA
- 맥락: 기사용 현장 태스크(배차 수락·상태 입력·인수증 사진)는 경량.
- 대안: (a) 네이티브 앱, (b) PWA, (c) 반응형 웹.
- 선택: (b) PWA.
- 이유: 앱스토어 심사·설치 마찰 회피. 오프라인/푸시 등 PWA 기능으로 현장 태스크에 충분. 배포 즉시성.

### ADR-4 — 화물정보망 반자동 폴백
- 맥락: 사용자가 자동연동을 요구했으나 대상 정보망(24시콜·화물맨)의 공개 공식 API 근거가 없음.
- 대안: (a) 크롤링 자동화, (b) 반자동(엑셀 업로드) 폴백, (c) 연동 배제.
- 선택: (b) 반자동 폴백 + 운영사 공식 문의 병행, 확보 시 자동 승격. (a) 크롤링 배제.
- 이유: 크롤링은 위법·약관 위반·불안정 위험(대법 2021도1533·정보통신망법). 반자동은 요구를 관리 가능한 형태로 충족.

### ADR-5 — 대행/딜러사 채택
- 맥락: 전자세금계산서·카카오 알림톡은 직접 연동 시 인증·심사·유지 부담.
- 대안: (a) 직접 연동, (b) 대행/딜러사 경유.
- 선택: (b) — 세금계산서=대행 API(팝빌/바로빌급), 카카오 알림=공식 딜러사, SMS 폴백.
- 이유: 대행/딜러사가 인증·심사·유지보수를 흡수. 3인 팀의 연동 운영 부담 절감.

### ADR-6 — 건별 정산 원장
- 맥락: 월마감·세금계산서·정산 이의가 혼재.
- 대안: (a) 월 집계를 원장으로, (b) 건별을 원장으로·월은 파생.
- 선택: (b).
- 이유: 건별 단일 진실 → 정정/재발행 시 원장만 갱신, 월마감·세금계산서는 재계산. 대사·감사 추적 용이.

### ADR-7 — 3자 장부 경계 2라인
- 맥락: 용차 재위탁 시 협력사 아래 실차주가 존재(3자 이상).
- 대안: (a) 실차주까지 장부화, (b) 청구/지급 2라인까지만 장부화·실차주는 참조.
- 선택: (b).
- 이유: 우리의 정산 책임 경계는 협력사까지. 실차주는 사고·클레임 대비 식별정보만 보관 → 책임·데이터 경계 명확.

### ADR-8 — 마진 = 파생
- 맥락: 마진(청구−지급)을 저장 값으로 둘지 파생으로 둘지.
- 대안: (a) 저장 값, (b) 파생.
- 선택: (b) 파생.
- 이유: 단가·오버라이드 변경 시 마진 일관성 자동 유지. 저장 값은 갱신 누락 위험.

### ADR-9 — 기술스택 TS 풀스택
- 맥락: 3인 팀·다접점(SPA·PWA·포털)·정산 트랜잭션 신뢰 필요.
- 대안: (a) TS 풀스택, (b) 백엔드 별도 언어(예: 다른 런타임) + JS 프런트.
- 선택: (a) — Node/NestJS + React/Next.js + PWA + PostgreSQL.
- 이유: 프런트/백 언어 통일로 3인 팀 생산성·코드 공유. PostgreSQL 트랜잭션 신뢰. 권장안 채택.

## 4. 연동 실현성 판정표

| 연동 대상 | 판정 | 방식 | 근거 |
|---|---|---|---|
| 전자세금계산서 | **성숙(실현 가능)** | 대행 API 경유(정/역발행) | 팝빌 등 상용 전자세금계산서 대행 API 존재 — https://www.popbill.com |
| 카카오 알림(알림톡) | **딜러사 경유** | 공식 딜러사 API + SMS 폴백 | 알림톡은 공식 딜러사(메시징 사업자) 경유 — 예: https://solapi.com (채널/템플릿 사전심사 필요) |
| 회계(더존) | **제품별 조건부** | 반자동(전표 내보내기·단방향) 기본, 제품 확정 시 API | 더존 대상 세부 제품 미확정(SA2) → 방식 확정 지연(R5) |
| 화물정보망 24시콜·화물맨 | **공개 API 근거 없음 → 반자동 폴백** | 엑셀 업로드 폴백 + 운영사 공식 문의 병행, 크롤링 배제 | 공개 오픈API 근거 미확인. 참고 오픈API 사례는 별개 서비스(예: 원콜 오픈API — 헬로티 기사 https://www.hellot.net). 크롤링은 위법 위험(대법원 2021도1533) |

> 크롤링 배제 근거: 대법원 2021도1533 — 타사 서비스 데이터 무단 수집(크롤링)의 위법성 판례.
> 정보통신망 이용촉진 및 정보보호 등에 관한 법률상 위험과 서비스 약관 위반 소지도 함께 고려.

## 5. 단계화 로드맵 (Phase 1 / 1.5 / 2 / 3 / 4)

| Phase | 목표 | 포함 | 이유 |
|---|---|---|---|
| **Phase 1** | 정산 코어 가동 | 마스터(거래처·차량·단가) + 수주 + 기본 배차 + 정산 코어(AR/AP·건별 원장·상태머신) | 최우선=정산. 핵심 가치를 먼저 출시 |
| **Phase 1.5** | 세금계산서 | 전자세금계산서 발행/역발행(대행 API·N:M·월 합산) | 정산 코어 직후 청구 마무리 필요 |
