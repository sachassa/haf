> 이 문서는 사용자 지시를 **소실 방지를 위해 축자(verbatim) 영속화**한 것이다. 지난 세션에서 이 태스크가 파일로 저장되지 않아 통째로 유실되었으므로, 착수 전 최우선으로 기록한다. 이 문서 자체는 신규 문서이며 기존 UAHF 정본을 수정하지 않는다.

## 목적

이번 작업은 **폴더 정리가 아니다.**

UAF의 장기 Architecture(v1.3 이후 포함)를 기준으로, Repository를 **앞으로 다시 변경하지 않는 것**을 목표로 Repository Architecture를 재구성한다.

이번 작업에서는:
- **코드 수정 금지**
- **Runtime 수정 금지**
- **기존 UAHF 수정 금지**

Repository Structure와 Markdown 이동 및 문서 구조만 변경한다.

## 중요 원칙

1. Repository는 **Layer 중심 구조**로 변경한다.
2. 각 Layer는 **독립적으로 사용**할 수 있어야 한다.
3. 각 Layer는 **독립적인 `.claude`**를 가진다. 최상위 `.claude`는 Global Default. Layer 하위 `.claude`는 Override만 수행.
4. 각 Layer는 자신의 **README**를 가진다.
5. 각 Layer는 자신의 **ARCHITECTURE**를 가진다.
6. ROADMAP는 **Layer별 Roadmap**를 가진다.
7. Root README는 전체 Framework 소개.
8. Root ARCHITECTURE는 **Layer 관계와 전체 구조만** 설명.
9. Root ROADMAP는 Framework 전체 Roadmap.
10. **Knowledge는 Layer가 아니다.** 모든 Layer가 Consult하는 공용 Knowledge Base.
11. **UAHF는 Runtime Layer의 구현체**다. Repository의 최상위 프로젝트가 아니다.
12. 기존 UAHF Source는 수정하지 않는다. **Directory만 이동**한다.
13. 기존 Entry / Discovery도 구현은 수정하지 않는다. **Directory와 문서 구조만** 변경한다.

## Planner (Opus) 선행 산출물

Planner(Opus)가 Repository를 **실제 분석**하여 다음을 먼저 제출한다:
1. Migration Table
2. Repository Tree
3. 이동 대상
4. 문서 수정 대상
5. 위험 요소
6. Architecture 검토

→ Advisor는 **Architecture 관점 검토** 후 최종 Repository 구조를 **사용자 승인안**으로 제출한다.

**대안 의무**: Repository를 분석한 결과 더 나은 구조가 있다면 **반드시 대안을 함께 제시**하고, 현재 제안과 비교하여 장단점을 설명한 뒤 최종안을 추천한다.

이번 작업에서는 코드를 수정하지 않는다. Repository Structure · Directory 이동 · Markdown 이동 · 문서 링크 수정만 수행한다.

## 북극성 — 최종 제품 목표 (사용자 진술 2026-07-09)

이 리팩토링이 향하는 최종 목적지. v1.2.1 구조는 이걸 위한 첫 걸음이다. (구조 이해용 컨텍스트 — 일부는 현재 작업 범위 아님)

- **설치형 부서 배포 도구.** 부서 내 모든 인원이 설치 후 사용하는 형태. haf를 각 프로젝트에 내려받는 게 아니라, **설치된 haf를 대상 프로젝트(예: 새 계산기 프로젝트)에서 호출**하면 haf 구조대로 작업이 구동된다. (프로젝트 = 대상, haf = 적용 도구)
- **Layer별 명령 호출.** `haf:<layer>` 형태(예: `haf:planning`). 현재는 진입 명령 `new`·`continue`만 존재(= uaf-new·uaf-continue). 비어있는 Layer는 구조 정리 후 구축.
- **독립 실행 + 체이닝.** 각 Layer 단독 사용 가능(uahf만/특정 Layer만) + 최초 Layer→최후 연결. 연결선 = Layer 간 계약 사슬: `Discovery Request → Project Contract → core loop`. 독립성 근거 = Project Contract가 UAHF의 **선택 입력**(부재 시 기존 운용 불변, uaf/ARCHITECTURE §2.1·UAF-INV ①).
- **루트 ARCHITECTURE = 라우터.** 루트 ARCHITECTURE.md가 각 Layer ARCHITECTURE.md를 가리키고 관계(연결)를 서술. 각 Layer는 독립 ARCHITECTURE 보유. → uaf/ARCHITECTURE.md 내용은 **분산**(파이프라인 관계→루트, 요소별→각 Layer).
- **AI 비종속 + Layer별 LLM 선택.** 특정 LLM 비종속. Layer별로 LLM 선택 가능(worker.md 선언 또는 시작 전 선택). **※ 현재 작업 범위 아님 — 후속.**
- **`.claude` override 모델 연결.** 설치된 haf = Global Default `.claude` / 대상 프로젝트·Layer 하위 = override.

**미래 트랙(후속, v1.2.1 밖):** Layer별 명령 표면(`haf:<layer>` — entry-binding 확장) · Layer별 LLM 선택(agent-binding) · 설치형 패키징(Scaffold/Install Manifest — 후보 (b) uahf-quickstart 계열). 명령 프리픽스 명명(`haf`/`uaf`/`uahf`)은 Adapter 표면 확정 대상.

## 설계 논의 — 미래 Layer 구축 (2026-07-09, Advisor 의견 · 미확정)

v1.2.1 구조 이후 Layer 구축 시 반영할 방향. 확정 spec 아님(논의 캡처 — 유실 방지).

**A. Layer 간 연결 = 타입 계약 파이프.**
- `entry ─[Discovery Request]→ discovery ─[Project Contract]→ planning/uahf ─→ execution`.
- 경계 payload = 자유서술(narrative)이 아닌 **타입 계약(schema)**. 이유: LLM 교체·독립 실행 시 다음 Layer가 안정 소비.
- 저장 = **대상 프로젝트의 `.claude/`**(`discovery-request/`·`project-contract/` — contract-binding 관례 확장). haf=설치형 무상태, 프로젝트별 상태는 그 프로젝트 `.claude/`에.
- 호출 = `haf:<layer>`가 입력 계약 읽기→실행→출력 계약 쓰기. 체이닝(사람 게이트에서 정지) 또는 독립 실행.
- **3구분(혼동 금지)**: Memory(공유 지식·횡단) / Layer 계약(파이프) / handoff(시간축).

**B. 컨텍스트 최소화 오케스트레이션 (최종 목표).**
- 현재 session-handoff = 메인 컨텍스트 소진 시 **사람이 수동으로** 새 세션+handoff 전달하는 workaround.
- 목표: 메인 LLM(오케스트레이터) 컨텍스트 **lean 유지**, 무거운 작업은 **sub-agent 위임**(각자 컨텍스트·결과만 반환), 상태는 **디스크 아티팩트로 외부화** → 수동 handoff 제거, 사람은 **승인 게이트만**.
- 전환: 수동 narrative handoff → **자동 구조화 체크포인트**(기계 재개 가능·사람 붙여넣기 불요).
- **이 세션이 이미 proto**: Advisor 오케스트레이션 + Planner/Worker/Verifier 위임(무거운 컨텍스트 격리) + 브리프/Memory 외부화.
- 근거 원칙: root ARCHITECTURE §3.6 Token Efficiency.
