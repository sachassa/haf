## §0. 이 문서의 위치와 정본 경계 (사전 절차서 성격)

- **이 문서는 시연 절차서(사전 절차서)다.** 시연을 **어떻게 수행하고 무엇으로 판정하는가**의 절차·입력·기대 기록 명세·판정 문장·기록 포맷·커버리지 매핑을 정의한다. 시연의 실제 **수행 기록**은 별도 산출물(후속 시연 Task T10 및 그 소산 — docs/v0.9-demo.md 등)이, **독립 판정**은 검증 단계(Verifier = CP2)가, **최종 승인**은 Advisor(CP3)가 담당한다. 이 절차서는 그 세 작업의 입력이다. **기대 명세와 실측 기록은 다르다(L-07)** — 본 절차서는 기대만 명세하고 실측 결과를 선취하지 않는다. 자기 점검은 최종 승인이 아니다(02 §3.2-A).
- **정본은 specs/12-scaffold.md §3(Core Contract)·§7(완료 기준)·§8(예)와 확정 인터페이스(scaffold-binding.md §2~§6·scaffold-template/ 13파일·docs/v0.9-install-guide.md)·loop-protocol.md·loop-binding.md §3·01 §3.1-C·13 §3.2-A이다.** 이 절차서는 그 계약·완료 기준·물리 구조를 **재정의·확장하지 않는다.** 계약 요소(3연산·6필드·CK-1~8·사유 코드·불변 규칙)·판정 문장·필드·물리 구조는 § 포인터·원문 인용으로만 참조하고, 필수/선택 표기·열거 값은 정본 그대로 보존한다.
- **판정 문장은 인용이다.** 각 판정 문장(§8-D)은 12 §7 완료 기준·§3.2-C 체크리스트 또는 ROADMAP v0.9 완료 조건의 **원문 인용 또는 그 검증 가능 환원(예/아니오)**이며, 새 판정 기준을 창설하지 않는다. Install Manifest 6필드·CK-1~8·Failure Report reason·Invariants INV-1~8·전이 이벤트 10필드는 전부 정본에서 인용한다.
- **기대 기록 명세는 정본 스키마의 인스턴스다(재정의 0).** §5·§6의 Work Graph 인스턴스·Install Manifest 기대 값·CK 판정표·loop-data 전이표·Bootstrap 상태·Uninstall 결과·Memory Update는 정본 스키마(work-graph.md §2·§3 / 12 §3.2-B / 12 §3.2-C / loop-state-record §2·03 §3.2-A / 01 §3.2-C / memory-store)를 이 시연 경로에 적용한 **기대 값 명세**이며, 필드·의미·필수 표기·열거 값을 재정의하지 않는다.
- **단일 흐름 — 과분해 금지(done 5).** v0.9 시연은 v0.8(3-서브시스템 병렬 집합)과 달리 **설치 → Bootstrap → 루프 동작**의 **단일 흐름**이다. 따라서 Work Graph는 **병렬 집합 1개·Task 1개**로 인스턴스화하며(§5), Loop 사이클도 1 사이클(§6.4)이다. 시연을 인위적으로 여러 Task로 과분해하지 않는다(07 §3.2-A 도출 문면 — 상호 선행 의존이 있는 설치 후속 연산은 별개 병렬 집합이 아니다).
- **라이브 표면 비오염(DP-E7 동형).** 시연의 **설치 대상은 격리된 신규 프로젝트 픽스처**(`docs/v0.9-demo-fixtures/new-project/`)이며, 라이브 `.claude/`·라이브 `framework/core`·`framework/runtime`·`specs/`·기존 loop-data 9파일·기존 memory-data 56건을 설치·수정·오염시키지 않는다(§4.1). 라이브 표면에 추가되는 것은 시연 오케스트레이션 사이클의 loop-data 기록(`framework/adapters/claude/loop-data/v09-demo-scaffold.jsonl` — 시연 네임스페이스, append-only)과 Memory Update의 memory-data append(BPD- 후보)뿐이다(§6.4·§6.6·v0.5~v0.8-demo loop-data 관례 동형).
- **하네스 상태 전제(Bootstrap) — 형태 A(DP-U1·DP-L3).** 이 하네스는 현재 Bootstrap 상태다. Install/VerifyInstall/Uninstall 3연산은 **형태 A 문서 절차**로 실현되고(scaffold-binding DP-U1), 시연 사이클 구동은 loop-protocol.md §6 DP-L3의 형태 A 해석("규격 + 실물 사이클 구동 시연")으로 실현된다. 무인 설치 실행기·검증 실행기·무인 자동 루프 구동(형태 B)은 미도입이다. 본 절차서는 각 단계에서 **무엇을 배치·확인·관측하는가**를 명세하며 특정 무인 자동화를 전제하지 않는다.
- **실측 기반 상태 서술(L-07).** "실재/존재/부재" 주장은 파일 시스템 확인 후에만 기입한다. §4·§6의 "현 시점 실측" 값은 본 작성 시 직접 실측(2026-07-06)에 근거한다 — 미존재를 실재로, 미래 산출물(T10이 생성할 픽스처·loop-data·Memory Update)을 현재 실재로 쓰지 않는다(§10.1 실측 목록).
- **라벨 주의(새 용어 신설 없음).** "시연·사전 절차서·판정 문장·예/아니오 환원·기대 기록 명세·기록 포맷·픽스처·라이브 표면·커버리지 매핑·시연 네임스페이스"는 조직 편의를 위한 **서술 라벨**이며 Glossary 표제어가 아니다. 계약 용어(Scaffold·Project Template·Install Manifest·설치 검증 체크리스트·Work Graph·Task·병렬 집합·소유 경계·루프 상태 기록·전이 이벤트·회수 집합)와 필드명·열거 값은 전부 Glossary §3.2-D/J·12 §3·loop-binding §3 정본에서 인용한다. `형태 A/B`·`DP-U1`·`DP-A3`·`DP-L3`·`DP-E7`·`DP-E8`은 확정 인터페이스·세션 결정의 라벨 인용이다. `BPD-`는 v0.6~v0.8-demo 선례 인용이지 새 용어 신설이 아니다.

### §3.2 기록 요건 (재발 방지·대조·Consult)

1. **실경로·실값 인용 ("설치했다" 서술 금지, L-07).** "근거 (관측한 것)"에는 추상 주장이 아니라 **실재 파일 경로와 실값**을 남긴다 — 픽스처의 Install Manifest 실 필드 값, 설치된 산출물 경로 실재, CK-1~8 항목별 판정 근거, Bootstrap `state` 실값, loop-data `v09-demo-scaffold.jsonl`의 전이 이벤트 **line 원문**(또는 필드 값 전건), 멱등성 재설치 diff 목록, Uninstall 후 잔여물 목록, Memory Update가 append한 memory-data 항목의 실 id·`source`·`stable_id`. "설치→루프가 동작했다"·"CK 전건 통과" 류의 서술만으로는 근거가 불충분하다(L-07 — 상태 서술은 실측 후 기록). 파일이 실제로 존재하고 내용이 명세와 일치함을 실측으로 확인한 뒤 기입한다.
2. **`at`·시각 주장은 순서 값 / 실측 구분 (L-09).** loop-data의 `at` 필드는 **순서 값**이다(loop-binding §3.3 — 사이클 내 단조 증가 순서 값, 물리 벽시계 시각 아님). 수행 기록은 `at`을 "실제 수행 시각"으로 서술하지 않는다. Install Manifest `timestamp`(선택)도 순서 값 또는 실측 mtime으로 구분해 기입한다. 시각 주장을 넣지 않으면 넣지 않았음을 근거에 명시한다(L-09).
3. **설치·루프·제거 재구성 확인.** 수행 기록은 산출 소산만으로 시연을 재구성·검증할 수 있음을 아래로 확인한다:
   - **(가) 라이브 표면 무변경·픽스처 격리** — 시연 전 라이브 표면 스냅샷과 시연 후 재열거를 대조해, 추가·변경이 선언된 시연 산출물(픽스처 `docs/v0.9-demo-fixtures/`·loop-data `v09-demo-scaffold.jsonl`·memory-data append분)뿐이고 라이브 `.claude/`·`framework/core`·`framework/runtime`·`specs/`·기존 loop-data 9파일·기존 memory-data 56건 변경 0임을 전수 대조한다(§6.6·DP-E7 동형).
   - **(나) 설치 계약 준수 확인** — Install Manifest 6필드·`frameworkVersion`=`"v0.9"`·`specVersion`=`"v0.1"`·`installedModules` 최소 집합·CK-1~8 판정 근거·Bootstrap `state=Ready`·설치된 Core CK-6 스캔 0.
   - **(다) 루프·검증·제거 완결 확인** — loop-data 1사이클이 Consult→…→Complete를 `retry_count`=0·CP2 Pass로 완주함을 확인하고(개별 검증 통과 — 구현 주체 Worker와 검증 주체 Verifier/Advisor 분리), Uninstall이 `installedArtifacts`만 제거·`preservedPaths` 보존·잔여물 0임을 복원한다(§6.4·§6.5).
4. **시연 착수 시 Memory Consult 수행·회수 집합 기록.** 시연 수행 Task는 착수(Decompose·Consult) 시 Memory Service Interface로 회수(Recall)를 실제 수행한다 — `purpose`(예: "v0.9 Scaffold 설치·Bootstrap·루프 구동·기존 파일 보호 관련 Active Lesson·BP 회수")와 `scope`(narrowing: `kind`=`lesson`/`best-practice`, `labels`: status=Active + 상황 투영), 기본 `detail`=index를 명시한다(memory-binding §3.2 단계 1·2). 회수된 집합(회수 건수·매칭 라벨·회수된 `id` 목록)을 수행 기록에 남기고, **그 회수 집합 참조(mi-id 배열)를 사이클 Consult 전이 이벤트의 `ref`에 기록**한다(loop-binding §3.3 DP-L5). 회수·기록이 단일 Port(Recall) 경유·우회 0건임을 확인한다(03 INV-7). **주: Scaffold 연산 자체는 Memory를 읽거나 쓰지 않는다(12 §5) — 회수·기록은 시연을 감싸는 오케스트레이션 Loop 사이클(03 §5)의 것이며, 그 구분을 명시한다(§6.4·§6.6).**

## §4. 픽스처 명세 (done 3 — DP-E7 동형)

시연은 격리된 신규 프로젝트 픽스처를 대상으로 설치·검증·부트스트랩·루프·제거를 구동한다. 이 절은 그 픽스처의 **명세**를 확정한다 — **픽스처의 실물 생성은 이 절차서 소관이 아니라 후속 시연 Task T10 소관이다**(constraint, §0). 픽스처는 저장소 실계약 문서·라이브 설정 표면을 건드리지 않는 자기완결 대상물이다.

### §4.1 위치·격리 경계 (라이브 표면 vs 픽스처 경계 정직 구분 — DP-E7 동형)

- **신규 프로젝트 픽스처 경계.** 설치 대상 = **`docs/v0.9-demo-fixtures/new-project/`** (신규 디렉터리·격리 경계·v0.5~v0.8-demo-fixtures 관례 동형). 설치 전 상태 = **UAHF 산출물 0건(빈 프로젝트)** + 기존 파일 보호 시연용 사전 배치 파일 1개(§4.3). 이 디렉터리와 파일은 후속 시연 Task T10이 생성한다(**현 시점 미존재** — 본 작성 시 직접 실측: `docs/`에 v0.5~v0.8-demo-fixtures만 실재, `v0.9-demo-fixtures/` 부재).
- **설치 원본은 라이브 scaffold-template/.** Install은 `framework/adapters/claude/scaffold-template/`(T4 확정 13파일)을 **읽어** 픽스처 경계로 배치한다(scaffold-binding §3.1·§6). 원본(scaffold-template/)은 **읽기만** 하고 수정하지 않는다(07 R4).
- **라이브 표면 비오염(DP-E7 동형).** 설치 산출물은 **전부 픽스처 경계(`docs/v0.9-demo-fixtures/new-project/`) 안**에 배치된다 — 라이브 `.claude/`·라이브 `framework/core`·`framework/runtime`·`framework/adapters`·`specs/`를 설치·수정·오염시키지 않는다. 즉 픽스처의 설치본 `.claude/`는 `docs/v0.9-demo-fixtures/new-project/.claude/`이지 라이브 `.claude/`가 아니다(오인·중복 로드 방지).
- **라이브 표면에 추가되는 것(정직).** 시연 중 라이브 표면에 추가되는 것은 두 가지뿐이다: (a) 시연 오케스트레이션 Loop 사이클의 loop-data 기록 `framework/adapters/claude/loop-data/v09-demo-scaffold.jsonl`(시연 네임스페이스·append-only·기존 9파일 무변경 — §6.4·delegation done 1 ④), (b) Memory Update의 memory-data append(BPD- 후보·기존 56건 무변경 — §6.6). 이 둘은 v0.5~v0.8-demo가 loop-data·memory-data 시연 네임스페이스에 append한 관례와 동형이며 라이브 계약 문서 오염이 아니다.
- **CP2 전수 스캔 제외 경계 (verifier_scope 제외, DP-E7 동형).** 12 §7-10(§3 AI 비의존, 마일스톤 CP2 소관 — specs/12 §3 본문 대상) 전수 스캔이 수행될 때, **픽스처 경계(`docs/v0.9-demo-fixtures/`)와 설치본의 물리 토큰**(픽스처의 `.claude/`·Adapter 경계 배치·Install Manifest의 `"v0.9"` 등)은 대상 경계에서 제외하고 제외 사실을 `verifier_scope`에 명시한다. 픽스처의 정당한 환경 토큰(Adapter 격리 지점·설치 산출물)이 실계약 spec(12 §3) 경계의 위반으로 계상되지 않게 한다.

### §4.2 머리 명시 요건 (필수)

- **"시연 픽스처 — 실계약 문서·라이브 설정 표면 아님."** 픽스처가 검증 대상 계약 문서나 라이브 하네스 설정이 아니라 시연을 위해 구성된 격리 대상물임을 표시한다. 특히 픽스처의 `.claude/` 설치본은 라이브 `.claude/`와 구분됨을 명시한다(오인·중복 로드 방지).

**moduleSelection 최소 집합 (done 3).** ① Install의 `moduleSelection`은 **최소 필수 집합**을 반드시 포함한다(12 INV-2, install-manifest.template.md·docs/v0.9-install-guide §2.1). 최소 집합 = Runtime Bootstrap 필수 계약 + 최소 구성 집합(13 §3.2-A 5요소)을 만족하는:

- `runtime` — Runtime 호스팅·모듈 시스템 (필수).
- `agent` — Agent 역할 4종 + 위임/완료·실패 보고 프로토콜 (필수).
- `verifier` — 검증 게이트(구현 주체와 검증 주체 분리) (필수).

선택 Module(`loop`·`memory`·`workflow`·`plugins` 등)은 이 시연에 필요하지 않으므로 **추가하지 않는다**("필요한 모듈만" — 12 INV-2·CK-2). ④ Loop 1사이클(CK-5)은 설치된 `agent`·`verifier` 모듈이 제공하는 역할 4종 + 검증 게이트 위에서 **핵심 루프 형태 A**(scaffold-binding §2 행 10)로 실증되며, 별도 `loop` 모듈 설치를 요구하지 않는다. 최소 집합 미달이면 Install이 `ModuleSelectionInvalid`로 거부됨을 §8-F가 다룬다.

**픽스처 경계의 정직.** 픽스처 파일은 라이브 계약 문서의 결함이 아니다 — 픽스처 경계 내부에만 존재하고, 마일스톤 CP2의 specs/12 §3 정적 스캔(§2)에서 verifier_scope로 제외된다(§4.1). 사전 배치 사용자 파일(README.md)은 의도적 결함이 아니라 INV-3 보호 대상의 정상 구성물이다.

**claim(완료 보고)의 지위.** 시연 사이클의 Execute는 Worker 완료 보고(02 §3.2-C, self_check 포함)를 산출하나, 그 self_check "충족" 주장은 CP2 판정의 **참고 입력**일 뿐 판정 근거가 아니다(06 독립성, 02 §3.2-A). CP2는 산출물(Install Manifest·설치된 구조·loop-data·Uninstall 결과)을 근거로 독립 판정하여 Pass를 낸다(픽스처는 CP2 Pass가 기대되는 통과 케이스로 설계).

### §6.3 Bootstrap 상태 기대 (01 §3.1-C — Ready)

③ Runtime Bootstrap이 산출할 Runtime Context `state`의 **기대 값**이다(01 §3.2-C).

- **기존 파일 보호(INV-3·CK-8).** 재설치 시 README.md는 사용자 소유 기존 파일이므로 덮어쓰지 않고 보존하며 `preservedPaths`=`[README.md]`에 기록. 강제 옵션 없으면 무변경(강제 시 `ConflictWithExisting` 경고 — §8-F).
- **Uninstall 결과(INV-5).** Install Manifest의 `installedArtifacts`만 제거하고 `preservedPaths`(README.md)는 **보존**하며, 제거 후 남은 항목(Manifest 소유이나 제거되지 않은 것) **잔여물 = 0** 기대. 잔여물이 있으면 잔여 경로를 `UninstallResidue`로 보고(§8-F). 제거 결과 = { 제거된 산출물 목록 = installedArtifacts, 보존 목록 = [README.md], 잔여물 목록 = [] }.

### §6.6 Memory Update 실기록 기대 · 라이브 표면 무변경 측정 절차 (memory-binding §3 / ROADMAP 정합)

- **Memory Update(정식 append).** 시연 오케스트레이션 사이클의 Learn→Memory Update는 도출한 후보를 **정식 memory-data에 append**한다(memory-binding §3.1 Record — `store/<id>.json` 쓰기 + `index/index.jsonl` line append 정합, 단일 Port 경유·우회 0건). 도출 후보 = **성공한 신규 프로젝트 설치→Bootstrap→루프 구동 단일 흐름 패턴** → **Best Practice 후보(시연 네임스페이스 BPD-)**(07 §5·AGENT.md — 성공은 BP 후보). 본 통과 케이스는 실패가 없으므로 Lesson 후보(LD-) 기대 0건이나, 시연 중 예기치 못한 실패가 관측되면 은폐 없이 LD- 후보로 기록한다(§8-F, 02 O5). `source`=시연 유래(예: "v0.9-demo" 또는 T10 확정 식별자)·status=`Candidate`(승격 승인은 Advisor 전속, 05 INV-4). 라벨 투영은 memory-binding §5.4 정본 키를 따른다.
- **mi 번호 실측 순차 배정·기존 무변경(선취 금지).** `id`는 memory-binding §2 스킴(`mi-<정렬가능토큰>`)으로 **수행 시점 실측으로 순차 배정**한다. **현 시점 store는 실측 56건**(본 작성 시 직접 실측)이므로 시연 append는 그 다음 순번에서 시작하되 정확한 번호·건수는 T10이 수행 시점에 실측해 배정한다(**선취 금지** — 구체 번호·건수를 본 절차서가 확정하지 않는다). **기존 56건은 무변경** append-only.
- **라이브 표면 무변경 측정 절차(ROADMAP ③ 정합·DP-E7 동형).** "라이브 표면 비오염"을 **예/아니오 판정 가능한 전수 대조 절차**로 확정한다:
  1. **시연 전 라이브 스냅샷.** 시연 착수 전, 라이브 표면 목록·상태를 스냅샷 — 라이브 `.claude/`·`framework/core/`·`framework/runtime/`·`framework/adapters/`(scaffold-template/ 포함)·`specs/`·기존 loop-data 9파일·기존 memory-data 56건.
  2. **시연 후 재열거.** 시연(① Install ~ ⑤ Uninstall + Memory Update) 후 동일 경계를 다시 열거한다.
  3. **전수 대조.** 두 목록의 차집합을 계산한다. **추가·변경이 선언된 시연 산출물뿐이고 라이브 표면 변경 0**이면 라이브 표면 무변경(예). 허용되는 추가분(선언된 시연 산출물) = { 픽스처 경계(`docs/v0.9-demo-fixtures/` 신규 디렉터리·파일 — Uninstall 후에도 픽스처 자체는 시연 기록으로 잔존) · loop-data 신규 1파일(`v09-demo-scaffold.jsonl`) · memory-data BPD- append분 · 시연 수행 기록(docs/v0.9-demo.md 등) }.
  4. **전 부류 전수(정직).** 추가분의 **전 부류**(픽스처·loop-data·memory-data)를 스캔한다 — 한 부류만 확인하고 다른 부류를 통과로 간주하지 않는다(좁은 대리 지표 금지, 06 V4). 라이브 표면 파일 중 하나라도 변경이 있으면 라이브 표면 오염(아니오), DP-E7 위반이다.
  5. **픽스처 내 Uninstall 순증가 구분.** 픽스처 내부(`docs/v0.9-demo-fixtures/new-project/`)의 설치본은 ⑤ Uninstall로 `installedArtifacts`가 제거되어 잔여물 0이 되나, README.md(preservedPaths)와 시연 기록(Install Manifest·verify-scaffold.md 등)은 시연 소산으로 잔존한다 — 이는 라이브 표면이 아니라 픽스처 경계 내부이므로 라이브 표면 무변경 판정과 무관하다.

## §7. 수행 주체·역할 배치 (Advisor 확정 시연 설계)

- **Advisor 주관 구동(사이클 오케스트레이션 = 주 세션).** 시연은 **Advisor(주 세션)**가 주관 구동한다 — 사이클 오케스트레이션(위임 수령 → Consult → Plan → Execute → Verify → Learn → Memory Update → Complete, loop-protocol §3)을 Advisor 주 세션이 구동한다. 분해 채택(Planner 초안 채택)·위임·CP3 최종 승인은 Advisor가 수행한다(02 §3.1).
- **Planner·Worker·Verifier 실위임(모의 시연 금지, L-07 실측 요건).** 시연은 기록물만 작성하는 **모의 시연이 아니다** — **Decompose 초안은 Planner 서브에이전트**(`.claude/agents/planner.md`, DP-E8 `model: opus`)에, **Execute는 Worker 서브에이전트**(`.claude/agents/worker.md`, `model: opus`)에, **CP2는 Verifier 서브에이전트**(`.claude/agents/verifier.md`, DP-E8 `model: opus`)에 **실제 위임**한다(loop-binding §5.1 역할 실행 = 서브에이전트 디스패치). 실 산출물(픽스처 설치본·Install Manifest·Bootstrap `state`·loop-data·Uninstall 결과)이 생성되고 실 판정이 이뤄진 뒤에만 그 결과를 Work Graph 인스턴스·전이 이벤트·CP2 리포트로 남긴다(L-07 — "설치했다" 서술 금지, 실측 후 기록). Planner 초안(단일 Task 분해)은 Advisor 채택 대상이다.
- **역할 ↔ actor 대응.** 사이클 전이 이벤트 `actor`는 그 전이를 유발한 역할이다 — CP1(Worker 자체 점검)은 Execute→Verify 전이의 근거, CP2(Verifier 독립 판정)는 Verify 전이의 판정, CP3(Advisor 최종 승인)는 Complete 진입 게이트. 본 시연 사이클은 사람 개입이 없으므로 `actor`=human 0건이다(§6.4).
- **검증 게이트(구현/검증 주체 분리).** 구현 주체(Worker)와 검증 주체(Verifier CP2/Advisor CP3)가 분리되어, 구현자가 자신의 산출물을 최종 승인하지 못함을 이 사이클이 실증한다(13 §3.2-A 검증 게이트 — docs/v0.9-install-guide §2.4). 이는 ④ Loop 1사이클(CK-5)의 핵심 성질이다.
- **후속 담당(T10).** 픽스처(`docs/v0.9-demo-fixtures/`)·CP2 리포트(verify-scaffold.md)·loop-data 1파일·Memory Update memory-data append·시연 수행 기록(docs/v0.9-demo.md)의 실물 생성은 **후속 시연 Task T10** 담당이다. 본 절차서(Task T9)는 그 실행 명세만 확정하며, 픽스처·기록물·시연 실물을 생성하지 않는다(§0 소유 경계).

## §8. 시연 — 절차 단계 · 입력 · 기대 기록 명세 · 판정 문장 · 기록 포맷 · 실패 처리

목표: 신규 프로젝트 픽스처에 Install → VerifyInstall(CK-1~8) → Bootstrap(Ready) → Loop 1사이클을 순차 구동하고, 멱등성·기존 파일 보호·Uninstall 안전을 보인다. 근거: 12 §3·§7·§8, scaffold-binding §2~§6, docs/v0.9-install-guide, 01 §3.1-C, 13 §3.2-A, loop-protocol·loop-binding §3.

### (A) 절차 단계

1. **착수·회수 (Consult).** Advisor(주 세션)가 v0.9 시연(목표·범위)을 수령한다. Memory Consult 회수(Recall)를 수행하고(§3.2 요건 4 — 설치·Bootstrap·루프·기존 파일 보호 관련 Active Lesson·BP), 회수 집합을 기록한다(사이클 seq1 `ref`).
2. **Decompose (Planner 초안 + Advisor 채택).** Planner 서브에이전트가 단일 Task(T-SD) Work Graph 초안을 제출한다(§5.2). Advisor가 분해 검사(완료 조건 보유·인터페이스 계약 보유·소유 경계·의존 비순환)를 대조하고 단일 Task·병렬 집합 1개(과분해 금지)를 확인해 **채택**한다.
3. **Dispatch·Execute (Worker 실위임) — ①~⑤ 순차 구동.** Advisor가 T-SD를 02 §3.2-B 위임 메시지로 Worker 서브에이전트에 디스패치한다. Worker의 Execute가 다음을 순차 구동한다:
   - **① Install** — scaffold-template/(T4 확정 13파일)을 픽스처 `docs/v0.9-demo-fixtures/new-project/`로 배치한다(scaffold-binding §3.1 절차: 입력 접근성·moduleSelection 검사 → 기존 파일 처리(보존 기본) → Project Template 배치 `dot-claude/*`→`.claude/*`·`framework/{core,runtime,adapters}/`·`specs/`(+ 기준선) → Install Manifest 생성). moduleSelection=`[runtime,agent,verifier]`(§4.3). Install Manifest 실물 생성(§6.1 — `frameworkVersion`=`"v0.9"`·`specVersion`=`"v0.1"`·preservedPaths=[] 최초). **라이브 `.claude/`·`framework/`·`specs/`는 오염하지 않는다**(§4.1).
   - **② VerifyInstall** — CK-1~CK-8을 각각 scaffold-binding §5 검사 방법(파일 조회·텍스트 검색·명령 실행)으로 실행해 항목별 통과를 판정한다(§6.2 — 전 항목 충족 기대). CK-6은 설치된 `framework/core/`·`framework/runtime/` 전수 스캔(instance 토큰 0).
   - **③ Runtime Bootstrap** — 설치 직후 세션/턴에서 Bootstrap(01 §3.1-C)을 재현하고 `state=Ready`를 관측한다(§6.3, CK-4).
   - **④ Loop 1사이클** — 핵심 루프(위임 Advisor → 구현 Worker → 독립 검증 Verifier CP2 → 최종 승인 Advisor CP3)를 1 사이클 구동하고, 전이 이벤트를 `framework/adapters/claude/loop-data/v09-demo-scaffold.jsonl`에 7 line append한다(§6.4, CK-5·03 INV-3 append-only·기존 9파일 무변경). 구현 주체(Worker)와 검증 주체(Verifier/Advisor) 분리를 확인한다.
   - **⑤ 멱등성·기존 파일 보호·Uninstall** — 사전 배치 사용자 파일(README.md) 존치 상태에서 Install 재실행 → 멱등성(설치 산출물 diff 0, INV-4)·기존 파일 보호(preservedPaths=[README.md] 기록·무변경, INV-3·CK-8)를 보인다. 이어 Uninstall이 `installedArtifacts`만 제거하고 preservedPaths(README.md)를 보존하며 잔여물 0을 보고함을 보인다(§6.5, INV-5).
4. **Verify (Verifier 실위임, CP2 Pass).** Verifier 서브에이전트가 산출물(Install Manifest·설치된 구조·CK 판정·Bootstrap state·loop-data·Uninstall 결과)을 T-SD `done`에 대해 독립 판정한다(verify-scaffold.md, Pass 기대). Worker self_check "충족" 주장은 참고 입력일 뿐 판정 근거가 아니다(06 독립성).
5. **Learn→Memory Update (Workflow/사이클 수준, 07 §5).** 성공한 신규 프로젝트 설치→Bootstrap→루프 구동 단일 흐름 패턴 → Best Practice 후보(BPD-)를 정식 memory-data에 append(§6.6 — `source` 시연 유래·status=Candidate·단일 Port). 기존 56건 무변경.
6. **최종 승인 (CP3).** Advisor가 시연 전체(설치→Bootstrap→루프·멱등·보호·제거)의 판정(§8-D)을 최종 승인한다(CP3 — 마일스톤 게이트). §3 AI 비의존(12 §7-10)은 CP2가 specs/12 §3 본문 정적 스캔으로 직접 판정한다(§2, 픽스처·라이브 표면 verifier_scope 제외).

### (F) 실패 처리 규칙 (v0.8-demo-procedure §8-F 동형)

시연이 기대 관측과 **다르게 관측될 때**의 처리 규칙이다.

1. **은폐 없이 그대로 기록한다.** 관측이 기대와 달라도 실제 관측을 §3 기록 포맷의 "근거 (관측한 것)"에 그대로 남긴다. 실패·불일치를 숨기지 않는다(Worker 금지 사항 — 실패 은폐 금지, 02 O5·INV-5). Install Manifest 실값·CK 판정·Bootstrap state·loop-data line 원문·Uninstall 결과를 그대로 인용한다.
2. **판정 값으로 표기한다.** 기대와 다르게 관측되면 해당 판정의 "관측 결과"를 **위반**으로 표기한다. 근거 부족·검사 범위 한계로 확정 불가면 **판정 불가**로 표기하며, 판정 불가를 충족으로 위장하지 않는다.
3. **재작업 여부 판단은 게이트 소관이다.** 이 절차서와 수행 기록은 관측·기록까지만 한다. 위반·판정 불가의 **재작업 여부 판단**은 검증 단계(Verifier = CP2)와 Advisor(CP3)의 소관이다.
4. **Scaffold 연산 실패는 Failure Report로.** Install/VerifyInstall/Uninstall 연산이 실패하면 공통 Failure Report(12 §3.2-D — `operation`·`target`·`reason`·`location`)로 기록한다. reason 열거(정본 12 §3.2-D): `TargetNotWritable`·`ConflictWithExisting`·`ModuleSelectionInvalid`·`BootstrapWouldFail`·`IncompleteInstall`·`UninstallResidue`. 예: moduleSelection 최소 집합 미달 → `ModuleSelectionInvalid`(§4.3), Bootstrap 필수 계약 미충족 → `BootstrapWouldFail`·state=Failed(§6.3), 산출물 누락 → `IncompleteInstall`(location=실패 CK), 제거 후 잔여물 → `UninstallResidue`(location=잔여 경로). 본 시연은 정상 경로(통과 케이스)를 기대하며 음성 케이스를 유도하지 않으나, 관측되면 은폐 없이 기록한다.
5. **라이브 표면 오염 = 위반.** 시연이 기대하는 것은 라이브 표면 무변경(설치 산출물은 픽스처 경계 안에만)이다. 라이브 `.claude/`·`framework/core`·`framework/runtime`·`specs/`·기존 loop-data 9파일·기존 memory-data 56건 중 하나라도 변경되면 DP-E7 **위반**으로 표기한다(§6.6). Uninstall 후 픽스처 설치본에 잔여물이 남으면 `UninstallResidue`·INV-5 위반이다.
6. **연산 실패와 정상 경로의 구분.** 시연 중 연산 자체가 수행 불능(서브에이전트 디스패치 불가·설치 배치 불가·Bootstrap 불가·loop-data 기록 불가)이면 이는 **연산 실패**이며, 정상 경로(설치→검증→Bootstrap→루프→멱등·보호·제거 성립)와 다르다. 둘을 혼동해 기록하지 않는다.
